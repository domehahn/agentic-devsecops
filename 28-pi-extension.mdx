Security Controls sind am wirksamsten, wenn sie dort verfügbar sind, wo Entscheidungen stattfinden. Die Pi Extension bringt SkillSpector direkt in eine Agent-Session: Der Agent kann einen Skill über ein registriertes Tool prüfen, bevor er ihn weiterverwendet.

Das reduziert Reibung – und macht die Toolgrenze des Scanners zu einem zentralen Teil des Sicherheitsmodells.

<KeyTakeaway>
Security wird wahrscheinlicher genutzt, wenn sie im Agentenworkflow eingebaut ist. Die Integration darf dabei nicht die Trust Boundaries des Scanners aufweichen.
</KeyTakeaway>

## Was das Feature wirklich bedeutet

Eine Agent-Integration sollte sichere Defaults besitzen. Der aufrufende Agent kontrolliert zwar Parameter, darf aber nicht automatisch zusätzliche Privilegien erhalten. Insbesondere LLM-Semantik, Remote-URLs und zusätzliche YARA-Regeln sollten bewusst konfiguriert werden.

Außerdem muss die Extension verhindern, dass Secrets aus der Umgebung in Toolausgaben gespiegelt werden.

## SkillSpector

SkillSpector liefert eine dokumentierte Pi Extension. Sie registriert `skillspector_scan` und ruft die bestehende CLI auf. `noLlm` ist standardmäßig `true`; optional können Format, Output, Provider, Modell und zusätzliche YARA-Regeln gesetzt werden. Die Extension liest laut Dokumentation keine `.env` und redigiert secret-artige Ausgabe.

Das ist eine sehr konkrete, produktnahe Integration in Agent Workflows.

## `skil`

`skil` besitzt aktuell keine Pi-spezifische Extension. Seine Agentenintegration erfolgt generischer über CLI, MCP Scanner Service und die öffentlichen Erweiterungsschnittstellen.

Damit fehlt die Convenience-Integration für Pi, nicht aber die grundsätzliche Möglichkeit, `skil` über andere Tooling-Schichten aufzurufen.

## Praxisbeispiel

In Pi kann ein Agent sinngemäß anweisen:

```text
Use skillspector_scan on tests/fixtures/safe_skill/SKILL.md with noLlm=true.
```

Das entspricht einem lokalen statischen CLI-Scan. Der sichere Default ist wichtig: Eine Agent-Session aktiviert nicht automatisch einen externen LLM-Provider.

## Security- und DevSecOps-Einordnung

- Agent-Tool mit statischem/no-LLM Default starten.
- Secrets aus Toolausgabe redigieren.
- Extension-Konfiguration und CLI-Version gemeinsam versionieren.
- Negative Scanergebnisse außerhalb der Agentenentscheidung gaten.
- Remote- und Providerfähigkeiten nur bewusst freigeben.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

## Direkter Vergleich

| Aspekt | SkillSpector | `skil` |
| --- | --- | --- |
| Feature vorhanden | ja | nein / nicht als gleichwertiges Feature |
| Schwerpunkt | Integration und Scanner-Ergonomie | explizite Trust Boundaries und Evidence |
| Bewertung | SkillSpector-only | SkillSpector-only |

**Bewertung aus der Vergleichsmatrix:** SkillSpector-only.

## Typische Fehlinterpretation

„Eine Extension ist nur eine bequeme CLI-Abkürzung.“ Sie verändert, wer den Scan auslösen und parametrisieren kann. Damit wird die Agent-Tool-Schnittstelle Teil des Threat Models.

## Einordnung in die Pipeline

Dieses Feature betrifft die **Integration und Laufzeit des Scanners selbst**. Damit wird nicht nur der Skill analysiert, sondern auch festgelegt, über welche Tool-, Prozess- oder Containergrenze Security-Funktionen erreichbar sind.

Für produktive Nutzung sollten Identität, Dateisystemzugriff, Netzwerk, Secrets und Auditlogs der Scanner-Runtime genauso behandelt werden wie bei jedem anderen sicherheitskritischen Service.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Hier ist SkillSpector klar voraus: Die Pi Extension ist fertig dokumentiert und direkt nutzbar. `skil` bietet allgemeinere Integrationspunkte, aber keine gleichwertige Pi-spezifische Developer Experience.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
