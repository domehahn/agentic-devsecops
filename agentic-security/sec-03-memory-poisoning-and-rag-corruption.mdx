Memory makes agents useful. A system can store preferences, continue previous work, reuse successful solution paths, and access large knowledge collections through RAG.

That creates a new security question:

> What happens when **untrusted input today** becomes **trusted context tomorrow**?

The third part of **“Agentic Security & Adversarial AI”** examines two related but distinct attack classes:

1. **RAG / Knowledge Base Poisoning:** The external knowledge store contains manipulated evidence.
2. **Persistent Memory Poisoning:** Agents store attacker-influenced information and reuse it in later sessions.

---

## 1. Memory Is Not a Neutral Data Store

In agent systems, memory can take different forms:

```text
Working Memory
- current context

Conversation Summary
- compressed history

Semantic Memory
- facts / preferences

Episodic Memory
- past actions / experiences

RAG Knowledge Base
- external documents

Procedural Memory
- reused strategies / rules
```

Each memory class influences later decisions differently.

A stored fact such as

> “Project X uses PostgreSQL”

is different from a stored behavioral rule such as

> “When deployment problems occur, always execute Tool Y.”

The latter sits much closer to the control plane.

---

## 2. RAG Poisoning: Attacking the Evidence Layer

PoisonedRAG systematically studied knowledge-corruption attacks against RAG systems. The work was published at USENIX Security 2025.[^1]

The attack concept:

```text
Attacker
   ↓
injects malicious documents
   ↓
Knowledge Database
   ↓
Retriever selects poisoned evidence
   ↓
LLM generates attacker-influenced answer
```

In their experimental setups, the authors showed that even a small number of deliberately crafted documents could achieve high attack success rates for selected target queries.[^1]

These results are not a universal success rate for every RAG system. They do show, however, that the knowledge base itself is a security-relevant attack surface.

---

## 3. Why “Embedding Poisoning” Is More Than High Cosine Similarity

An attacker does not have to mathematically “hack” the vector space.

In practice, it is often enough to:

1. Get manipulated content into an indexed source.
2. Phrase that content so it appears highly relevant to target queries.
3. Have the retriever return it.
4. Have the generator treat it as evidence.

Attack surfaces can include:

- enterprise wikis,
- public websites,
- uploaded documents,
- support tickets,
- Git repositories,
- knowledge-ingestion APIs,
- user-generated content.

Classic content governance therefore becomes RAG security.

---

## 4. Persistent Memory Poisoning

With persistent agents, an attack can potentially survive beyond a single session.

```text
Session 1:
untrusted input
   ↓
memory write
   ↓
persistent store

Session 10:
new benign query
   ↓
retrieval of poisoned memory
   ↓
behavioral influence
```

OWASP now describes Memory & Context Poisoning as a distinct agentic attack surface and emphasizes that stored context can influence future planning and tool use.[^2]

Current research from 2025/2026 likewise examines attacks in which poisoned experiences or persistent memory entries are later retrieved again.[^3]

---

## 5. The Dangerous Trust Upgrade

The central design problem is:

```text
External Web Content
trust = UNTRUSTED

↓ summarized by agent
↓ stored as "memory"

Memory Entry
trust = ?
```

Many systems lose provenance when storing information.

After a few days, all that remains may be:

```text
"User prefers authentication method X."
```

rather than:

```text
source = external_document
confidence = 0.4
created_by = summarizer-v2
reviewed = false
```

Untrusted data has effectively been promoted.

<Warning>
**Never promote data to a higher trust level merely because an LLM summarized it.**
</Warning>

---

## 6. Tenant Isolation: The Worst Failure Is Cross-User Memory

Memory must always be bound to the correct security principal.

Unsafe:

```text
vector_store.search(query)
```

Safer:

```text
vector_store.search(
  query,
  filter = {
    tenant_id: current_tenant,
    owner_id: current_user,
    classification: allowed_labels
  }
)
```

Enforcement must be deterministic. A prompt such as

> “Use only memories belonging to the current user.”

is not tenant isolation.

---

## 7. Provenance as Mandatory Metadata

Every stored entry should answer at least:

```yaml
memory_id: mem-01842
source_type: external_document
source_id: ticket-991
tenant_id: acme
created_at: 2026-08-23T12:00:00Z
writer: agent-memory-service
trust_level: untrusted-derived
review_status: unreviewed
model_version: summarizer-v4
```

This lets the system distinguish between:

- user-confirmed facts,
- system-derived facts,
- external claims,
- inferred preferences,
- security-sensitive instructions.

Memory without provenance becomes a difficult-to-audit data graveyard.

---

## 8. Write Policy: Not Everything Should Be Stored

An agent should not automatically persist every observed piece of information.

A memory-write policy can distinguish:

```text
ALLOW:
- explicitly confirmed preference
- project context explicitly saved by user

REVIEW:
- inferred preference
- long-term summary

DENY:
- secrets
- credentials
- external instructions
- security policy overrides
- data from another tenant
```

Importantly, the decision should not be left to an LLM alone.

---

## 9. Retrieval Policy: Even Legitimate Memories Are Context-Dependent

A memory entry can be authentic and still be inappropriate for the current task.

Example:

```text
Memory:
"The old API gateway uses a 30s timeout."
Version: v1
```

The current query concerns v3.

Memory retrieval therefore needs:

- versioning,
- validity windows,
- scope,
- relevance,
- trust,
- recency.

---

## 10. Cryptographic Provenance: Useful, but Not Proof of Truth

Digital signatures or HMACs can prove:

> This content came from source X and has not been modified afterward.

They do not prove:

> The content is true or safe.

A signed compromised document remains compromised.

Cryptographic provenance is therefore an **integrity control**, not semantic validation.

---

## 11. Sanitization by a Second LLM Is Not Enough

A common pattern is:

```text
Memory candidate
→ safety classifier / LLM
→ safe memory
```

That can help, but remains probabilistic.

A more robust approach combines:

```text
schema rules
+ source allowlist
+ tenant validation
+ secret detection
+ LLM classification
+ human review for high-trust memory
```

The authority of the memory entry determines how strict the controls need to be.

---

## 12. Rollback and Quarantine

Memory systems need the same operational capabilities as other data platforms:

- version history,
- soft delete,
- quarantine,
- source revocation,
- re-indexing,
- incident tagging,
- replay.

If a compromised wiki document is discovered, the system must be able to answer:

> Which memory entries and answers were derived from it?

That requires data lineage.

---

## 13. Retrieval Diversity Against a Single Dominant Poison Chunk

A poisoning attack benefits when one manipulated chunk dominates the entire evidence context.

Possible countermeasures include:

- source diversity,
- duplicate suppression,
- independent retrieval channels,
- authoritative-source priority,
- contradiction detection,
- citation requirements.

Example:

```text
Top 5:
3 hits from attacker-controlled source
2 from authoritative docs

→ Risk Signal
```

This is not a perfect defense, but it is a useful anomaly signal.

---

## 14. Monitoring for Memory Security

Measurable events include:

```text
memory.write
memory.read
memory.promote_trust
memory.delete
memory.quarantine
rag.document.ingest
rag.source.revoke
```

Additional fields should include:

- actor,
- tenant,
- source,
- policy decision,
- risk score,
- model version.

This makes incident reconstruction possible.

---

## 15. Security Tests

A regression suite should verify:

```text
[ ] untrusted document tries to create long-term instruction
[ ] memory from tenant A queried by tenant B
[ ] stale memory conflicts with newer source
[ ] poisoned document ranks high for target query
[ ] source revoked after indexing
[ ] memory write contains secret
[ ] unverified memory tries to trigger write tool
[ ] duplicate poisoned chunks dominate top-k
```

Success does not merely mean the LLM says “no.” Success means the architecture prevents the unauthorized trust transfer.

---

## 16. Memory Promotion as an Explicit Process

Not every stored entry should have the same authority.

```text
untrusted observation
   ↓
candidate memory
   ↓ validation
verified fact
   ↓ optional human confirmation
trusted preference / policy fact
```

This process resembles data-quality pipelines and prevents a single external observation from immediately gaining persistent control.

---

## 17. Conflicting Memory Resolution

When two entries conflict:

```text
Memory A:
source = user-confirmed
timestamp = recent

Memory B:
source = external-document
timestamp = old
```

it should not simply be the semantically closest entry that wins.

A resolver can prioritize:

1. Trust Level
2. Authority of Source
3. Version
4. Recency
5. User Confirmation
6. Semantic Relevance

---

## 18. Memory Budgets as a Security Control

Aggressive persistence increases not only cost but attack surface.

An agent can limit:

- number of persistent entries,
- lifetime,
- write frequency,
- source types,
- maximum trust level of automatically generated memories.

Less persistent state means less material that can be poisoned permanently.

## Conclusion

RAG and memory move knowledge out of model parameters into explicit stores. That improves updateability and control—but creates a new trust boundary.

The first question is not:

> “Is this memory entry semantically relevant?”

It is:

> **Where did it come from, who owns it, how trustworthy is it, and what effects is it allowed to have?**

The next part moves from the content supply chain to the **tool supply chain**: MCP servers, tool poisoning, rug pulls, and agent skills.
