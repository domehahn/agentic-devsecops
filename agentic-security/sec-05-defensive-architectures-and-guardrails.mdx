There is no single guardrail that makes a production AI agent “safe.”

Not the system prompt. Not a second LLM. Not a regex list. Not sandboxing. Not human-in-the-loop.

Security emerges from **multiple independent boundaries**, so that the failure of one layer does not automatically compromise the system.

The final part of **“Agentic Security & Adversarial AI”** therefore constructs a defense-in-depth architecture from the attack classes covered in the previous parts: prompt injection, tool abuse, memory poisoning, and supply-chain risk.

---

## 1. The Right Mental Model: The Agent Is Not the Security Boundary

Unsafe design:

```text
User / Web / RAG
       ↓
      LLM
       ↓
"LLM decides safely"
       ↓
Production Tools
```

More robust:

```text
Untrusted Inputs
      ↓
Context / Provenance Layer
      ↓
LLM Planner
      ↓
Capability Broker
      ↓
Policy Enforcement
      ↓
Approval / Sandbox
      ↓
External Systems
```

The model remains central to reasoning. But **no privileged effect depends solely on the model interpreting context correctly**.

---

## 2. Define Trust Zones

An agent system should classify data by provenance.

### Zone U – Untrusted External

- web,
- email,
- user content,
- public repositories,
- third-party MCP,
- RAG documents without verified provenance.

### Zone I – Internal but Unverified

- automatically generated summaries,
- agent memory,
- LLM-extracted entities,
- tool outputs.

### Zone T – Trusted Authoritative

- signed policies,
- IAM claims,
- CMDB,
- approved configuration,
- server-side ACLs.

### Zone E – Effect Plane

- production DB,
- deployment,
- payment,
- messaging,
- IAM changes.

Data must not implicitly move from U to T.

---

## 3. Preserve Provenance Throughout the Pipeline

Instead of:

```text
"context": "..."
```

systems should carry metadata:

```json
{
  "content": "...",
  "source_id": "ticket-1842",
  "source_type": "external_user",
  "trust": "untrusted",
  "tenant": "acme"
}
```

These metadata can:

- filter retrieval,
- control prompt structure,
- influence policies,
- enable audit,
- trigger quarantine.

Provenance is not a complete defense, but without provenance, trust decisions are difficult to make reliably.

---

## 4. The Quarantine / Dual-Model Pattern

A useful pattern separates untrusted content from a privileged agent:

```text
Web / PDF / Mail
      ↓
Reader / Extractor
(no privileged tools)
      ↓
typed representation
+ provenance
      ↓
Privileged Planner
```

The first process may analyze content but cannot trigger sensitive effects.

Importantly, this pattern is **not** “the proven solution to prompt injection.” It is an additional isolation layer. A manipulated extractor can still produce incorrect data.

The privileged layer therefore still needs its own policies.

---

## 5. Capability Broker

The agent does not receive every tool permanently.

```text
Task:
"Analyze build failures"

Broker grants:
- read_repo
- run_tests_in_sandbox
- read_build_logs

Broker denies:
- deploy_prod
- modify_iam
- read_payroll
```

Capabilities can be issued dynamically, briefly, and per task.

This reduces:

- tool surface,
- prompt-injection impact,
- credential exposure,
- accidental actions.

---

## 6. Policy Enforcement Point

A deterministic control layer belongs between the model and the tool executor:

```text
Request:
subject=user123
action=repository.commit
resource=acme/api
risk=medium

Policy:
allow if
- user has write
- branch != main
- sandbox tests passed
```

The model must not both interpret and execute the policy itself.

Policy-as-code techniques can be useful here as long as policies are evaluated independently of untrusted prompt context.

---

## 7. Risk-Tiered Actions

Not every tool call requires the same approval flow.

### Tier 0 – Read Only

- search docs,
- read logs,
- inspect code.

### Tier 1 – Reversible Write

- create branch,
- open draft issue,
- modify temporary workspace.

### Tier 2 – Significant Write

- merge pull request,
- send external email,
- change staging data.

### Tier 3 – High Impact

- production deploy,
- delete production data,
- IAM changes,
- payments.

The higher the tier:

- stronger policy,
- more evidence,
- human approval,
- shorter-lived credentials,
- stricter audit requirements.

---

## 8. Sandboxing: Isolate Code Execution

A production coding agent often needs shell or code execution.

Minimum requirements:

```text
ephemeral execution
restricted filesystem
no host mounts by default
controlled network
resource limits
time limits
no ambient cloud credentials
separate UID
immutable base image
```

Especially critical:

- Docker socket,
- Kubernetes admin credentials,
- SSH agent forwarding,
- cloud metadata endpoints,
- home-directory mounts.

A sandbox escape must not automatically imply host or cloud-admin privileges.

---

## 9. Egress Controls

If an agent only analyzes internal documentation, its tool sandbox may not need unrestricted internet access.

```text
default deny

allow:
docs.company.example
git.company.example

deny:
arbitrary domains
metadata services
private networks outside scope
```

Egress filtering limits data exfiltration and supply-chain downloads.

---

## 10. Identity and Credential Isolation

Every agent run should have a traceable principal.

```text
human user
   ↓ delegated identity
agent run
   ↓ scoped token
tool
   ↓ resource
```

The current MCP authorization specification requires, for HTTP-based scenarios, resource/audience-bound tokens and prohibits token passthrough, among other controls.[^1]

That fits a zero-trust principle:

> Every resource independently verifies that this exact token is intended for it.

---

## 11. Memory Security

Long-term memory must be treated as persistent security state.

Controls include:

- tenant isolation,
- write policies,
- provenance,
- trust levels,
- expiration,
- review,
- quarantine,
- versioning.

OWASP explicitly highlighted Memory & Context Poisoning as a relevant agentic-security surface in 2026.[^2]

---

## 12. Supply-Chain Controls

For MCP servers, skills, and agent plugins:

```text
allowlisted source
→ review
→ pin version / manifest
→ sandbox
→ restricted permissions
→ egress policy
→ runtime drift detection
```

Tool descriptions and metadata must not be assumed trustworthy by default. This aligns with the trust-and-safety guidance in the MCP specification.[^3]

---

## 13. Immutable Audit—but Privacy-Aware

An agent should generate structured events:

```json
{
  "run_id": "run-7281",
  "actor": "user123",
  "action": "deploy_service",
  "resource": "payments-staging",
  "policy_decision": "allow",
  "approval_id": "approval-882",
  "tool_result": "success"
}
```

“Immutable” does not mean storing every chain-of-thought or every secret forever.

Audit design must simultaneously account for:

- incident reconstruction,
- data minimization,
- retention,
- secret redaction,
- access control.

---

## 14. Guardrails Are Several Different Control Types

The term “guardrail” is too vague unless the layer is named.

### Model Guardrails

- system instructions,
- safety training,
- content classifier.

### Data Guardrails

- PII redaction,
- RAG ACL,
- provenance,
- source validation.

### Tool Guardrails

- schema,
- allowlist,
- parameter validation.

### Authorization Guardrails

- IAM,
- policy engine,
- scopes.

### Runtime Guardrails

- sandbox,
- egress,
- resource quota.

### Process Guardrails

- human approval,
- change management,
- security review.

Defense in depth emerges from **different failure domains**.

---

## 15. Security Evaluation Instead of Intuition

Since 2025/2026, OWASP has published substantially broader guidance on agentic threats and production hardening.[^4] In parallel, AgentDojo provides a scientific environment in which utility and prompt-injection robustness can be evaluated together.[^5]

An internal testing program should include at least:

```text
Prompt Injection
Tool Abuse
Cross-Tenant Access
Memory Poisoning
MCP Tool Poisoning
Credential Scope
Egress Attempts
Approval Bypass
Sandbox Escape Assumptions
Replay / Duplicate Actions
```

---

## 16. Fail-Safe Defaults

If security context is missing:

```text
unknown tenant
unknown tool version
missing approval
unverified source
expired token
policy unavailable
```

the default should not be “best effort.”

It should be:

```text
DENY / DEGRADE TO READ-ONLY
```

This is especially important because agents are often optimized to finish tasks “somehow.”

---

## 17. Degraded Mode

Security does not always require a complete shutdown.

Example:

```text
Production credential broker unavailable
→ agent remains in analysis mode
→ can generate deployment plan
→ cannot deploy
```

This preserves utility without weakening trust boundaries.

## 18. Reference Architecture

```text
                    ┌────────────────────┐
                    │       User         │
                    └─────────┬──────────┘
                              ↓
                    ┌────────────────────┐
                    │ Identity / Session │
                    └─────────┬──────────┘
                              ↓
               ┌─────────────────────────────┐
               │ Context + Provenance Layer  │
               └──────────────┬──────────────┘
                              ↓
                    ┌────────────────────┐
                    │    LLM Planner     │
                    └─────────┬──────────┘
                              ↓
                    ┌────────────────────┐
                    │ Capability Broker  │
                    └─────────┬──────────┘
                              ↓
                    ┌────────────────────┐
                    │ Policy Enforcement │
                    └─────────┬──────────┘
                              ↓
             ┌────────────────┴────────────────┐
             ↓                                 ↓
      Human Approval                     Auto-Approved
      for High Risk                      Low-Risk Action
             \                                 /
              └──────────────┬────────────────┘
                             ↓
                    ┌────────────────────┐
                    │ Sandbox / Executor │
                    └─────────┬──────────┘
                              ↓
                    ┌────────────────────┐
                    │ External Resource  │
                    └────────────────────┘

All stages → structured audit / telemetry
```

---

## 19. What Should Not Be Promised

No serious architecture can currently guarantee:

- 100% prompt-injection resistance,
- 100% freedom from hallucinations,
- complete detection of malicious tool metadata,
- error-free autonomous planning,
- safe use of arbitrary third-party tools.

Security engineering works through **risk reduction and blast-radius control**, not absolute promises.

---

## 20. Security Gates in the SDLC

Agentic security belongs in the development process:

```text
Design
→ threat model

Pull Request
→ static checks + policy tests

CI
→ prompt-injection regression
→ tool authorization tests
→ sandbox tests

Pre-Production
→ adversarial evaluation

Production
→ telemetry + incident response
```

Security implemented only as a runtime filter comes too late.

---

## 21. Incident Response for Agents

An incident requires answerable questions:

1. Which model version was active?
2. Which tools were available?
3. Which credentials were issued?
4. Which untrusted sources were read?
5. Which memory entries were written?
6. Which tool definitions were active?
7. Which policy decisions were made?
8. Which external effects occurred?

The relevant artifacts must therefore be versioned and correlatable.

---

## 22. Kill Switch and Capability Freeze

Production platforms need a fast response mechanism:

```text
disable tool
revoke credential
quarantine MCP server
force read-only
disable memory writes
block egress
```

A kill switch must exist outside the LLM. A compromised agent must not be able to disable it itself.

## Conclusion of the Series

The five parts support one common thesis.

### Prompt Injection

Untrusted content can manipulate reasoning.

### Tool Abuse

Manipulated reasoning becomes dangerous when it has broad capabilities.

### Memory Poisoning

Untrusted content can persist across sessions.

### Supply Chain

External components can change instructions, code, and tool behavior.

### Defensive Architecture

The response is a layered trust architecture:

> **Untrusted input must never reach a privileged effect without independent policy, identity, and capability boundaries.**

That is the core of agentic security.
