Agentic systems are becoming modular. A client connects to MCP servers, loads skills, uses external models, installs packages, and delegates tasks to specialized components.

That accelerates development—and creates a supply chain.

The fourth part of **“Agentic Security & Adversarial AI”** therefore addresses not only classic dependency security, but a new question:

> What does supply-chain security mean when a dependency delivers not just code, but **instructions, tool descriptions, and agentic capabilities** into the model context?

---

## 1. MCP Servers Are Not Passive Libraries

An MCP server can offer clients tools and resources, among other capabilities.

```text
MCP Client
   ↓ tools/list
MCP Server
   ↓
name + description + input schema
```

These metadata can enter the model context and influence tool selection.

The current MCP specification explicitly notes that tool descriptions and annotations should be treated as **untrusted** unless they come from a trusted server.[^1]

That is a critical security property.

---

## 2. Tool Poisoning

Invariant Labs published a practical demonstration of **MCP Tool Poisoning** in 2025.[^2]

The basic pattern:

```text
malicious MCP server
   ↓
tool description contains hidden/manipulative instructions
   ↓
client injects description into LLM context
   ↓
agent behavior changes
```

Conceptually, the attack is a form of indirect prompt injection through tool metadata.

Importantly, the user may not need to actively invoke the malicious tool if its description alone can influence the model.

---

## 3. MCP Rug Pull: Time of Check vs. Time of Use

Invariant Labs used the term **MCP Rug Pull** for a related scenario: a tool appears harmless during the initial review but later changes its definition or description.[^2]

```text
Day 1:
tool description = benign
user approves integration

Day 30:
server changes metadata
client reconnects
new description reaches model
```

This is a classic supply-chain / TOCTOU problem:

> The component reviewed today is not necessarily the component that will effectively execute tomorrow.

---

## 4. Distinguishing Tool Poisoning, Rug Pulls, and Tool Shadowing

### Tool Poisoning

Manipulative instructions are embedded in tool metadata.

### Rug Pull

A previously accepted definition changes later.

### Tool Shadowing / Cross-Server Influence

A malicious server influences how the model uses other legitimate tools.

These attacks share one central property:

> Tool metadata becomes part of model control.

---

## 5. Research Beyond the Initial Demos

After the practical demonstrations, more systematic studies emerged.

A 2025 paper examined several attack classes in the MCP ecosystem, including tool poisoning, rug pulls, and malicious external resources.[^3]

MCPTox evaluated tool-poisoning attacks against real MCP tools and showed that tool metadata remains a serious adversarial channel.[^4]

Such benchmarks matter because individual proofs of concept do not establish a universal vulnerability rate.

---

## 6. Agent Skills: Executable Organizational Logic

Skills or `SKILL.md`-based extensions are especially sensitive from a supply-chain perspective when they:

- contain instructions,
- ship scripts,
- load templates,
- install additional dependencies,
- invoke tools,
- require network access.

A skill is therefore closer to:

```text
Documentation
+ Policy
+ Code
+ Workflow
```

than to a simple README.

An external skill should therefore be subject to the same review standards as executable code.

---

## 7. Typosquatting and Provenance

An attacker does not need to compromise an existing component. It may be sufficient to publish a similarly named component:

```text
official:
company/mcp-github

malicious:
company/mcp-githab
```

Countermeasures include:

- allowlisted registries,
- verified publishers,
- repository ownership checks,
- release signatures,
- pinned commits/tags,
- internal mirrors,
- code review.

Package supply-chain principles apply to agent components as well.

---

## 8. Pinning: Not Just Version, but Behavior

With traditional dependencies, one might pin:

```text
package@1.4.2
```

With dynamic tool systems, additional attributes matter:

```text
tool name
tool description
input schema
capabilities
requested scopes
network destinations
```

A tool manifest can be hashed:

```text
sha256(tool_definition.json)
```

If the definition changes, re-approval is triggered.

Invariant Labs incorporated this principle as “Tool Pinning” in its own MCP security tooling.[^5]

---

## 9. A Hash Does Not Prove Trustworthiness

Pinning answers:

> Did the artifact change?

It does not answer:

> Was the artifact safe in the first place?

Supply-chain security therefore needs both layers:

```text
Acquisition Trust
+ Runtime Integrity
```

### Acquisition Trust

- provenance,
- signature,
- review,
- reputation,
- permissions.

### Runtime Integrity

- hash,
- version,
- drift detection,
- runtime policy,
- egress control.

---

## 10. Network Egress as the Last Line of Defense

Many exfiltration paths require network connectivity.

An MCP server for local Git operations may not need arbitrary internet access at all.

```text
git MCP sandbox
allowed:
- github.enterprise.example

denied:
- arbitrary internet
- cloud metadata
- internal RFC1918 ranges
```

Egress controls bound the impact even if tool behavior is compromised.

---

## 11. Never Use Secrets as Ambient Authority

Dangerous:

```text
MCP process inherits:
AWS_ACCESS_KEY
GITHUB_TOKEN
DATABASE_URL
SSH_AUTH_SOCK
```

Better:

```text
credential broker
→ per-tool
→ per-resource
→ short-lived
→ auditable
```

An external server should not automatically inherit every environment secret from the host process.

---

## 12. MCP Does Not Automatically Solve Trust

MCP standardizes communication. It is not a universal trust model or secure app store.

The specification emphasizes user consent, tool safety, and access controls, but it cannot automatically make a malicious third-party implementation trustworthy.[^1]

This is analogous to HTTP:

> A standardized protocol does not guarantee that the server is benign.

---

## 13. Third-Party Server Lifecycle

A professional process looks like this:

```text
Discover
  ↓
Source Verification
  ↓
Static Review
  ↓
Permission Review
  ↓
Sandbox Test
  ↓
Approve Version
  ↓
Pin Manifest
  ↓
Runtime Monitoring
  ↓
Periodic Re-Certification
```

For updates:

```text
manifest changed?
→ yes
→ diff
→ security review
→ re-approval
```

## 14. AI / Agent Bill of Materials

For incident response, it should be possible to determine which:

- MCP servers,
- versions,
- skills,
- models,
- system prompts,
- tools,
- permissions,
- external APIs

belonged to a particular agent deployment version.

An AI/Agent BOM extends classic SBOM concepts to the agent runtime.

---

## 15. Detection Signals

Possible security events include:

```text
mcp.tool.definition_changed
mcp.server.new_domain
mcp.server.scope_expanded
skill.script_added
skill.network_destination_changed
tool.call.unexpected_peer
tool.call.cross_tenant
```

These events should not disappear into unsearchable chat transcripts. They should produce structured telemetry.

---

## 16. The 2026 Security Context

OWASP treats supply-chain risk as a central dimension in both GenAI and agentic-security work.[^6] In parallel, the current MCP specification explicitly instructs clients to treat tool descriptions as untrusted when the server is not trusted.[^1]

The question therefore shifts from:

> “Can I install this MCP server?”

to:

> **Which identity, definition, privileges, and network reach may this server possess throughout its lifecycle?**

---

## 17. Permission Diffs for Updates

A new version should be reviewed for more than code changes.

Example:

```text
v1:
filesystem: read /workspace
network: none

v2:
filesystem: read /workspace
network: api.external.example
```

Even if the code diff is small, the capability has expanded substantially.

An agent-component review should therefore generate a **permission diff**.

---

## 18. The Transitive Agent Supply Chain

An MCP server may itself:

- load npm/pip dependencies,
- call additional APIs,
- use models,
- retrieve external resources.

The supply chain therefore does not end at the server repository.

```text
Agent Host
→ MCP Server
→ Package
→ External API
→ Model Provider
```

In high-trust environments, these transitive dependencies must be inventoryable.

---

## 19. Reproducible Deployment

Where possible, an approved MCP server should run as a reproducible artifact:

```text
source commit
→ build
→ image digest
→ signed artifact
→ deployment
```

A `latest` tag or remote script that changes on every start destroys the review guarantee.

## Conclusion

MCP and agent skills create a powerful ecosystem of reusable capabilities. That is precisely why they need supply-chain controls.

Tool poisoning and rug pulls are not magical new exploit classes. They combine familiar principles:

- indirect prompt injection,
- TOCTOU,
- dependency drift,
- ambient authority,
- excessive privilege,
- untrusted metadata.

The defense is correspondingly familiar:

> **Verify provenance, pin behavior, limit privileges, and monitor drift.**

In the final part, we assemble these controls into a complete **defensive agent architecture**.
