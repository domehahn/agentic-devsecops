## Information flow as the organizing model

Many agent failures are not caused by a single dangerous API. They arise because data crosses a boundary it was never meant to cross. A URL from a user reaches an HTTP client, a secret read from the environment reaches a log or network sink, or model-produced text becomes a process argument. Taint tracking turns those narratives into explicit data-flow relations.

The central invariant is causal: a relevant source must not reach a sensitive sink unless the path contains a sanitizer or declassifier that is valid for that specific sink and trust model. The original `skil` control model expresses the same idea as `SOURCE -> propagation* -> [SANITIZER] -> SINK`. That relation is more useful than a label such as “suspicious” because it specifies what must be evidenced and what a legitimate counterexample must break.

## Witness paths: what a finding should prove

A deliberately small positive fixture from the source property illustrates the boundary:

```python
value = request.args["url"]
normalized = value.strip()
requests.get(normalized)
```

The safe counterexample changes the semantics rather than merely deleting a suspicious token:

```python
value = request.args["url"]
url = validate_against_allowlist(value)
requests.get(url, timeout=3)
```

The purpose of pairing them is not to teach exploitation. It is to force the detector to explain which relation changes between the two cases. A scanner that fires on both has learned vocabulary; a scanner that can explain the difference has begun to model the security property.

## Sources, labels, and propagation

A taint engine attaches origin information to values and propagates that information through assignments, container literals, selected transformations and function calls. The label does not mean “malicious”; it means “origin matters for this sink.” This distinction lets one value be safe for display but unsafe for command execution, and avoids collapsing every untrusted value into the same severity. This also improves explainability. Reviewers can see the specific security fact rather than receiving a generic severity label, and future tooling can compose that fact with independent findings without double-counting the same evidence.

## Why sanitization must be sink-specific

HTML escaping is not a shell sanitizer. Stripping whitespace is not an SSRF defense. URL parsing is not authorization. A high-quality engine models sanitizers as sink-specific semantic operations. The same function may declassify one threat dimension while leaving others intact. This is why simple “sanitized=true” flags create dangerous false negatives. A useful implementation records both the positive observation and the guard that would have made the path safe. That makes remediation testable and turns false-positive handling into explicit logic instead of a collection of suppressions.

## Interprocedural flow changes the result

Real code passes data through helper functions, object fields and wrappers. Local analysis can miss the path unless functions have summaries that describe which parameters influence which return values or side effects. Conservative summaries improve recall, but they also require explicit coverage states for reflection, dynamic dispatch and unresolved external calls. The same model supports change detection: when identity, configuration or code changes, the platform can recompute the relation and show exactly which part of the previously reviewed assumption no longer holds.

## Path and field sensitivity matter

An object may contain both public and secret fields; a branch may validate one path but not another. Field-insensitive analysis can overtaint everything, while path-insensitive analysis can credit a validator that does not dominate the dangerous sink. The practical goal is not maximal theoretical precision but enough structural precision to distinguish the reviewed safe path from the unsafe one. In an agentic environment this distinction becomes operational because model-generated plans can select the relevant value or capability at runtime. The host therefore needs evidence that can survive from code review into execution policy.

## Agentic systems add semantic sources

Traditional taint catalogs begin with HTTP parameters, files and environment variables. Agentic systems add tool metadata, retrieved documents, memory records, model outputs and cross-agent messages. These are control-bearing inputs even when they are grammatically natural language. Treating them as sources allows the same information-flow framework to connect prompt injection to code execution or exfiltration findings. The design implication is that detection and authorization must remain separate: the scanner identifies the condition, while a policy layer decides whether the condition is permissible in this deployment context.

## Interprocedural uncertainty

For this property, a finding is defensible only when the scanner can reconstruct the relation `SOURCE -> propagation* -> [SANITIZER] -> SINK` from observable evidence. The relevant implementation controls are `SKIL-TAINT-NETWORK`, `SKIL-TAINT-EXECUTION`, `SKIL-TAINT-FILESYSTEM-WRITE`, `SKIL-TAINT-LOG`. The mechanism—Source→Sink Information-Flow Analysis—should therefore emit more than a Boolean match: reviewers need location, the structured observation, context resolution, the decision path, and the coverage state. The source material characterizes current coverage as FULL for modeled sources and sinks; that statement should travel with the finding rather than being lost in presentation.

## False positives, ambiguity, and safe counterexamples

False positives usually come from overtainting, imprecise aliases, or treating generic validation as universal sanitization. Findings should include the complete path or a compact witness path so reviewers can see why the source is believed to reach the sink.

Coverage should be treated as first-class security data. Deterministic syntax and configuration observations can often be reproduced exactly, while intent, future identity and runtime targets may remain uncertain. A mature scanner reports those asymmetries instead of collapsing them into one confidence score. This is particularly important in agentic systems, where the model may choose arguments and tools only after deployment.

## From static flow to runtime enforcement

Use egress policy, filesystem policy and execution brokers as sink-side enforcement. Runtime controls are especially important for flows that static analysis marks as partially resolved. The runtime decision can then enrich the original static finding with concrete target, identity and outcome evidence.

Defense in depth is intentionally redundant. Authoring lint, static analysis, contract verification, supply-chain verification, runtime policy and audit telemetry answer different questions. A strong result from one layer should never be used as a reason to remove the others.

## Evaluation methodology

True-positive fixtures should cover canonical violations, while true-negative fixtures should intentionally reuse similar tokens and syntax so the detector proves it understands context. Boundary cases should change one security-relevant fact at a time. Mutation tests can vary scope, target, normalization, version, guard, or sink. Holdout fixtures protect against overfitting to the public examples. For **Taint Tracking for Agentic Skills**, the most valuable tests are those that preserve the surface appearance while changing the underlying security relation; that is how the suite verifies semantics instead of vocabulary.

For `skil`, implementation claims should be checked against the repository’s control matrix, external-control crosswalk, analyzer tests and any provider-specific tests. Provider-backed coverage—such as OSV or external rule packs—must state whether the provider actually ran.

## Architecture drill-down: from finding to enforceable boundary

A design review for this code semantics property should begin by drawing the trust boundary rather than opening with a rule ID. Identify who controls the input, which component interprets it, what authority is available at that point, and which deterministic guard is expected to stop an unsafe transition. Then map `SOURCE -> propagation* -> [SANITIZER] -> SINK` onto that diagram. The purpose of Source→Sink Information-Flow Analysis is to provide one or more observable edges in that model; it is not a substitute for the model itself. Reviewers should ask whether the same relation can be created indirectly through wrappers, generated configuration, aliases, cached metadata, transitive dependencies, or delegated tools. If so, the implementation needs either deeper static summaries or a runtime control at the unresolved boundary. Finally, confirm that evidence identifiers survive across CI, packaging and runtime so an observed denial or drift event can be traced back to the assumption approved in code review.

The paired fixtures also serve as an architectural regression test. The unsafe example begins with `value = request.args["url"]` while the safe example begins with `value = request.args["url"]`. The important difference is the security relation, not the cosmetic text. If a refactor causes both to produce the same result, the detector or policy has lost a meaningful distinction.

## Common implementation traps

Several implementation mistakes recur around **Taint Tracking for Agentic Skills**, even when the high-level policy is correct:

**1. Treating strings as equivalent to syntax.** Comments, literals and generated text can contain dangerous-looking tokens without being executable, while benign-looking wrappers can hide a real interpreter boundary. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**2. Conflating detection with remediation.** Quoting, normalization or encoding changes are not universally valid sanitizers; the guard must be proven appropriate for the specific sink and language semantics. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**3. Dropping derived-artifact provenance.** If a decoder, parser or data-flow pass produces a second representation, reviewers need to know exactly which original bytes and transformation produced it. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

A useful review discipline is to turn every exception into a scoped, expiring artifact with an owner and rationale. Permanent blanket suppressions hide whether the architecture improved; narrow exceptions preserve the signal and make technical debt measurable.

## How this property composes with adjacent findings

**Prompt injection to sensitive sink.** Taint tracking is the connective tissue between content-layer attacks and concrete effects. A retrieved instruction may be tagged as untrusted control data, propagated through an agent plan, and then reach a network, process, filesystem, or logging sink. The combined path is stronger evidence than either “prompt injection” or “network call” alone because it shows causality.

This composition model is deliberately graph-like: each detector contributes a typed fact and shared evidence identifiers allow a higher-level policy engine to connect them. That prevents one rule from becoming an overloaded catch-all and makes severity escalation explainable.

## Operational signals and measurable assurance

Useful metrics include source-to-sink witness-path completeness, unresolved-call rate, sanitizer classification accuracy, and the share of runtime denials that were predicted statically. These reveal where the information-flow model needs new summaries or source/sink definitions.

Metrics should be tied to an explicit denominator and deployment profile. A low finding count may mean strong controls, weak coverage, or simply little exposure; telemetry and coverage state are needed to tell those cases apart. Trend the data over time and review unexpected changes in both positive findings and scanner-negative regression behavior.

## Engineering implications beyond the scanner

Code-oriented properties benefit from a two-stage architecture: parser or byte-level analyzers first produce deterministic facts, then a composition layer connects those facts to data flow, execution or supply-chain context. This keeps the core detector reproducible and makes semantic enrichment optional rather than authoritative. When code is generated or fetched dynamically, the runtime should rescan the materialized artifact before execution instead of assuming the build-time scan still describes it.

The broader lesson is that an agentic skill is simultaneously text, code, configuration, a tool contract and a supply-chain artifact. Security review should follow the boundary that is actually crossed—data, authority, identity, execution, or control-plane visibility—rather than forcing every risk into the same detection template.

## Design consequences for agent platforms

A reviewer should be able to answer four questions before accepting this property as controlled:

1. **What exact security relation is being asserted?** Here it is `SOURCE -> propagation* -> [SANITIZER] -> SINK`.
2. **What concrete evidence supports the relation?** The evidence must come from Source→Sink Information-Flow Analysis, not from a keyword alone.
3. **What near-neighbor safe case has been tested?** The paired negative fixture should differ in the property, not merely in spelling.
4. **What remains outside static visibility?** Runtime identity, dynamic values, provider state and policy decisions must be named explicitly.

## Conclusion

**Taint Tracking for Agentic Skills** is valuable only when it is treated as a falsifiable security property rather than a checklist term. The goal is not to declare an entire skill “malicious” or “safe.” The goal is to state what boundary may be crossed, show the evidence that supports that statement, preserve the coverage limits, and make the safe countercondition explicit. That produces findings engineers can test, reviewers can reproduce, and runtime policy can enforce.
