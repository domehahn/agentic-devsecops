## Agent state is control-plane data

Agent configuration directories are often more sensitive than application source. They can contain provider settings, tool registrations, session state, prompts, workspace history and credential references. A skill that can freely inspect another agent’s home-directory state may bypass the isolation assumptions of the entire host.

Agent configuration should be treated as control-plane data. Skills receive only the configuration explicitly required for their task; peer-agent settings, histories and private state remain outside the workspace trust boundary by default. The original `skil` control model expresses the same idea as `READ(OTHER_AGENT_PRIVATE_STATE_OR_CONFIG)`. That relation is more useful than a label such as “suspicious” because it specifies what must be evidenced and what a legitimate counterexample must break.

## Own state versus peer state

A deliberately small positive fixture from the source property illustrates the boundary:

```bash
cat ~/.claude/settings.json
cat ~/.codex/config.toml
```

The safe counterexample changes the semantics rather than merely deleting a suspicious token:

```md
Read only configuration shipped with this skill. Do not inspect other agent configuration, history, sessions, or credentials.
```

The purpose of pairing them is not to teach exploitation. It is to force the detector to explain which relation changes between the two cases. A scanner that fires on both has learned vocabulary; a scanner that can explain the difference has begun to model the security property.

## Why the home directory is dangerous ambient authority

Many developer tools store state under `~/.config`, tool-specific dot directories or platform key stores. Mounting an entire home directory into an agent sandbox converts unrelated local state into ambient authority. A useful implementation records both the positive observation and the guard that would have made the path safe. That makes remediation testable and turns false-positive handling into explicit logic instead of a collection of suppressions.

## Reconnaissance without direct credential theft

Even without raw secrets, configuration reveals provider endpoints, model choices, installed plugins, repository paths and policy settings. That reconnaissance can guide later prompt injection, tool abuse or cross-agent targeting. The same model supports change detection: when identity, configuration or code changes, the platform can recompute the relation and show exactly which part of the previously reviewed assumption no longer holds.

## Own-state and peer-state must be distinguished

A skill may legitimately read configuration shipped inside its own package. Detection therefore needs path normalization and ownership context rather than treating every “config” filename as sensitive. The relevant relation is access to private state outside the skill’s declared scope. In an agentic environment this distinction becomes operational because model-generated plans can select the relevant value or capability at runtime. The host therefore needs evidence that can survive from code review into execution policy.

## Filesystem policy should encode the boundary

The strongest design mounts only the project and explicit inputs, with agent-control directories absent or read-denied. Static findings then become design feedback, while runtime policy provides the actual containment. The design implication is that detection and authorization must remain separate: the scanner identifies the condition, while a policy layer decides whether the condition is permissible in this deployment context.

## Control-plane APIs are safer than raw files

If a skill needs a setting, the host can expose a narrow API returning the single approved value. This preserves abstraction, avoids leaking unrelated configuration and allows auditing of exactly what was requested. This also improves explainability. Reviewers can see the specific security fact rather than receiving a generic severity label, and future tooling can compose that fact with independent findings without double-counting the same evidence.

## Mount design and filesystem isolation

A useful finding is a compact proof obligation. It should answer: where did the evidence originate, what intermediate representation did agent-state path/noun boundary detection derive, why does that evidence satisfy `READ(OTHER_AGENT_PRIVATE_STATE_OR_CONFIG)`, and what uncertainty remains? `skil` maps this property to `SKIL-BOUNDARY-AGENT-STATE`. The declared coverage is FULL for documented agent directories, which means any unresolved runtime identity, dynamic dispatch, provider failure, or semantic ambiguity should be represented explicitly instead of being converted into an artificial 'safe' result.

A compact machine-readable evidence record can retain the essentials without pretending to encode the entire analysis:


## False positives, ambiguity, and safe counterexamples

Security tools and migration utilities may intentionally inspect multiple agent configs. Such tools should declare that capability explicitly and run in a dedicated administrative profile, not rely on the same permissions as ordinary task skills.

No static property is a complete verdict on the artifact. The detector can establish local evidence about syntax, identity, data flow or declared authority; it cannot guarantee what an external registry, remote server or model will do later. Engineering decisions should therefore compose static findings with contract verification, supply-chain attestation and runtime policy rather than demanding impossible certainty from one layer.

## Narrow host APIs instead of raw files

Use separate Unix users or sandbox identities, narrow mounts, deny home-directory traversal, keep credential material in a broker or secret store, and audit every exceptional access to agent-control state.

Defense in depth is intentionally redundant. Authoring lint, static analysis, contract verification, supply-chain verification, runtime policy and audit telemetry answer different questions. A strong result from one layer should never be used as a reason to remove the others.

## Administrative exceptions

Evaluation should measure more than raw detection count. Precision matters because noisy controls are disabled; recall matters because adversarial variants are the point of the exercise. For structural properties, report supported syntax classes and unresolved constructs. For provider-backed checks, include provider-availability and freshness tests. Differential comparisons are useful, but property equivalence is more meaningful than finding-count parity. For **Agent Configuration Snooping**, the most valuable tests are those that preserve the surface appearance while changing the underlying security relation; that is how the suite verifies semantics instead of vocabulary.

For `skil`, implementation claims should be checked against the repository’s control matrix, external-control crosswalk, analyzer tests and any provider-specific tests. Provider-backed coverage—such as OSV or external rule packs—must state whether the provider actually ran.

## Architecture drill-down: from finding to enforceable boundary

The architectural question behind **Agent Configuration Snooping** is where interpretation and authority meet. Start with the reviewed artifact and follow the relevant identity, value, or capability through every transformation until the policy decision or side effect occurs. `READ(OTHER_AGENT_PRIVATE_STATE_OR_CONFIG)` is the compact invariant that should remain stable even when implementation syntax changes. agent-state path/noun boundary detection supplies static evidence, but the design should also specify what happens when analysis cannot resolve a value. High-assurance systems fail closed for high-impact operations, expose a bounded approval path for exceptional cases, and log the final resolved identity or target. The review is incomplete if it only proves that today's fixture is detected; it should also show how a future variant is constrained by architecture rather than by the exact spelling in the test corpus.

The paired fixtures also serve as an architectural regression test. The unsafe example begins with `cat ~/.claude/settings.json` while the safe example begins with `Read only configuration shipped with this skill. Do not inspect other agent configuration,`. The important difference is the security relation, not the cosmetic text. If a refactor causes both to produce the same result, the detector or policy has lost a meaningful distinction.

## Common implementation traps

Several implementation mistakes recur around **Agent Configuration Snooping**, even when the high-level policy is correct:

**1. Using a contract vocabulary that is too coarse to enforce.** A declaration such as 'network' is weak if the runtime cannot distinguish approved targets from arbitrary egress. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**2. Interpreting absence of static observation as proof that a capability is unused.** Dynamic frameworks, reflection and remote configuration require explicit coverage states and sometimes runtime evidence. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**3. Mounting global control-plane state for convenience.** Home directories, peer skill directories and MCP config files create ambient authority that bypasses the intended capability model. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

A useful review discipline is to turn every exception into a scoped, expiring artifact with an owner and rationale. Permanent blanket suppressions hide whether the architecture improved; narrow exceptions preserve the signal and make technical debt measurable.

## How this property composes with adjacent findings

**Agent-state access plus secret or routing discovery.** Reading another agent’s configuration can reveal credentials directly, but it can also reveal tool names, trusted endpoints, hidden prompts, or policy settings that support later attacks. Boundary findings should retain what class of state was accessed so downstream analysis can distinguish reconnaissance from direct secret exposure.

This composition model is deliberately graph-like: each detector contributes a typed fact and shared evidence identifiers allow a higher-level policy engine to connect them. That prevents one rule from becoming an overloaded catch-all and makes severity escalation explainable.

## Operational signals and measurable assurance

Track reads of control-plane directories, denied home-directory traversals, administrative exceptions, configuration classes accessed, and whether any access exposed secret-bearing material. Ordinary skills should trend toward zero cross-agent reads.

Metrics should be tied to an explicit denominator and deployment profile. A low finding count may mean strong controls, weak coverage, or simply little exposure; telemetry and coverage state are needed to tell those cases apart. Trend the data over time and review unexpected changes in both positive findings and scanner-negative regression behavior.

## Engineering implications beyond the scanner

Capability and isolation properties become most valuable when compiled into runtime controls. A declaration can drive egress filters, filesystem mounts, process brokers, secret scopes and delegation edges. Static observations then test whether implementation and contract agree, while runtime denials expose behaviors the static analyzers could not resolve. This feedback loop turns the contract into a living security boundary instead of documentation that gradually drifts from reality.

The broader lesson is that an agentic skill is simultaneously text, code, configuration, a tool contract and a supply-chain artifact. Security review should follow the boundary that is actually crossed—data, authority, identity, execution, or control-plane visibility—rather than forcing every risk into the same detection template.

## Validation and audit

A reviewer should be able to answer four questions before accepting this property as controlled:

1. **What exact security relation is being asserted?** Here it is `READ(OTHER_AGENT_PRIVATE_STATE_OR_CONFIG)`.
2. **What concrete evidence supports the relation?** The evidence must come from agent-state path/noun boundary detection, not from a keyword alone.
3. **What near-neighbor safe case has been tested?** The paired negative fixture should differ in the property, not merely in spelling.
4. **What remains outside static visibility?** Runtime identity, dynamic values, provider state and policy decisions must be named explicitly.

## Conclusion

**Agent Configuration Snooping** is valuable only when it is treated as a falsifiable security property rather than a checklist term. The goal is not to declare an entire skill “malicious” or “safe.” The goal is to state what boundary may be crossed, show the evidence that supports that statement, preserve the coverage limits, and make the safe countercondition explicit. That produces findings engineers can test, reviewers can reproduce, and runtime policy can enforce.
