Markdown verbindet strukturierte Security-Ergebnisse mit einer Form, die Menschen in Git-Plattformen, Tickets, Wikis und Pull Requests unmittelbar lesen können.

Das Feature ist damit nicht nur eine Komfortfunktion.

Es verändert, **welcher Kontext geprüft wird, welche Vertrauensgrenzen gelten und wie belastbar das Ergebnis später in CI/CD oder Security-Governance verwendet werden kann**.

## Was das Feature leistet

Ein Markdown-Report kann Zusammenfassung, Findings, Evidenz, Remediation und Coverage in klaren Abschnitten darstellen. Im Gegensatz zur Terminalausgabe bleibt die Formatierung auch in gespeicherten Artefakten oder Review-Kommentaren erhalten.

Das Format sollte aus denselben internen Finding-Daten wie JSON erzeugt werden. So bleibt die Semantik konsistent und nur die Präsentation ändert sich.

## Typischer Ablauf

Unabhängig von der konkreten Implementierung sollte der Ablauf klar getrennte Phasen besitzen:

```text
Input
  ↓
Validierung und Normalisierung
  ↓
Feature-spezifische Verarbeitung
  ↓
Security-Analyse
  ↓
Findings + Coverage + technischer Status
  ↓
Policy-Entscheidung
```

Diese Trennung ist wichtig, weil ein technischer Fehler bei Beschaffung, Parsing oder Providerzugriff nicht dieselbe Bedeutung hat wie ein tatsächlich unauffälliges Prüfergebnis.

## Negatives Beispiel

Ein Report kopiert ungefiltert Artefakttext in Markdown:

```markdown
## Finding
<script>alert('x')</script>
```

Je nach Renderer kann eingebettetes HTML unerwünschtes Verhalten oder zumindest irreführende Darstellung erzeugen. Lange Snippets können außerdem den gesamten Review dominieren.

## Positives Beispiel

Der Renderer escaped problematische Inhalte, begrenzt Snippet-Länge und strukturiert Findings:

```markdown
## HIGH — NET-004

**Datei:** `config.yaml:18`

Unbeschränkter externer Endpunkt erkannt.

**Empfehlung:** Zielhost per Allowlist begrenzen.
```

Eine Zusammenfassung am Anfang ermöglicht schnelle Triage; Details bleiben darunter nachvollziehbar.

<KeyTakeaway>
Markdown macht Findings reviewbar. Ein sicherer Renderer behandelt Evidenz weiterhin als untrusted content und optimiert den Bericht für Triage statt für maximale Rohdatenmenge.
</KeyTakeaway>

## Security- und Betriebsaspekte

Markdown ist nicht automatisch „nur Text“. Renderer können HTML, Links und eingebettete Inhalte unterschiedlich behandeln. Untrusted Evidenz sollte escaped und externe Links sollten bewusst erzeugt werden.

Bei automatisch geposteten PR-Kommentaren sind Größenlimits und Aktualisierungsstrategien wichtig, damit nicht bei jedem Lauf neue Megakommentare entstehen.

Ein professioneller Betrieb sollte außerdem drei Zustände konsequent auseinanderhalten:

```text
clean      = geprüft, kein relevanter Befund
finding    = geprüft, mindestens ein relevanter Befund
incomplete = Prüfung technisch oder fachlich nicht vollständig
```

Gerade der dritte Zustand ist für DevSecOps entscheidend.

Ein Scanner darf fehlende Coverage nicht als positives Sicherheitsurteil darstellen.

## Wo das Feature sinnvoll eingesetzt wird

Geeignet für Pull Requests, Tickets, Wiki-Dokumentation, Release-Reports und menschliche Freigaben. Markdown ist besonders stark, wenn Befunde gemeinsam diskutiert werden.

Für programmatische Policies bleibt JSON oder SARIF die bessere Primärschnittstelle.

Die konkrete Aktivierung sollte deshalb aus dem gewünschten Trust-Modell abgeleitet werden und nicht allein aus technischer Verfügbarkeit.

## Integration in eine DevSecOps-Pipeline

In einer Pipeline sollte das Feature nicht isoliert betrachtet werden.

Ein belastbares Muster ist:

```text
Source / Artifact
      ↓
Input-Validierung
      ↓
Deterministische Analyse
      ↓
optionale erweiterte Analyse
      ↓
normalisierte Findings
      ↓
Policy Gate
      ↓
Report / Audit Evidence
```

Dabei sollte jeder Report mindestens folgende Informationen transportieren:

- Identität des analysierten Artefakts
- aktive Analyseverfahren
- übersprungene oder nicht verfügbare Prüfschritte
- stabile Regel- oder Finding-IDs
- Schweregrad und Evidenz
- Scanner- und Regelversion
- eindeutiger technischer Abschlussstatus

Damit wird das Feature nicht nur ausführbar, sondern **auditierbar**.

## Fazit

Markdown macht Findings reviewbar. Ein sicherer Renderer behandelt Evidenz weiterhin als untrusted content und optimiert den Bericht für Triage statt für maximale Rohdatenmenge.

Der eigentliche Wert entsteht dann, wenn das Feature mit klaren Grenzen, reproduzierbaren Eingaben und transparenten Ergebnissen in den Entwicklungsprozess eingebettet wird.
