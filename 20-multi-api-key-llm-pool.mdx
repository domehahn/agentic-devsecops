LLM-gestützte Batch-Scans stoßen schnell an Rate Limits. Ein Multi-Key-Pool verteilt Requests auf mehrere Credentials und kann damit Durchsatz sowie Resilienz erhöhen – sofern die Keys tatsächlich unabhängige Limits besitzen.

Das Feature ist primär operativ, hat aber direkte Security-Auswirkungen: Mehr Credentials bedeuten mehr Secret Material und komplexere Zuordnung von Requests zu Identitäten.

<Warning>
Mehr API-Keys erhöhen nicht nur Durchsatz, sondern auch Secret-Sprawl. Skalierung sollte die Identity- und Audit-Grenzen nicht verwischen.
</Warning>

## Was das Feature wirklich bedeutet

Pooling sollte nicht heimlich in der Anwendung passieren. Security Teams müssen wissen, welche Keys zu welchem Provider und welchem Modell gehören, wie Fehler behandelt werden und ob verschiedene Konten unterschiedliche Datenrichtlinien haben.

Ein Pool aus heterogenen Endpoints kann Ergebnisse außerdem semantisch weniger vergleichbar machen.

## SkillSpector

Der SkillSpector-Batch-Scanner dokumentiert `SKILLSPECTOR_API_KEYS` als Multi-Key-Pool. Ein Eintrag enthält Key, Base URL und Modell; mehrere Einträge werden per Semikolon getrennt und Requests über den Pool verteilt. Ein Single-Key-Fallback bleibt möglich.

Das ist eine klare Stärke für große LLM-Scan-Kampagnen und hohe Concurrency.

## `skil`

`skil` besitzt eine Provider-Abstraktion und parallele Collection Scans, aber keinen gleichwertigen First-Class-Multi-API-Key-Pool in der dokumentierten CLI. Ein externer Gateway, Load Balancer oder eigener Provider könnte diese Aufgabe übernehmen.

Damit liegt die Skalierungsverantwortung stärker außerhalb des Scanners.

## Praxisbeispiel

```bash
# SkillSpector Batch Pool
export SKILLSPECTOR_API_KEYS='key1|https://api.example/v1|model-a;key2|https://api.example/v1|model-a'
python -m contrib.batch_scan.batch_scan ./skills --workers 20

# skil: typischerweise ein freigegebenes Gateway als einzelner Provider-Endpunkt
skil scan-all ./skills --workers 8 --semantic --semantic-model model-a
```

Ein Enterprise-Muster ist, Key-Pooling gar nicht im Scanner zu machen, sondern hinter einem zentralen LLM-Gateway mit eigener Rate-Limit- und Auditlogik.

## Security- und DevSecOps-Einordnung

- Jeden Key als eigenes Secret mit Lifecycle behandeln.
- Keine Keys aus verschiedenen Datenverarbeitungszonen unkontrolliert mischen.
- Provider/Modell pro Request in Evidence dokumentieren.
- Account-Level-Rate-Limits beachten – mehrere Keys bringen dort keinen zusätzlichen Durchsatz.
- Zentrales Gateway erwägen, wenn Governance wichtiger als lokales Pooling ist.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

## Direkter Vergleich

| Aspekt | SkillSpector | `skil` |
| --- | --- | --- |
| Feature vorhanden | ja | ja |
| Schwerpunkt | Integration und Scanner-Ergonomie | explizite Trust Boundaries und Evidence |
| Bewertung | SkillSpector stärker | SkillSpector stärker |

**Bewertung aus der Vergleichsmatrix:** SkillSpector stärker.

## Typische Fehlinterpretation

„Drei Keys bedeuten dreifachen Durchsatz.“ Nur wenn die Limits unabhängig sind. Account-, Organisation- oder Endpoint-Limits können alle Keys gemeinsam drosseln.

## Einordnung in die Pipeline

Dieses Feature ist vor allem für die **Skalierungs- und Betriebsstufe** relevant. Collection Discovery, Parallelität und Providerlimits sollten zentral konfiguriert werden. Einzelne Skill-Ergebnisse müssen trotz Aggregation separat nachvollziehbar bleiben.

Für Registry-Betrieb empfiehlt sich ein regelmäßiger vollständiger Re-Scan zusätzlich zu PR-Gates, damit neue Scannerregeln oder Vulnerability-Daten auch unveränderte Skills erneut bewerten.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

SkillSpector ist bei eingebautem Multi-Key-Pooling stärker. `skil` kann über externe Providerinfrastruktur skalieren, bringt den Pool aber nicht als vergleichbare Kernfunktion mit. Für große semantische Batch-Scans ist das ein echter operativer Unterschied.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
