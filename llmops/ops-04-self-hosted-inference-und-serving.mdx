Self-hosted inference is often justified with two arguments: data sovereignty and lower cost. Both can be valid—but both are **workload-dependent**. A GPU that runs around the clock at poor utilization is not automatically cheaper than an API. And a model in your own data center is not automatically “sovereign” if the model license, telemetry, build images, or management plane still create external dependencies.

The technical challenge of LLM serving lies primarily in an unusual resource profile: model weights consume large amounts of GPU memory, while the **KV cache** grows dynamically for every active sequence. At the same time, requests vary significantly in prompt length and generation duration.

Systems such as **vLLM** were built specifically for this problem.[^1]

---

## 1. Why Naive Inference Wastes GPU Memory

During autoregressive generation, the model stores key and value states from previous tokens so they do not have to be recomputed from scratch for every new token.

```text
Request A: [token token token ........]
Request B: [token ....]
Request C: [token token token token ..............]
```

Sequences grow at different rates. Static reservation for maximum sizes leads to fragmentation and unused memory.

Less usable KV memory means smaller batches—and therefore poorer GPU utilization.

---

## 2. PagedAttention: Virtual-Memory Ideas for the KV Cache

The vLLM work by Kwon et al. transfers the paging principle of virtual-memory management to the KV cache.[^1]

```text
Logical KV sequence
  ├─ block 0 -> physical block 17
  ├─ block 1 -> physical block 03
  └─ block 2 -> physical block 91
```

Instead of preallocating one large contiguous memory region per request, KV blocks are managed flexibly.

In their evaluation, the authors report **near-zero KV-cache waste** and 2–4× higher throughput than the systems compared at the time at similar latency—depending on model, sequence length, and decoding setup.[^1]

The qualification matters: this is a benchmark result from the paper, not a universal guarantee that every modern deployment will reproduce exactly the same factor.

---

## 3. Continuous / In-Flight Batching

Traditional batching waits until every request in a batch has finished. For text generation, this is inefficient because sequences have different lengths.

```text
Batch:
A: █████████████
B: ███           -> slot idle
C: ███████       -> slot idle
```

Continuous, or in-flight, batching can continuously replace completed requests with new ones.

```text
GPU scheduler
   ↓
active sequences change every decoding step
```

NVIDIA TensorRT-LLM also uses scheduling and KV-cache mechanisms in which new requests can be admitted depending on available KV memory.[^2]

---

## 4. Throughput and Latency Are Different Optimization Goals

A serving system can maximize throughput by building large batches. An interactive chat workload, by contrast, needs low time to first token.

Typical metrics include:

```text
TTFT  = Time to First Token
TPOT  = Time per Output Token
ITL   = Inter-Token Latency
RPS   = Requests per Second
TPS   = Tokens per Second
```

For agents, additional factors matter:

- tool wait times,
- long contexts,
- burst behavior from multiple parallel sub-agents.

A platform should define SLOs per workload class instead of treating “maximum TPS” as the only objective.

---

## 5. Open Weight Is Not Automatically Open Source

Many self-hostable models publish their weights but use custom licenses. “Open-source LLM” is therefore not the most precise label for every downloadable model.

Before deployment, the model catalog should include:

```yaml
model: example-70b
license: reviewed
commercial_use: approved
weights_source: pinned
checksum: sha256:...
allowed_use_cases:
  - internal-code-assistance
```

Software supply-chain governance applies to model weights as well.

---

## 6. Quantization Is a Capacity Lever with Quality Risk

FP16/BF16 models require roughly two bytes per parameter for the weights alone. Lower precision can substantially reduce memory consumption.

```text
BF16 -> larger / high precision
FP8  -> lower
INT8 -> lower
INT4 -> strongly reduced
```

Actual memory requirements depend on format, metadata, KV cache, and runtime. More importantly, quantization must not be evaluated on perplexity alone. For agents, tool selection, code quality, and reasoning evals are relevant.

---

## 7. Parallelism: One Model Does Not Always Fit on One GPU

Large models require multiple GPUs.

Possible strategies include:

- Tensor Parallelism,
- Pipeline Parallelism,
- Data Parallelism / Replica Serving,
- Expert Parallelism for MoE models.

Each strategy changes network traffic, failure domains, and scheduling. An eight-GPU node is not simply “eight times one GPU.”

For high utilization, topology and interconnect—such as NVLink/NVSwitch or the cluster network—are part of performance design.

---

## 8. The Hardest Part Is Capacity Planning

API usage shifts capacity planning to the provider. Self-hosting brings it back in-house.

You need to model:

```text
concurrent requests
input length distribution
output length distribution
model size
KV cache per token
batching efficiency
SLO target
headroom
failure reserve
```

The average is not enough. Agents create heavy tails: individual repository tasks can have extremely long contexts and many generation steps.

---

## 9. Self-Hosting Needs a Model Gateway

Applications should not point directly to individual vLLM instances.

```text
Applications
     ↓
Model Gateway
  - auth
  - quota
  - routing
  - model catalog
  - tracing
  - rate limits
     ↓
Inference Pools
```

This makes it possible to swap models, perform canary deployments, and measure usage per team.

---

## 10. Security and Isolation

A self-hosted model API often processes highly sensitive prompts. It therefore requires:

- TLS and private network paths,
- workload identity,
- tenant authorization,
- minimized prompt logging by default,
- checksums for model artifacts,
- pinned container images,
- regular CVE and dependency patching,
- a separate admin plane.

“The data never leaves our data center” is only one property. Security still requires defense in depth.

---

## 11. API vs. Self-Hosted: Break-Even Is Multidimensional

A financial comparison:

```text
Managed API:
variable inference cost
+ low infrastructure ops

Self-hosted:
GPU amortization / rental
+ idle capacity
+ platform engineering
+ power / cooling / networking
+ operations
+ model lifecycle
```

At consistently high throughput, self-hosting can become economically attractive. With highly variable or low utilization, an API may be more efficient.

There are also non-monetary criteria: data control, model choice, latency, provider lock-in, and regulatory requirements.

---

## 12. Benchmark on Your Own Workload

Before making a decision, the same representative traces should be run against several serving options:

```text
Dataset of production-like prompts
      ↓
API Provider A
vLLM Config B
TensorRT-LLM Config C
      ↓
Compare:
quality
TTFT
TPOT
throughput
GPU utilization
cost/successful-task
```

Without a quality comparison, a faster quantized model is not necessarily an improvement.

---

## 13. Model Lifecycle: Serving Is Not the Same as Operating a Model

A production pool needs more than a container with weights. Model releases must be treated like other production artifacts:

```text
Download / Build
  ↓ checksum + license review
Model Registry
  ↓
Offline Evals
  ↓
Load / stress test
  ↓
Canary endpoint
  ↓
Online quality + performance
  ↓
Promotion or rollback
```

A new model can be technically faster while degrading tool-calling quality. Rollouts therefore need both infrastructure and domain-quality metrics.

## 14. Prefix Caching and KV Sharing Change Workload Economics

Many requests share large prefixes—system instructions, tool schemas, or repository context. Modern serving systems can partially reuse such structures. The potential gain, however, depends heavily on prompt identity, cache lifetime, and scheduling.

This creates a new optimization lever for platform teams: stable system components should not vary unnecessarily on every request. Even timestamps or randomly ordered tool lists can prevent cache hits.

The optimization must again be checked against isolation requirements. Tenant-specific or confidential prefixes must not be shared across tenant boundaries because of poorly designed cache keys.

## 15. GPU Failures and Rollouts Need Capacity Headroom

A cluster at 95% sustained utilization may look financially efficient, but it leaves little room for a GPU failure or rolling upgrade. Resilience requires reserve capacity.

```text
steady-state demand
+ burst headroom
+ failure headroom
+ rollout headroom
= required capacity
```

The economic optimum is therefore not maximum nominal GPU utilization. It is the highest utilization at which required SLOs can still be met during maintenance and failures.

## Conclusion

Self-hosted inference is not merely an infrastructure decision. It combines **model licensing, GPU memory management, scheduling, quality evaluation, security, and FinOps**.

vLLM demonstrates with PagedAttention why efficient KV-cache management is central to high-throughput serving. The original work reports 2–4× throughput over the compared systems at the same latency and near-zero KV-cache waste—under its respective test conditions.[^1]

Whether self-hosting is the right choice, however, depends on the actual workload. The relevant metric is not tokens per second alone, but **quality and cost per successful task under the required SLOs**.

The final part of the LLMOps series therefore addresses what remains true regardless of hosting model: **how an agent system continues operating when a provider, model, tool, or region fails.**
