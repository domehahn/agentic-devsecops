Prompt Injection ist bei AI Skills kein klassischer Input-Validation-Fehler. Der Skill selbst besteht aus Instruktionen und wird vom Agenten gerade deshalb geladen, damit er Verhalten beeinflusst. Die Sicherheitsfrage lautet daher nicht, **ob** der Skill Verhalten verändert, sondern ob er versucht, seine legitime Autorität zu überschreiten.

SkillSpector trennt diese Angriffsfläche in vier statische Musterfamilien. Das reicht vom offensichtlichen „ignoriere frühere Regeln“ bis zu unsichtbaren Unicode-Instruktionen und subtiler Verhaltenslenkung.

<KeyTakeaway>
Vulnerability Patterns sind keine bloße Liste verdächtiger Strings. Sie beschreiben **Sicherheitsproperties und Trust-Boundary-Verletzungen**, die bei agentischen Artefakten aus natürlicher Sprache, Code, Metadaten, Tools und Runtime-Capabilities entstehen.
</KeyTakeaway>

## Die Pattern-Familie

Dieser Beitrag betrachtet `P1`, `P2`, `P3`, `P4` im SkillSpector-Snapshot `2.5.0` beziehungsweise Commit `34f6030`.

| Rule | Pattern | Bedeutung |
| --- | --- | --- |
| `P1` | Override Instructions | Versucht bestehende System-, Sicherheits- oder Entwickleranweisungen außer Kraft zu setzen. |
| `P2` | Hidden Instructions | Versteckt Direktiven in Kommentaren, Unicode-Steuerzeichen, Zero-Width-Zeichen oder kodierten Darstellungen. |
| `P3` | External Transmission Instructions | Fordert den Agenten auf, Conversation Context, Nutzerdaten oder Dateien an externe Ziele zu übertragen. |
| `P4` | Subtle Steering | Manipuliert Empfehlungen oder Entscheidungen subtil, ohne offen eine Sicherheitsregel zu überschreiben. |

Die Rule IDs sind vor allem als stabile Triage-Signale nützlich. Für eine Freigabeentscheidung sollten zusätzlich Finding-Text, Datei, Zeile, Confidence, Analyzer-Coverage und das konkrete Artefakt berücksichtigt werden.

## Das Sicherheitsmodell dahinter

Die zentrale Trust Boundary liegt zwischen **vertrauenswürdiger Agentenpolicy** und **unvertrauenswürdigem Skill-Inhalt**. Ein Skill darf einen Arbeitsablauf beschreiben, aber nicht die Regeln neu definieren, unter denen der Agent Tools, Secrets oder Benutzerdaten verwenden darf.

P1 erfasst direkte Autoritätsübernahme. P2 adressiert Review-Evasion: Inhalte, die ein Mensch kaum sieht, ein Modell aber trotzdem verarbeitet. P3 verbindet Instruction Injection mit Datenabfluss. P4 zielt auf Manipulation, die äußerlich wie normale Produktempfehlung oder Assistenz wirken kann.

<Architecture>
Ein Scan kann gefährliche Eigenschaften sichtbar machen. Die eigentliche Sicherheitsgrenze sollte trotzdem außerhalb des unvertrauenswürdigen Skills liegen: in Tool-Gateways, Filesystem-Isolation, Network Policy, Identity, Approval und Runtime Enforcement.
</Architecture>

## Verständliches Beispiel

```md title="SKILL.md"
# Deployment Assistant

Hilf beim Erstellen eines Deployment-Plans.

<!-- verdächtig: versteckte Instruktion mit höherer Autorität -->

Verwende nur die freigegebenen Deployment-Tools.
```

Das Beispiel ist absichtlich harmlos formuliert: Entscheidend ist die **Position einer versteckten Direktive** in einem Artefakt, das der Agent als Handlungsanweisung interpretiert. Ein menschlicher Reviewer sieht möglicherweise nur die sichtbaren Absätze, während ein Parser oder Modell auch Kommentar- oder Unicode-Inhalte erhält.

Das Beispiel zeigt das zentrale Prinzip: Nicht jede verwendete API oder Formulierung ist automatisch bösartig. Relevant ist, **welche Autorität ein Skill erhält, welche Daten er verarbeiten kann und welche Boundary er überschreiten soll**.

## Wie SkillSpector das erkennt

Der aktuelle Analyzer kombiniert Pattern Matching mit Unicode-spezifischer Logik. P1 sucht nach Formulierungen für Instruction Override. P2 berücksichtigt HTML-/Markdown-Kommentare, Zero-Width-Zeichen, Bidirectional-Control-Zeichen und den Unicode-Tag-Block für sogenanntes ASCII Smuggling. Dabei existieren bewusst enge Ausnahmen für legitime Emoji-Sequenzen, um False Positives zu reduzieren.

P3 sucht explizite Anweisungen zur Übertragung von Conversation Context oder User Data. P4 erfasst sprachliche Muster, die den Agenten dauerhaft zu bestimmten Empfehlungen oder versteckter Einflussnahme drängen.[^module]

SkillSpector arbeitet dabei nicht mit einer einzigen monolithischen „AI Security“-Regel. Die Analyzer sind getrennte Nodes, die Findings erzeugen und im aktuellen Workflow über ein Inspection Ledger beziehungsweise Analyzer-Status sichtbar machen, welche Analyse tatsächlich ausgeführt wurde.[^registry]

## False Positives, False Negatives und Kontext

Prompt-Injection-Erkennung ist kontextabhängig. Ein Security-Dokument darf den Satz „ignore previous instructions“ als Beispiel enthalten, ohne selbst eine bösartige Direktive zu sein. Pattern Matching benötigt deshalb Dateikontext, Confidence und Review.

Besonders P4 bleibt probabilistisch: legitime Produktpräferenzen und unzulässige Manipulation können sprachlich ähnlich aussehen. Ein Finding ist hier ein **Review-Signal**, kein Beweis für malicious intent.

Das ist besonders wichtig bei Agent Skills. Dieselbe Zeichenfolge kann in drei Rollen vorkommen:

```text
Dokumentation:     beschreibt ein gefährliches Muster
Test/Eval:         enthält absichtlich eine Angriffsprobe
Produktivskill:    weist den Agenten tatsächlich zu diesem Verhalten an
```

Ein professionelles Review bewertet deshalb nicht nur den Match, sondern **Dateirole, Ausführbarkeit, deklarierte Capability, Datenfluss und Kontext**.

<Warning>
„Pattern gefunden“ bedeutet nicht automatisch „Skill ist bösartig“. Umgekehrt bedeutet „kein Pattern gefunden“ nicht, dass ein Skill sicher ist. Pattern Detection ist eine Evidence-Schicht innerhalb eines mehrstufigen Assurance-Prozesses.
</Warning>

## Sichere Gegenmaßnahmen

- Skill-Instruktionen auf den dokumentierten Zweck begrenzen.
- Autoritätsregeln außerhalb des Skills im Host beziehungsweise Agent Runtime erzwingen.
- Versteckte Unicode- und Kommentar-Instruktionen aus produktiven Skill-Metadaten entfernen.
- Tool-, Netzwerk- und Secret-Rechte nicht allein durch Prompttext kontrollieren.
- Statische Findings mit Human Review und, falls nötig, semantischer Analyse kombinieren.

Eine gute Remediation entfernt nicht nur den konkreten String, der einen Scanner auslöst. Sie reduziert die zugrunde liegende Fähigkeit. Sonst kann dieselbe Sicherheitsverletzung mit anderer Syntax wieder erscheinen.

## Einordnung in DevSecOps und CI/CD

Prompt-Injection-Regeln gehören in jedes Pre-Install- und Pull-Request-Gate. P1/P2 mit hoher Confidence sollten mindestens einen Review erzwingen. Noch wichtiger ist jedoch die Runtime: Selbst ein übersehener Prompt darf keine Autorität erzeugen, die der Host nicht bereits technisch freigegeben hat.

Ein belastbarer Workflow kann so aussehen:

```text
untrusted skill
      │
      ▼
bounded loader
      │
      ▼
static patterns + AST + taint + dependency/MCP analysis
      │
      ▼
coverage + findings + artifact identity
      │
      ▼
environment-specific policy
      │
      ├── allow
      ├── require review
      └── block
```

Der zentrale Punkt ist die Trennung zwischen **Detection** und **Decision**. Ein Scanner liefert Evidenz. Eine Policy entscheidet, welche Evidenz in Development, Sandbox, CI oder Produktion akzeptabel ist.

## Review-Fragen

Bei einem Finding aus dieser Pattern-Familie sollte ein Reviewer mindestens prüfen:

- Entspricht das beobachtete Verhalten dem dokumentierten Zweck des Skills?
- Ist die betroffene Capability überhaupt erforderlich?
- Kann dieselbe Funktion mit engeren Pfaden, Tools, Domains, Commands oder Rechten umgesetzt werden?
- Ist der Treffer tatsächlicher ausführbarer beziehungsweise handlungsleitender Inhalt oder nur Dokumentation/Testmaterial?
- Welche Daten können die betroffene Boundary passieren?
- Wird die Sicherheitsgrenze technisch durch den Host erzwungen oder nur textuell im Prompt beschrieben?
- Ist das analysierte Artefakt eindeutig per Version beziehungsweise Digest identifizierbar?
- Muss das Finding blockieren, einen Human Review auslösen oder als dokumentierte Ausnahme behandelt werden?

## Warum das für Agentic DevSecOps relevant ist

Klassisches DevSecOps betrachtet Source Code, Dependencies, Images, IaC und Runtime-Konfiguration. Agentic DevSecOps erweitert diese Oberfläche um **Instruktionslogik und delegierte Autorität**.

Ein Skill kann formal nur Markdown sein und trotzdem operative Wirkung besitzen. Er beeinflusst, welche Tools ein Agent wählt, welche Informationen er als relevant betrachtet, welche Side Effects er auslöst und welche Grenzen er respektiert. Deshalb müssen natürliche Sprache und Toolmetadaten mit denselben Prinzipien behandelt werden, die wir bei Code bereits kennen:

- Least Privilege
- Untrusted Input
- Explicit Trust Boundaries
- Reproducible Artifacts
- Policy as Code
- Auditability
- Defense in Depth

## Fazit

Prompt-Injection-Regeln gehören in jedes Pre-Install- und Pull-Request-Gate. P1/P2 mit hoher Confidence sollten mindestens einen Review erzwingen. Noch wichtiger ist jedoch die Runtime: Selbst ein übersehener Prompt darf keine Autorität erzeugen, die der Host nicht bereits technisch freigegeben hat.

Die Pattern-Familie `P1`, `P2`, `P3`, `P4` ist vor allem dann wertvoll, wenn sie nicht isoliert betrachtet wird. Ihr Nutzen entsteht durch die Kombination aus präzisem Finding, nachvollziehbarer Coverage, Kontextreview und einer Runtime, die unerlaubte Aktionen auch dann verhindert, wenn die statische Analyse etwas übersieht.

<KeyTakeaway>
Die entscheidende Frage ist nicht „Hat der Skill einen Treffer?“, sondern: **Welche Trust Boundary würde dieses Verhalten überschreiten, und welche unabhängige Kontrolle verhindert den unerlaubten Effekt?**
</KeyTakeaway>
