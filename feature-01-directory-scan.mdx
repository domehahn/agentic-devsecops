Ein Verzeichnis-Scan behandelt einen gesamten Projektbaum als zusammenhängendes Prüfobjekt. Das ist entscheidend, wenn sicherheitsrelevante Aussagen nicht in einer einzelnen Datei stehen, sondern über Konfiguration, Quelltext, Metadaten, Abhängigkeiten und eingebettete Ressourcen verteilt sind.

Das Feature ist damit nicht nur eine Komfortfunktion.

Es verändert, **welcher Kontext geprüft wird, welche Vertrauensgrenzen gelten und wie belastbar das Ergebnis später in CI/CD oder Security-Governance verwendet werden kann**.

## Was das Feature leistet

Bei einem Directory Scan wird ein Wurzelverzeichnis rekursiv erfasst, normalisiert und anschließend als konsistenter Befundkontext analysiert. Ein robuster Scanner unterscheidet reguläre Dateien, symbolische Links, versteckte Dateien, generierte Inhalte, Binärdateien und bekannte Ausschlussmuster. Wichtig ist, dass die Inventarisierung vor der eigentlichen Analyse deterministisch erfolgt.

Die Sicherheitswirkung entsteht vor allem durch Korrelation. Eine Konfigurationsdatei kann Netzwerkzugriff erlauben, ein Skript kann diese Berechtigung nutzen und eine Manifestdatei kann zusätzliche Abhängigkeiten nachladen. Ein dateiweiser Blick erkennt diese Beziehungen nur eingeschränkt.

## Typischer Ablauf

Unabhängig von der konkreten Implementierung sollte der Ablauf klar getrennte Phasen besitzen:

```text
Input
  ↓
Validierung und Normalisierung
  ↓
Feature-spezifische Verarbeitung
  ↓
Security-Analyse
  ↓
Findings + Coverage + technischer Status
  ↓
Policy-Entscheidung
```

Diese Trennung ist wichtig, weil ein technischer Fehler bei Beschaffung, Parsing oder Providerzugriff nicht dieselbe Bedeutung hat wie ein tatsächlich unauffälliges Prüfergebnis.

## Negatives Beispiel

Ein Team prüft nur `manifest.yaml`, weil dort die deklarierte Funktion beschrieben ist. Im Unterverzeichnis `scripts/` liegt jedoch ein Shell-Skript, das Umgebungsvariablen ausliest und an einen externen Host sendet.

```text
project/
├── manifest.yaml
├── README.md
└── scripts/
    └── bootstrap.sh
```

Die Prüfung meldet „unauffällig“, obwohl das ausführbare Verhalten außerhalb der betrachteten Datei liegt. Der Fehler ist nicht mangelnde Signaturqualität, sondern eine unvollständige Erfassung des Prüfobjekts.

## Positives Beispiel

Der Scanner inventarisiert zuerst den gesamten Baum und bindet alle Funde an denselben Artefaktkontext.

```bash
scanner scan ./project
```

Die Ausgabe kann anschließend Beziehungen herstellen:

```text
manifest.yaml  -> erlaubt Netzwerkzugriff
bootstrap.sh   -> liest TOKEN aus der Umgebung
bootstrap.sh   -> sendet Daten an api.example.invalid
Ergebnis       -> hoher Exfiltrationsverdacht
```

Damit wird nicht nur eine verdächtige Zeile gefunden, sondern die effektive Wirkung im Gesamtartefakt bewertet.

<KeyTakeaway>
Ein Verzeichnis ist ein Sicherheitskontext. Erst die vollständige, begrenzte und reproduzierbare Inventarisierung macht dateiübergreifende Beziehungen zuverlässig prüfbar.
</KeyTakeaway>

## Security- und Betriebsaspekte

Rekursion darf nicht bedeuten, dass beliebig außerhalb des vorgesehenen Wurzelverzeichnisses gelesen wird. Symbolische Links, Mountpoints, sehr große Dateien und rekursive Archivstrukturen benötigen klare Grenzen. Ebenso wichtig sind reproduzierbare Ignore-Regeln: Ein CI-Lauf sollte denselben Dateisatz analysieren wie ein lokaler Lauf.

Für sensible Repositories empfiehlt sich außerdem ein explizites Dateibudget, Größenlimits und eine nachvollziehbare Liste übersprungener Dateien. „Nicht geprüft“ ist ein eigener Zustand und darf nicht mit „kein Befund“ gleichgesetzt werden.

Ein professioneller Betrieb sollte außerdem drei Zustände konsequent auseinanderhalten:

```text
clean      = geprüft, kein relevanter Befund
finding    = geprüft, mindestens ein relevanter Befund
incomplete = Prüfung technisch oder fachlich nicht vollständig
```

Gerade der dritte Zustand ist für DevSecOps entscheidend.

Ein Scanner darf fehlende Coverage nicht als positives Sicherheitsurteil darstellen.

## Wo das Feature sinnvoll eingesetzt wird

Directory Scans eignen sich für Pull-Request-Gates, Release-Prüfungen, Artefaktannahme und lokale Reviews. Besonders wertvoll sind sie, wenn Konfiguration und Implementierung gemeinsam beurteilt werden müssen.

Weniger geeignet ist das Feature, wenn bewusst nur eine einzelne, bereits isolierte Datei untersucht werden soll. Dann ist ein Single-File-Modus schneller und semantisch präziser.

Die konkrete Aktivierung sollte deshalb aus dem gewünschten Trust-Modell abgeleitet werden und nicht allein aus technischer Verfügbarkeit.

## Integration in eine DevSecOps-Pipeline

In einer Pipeline sollte das Feature nicht isoliert betrachtet werden.

Ein belastbares Muster ist:

```text
Source / Artifact
      ↓
Input-Validierung
      ↓
Deterministische Analyse
      ↓
optionale erweiterte Analyse
      ↓
normalisierte Findings
      ↓
Policy Gate
      ↓
Report / Audit Evidence
```

Dabei sollte jeder Report mindestens folgende Informationen transportieren:

- Identität des analysierten Artefakts
- aktive Analyseverfahren
- übersprungene oder nicht verfügbare Prüfschritte
- stabile Regel- oder Finding-IDs
- Schweregrad und Evidenz
- Scanner- und Regelversion
- eindeutiger technischer Abschlussstatus

Damit wird das Feature nicht nur ausführbar, sondern **auditierbar**.

## Fazit

Ein Verzeichnis ist ein Sicherheitskontext. Erst die vollständige, begrenzte und reproduzierbare Inventarisierung macht dateiübergreifende Beziehungen zuverlässig prüfbar.

Der eigentliche Wert entsteht dann, wenn das Feature mit klaren Grenzen, reproduzierbaren Eingaben und transparenten Ergebnissen in den Entwicklungsprozess eingebettet wird.
