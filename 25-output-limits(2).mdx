It is tempting to treat output length as a user-experience preference. In agentic systems, that view is incomplete. A generated response can be stored, embedded, indexed, forwarded to other agents, parsed by downstream code, copied into a context window, or used to trigger additional work. An unbounded output is therefore not just verbose—it can become a **resource-amplification primitive**.

The **Output Limits** property protects the invariant:

```text
GENERATION ∧ MAX_OUTPUT_BOUND=NONE|UNLIMITED
```

`skil` maps the property to `SKIL-OUTPUT-LIMIT`. The source correctly describes static coverage as **partial**, because output bounds may be enforced by a model provider, API gateway, runtime policy, or deployment configuration that is invisible in the scanned artifact.

## Why finite generation is a security control

Suppose one model call generates 50,000 tokens. That output might then be:

- embedded into thousands of vector dimensions;
- sent to another model whose input is billed separately;
- persisted to a database;
- rendered in a browser;
- parsed by a JSON or Markdown processor;
- or split into many follow-up tasks.

The initial generation can therefore amplify across the system.

A useful approximation is:

```text
TotalCost ≈ GenerationCost
          + DownstreamProcessing(OutputSize)
          + FollowUpCalls(OutputSize)
          + StorageAndIndexing(OutputSize)
```

The relationship need not be linear. If a large output causes a router to create one task per item, downstream work may grow superlinearly.

<KeyTakeaway>
An output ceiling is not merely “max_tokens.” It is a contract about how much data one reasoning step is allowed to introduce into the rest of the system.
</KeyTakeaway>

## The obvious positive and negative forms

The source-positive configuration is:

```yaml
generation:
  max_tokens: null
  output_limit: unlimited
```

This is strong static evidence because the configuration explicitly disables a bound.

The negative form is:

```yaml
generation:
  max_tokens: 1200
  timeout_seconds: 30
```

This expresses two different controls: amount of generated material and duration of the request.

A scanner should not treat every missing local `max_tokens` field as a definitive vulnerability. Provider defaults may enforce a cap. The artifact may inherit a policy. That is why evidence should distinguish **explicitly unlimited** from **locally unspecified**.

## Output size interacts with context windows

The existence of very large context windows can create a false sense that output limits no longer matter.

Context size is a capacity, not a recommended payload size.

Large outputs create several operational effects:

1. **context displacement** — future prompts may lose more relevant material;
2. **latency** — generation time grows with output length;
3. **cost** — output tokens are often billed;
4. **memory pressure** — downstream systems may buffer or serialize the payload;
5. **parser complexity** — extremely large structured responses are harder to validate safely;
6. **secondary model amplification** — another model may have to ingest the entire output.

The correct bound should therefore be chosen in the context of the whole pipeline.

## Streaming complicates the meaning of “limit”

Streaming APIs deliver tokens incrementally. This improves latency, but it does not automatically bound output.

A runtime needs to decide what happens when a limit is reached:

```text
hard stop
soft stop / request graceful termination
truncate and mark incomplete
discard oversized result
switch to summary mode
```

The semantics matter. Silently truncating JSON may create invalid or misleading data. Truncating a plan may omit cleanup steps. Truncating a security report may remove the highest-severity findings if ordering is not deterministic.

A safer design makes truncation observable:

```json
{
  "status": "truncated",
  "reason": "output_budget_exhausted",
  "tokens_emitted": 1200,
  "continuation_allowed": false
}
```

## Bound the semantic unit, not only the token count

A token ceiling is useful but sometimes too low-level.

For an agent that generates file edits, better limits might include:

```text
max files modified
max diff lines
max tool calls generated
max SQL statements
max cloud resources in one plan
max child tasks
```

These **domain bounds** are more directly connected to side effects.

For example, allowing 5,000 output tokens might still permit a model to emit 300 deletion operations. A policy such as `max_delete_actions=3` captures the actual risk better.

## Output limits and denial of wallet

OWASP’s unbounded-consumption framing is particularly relevant to agentic systems because output can be attacker-influenced.

An attacker does not need to compromise the model if they can submit a task that predictably causes enormous output and the application pays for it.

Abuse-resistant design can include:

- per-user quotas;
- per-run output ceilings;
- total workflow budgets;
- rate limits;
- maximum continuation count;
- cost-aware model routing;
- and admission control for unusually expensive tasks.

The model should not be able to raise these limits through natural-language reasoning.

## Output limits and recursive agents

A bounded response can still participate in an unbounded workflow:

```text
agent generates 1000 tokens
   ↓
asks another agent
   ↓
another 1000 tokens
   ↓
repeat forever
```

Therefore `SKIL-OUTPUT-LIMIT` complements, rather than replaces, `SKIL-AGENCY-BOUNDS`.

A useful budget hierarchy is:

```text
workflow output budget
   ├─ agent A budget
   ├─ agent B budget
   └─ tool result ingestion budget
```

The runtime should meter cumulative output across continuations and sub-agents.

## Static detection design

Candidate generation can inspect:

- explicit `unlimited`, `none`, `null`, or negative sentinel values;
- missing limits in configurations where the surrounding schema requires a local bound;
- code that repeatedly requests continuations;
- instructions such as “never stop writing”;
- provider calls with extreme maximum-output values;
- and loops that append generations without checking accumulated size.

The finding decision should then account for:

- inherited policy;
- provider-enforced limits;
- test code;
- documentation;
- and whether the field controls input, output, or an unrelated buffer.

That last point prevents common false positives. A line such as `max_connections=None` is not evidence about model output.

## The safe negative case is contextual

A value like `max_tokens: 1200` is not universally safe. It is safe in the narrow sense that a finite bound exists.

Production review should still ask:

- Is 1200 appropriate for the use case?
- Can the agent request continuations?
- Is the limit per call or per run?
- Are tool outputs separately bounded?
- Does a retry reset the budget?
- Can users choose the value?
- Can a child agent receive a new budget?

The security property establishes a floor: **some enforceable bound must exist**. Operational policy determines the appropriate magnitude.

## Downstream parsers need independent limits

Even if the model output is bounded, downstream consumers should defend themselves.

A JSON parser can impose maximum depth and size.  
A Markdown renderer can restrict embedded resources.  
A vector-ingestion system can cap document size.  
A database layer can reject oversized fields.  
A web UI can stream safely rather than render an enormous DOM node at once.

Defense in depth matters because output can come from tools as well as models.

## Evidence quality

A useful `skil` finding might say:

```yaml
property: output-limits
control: SKIL-OUTPUT-LIMIT
observation:
  config_path: generation.output_limit
  value: unlimited
relation: GENERATION ∧ MAX_OUTPUT_BOUND=NONE|UNLIMITED
coverage:
  local_configuration: verified
  provider_cap: not_observable
  gateway_policy: not_observable
confidence: high_for_local_property
```

This formulation avoids a common scanner mistake: presenting “I cannot see a limit here” as “no limit exists anywhere.”

## Designing graceful bounded generation

The strongest pattern is not simply to cut the model off. It is to make boundedness part of the protocol.

For long tasks, an agent can return a continuation object:

```json
{
  "status": "partial",
  "completed_sections": 4,
  "remaining_sections": 2,
  "continuation_token": "opaque-id"
}
```

The host—not the model—decides whether another budget allocation is permitted.

This keeps control outside the probabilistic component.

## Metrics that reveal limit failures

Useful production metrics include:

- p50/p95/p99 output tokens per call;
- output tokens per successful workflow;
- number of continuations;
- truncation rate;
- percentage of outputs that hit the hard ceiling;
- downstream bytes generated per input byte;
- cost per workflow;
- and unusually high output-to-input ratios.

A sudden rise in these metrics can indicate either a product regression or adversarial abuse.

## Deep dive: output amplification across downstream systems

Output limits should be derived from the entire pipeline, not only the model provider.

Suppose a 10,000-token output is split into 100 chunks, each embedded and summarized by another model. One generation has created over one hundred downstream operations.

This can be represented as an amplification factor:

```text
A = downstream_work / generated_output
```

A high amplification factor means even modest output growth can cause large cost or latency increases.

Architects should therefore model:

```text
max model output
× max fan-out per item
× max downstream calls
```

and choose bounds accordingly.

### Structured output can have semantic size limits

A JSON response with 1,000 small objects may fit within the token cap yet create too many side effects.

Domain-specific limits can be more meaningful:

```yaml
plan:
  max_actions: 20
  max_files: 10
  max_delete_actions: 2
  max_external_destinations: 1
```

These limits express what the system actually cares about.

### Continuations are a potential bypass

A model can respect `max_tokens=1200` per call and still generate indefinitely through continuation:

```text
call 1 -> "continue"
call 2 -> "continue"
...
```

Therefore the runtime should count cumulative output across the **workflow**, not only the API call.

A continuation should consume from the remaining run budget, and the agent should not mint a new budget simply by changing conversation IDs.

### Truncation can become a correctness vulnerability

If the system truncates output without preserving semantic integrity, the model may produce:

```json
{"actions":[
  {"type":"backup"},
  {"type":"delete"},
  ...
```

and the truncation may remove the compensating or approval step.

Safer designs validate complete structured units and reject incomplete outputs rather than executing the prefix.

### Backpressure

Streaming systems need backpressure. If downstream consumers cannot process data quickly enough, the producer should slow down or stop instead of buffering indefinitely.

This is standard distributed-systems engineering, but it becomes relevant to agent security when model outputs can be very large or attacker-influenced.

A complete output-limit policy therefore spans:

```text
generation
transport
buffering
parsing
storage
downstream fan-out
```

The model provider’s token cap is only the first layer.

## Final perspective

Output limits sit at the intersection of security, economics, latency, and correctness. They are easy to dismiss because they do not look like a traditional vulnerability. Yet an unbounded generator can become the first stage of a cascading resource failure.

`SKIL-OUTPUT-LIMIT` should therefore answer a concrete question:

> **Where is the finite boundary on the amount of model-produced data that a single operation, agent, and workflow may inject into the rest of the system?**

If that boundary exists only as a hope that “the model will probably be concise,” it is not a boundary.
