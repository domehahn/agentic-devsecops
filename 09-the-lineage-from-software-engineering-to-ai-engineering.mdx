It is easy to tell the history of software as a ladder:

```text
Software Engineering
      ↓
Agile
      ↓
DevOps
      ↓
DevSecOps
      ↓
MLOps
      ↓
AI Engineering
```

That diagram is useful—and wrong if interpreted literally.

These disciplines did not simply replace one another.

They accumulated because the boundary of the engineered system kept expanding.

## 1. Software Engineering: manage system complexity

The NATO conference in Garmisch in 1968 is an important historical marker for the effort to treat software construction as an engineering problem.[^nato]

The boundary was approximately:

```text
program
+
software system
+
development process
```

The core problem was scale.

## 2. Agile: reduce the cost of learning

The Agile Manifesto in 2001 emphasized working software, collaboration, responsiveness, and short feedback cycles.[^agile]

The engineering boundary did not fundamentally change.

The feedback model did.

```text
build less
learn sooner
adapt faster
```

## 3. CI/CD: engineer the path to production

Continuous Integration and Continuous Delivery turned frequent feedback into technical infrastructure.[^ci][^cd]

The engineered system now included:

```text
source
build
tests
artifact
deployment path
```

Delivery itself became software.

## 4. DevOps: include operations

The 2009 Flickr "10+ Deploys Per Day" presentation and the first devopsdays in Ghent are useful milestones in the early DevOps movement.[^flickr][^devopsdays]

The boundary expanded again:

```text
development
+
delivery
+
production operations
```

Production became part of the feedback loop.

## 5. DevSecOps: include continuous security

As automated delivery gained authority, security increasingly had to move into the same lifecycle.

NIST's SSDF formalizes secure practices that can be integrated into SDLC implementations rather than treated as a separate late phase.[^ssdf]

The boundary now includes:

```text
code
pipeline
dependencies
artifacts
infrastructure
security evidence
```

## 6. MLOps: include data and models

Production ML breaks the assumption that behavior is determined primarily by code.

Google's research on hidden ML technical debt and production-readiness testing documented engineering concerns around ML systems well beyond model accuracy alone.[^debt][^testscore]

The lifecycle expands to:

```text
code
+
data
+
training
+
model
+
monitoring
```

## 7. AI Engineering: include AI behavior and system risk

SEI began publishing explicit AI Engineering practices in 2019 and later described the field as combining systems engineering, software engineering, computer science, and human-centered design.[^sei]

NIST's AI RMF then provided a broader lifecycle framework for managing risks of AI systems.[^airmf]

The system boundary becomes:

```text
software
data
models
humans
environment
evaluation
risk
```

## The common pattern

Every stage can be described using the same transformation:

```text
new source of complexity
        ↓
old engineering model becomes incomplete
        ↓
new practices expand the lifecycle
```

<KeyTakeaway>
AI Engineering is not the successor that makes DevSecOps obsolete. It depends on DevSecOps and extends it to new artifacts, behaviors, and risks.
</KeyTakeaway>

## What carries forward

AI systems still need:

```text
requirements
architecture
version control
testing
CI/CD
observability
incident response
security
supply-chain integrity
```

And they additionally need:

```text
data lineage
model identity
evaluation
behavioral monitoring
AI risk management
tool boundaries
human oversight
```

This is why "AI engineering" should not mean "calling an AI API."

It means applying engineering discipline to systems whose behavior depends on AI.

## A modern engineering lifecycle

A useful synthesis is:

```text
SPECIFY
   ↓
BUILD
   ↓
TEST
   ↓
SCAN
   ↓
VERIFY
   ↓
EVALUATE
   ↓
DELIVER
   ↓
ENFORCE
   ↓
OBSERVE
   ↓
LEARN
   ↺
```

Different systems require different controls.

But the direction is clear: as software gains more autonomy and more access to real-world capabilities, **verification and enforcement become more important, not less**.

The history is therefore not a migration away from software engineering.

It is software engineering expanding to meet a larger system.
