Agile made short feedback loops desirable. Continuous Integration and Continuous Delivery made them increasingly practical.

The difference is important.

A team can plan in two-week iterations and still require a painful manual release every three months. Delivery speed is constrained not only by how work is planned, but by how reliably changes can move from source control into a production-like state.

## Continuous Integration attacks integration risk

Martin Fowler describes Continuous Integration as frequent integration into a shared codebase, with automated builds and tests used to detect integration errors quickly.[^fowler-ci]

The core idea is economic:

```text
small integration problem
× frequent detection
```

is usually easier to handle than:

```text
many accumulated changes
× late integration
```

CI therefore makes integration a routine event instead of a project phase.

## Continuous Delivery expands the automated path

In 2010, Jez Humble described the work that became the book *Continuous Delivery* as covering build and deployment automation, CI, test automation, environments, configuration management, version control, data migrations, and governance. He summarized its themes as automation and collaboration.[^cd-2010]

That combination is crucial.

A delivery pipeline is not simply:

```text
compile
```

It is an automated path for creating evidence:

```text
commit
  ↓
build
  ↓
tests
  ↓
package
  ↓
environment validation
  ↓
deployable release
```

<KeyTakeaway>
CI/CD turned software delivery into an engineered feedback system: every change could produce automated evidence about whether it was still releasable.
</KeyTakeaway>

## Delivery and deployment are not identical

Continuous Delivery and Continuous Deployment are often treated as synonyms, but the distinction matters.

Humble explained in 2010 that Continuous Deployment releases every good build automatically, while Continuous Delivery means the system is kept in a state where software can be released reliably; the decision to release may still be explicit.[^cd-vs-deploy]

That distinction becomes important later for security and governance.

Automation does not require removing policy gates.

It makes those gates repeatable.

## Automation changes the cost of change

Manual release processes create incentives for large batches:

```text
release is expensive
       ↓
release less often
       ↓
more changes per release
       ↓
higher release complexity
```

Automation can reverse that loop:

```text
release path is repeatable
       ↓
smaller changes are viable
       ↓
failures are easier to isolate
       ↓
feedback arrives sooner
```

This is one of the foundations on which DevOps grew.

## Production becomes part of the engineering loop

Once a delivery pipeline can move changes quickly, another question becomes unavoidable:

```text
Who owns what happens after deployment?
```

Traditional separation often looked like:

```text
developers → release artifact → operations
```

But high-frequency web services created strong incentives for shared tooling, shared metrics, automated infrastructure, and shared operational responsibility.

That was not merely a tooling change.

It was an organizational one.

## CI/CD also creates a future security control point

A pipeline that can automatically build, test, and deploy software can also automatically perform:

```text
dependency scanning
SAST
secret detection
SBOM generation
policy checks
artifact signing
provenance
```

That becomes central to DevSecOps.

But before security was systematically integrated into the pipeline, another barrier had to be addressed: the wall between development and operations.

That is where the DevOps movement enters the story.
