SARIF ist ein standardisiertes Format für Ergebnisse statischer Analyse. Ein Scanner kann damit Findings in Plattformen einspeisen, die Code-Scanning, Annotationen und Security-Triage bereits unterstützen.

Das Feature ist damit nicht nur eine Komfortfunktion.

Es verändert, **welcher Kontext geprüft wird, welche Vertrauensgrenzen gelten und wie belastbar das Ergebnis später in CI/CD oder Security-Governance verwendet werden kann**.

## Was das Feature leistet

SARIF trennt Regeln, Runs, Locations, Messages und Properties. Dadurch lassen sich wiederkehrende Regeldefinitionen zentral beschreiben und einzelne Findings sauber auf Dateien und Positionen abbilden.

Die Stärke liegt in Interoperabilität. Ein Scanner muss keine eigene Review-Oberfläche bauen, wenn die Zielplattform SARIF versteht.

## Typischer Ablauf

Unabhängig von der konkreten Implementierung sollte der Ablauf klar getrennte Phasen besitzen:

```text
Input
  ↓
Validierung und Normalisierung
  ↓
Feature-spezifische Verarbeitung
  ↓
Security-Analyse
  ↓
Findings + Coverage + technischer Status
  ↓
Policy-Entscheidung
```

Diese Trennung ist wichtig, weil ein technischer Fehler bei Beschaffung, Parsing oder Providerzugriff nicht dieselbe Bedeutung hat wie ein tatsächlich unauffälliges Prüfergebnis.

## Negatives Beispiel

Alle Befunde verwenden dieselbe generische Rule ID:

```text
ruleId: scanner-warning
```

Schweregrade stehen nur im Nachrichtentext und Dateipfade sind absolute Runner-Pfade wie `/builds/runner123/project/config.yaml`. Die Zielplattform kann Findings weder stabil gruppieren noch korrekt dem Repository zuordnen.

## Positives Beispiel

Jede Regel besitzt eine stabile ID und Metadaten:

```json
{
  "ruleId": "NET-004",
  "level": "error",
  "locations": [{
    "physicalLocation": {
      "artifactLocation": {"uri": "config.yaml"},
      "region": {"startLine": 18}
    }
  }]
}
```

Repository-relative Pfade und stabile IDs ermöglichen Annotationen, Deduplizierung und History Tracking.

<KeyTakeaway>
SARIF ist mehr als JSON mit anderem Schema. Stabile Regelidentitäten und korrekte Locations machen Scannerbefunde zu erstklassigen Code-Scanning-Ergebnissen.
</KeyTakeaway>

## Security- und Betriebsaspekte

SARIF kann große Mengen Quelltext und Properties enthalten. Reports sollten nur notwendige Evidenz aufnehmen und Secrets redigieren. Absolute lokale Pfade können interne Infrastrukturinformationen preisgeben.

Die Mapping-Logik von internem Severity-Modell zu SARIF-Level sollte dokumentiert sein, damit „warning“ und „error“ nicht willkürlich wechseln.

Ein professioneller Betrieb sollte außerdem drei Zustände konsequent auseinanderhalten:

```text
clean      = geprüft, kein relevanter Befund
finding    = geprüft, mindestens ein relevanter Befund
incomplete = Prüfung technisch oder fachlich nicht vollständig
```

Gerade der dritte Zustand ist für DevSecOps entscheidend.

Ein Scanner darf fehlende Coverage nicht als positives Sicherheitsurteil darstellen.

## Wo das Feature sinnvoll eingesetzt wird

SARIF ist ideal für GitHub Code Scanning, kompatible DevSecOps-Plattformen und zentrale Findingsysteme. Es ergänzt JSON um ein standardisiertes Analysemodell.

Für einfache CLI-Nutzung ist SARIF unnötig komplex; dort sind Terminal und Markdown geeigneter.

Die konkrete Aktivierung sollte deshalb aus dem gewünschten Trust-Modell abgeleitet werden und nicht allein aus technischer Verfügbarkeit.

## Integration in eine DevSecOps-Pipeline

In einer Pipeline sollte das Feature nicht isoliert betrachtet werden.

Ein belastbares Muster ist:

```text
Source / Artifact
      ↓
Input-Validierung
      ↓
Deterministische Analyse
      ↓
optionale erweiterte Analyse
      ↓
normalisierte Findings
      ↓
Policy Gate
      ↓
Report / Audit Evidence
```

Dabei sollte jeder Report mindestens folgende Informationen transportieren:

- Identität des analysierten Artefakts
- aktive Analyseverfahren
- übersprungene oder nicht verfügbare Prüfschritte
- stabile Regel- oder Finding-IDs
- Schweregrad und Evidenz
- Scanner- und Regelversion
- eindeutiger technischer Abschlussstatus

Damit wird das Feature nicht nur ausführbar, sondern **auditierbar**.

## Fazit

SARIF ist mehr als JSON mit anderem Schema. Stabile Regelidentitäten und korrekte Locations machen Scannerbefunde zu erstklassigen Code-Scanning-Ergebnissen.

Der eigentliche Wert entsteht dann, wenn das Feature mit klaren Grenzen, reproduzierbaren Eingaben und transparenten Ergebnissen in den Entwicklungsprozess eingebettet wird.
