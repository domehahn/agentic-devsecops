## Why wildcards are temporal privilege

A wildcard is attractive because it solves integration friction: the agent can discover new tools without constant configuration changes. Security sees the opposite property. The authorization surface can expand when the server, plugin set or tool catalog changes, even though no human reviewed a new permission.

The safe unit of authority is an explicit, reviewable capability set—not a syntactic shortcut that delegates future authorization decisions to whatever tools happen to exist at runtime. The original `skil` control model expresses the same idea as `MCP_PERMISSION_SET contains wildcard/all/full/any`. That relation is more useful than a label such as “suspicious” because it specifies what must be evidenced and what a legitimate counterexample must break.

## Discovery is not authorization

MCP allows clients to discover available tools, but the fact that a server advertises a tool does not mean every agent should be allowed to call it. Hosts should keep discovery metadata separate from the policy that maps identities and tasks to callable methods. The design implication is that detection and authorization must remain separate: the scanner identifies the condition, while a policy layer decides whether the condition is permissible in this deployment context.

## Explicit capability sets

An allowlist of `*` does not only authorize today’s tools; it authorizes tomorrow’s additions. This makes tool-catalog mutation a privilege-expansion path. Explicit names or capability classes constrain that temporal drift. This also improves explainability. Reviewers can see the specific security fact rather than receiving a generic severity label, and future tooling can compose that fact with independent findings without double-counting the same evidence.

## The 2026-07-28 protocol improves enforceability, not least privilege automatically

The current MCP revision makes requests more self-describing and exposes method/tool names in routable headers, which can help gateways meter and authorize requests. Those mechanics make policy easier to enforce, but they do not decide which tools should be permitted. Least privilege remains a host responsibility. A useful implementation records both the positive observation and the guard that would have made the path safe. That makes remediation testable and turns false-positive handling into explicit logic instead of a collection of suppressions.

## Tool identity needs pinning

An allowlist is only meaningful if the name resolves to a stable, reviewed tool identity. Metadata fingerprints, server identity and lockfiles can prevent a familiar name from silently changing behavior between review and execution. The same model supports change detection: when identity, configuration or code changes, the platform can recompute the relation and show exactly which part of the previously reviewed assumption no longer holds.

## Destructive tools deserve a second boundary

Even explicit authorization may be too broad for irreversible operations. Deploy, delete, transfer, credential-management and production-write tools should require task-scoped approval or stronger policy predicates in addition to name-based permission. In an agentic environment this distinction becomes operational because model-generated plans can select the relevant value or capability at runtime. The host therefore needs evidence that can survive from code review into execution policy.

## Tool identity and catalog change

A deliberately small positive fixture from the source property illustrates the boundary:

```json
{"allowedTools": ["*"]}
```

The safe counterexample changes the semantics rather than merely deleting a suspicious token:

```json
{"allowedTools": ["repo.read", "issue.comment"]}
```

The purpose of pairing them is not to teach exploitation. It is to force the detector to explain which relation changes between the two cases. A scanner that fires on both has learned vocabulary; a scanner that can explain the difference has begun to model the security property.

## False positives, ambiguity, and safe counterexamples

A wildcard in documentation or a JSON Schema regex is not necessarily a permission wildcard. The detector should parse MCP configuration fields structurally and identify the scope in which `*`, `all`, `any` or equivalent tokens actually grant authority.

Coverage should be treated as first-class security data. Deterministic syntax and configuration observations can often be reproduced exactly, while intent, future identity and runtime targets may remain uncertain. A mature scanner reports those asymmetries instead of collapsing them into one confidence score. This is particularly important in agentic systems, where the model may choose arguments and tools only after deployment.

## Structural detection without regex confusion

Enforce tool allowlists at the host or gateway, validate server/tool identity, require user or policy approval for high-impact calls, and record both the resolved tool identity and the authorization decision in the trace.

Defense in depth is intentionally redundant. Authoring lint, static analysis, contract verification, supply-chain verification, runtime policy and audit telemetry answer different questions. A strong result from one layer should never be used as a reason to remove the others.

## Runtime enforcement

True-positive fixtures should cover canonical violations, while true-negative fixtures should intentionally reuse similar tokens and syntax so the detector proves it understands context. Boundary cases should change one security-relevant fact at a time. Mutation tests can vary scope, target, normalization, version, guard, or sink. Holdout fixtures protect against overfitting to the public examples. For **MCP Wildcards and Excessive Tool Authority**, the most valuable tests are those that preserve the surface appearance while changing the underlying security relation; that is how the suite verifies semantics instead of vocabulary.

For `skil`, implementation claims should be checked against the repository’s control matrix, external-control crosswalk, analyzer tests and any provider-specific tests. Provider-backed coverage—such as OSV or external rule packs—must state whether the provider actually ran.

## Architecture drill-down: from finding to enforceable boundary

A design review for this MCP trust surface property should begin by drawing the trust boundary rather than opening with a rule ID. Identify who controls the input, which component interprets it, what authority is available at that point, and which deterministic guard is expected to stop an unsafe transition. Then map `MCP_PERMISSION_SET contains wildcard/all/full/any` onto that diagram. The purpose of structured MCP wildcard permission detection is to provide one or more observable edges in that model; it is not a substitute for the model itself. Reviewers should ask whether the same relation can be created indirectly through wrappers, generated configuration, aliases, cached metadata, transitive dependencies, or delegated tools. If so, the implementation needs either deeper static summaries or a runtime control at the unresolved boundary. Finally, confirm that evidence identifiers survive across CI, packaging and runtime so an observed denial or drift event can be traced back to the assumption approved in code review.

The paired fixtures also serve as an architectural regression test. The unsafe example begins with `{"allowedTools": ["*"]}` while the safe example begins with `{"allowedTools": ["repo.read", "issue.comment"]}`. The important difference is the security relation, not the cosmetic text. If a refactor causes both to produce the same result, the detector or policy has lost a meaningful distinction.

## Common implementation traps

Several implementation mistakes recur around **MCP Wildcards and Excessive Tool Authority**, even when the high-level policy is correct:

**1. Trusting model-visible metadata as if it were authorization policy.** Descriptions and schemas can guide planning, but deterministic host policy must own credentials, capability scope and approvals. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**2. Binding policy only to a display name.** Tool identity, server identity, metadata fingerprint and issuer relationships may need to be pinned so review survives catalog changes. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**3. Validating only at discovery time.** Cached catalogs, changed defaults, mutable packages and long-lived approvals create time-of-check/time-of-use gaps unless the host revalidates before high-impact calls. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

A useful review discipline is to turn every exception into a scoped, expiring artifact with an owner and rationale. Permanent blanket suppressions hide whether the architecture improved; narrow exceptions preserve the signal and make technical debt measurable.

## How this property composes with adjacent findings

**Wildcard authorization plus catalog drift.** The dangerous scenario is not merely the token `*`; it is a permission rule that automatically absorbs newly advertised tools. If the tool catalog changes and the authorization set expands without review, the system has experienced privilege drift. Catalog fingerprinting and explicit policy diffing make that drift visible.

This composition model is deliberately graph-like: each detector contributes a typed fact and shared evidence identifiers allow a higher-level policy engine to connect them. That prevents one rule from becoming an overloaded catch-all and makes severity escalation explainable.

## Operational signals and measurable assurance

Measure wildcard occurrences in effective policy, tool-catalog changes that would have expanded authority, explicit-tool coverage, denied calls outside task scope, and the fraction of destructive calls that pass an independent approval gate.

Metrics should be tied to an explicit denominator and deployment profile. A low finding count may mean strong controls, weak coverage, or simply little exposure; telemetry and coverage state are needed to tell those cases apart. Trend the data over time and review unexpected changes in both positive findings and scanner-negative regression behavior.

## Engineering implications beyond the scanner

MCP security is split between protocol mechanics and host policy. The 2026-07-28 revision improves routability, caching semantics and authorization hardening, but it deliberately does not make tool descriptions trusted or grant least privilege automatically. Hosts still own capability selection, token scope, approval, identity pinning and the decision about what model-visible metadata may influence planning.

The broader lesson is that an agentic skill is simultaneously text, code, configuration, a tool contract and a supply-chain artifact. Security review should follow the boundary that is actually crossed—data, authority, identity, execution, or control-plane visibility—rather than forcing every risk into the same detection template.

## Assurance tests

A reviewer should be able to answer four questions before accepting this property as controlled:

1. **What exact security relation is being asserted?** Here it is `MCP_PERMISSION_SET contains wildcard/all/full/any`.
2. **What concrete evidence supports the relation?** The evidence must come from structured MCP wildcard permission detection, not from a keyword alone.
3. **What near-neighbor safe case has been tested?** The paired negative fixture should differ in the property, not merely in spelling.
4. **What remains outside static visibility?** Runtime identity, dynamic values, provider state and policy decisions must be named explicitly.

## Conclusion

**MCP Wildcards and Excessive Tool Authority** is valuable only when it is treated as a falsifiable security property rather than a checklist term. The goal is not to declare an entire skill “malicious” or “safe.” The goal is to state what boundary may be crossed, show the evidence that supports that statement, preserve the coverage limits, and make the safe countercondition explicit. That produces findings engineers can test, reviewers can reproduce, and runtime policy can enforce.
