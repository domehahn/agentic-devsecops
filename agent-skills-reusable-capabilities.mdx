# Agent Skills: Turning General Language Models into Reusable, Governed Capabilities

A general-purpose language model is broad by design.

Organizations, however, operate through policies, procedures, tools, templates, domain conventions and quality criteria.

An engineer performing a security review follows a repeatable institutional method.

Agent Skills are one way to encode that method into reusable machine-readable artifacts.

## The Prompt Does Not Scale as Organizational Memory

Early LLM use often depended on one-off prompts.

```text
Review this application.
Check OWASP issues.
Inspect dependencies.
Analyze authentication.
Produce a report.
```

The user had to remember the process.

Skills move durable instructions out of ad hoc prompts.

The user can state:

```text
Perform a security review.
```

The skill supplies the procedure.

This is a transition from **prompt craftsmanship** to **capability engineering**.

## Skills as Context Programming

A language model only has access to information placed in active context or reachable through tools.

A skill injects targeted procedural context.

```text
general model
+
task
+
skill
=
specialized behavior
```

The weights do not change.

The active computation changes because context changes.

This makes skills closer to context programming than fine-tuning.

## The Open Agent Skills Format

The Agent Skills specification defines a lightweight open format based on a directory with a required `SKILL.md`.[^1]

A typical structure:

```text
security-review/
├── SKILL.md
├── scripts/
├── references/
└── assets/
```

`SKILL.md` contains YAML frontmatter and Markdown instructions.

Required metadata includes name and description.

Optional resources can bundle executable scripts, references, templates and data files.

## Progressive Disclosure

Loading every skill into every request would waste context.

Progressive disclosure enables:

```text
startup:
  skill name + description

activation:
  SKILL.md instructions

on demand:
  references / scripts / assets
```

This resembles lazy loading in software.

## Skills Are Not Agents

A skill describes *how to perform a class of work*.

An agent decides *when and how to act over time*.

```text
Skill
-----
procedure
knowledge
constraints
resources

Agent
-----
goal
state
control loop
tool selection
decision making
```

A skill can be used by multiple agents.

An agent can use multiple skills.

## Skills Are Not Tools Either

A tool executes an external capability.

A skill may instruct the model to inspect files, run scanners and summarize findings.

The tool provides mechanism.

The skill provides procedure.

## Tool Access Changes the Risk Profile

A text-only skill can influence output.

A tool-enabled skill can influence the world.

Security review must examine tool permissions, command construction, network access, credentials and filesystem access.

The skill becomes part of the software supply chain.

## Skills as Institutional Memory

A well-designed skill can encode how the organization performs a task, which standards apply, what evidence is required and what actions are prohibited.

This makes skills a form of institutional procedural memory.

But stale skills can perpetuate outdated policy.

Versioning is therefore mandatory.

## Skill Versioning

Treat skills like code:

```text
Git
code review
semantic versions
release notes
tests
signing
```

A production run should identify the exact skill version.

## Good Skills Reduce Freedom Intentionally

The purpose of a production skill is not to maximize creativity.

It is to reduce unnecessary decision space.

Bad:

```text
Perform a good security review.
```

Better:

```text
Inspect:
- authentication
- authorization
- secrets
- dependencies

Use:
- approved scanners

Do not:
- modify production
- upload code externally
```

## But Skills Should Not Encode Every Branch

Over-specification creates brittle prompt programs.

A good skill defines objectives, invariants, required checks, allowed resources and output contracts while leaving context-dependent reasoning to the model.

This resembles software API design:

```text
stable contract
flexible implementation
```

## Testing Skills Requires More Than Prompt Review

A skill is executable behavior once used by an agent.

Test positive cases, negative cases, adversarial cases, tool failures and model variation.

This is closer to software testing than prompt inspection.

## Skill Output Contracts

Define what success looks like.

Example:

```yaml
output:
  findings:
    - severity
    - evidence
    - remediation
  summary: required
```

Structured contracts improve downstream automation.

## Security Supply Chain

Skills can contain instructions, scripts and references.

Risks include prompt injection, credential access, hidden instructions, malicious scripts, dependency abuse and tool overreach.

Trust should depend on provenance.

## Signed Distribution and Provenance

A mature skill registry can record:

```yaml
skill: security-review
version: 2.4.1
digest: sha256:...
publisher: security-platform
reviewed_by: ...
```

Installation verifies identity and integrity.

Skills are becoming a software artifact class.

## Capability Declaration

A skill should ideally declare required capabilities:

```yaml
requires:
  - repository.read
  - scanner.execute
  - issue.create
```

The runtime compares requirements with policy.

Metadata alone should not be the enforcement layer.

## Skills and Agent Portability

A standardized format can reduce vendor coupling, but portability has limits.

Tool naming, sandbox behavior, model capability, memory and permission systems differ.

A skill can be syntactically portable while requiring semantic adaptation.

## Skill Dependency Management

Skills may reference scripts and external tools.

Document environment requirements and pin executable dependencies where practical.

A runtime should refuse activation when required capabilities are unavailable instead of allowing unsafe improvisation.

## Skill Composition

Multiple active skills can conflict.

Example:

```text
security skill:
  never send source externally

reporting skill:
  upload report to external service
```

Policy should outrank skill instructions.

A useful precedence model:

```text
platform policy
> workspace policy
> flow constraints
> skill instructions
> user preference
```

## Skill Evaluation as Release Engineering

Skill CI can:

```text
lint frontmatter
validate references
run security scanner
execute fixtures
compare eval baseline
sign artifact
```

This turns publishing into a controlled lifecycle.

## Skill Discovery Is a Routing Problem

When hundreds of skills exist, loading all descriptions becomes expensive and confusing.

A registry can index name, description, domain, capabilities and risk class.

The agent first retrieves likely skills, then activates one.

## Skill Risk Classes

Classify skills:

```text
text-only
read-only tool
reversible write
privileged action
code-execution
```

Higher-risk skills should require stronger review, signatures, sandboxing and approval.

## Skills as Cognitive Libraries

Software libraries package reusable computation.

Skills package reusable **procedural cognition**.

A library says:

```text
call this function
```

A skill says:

```text
approach this class of problems this way
```

## Layering Skills with Agents and Flows

A clean architecture:

```text
Flow
  ↓ orchestrates
Agent
  ↓ selects
Skill
  ↓ guides
Tool
  ↓ executes
External System
```

Each layer has a different responsibility.

## Conclusion

Agent Skills solve a real organizational problem: how to turn broad model capability into repeatable domain-specific work without retraining the model for every procedure.

They should be treated as context programs, institutional memory and supply-chain artifacts.

Their execution is probabilistic, which makes versioning, evaluation and security review indispensable.
