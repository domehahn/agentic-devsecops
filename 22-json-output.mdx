Sobald Scannerergebnisse automatisiert weiterverarbeitet werden, ist Terminaltext die falsche Schnittstelle. JSON macht Findings, Scores, Coverage und Metadaten strukturiert verfügbar und verhindert fragile Regex-Auswertung von Logs.

Für Agentic DevSecOps ist das besonders wichtig, weil Scan-Evidence später in Policy, Attestation, Dashboards oder Agent Workflows einfließen kann.

<Architecture>
JSON ist nicht nur ein Ausgabeformat. Es ist die API zwischen Scanner und nachgelagerter Security-Automatisierung.
</Architecture>

## Was das Feature wirklich bedeutet

Ein brauchbarer JSON-Vertrag braucht stabile Feldsemantik. IDs, Severity, Location und Fingerprint sollten nicht bei jeder Version anders heißen. Ebenso wichtig ist, fehlende Analyse von negativem Ergebnis zu unterscheiden.

Schema-Versionierung ist deshalb ein Security- und Integrationsfeature.

## SkillSpector

SkillSpector kann Scanberichte als JSON schreiben. Das Format ist für Batch-Verarbeitung und externe Tools vorgesehen und enthält die strukturierten Findings des Scanners.

Damit lassen sich etwa PR-Bots oder eigene Dashboards aufbauen, ohne die Terminalausgabe zu parsen.

## `skil`

`skil` nutzt JSON breit als Evidence-Format. Das öffentliche `ScanResult` enthält unter anderem `schema_version`, Artifact-Digest, Status, Verdict, `risk_score`, Maximum Severity, Findings, Coverage, Scanneridentitäten, Inspection Ledger, Completeness und Generierungszeitpunkt.

Diese Struktur eignet sich direkt als Input für nachgelagerte Policy- oder Evidence-Prozesse.

## Praxisbeispiel

```bash
skillspector scan ./skill --no-llm   --format json --output skillspector.json

skil scan ./skill --static-only   --format json --output skil.json
```

Eine Pipeline kann anschließend beispielsweise nur `CRITICAL`-Findings anzeigen, gleichzeitig aber den vollständigen Report für Audit und spätere Re-Evaluation aufbewahren.

## Security- und DevSecOps-Einordnung

- JSON-Schema oder Schema-Version prüfen, bevor Automatisierung Felder vertraut.
- Nicht nur Findings, sondern Coverage und Scanner-Version speichern.
- Report als unvertrauenswürdige Daten behandeln, wenn Inhalte aus dem Skill eingebettet werden.
- Artefakt-Digest im Report bevorzugen, um Evidence an den richtigen Prüfling zu binden.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

## Typische Fehlinterpretation

„Wenn es JSON ist, ist es automatisch eine stabile API.“ Ohne Schema-Version und dokumentierte Feldsemantik kann auch JSON zwischen Versionen Integrationen brechen.

## Einordnung in die Pipeline

Dieses Feature gehört in die **Reporting- und Integrationsstufe**. Ein guter Pipeline-Lauf erzeugt mindestens eine menschenlesbare Sicht und eine maschinenlesbare Evidence. So können Entwickler Findings verstehen, während Policy Engines und Dashboards stabile Strukturen konsumieren.

Das Ausgabeformat darf nicht bestimmen, ob ein Gate greift: Exit Code, strukturierter Status und Policy-Ergebnis sollten die technische Entscheidung tragen.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Funktional Gleichstand. Beide liefern JSON. `skil` positioniert den strukturierten Report besonders stark als Evidence-Objekt mit Digest-, Coverage- und Completeness-Bezug; SkillSpector bietet ebenfalls eine maschinenlesbare Basis für Automatisierung.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
