## Security decisions decay over time

Security review happens at a point in time. MCP servers, npm packages, container images and tool metadata can change later. If the runtime resolves a mutable reference such as `latest`, the component executed tomorrow may not be the one approved today. That is the essence of a rug-pull problem.

The invariant is temporal: reviewed identity at time t0 must equal resolved identity at execution time t1, or a new review decision must occur. Names are insufficient; version, digest, issuer and metadata fingerprint may all be part of the identity. The original `skil` control model expresses the same idea as `REVIEWED_IDENTITY(t0) != RESOLVED_IDENTITY(t1) without_review`. That relation is more useful than a label such as “suspicious” because it specifies what must be evidenced and what a legitimate counterexample must break.

## Locator, identity, and behavior

A package name or server URL tells the host where to look. It does not uniquely identify the bytes or behavior returned. Lockfiles should record immutable resolution details and the metadata relevant to policy decisions. In an agentic environment this distinction becomes operational because model-generated plans can select the relevant value or capability at runtime. The host therefore needs evidence that can survive from code review into execution policy.

## Lockfiles and metadata fingerprints

Tool descriptions, parameter schemas and defaults influence model behavior. A secure lock therefore may include canonicalized metadata fingerprints in addition to package or image digest. Changing the description can be a security-relevant event even if the executable artifact hash is unchanged. The design implication is that detection and authorization must remain separate: the scanner identifies the condition, while a policy layer decides whether the condition is permissible in this deployment context.

## Approval has an expiry condition

An approval tied only to a human click can outlive the facts the reviewer saw. Before execution, the host should revalidate tool identity, metadata fingerprint, authorization scope and high-impact arguments. If any security-relevant input changed, the approval should be invalidated or narrowed. This also improves explainability. Reviewers can see the specific security fact rather than receiving a generic severity label, and future tooling can compose that fact with independent findings without double-counting the same evidence.

## Provenance strengthens identity

Signatures and SLSA-style provenance can tie artifacts to expected publishers, repositories and build systems. They do not eliminate malicious updates from a trusted maintainer, but they make unauthorized substitution and opaque build drift harder. A useful implementation records both the positive observation and the guard that would have made the path safe. That makes remediation testable and turns false-positive handling into explicit logic instead of a collection of suppressions.

## Caching must respect identity

The 2026-07-28 MCP revision supports cache hints for list results. Caching improves efficiency, but security-sensitive hosts must bind cached tool catalogs to server identity and expiration semantics so stale metadata does not silently authorize a changed server. The same model supports change detection: when identity, configuration or code changes, the platform can recompute the relation and show exactly which part of the previously reviewed assumption no longer holds.

## Approval-to-execution drift

A deliberately small positive fixture from the source property illustrates the boundary:

```json
{"command":"npx","args":["some-mcp-server@latest"]}
```

The safe counterexample changes the semantics rather than merely deleting a suspicious token:

```json
{"command":"npx","args":["some-mcp-server@1.4.2"]}
// plus reviewed .skil/mcp-tools.lock.json metadata fingerprint
```

The purpose of pairing them is not to teach exploitation. It is to force the detector to explain which relation changes between the two cases. A scanner that fires on both has learned vocabulary; a scanner that can explain the difference has begun to model the security property.

## Caching without stale trust

A useful finding is a compact proof obligation. It should answer: where did the evidence originate, what intermediate representation did identity pinning + reviewed lockfile diff derive, why does that evidence satisfy `REVIEWED_IDENTITY(t0) != RESOLVED_IDENTITY(t1) without_review`, and what uncertainty remains? `skil` maps this property to `SKIL-MCP-003`, `SKIL-MCP-005`, `SKIL-BOUNDARY-MUTABLE-IMAGE`. ## False positives, ambiguity, and safe counterexamples

Not every version change is malicious. The detector should report mutable identity and unreviewed drift, not label an ordinary upgrade a “rug pull.” The security decision is whether the change bypassed the expected review and verification path.

No static property is a complete verdict on the artifact. The detector can establish local evidence about syntax, identity, data flow or declared authority; it cannot guarantee what an external registry, remote server or model will do later. Engineering decisions should therefore compose static findings with contract verification, supply-chain attestation and runtime policy rather than demanding impossible certainty from one layer.

## Legitimate upgrades versus bypassed review

Resolve immutable versions/digests, maintain a reviewed MCP tool lock, verify issuer/server identity, compare canonical metadata at call time, and require new approval when the reviewed security context changes.

Defense in depth is intentionally redundant. Authoring lint, static analysis, contract verification, supply-chain verification, runtime policy and audit telemetry answer different questions. A strong result from one layer should never be used as a reason to remove the others.

## Revalidation at runtime

Evaluation should measure more than raw detection count. Precision matters because noisy controls are disabled; recall matters because adversarial variants are the point of the exercise. For structural properties, report supported syntax classes and unresolved constructs. For provider-backed checks, include provider-availability and freshness tests. Differential comparisons are useful, but property equivalence is more meaningful than finding-count parity. For **MCP Rug Pulls and Mutable Identity**, the most valuable tests are those that preserve the surface appearance while changing the underlying security relation; that is how the suite verifies semantics instead of vocabulary.

For `skil`, implementation claims should be checked against the repository’s control matrix, external-control crosswalk, analyzer tests and any provider-specific tests. Provider-backed coverage—such as OSV or external rule packs—must state whether the provider actually ran.

## Architecture drill-down: from finding to enforceable boundary

The architectural question behind **MCP Rug Pulls and Mutable Identity** is where interpretation and authority meet. Start with the reviewed artifact and follow the relevant identity, value, or capability through every transformation until the policy decision or side effect occurs. `REVIEWED_IDENTITY(t0) != RESOLVED_IDENTITY(t1) without_review` is the compact invariant that should remain stable even when implementation syntax changes. identity pinning + reviewed lockfile diff supplies static evidence, but the design should also specify what happens when analysis cannot resolve a value. High-assurance systems fail closed for high-impact operations, expose a bounded approval path for exceptional cases, and log the final resolved identity or target. The review is incomplete if it only proves that today's fixture is detected; it should also show how a future variant is constrained by architecture rather than by the exact spelling in the test corpus.

The paired fixtures also serve as an architectural regression test. The unsafe example begins with `{"command":"npx","args":["some-mcp-server@latest"]}` while the safe example begins with `{"command":"npx","args":["some-mcp-server@1.4.2"]}`. The important difference is the security relation, not the cosmetic text. If a refactor causes both to produce the same result, the detector or policy has lost a meaningful distinction.

## Common implementation traps

Several implementation mistakes recur around **MCP Rug Pulls and Mutable Identity**, even when the high-level policy is correct:

**1. Trusting model-visible metadata as if it were authorization policy.** Descriptions and schemas can guide planning, but deterministic host policy must own credentials, capability scope and approvals. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**2. Binding policy only to a display name.** Tool identity, server identity, metadata fingerprint and issuer relationships may need to be pinned so review survives catalog changes. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**3. Validating only at discovery time.** Cached catalogs, changed defaults, mutable packages and long-lived approvals create time-of-check/time-of-use gaps unless the host revalidates before high-impact calls. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

A useful review discipline is to turn every exception into a scoped, expiring artifact with an owner and rationale. Permanent blanket suppressions hide whether the architecture improved; narrow exceptions preserve the signal and make technical debt measurable.

## How this property composes with adjacent findings

**Identity drift plus retained approval.** The critical composition is a changed artifact or metadata fingerprint combined with an approval that remains valid. Either fact alone may be legitimate; together they show an approval-to-execution gap. Revalidation should revoke or narrow the approval before the new identity receives authority.

This composition model is deliberately graph-like: each detector contributes a typed fact and shared evidence identifiers allow a higher-level policy engine to connect them. That prevents one rule from becoming an overloaded catch-all and makes severity escalation explainable.

## Operational signals and measurable assurance

Measure mutable MCP references, identity/fingerprint changes between review and call, approvals invalidated by drift, lockfile freshness, provenance verification failures, and cache entries rejected because server identity changed.

Metrics should be tied to an explicit denominator and deployment profile. A low finding count may mean strong controls, weak coverage, or simply little exposure; telemetry and coverage state are needed to tell those cases apart. Trend the data over time and review unexpected changes in both positive findings and scanner-negative regression behavior.

## Engineering implications beyond the scanner

MCP security is split between protocol mechanics and host policy. The 2026-07-28 revision improves routability, caching semantics and authorization hardening, but it deliberately does not make tool descriptions trusted or grant least privilege automatically. Hosts still own capability selection, token scope, approval, identity pinning and the decision about what model-visible metadata may influence planning.

The broader lesson is that an agentic skill is simultaneously text, code, configuration, a tool contract and a supply-chain artifact. Security review should follow the boundary that is actually crossed—data, authority, identity, execution, or control-plane visibility—rather than forcing every risk into the same detection template.

## Change-focused testing

A reviewer should be able to answer four questions before accepting this property as controlled:

1. **What exact security relation is being asserted?** Here it is `REVIEWED_IDENTITY(t0) != RESOLVED_IDENTITY(t1) without_review`.
2. **What concrete evidence supports the relation?** The evidence must come from identity pinning + reviewed lockfile diff, not from a keyword alone.
3. **What near-neighbor safe case has been tested?** The paired negative fixture should differ in the property, not merely in spelling.
4. **What remains outside static visibility?** Runtime identity, dynamic values, provider state and policy decisions must be named explicitly.

## Conclusion

**MCP Rug Pulls and Mutable Identity** is valuable only when it is treated as a falsifiable security property rather than a checklist term. The goal is not to declare an entire skill “malicious” or “safe.” The goal is to state what boundary may be crossed, show the evidence that supports that statement, preserve the coverage limits, and make the safe countercondition explicit. That produces findings engineers can test, reviewers can reproduce, and runtime policy can enforce.
