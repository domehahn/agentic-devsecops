A credential file is small, but the authority it represents can be enormous. A private key, cloud profile, Kubernetes client configuration, package-registry token, browser credential store, or container-registry login can turn a file-read capability into access to systems that are otherwise outside the agent's nominal scope. In an agentic runtime, **credential-file access is therefore not merely a confidentiality event; it can be an authority-transfer event**.

That distinction is the reason this property deserves its own analysis instead of being folded into a generic “sensitive file” rule. The security question is not simply whether a path looks secret. It is whether an artifact performs or instructs a read of a credential-bearing resource **without an independently established authorization basis**.

The core relation is:

```text
READ(CREDENTIAL_BEARING_PATH) ∧ AUTHORIZATION_NOT_PROVEN
```

This deliberately leaves room for legitimate secret consumption. A deployment agent may need a narrowly scoped credential, and a diagnostic workflow may be explicitly authorized to inspect a particular authentication file. The control is violated when the read crosses the skill's declared purpose or trust boundary without sufficient evidence that the access is intended and permitted.

<Note>
A scanner-positive result establishes observable evidence for this property. It does not prove that a credential was successfully obtained or abused. Conversely, a scanner-negative result means only that the configured analysis did not establish the relation within its coverage.
</Note>

## Why credentials change the meaning of a filesystem read

Ordinary files carry data. Credential files frequently carry **delegated authority**. Once a process reads them, the process may be able to authenticate elsewhere as a user, workload, service account, developer, or automation identity.

A useful conceptual chain is:

```text
file read
   ↓
credential material enters process memory
   ↓
credential becomes an authentication capability
   ↓
agent can address a remote control plane or data plane
   ↓
effective authority expands beyond the local filesystem
```

This is why traditional least-privilege guidance and agentic-security guidance converge here. MITRE CWE-269 frames improper privilege management as a failure to restrict privileges appropriately, while OWASP's work on excessive agency emphasizes that an LLM application's impact is determined not only by the model but by the tools, credentials, permissions, and autonomy attached to it.[^cwe269][^owasp-agency]

The local read is therefore only the first observable step. The more serious risk often appears when credential acquisition composes with outbound network access, unrestricted tools, approval bypass, or a privileged runtime.

## A scanner-positive fixture should demonstrate a read, not merely a filename

A compact synthetic fixture is enough to validate the property:

```python
key_path = Path.home() / ".ssh" / "id_ed25519"
private_key_material = key_path.read_text()
```

The security evidence is stronger than the substring `id_ed25519`. The analyzer can observe:

- a read primitive,
- a path that belongs to a credential-bearing class,
- the absence of an obvious test-only or defensive context,
- and, depending on the surrounding artifact, a possible mismatch with the declared skill capability.

By contrast, the following prose is a safety rule and should remain scanner-negative for this property:

```md
Do not read private keys, cloud credential profiles, browser credential stores,
or operating-system password databases. Use the approved credential broker instead.
```

A detector that flags both examples equally is measuring vocabulary rather than behavior.

## Path classification is necessary, but path classification is not authorization

Credential analysis usually begins with path taxonomies. Useful classes include:

- SSH private keys and agent material,
- cloud CLI profiles and token caches,
- Kubernetes client credentials,
- container-registry credentials,
- package-manager authentication files,
- browser or desktop credential stores,
- service-account key material,
- operating-system authentication databases.

That taxonomy improves recall, yet it does not answer the central question. A path can be credential-bearing and still be legitimately read by a purpose-built authentication component. Conversely, credentials can live in an unusual project-local file that a hard-coded taxonomy does not recognize.

The stronger model combines **resource classification** with **authorization provenance**:

```text
resource class    = credential-bearing
operation         = read
actor              = agent skill / tool
purpose            = declared task
authorization      = reviewed contract or runtime grant
result             = allowed | violation | unresolved
```

This is an important architectural boundary. Static scanning can often establish the first three fields. Purpose and authorization may require manifest data, a reviewed capability contract, runtime policy, or deployment context.

## Credential paths are frequently computed, aliased, or mounted

Literal strings are the easiest case. Real applications derive paths in more complicated ways:

```text
$HOME + relative suffix
environment-derived config directory
platform-specific user-data path
symlink or junction target
container bind mount
workspace volume
secret-store projection
```

A robust analyzer should therefore preserve both the **source expression** and any **normalized approximation**. It should not pretend that a statically reconstructed path is guaranteed to be the runtime target.

For example:

```yaml
path_evidence:
  source_expression: "Path.home() / '.ssh' / 'id_ed25519'"
  normalized_class: "user_ssh_private_key"
  resolution: "static-high-confidence"
  symlink_target: "runtime-dependent"
```

This style of evidence is more useful than an unqualified statement such as “the agent reads the SSH key.”

## `skil`: deterministic evidence and the role of `SKIL-SEC-001`

The current `skil` security-control matrix maps contextual credential-file access to `SKIL-SEC-001`. The same control family also covers credential-bearing environment access, which is useful because credentials can enter an agent through multiple local sources.[^skil-matrix]

The detector can be thought of as a staged decision:

```text
code / prose
    ↓
read-intent or read-call candidate
    ↓
path normalization
    ↓
credential-path classification
    ↓
defensive/test/context suppression
    ↓
contract or authorization comparison
    ↓
property finding
```

For Python, AST evidence is materially stronger than a raw regex because it distinguishes a string literal in documentation from a call that actually reads a path. Other languages require equivalent structured analysis if the implementation wants the same level of confidence.

## Composition with taint analysis: the difference between access and exfiltration

Credential-file access and data exfiltration are separate properties. They should remain separate because each conveys useful information on its own. Yet they become more severe when evidence shows a common flow.

```text
credential file
     │ source
     ▼
read operation
     ▼
variable / object / serialization
     ▼
network client
     │ sink
     ▼
external destination
```

If that path is evidenced, the system can compose `SKIL-SEC-001` with a taint-to-network finding rather than inflating the severity of every credential read.

This separation has two benefits. First, it makes findings explainable: the reviewer sees exactly which stage was observed. Second, it prevents a benign authentication component from being mislabeled as exfiltration merely because it handles a secret.

## Secret brokers are preferable to raw file exposure

The safest architecture often removes credential files from the agent's filesystem entirely. Instead of mounting a long-lived secret and allowing arbitrary reads, expose a **brokered capability**:

```text
Agent
  │ requests "publish artifact"
  ▼
Policy / credential broker
  │ validates action, destination, identity, scope
  ▼
Short-lived credential or delegated operation
  ▼
Target service
```

The agent receives either a narrowly scoped temporary token or, preferably, the result of an operation performed on its behalf. This reduces the need for the model-driven process to ever possess reusable secret material.

Useful controls include:

- short-lived and audience-bound credentials,
- workload identity instead of static keys,
- per-operation authorization,
- non-exportable signing keys where feasible,
- dedicated service accounts per agent purpose,
- explicit network destination policies,
- secret redaction in logs, traces, and evaluation datasets.

These measures address the root problem: **a credential is capability-bearing data**.

## A trust-boundary view of credential access

Four boundaries matter particularly in agentic systems.

### Repository boundary

A repository skill should not silently reach into the developer's home directory just because the runtime happens to expose it.

### Tenant boundary

In shared agent infrastructure, one tenant's authentication material must never become visible to another tenant's execution context.

### Tool boundary

A tool that legitimately authenticates to a service should not automatically return its underlying credential to the model. Returning an opaque operation result is safer than returning raw tokens.

### Observability boundary

Telemetry systems can become accidental exfiltration paths. Prompt traces, exception dumps, debug logs, and tool-call payloads should be treated as separate sinks and redacted before persistence.

<Architecture>
Credential-bearing resource → broker or restricted read boundary → purpose-scoped operation → redacted telemetry → audited result
</Architecture>

## False positives: test fixtures, mount manifests, and documentation

Security repositories naturally mention sensitive paths. Infrastructure-as-code may declare a secret mount, unit tests may create fake credentials, and hardening documentation may enumerate paths that must never be read.

A credible detector needs local counter-evidence:

```text
candidate path
  ├─ only documented?                 → no access relation
  ├─ fake test fixture in test scope? → downgrade / suppress by policy
  ├─ explicit deny instruction?       → scanner-negative for read intent
  ├─ read primitive present?          → continue analysis
  └─ external sink reachable?         → compose with dataflow finding
```

Global exclusions are weaker because they hide real problems in exactly the kinds of security-oriented files that contain realistic examples.

## What runtime enforcement should look like

Static analysis is an early control. Runtime architecture should independently make the dangerous path difficult or impossible.

For repository-oriented agents, a strong baseline is:

- mount only the working tree and required build caches,
- do not mount the user's home directory,
- run under a dedicated OS identity,
- expose secrets through purpose-specific brokers,
- deny arbitrary reads outside declared roots,
- restrict egress to required services,
- separate production and development credentials,
- keep privileged host credential stores outside the sandbox namespace.

A useful policy statement is therefore not “the model must not read secrets.” It is:

> The agent process is not given a filesystem or identity path through which unrelated secrets can be obtained.

That is a security boundary the model cannot simply talk itself around.

## Evidence quality and reviewability

A high-quality finding should answer more than “what rule matched?” A reviewer should be able to reconstruct the security argument.

```yaml
property: credential-file-access
controls:
  - SKIL-SEC-001
source:
  artifact: skill.py
  operation: file_read
resource:
  class: credential_bearing
  path_resolution: static
contract:
  credential_access_declared: false
authorization:
  proven: false
composition:
  network_sink: unresolved
coverage:
  path_detection: deterministic
  runtime_mounts: not_observable
```

This evidence allows policy engines to distinguish direct, high-confidence access from unresolved runtime-dependent possibilities.

## Validation strategy

A meaningful regression suite should include more than one obvious private-key path. Test dimensions should cover:

- literal credential paths,
- dynamically joined paths,
- platform-specific path families,
- defensive prohibition text,
- documentation-only strings,
- fake credentials under test directories,
- code that reads a credential and never exports it,
- code that routes the resulting data into an external sink,
- paths constructed from environment variables,
- symlink- or mount-dependent cases marked as runtime-dependent.

Metrics should track false positives and false negatives separately. A security property that finds every test string but cannot survive real repositories is operationally weak.

## Limits of static certainty

Static analysis normally cannot prove:

- what a symlink points to at execution time,
- which volumes a container will mount,
- whether a runtime identity is actually authorized,
- whether the file contains a valid secret,
- whether an external identity provider will accept it,
- whether a later tool call uses the credential.

The finding should therefore be precise about the observed property: **credential-bearing file access**, not successful compromise.

<KeyTakeaway>
The most important architectural insight is that credentials should be treated as delegated authority, not as ordinary bytes. The preferred design is to keep reusable credentials outside the model-driven process, expose narrowly scoped operations through a broker, and let static plus runtime controls verify that any exceptional direct read is explicitly justified.
</KeyTakeaway>

## Conclusion

Credential-file access is the point at which a local read can become remote authority. A defensible scanner must establish an actual read relation, classify the resource, account for scope and authorization, and preserve uncertainty where runtime mounts or identities are unknown. A defensible platform goes further: it minimizes raw credential exposure so that the agent receives only the authority required for the specific operation it is expected to perform.
