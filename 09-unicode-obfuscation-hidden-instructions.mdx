Attackers do not need new capabilities if they can hide old ones from review.

That is the security role of obfuscation: preserve behavior while changing representation.

## Unicode creates visual ambiguity

Two identifiers can look similar while containing characters from different scripts.

A hostname may visually resemble a trusted domain while using a Cyrillic character.

Text can also contain:

- bidirectional controls
- zero-width characters
- tag characters
- invisible separators

These mechanisms have legitimate uses, but they can also hide or reorder instructions.

## Normalize without destroying evidence

A scanner may need multiple views:

```text
original bytes
normalized text
visual-security representation
```

The original is required for evidence and hashing.

Normalized text is useful for semantic matching.

A security representation can expose:

```text
mixed scripts
invisible controls
confusables
Bidi changes
```

<Architecture>
Never replace the original artifact with normalized content. Normalize for analysis while preserving byte-accurate evidence.
</Architecture>

## Emoji are the false-positive trap

Many legitimate emoji use Unicode features that look suspicious to simplistic detectors:

```text
variation selectors
zero-width joiners
skin-tone modifiers
regional indicators
```

So this rule is wrong:

```text
contains zero-width code point
→ malicious
```

A security detector needs context.

For example, a ZWJ inside a valid emoji sequence is different from a zero-width character inserted into a security-sensitive keyword.

## Mixed scripts need scope

Multilingual prose is normal.

This is not automatically suspicious:

```text
English sentence followed by 日本語.
```

A higher-signal case is a sensitive token mixing lookalikes:

```text
trusted-domain.example
```

where one character is from another script but visually confusable.

Focus on:

```text
identifiers
hostnames
commands
security-sensitive words
```

rather than flagging every document containing multiple scripts.

## Encoded content is not automatically malicious

Base64 appears everywhere:

```text
certificates
binary assets
test fixtures
API payloads
documentation
```

Detection becomes useful when representation connects to dangerous behavior:

```text
Base64 decode
      ↓
dynamic execution
```

or:

```text
encoded hidden instruction
      ↓
agent interpretation
```

The relationship matters more than the encoding.

## Split strings evade literal patterns

Consider:

```python
name = "ev" + "al"
getattr(__builtins__, name)(payload)
```

or a natural-language instruction split across Markdown formatting.

The security property survives even though the literal token disappears.

For code, AST and constant folding can help.

For instructions, bounded normalization and intent analysis are more appropriate.

## Obfuscation should raise uncertainty carefully

Some scanners treat obfuscation as proof of maliciousness.

That creates noise.

A better model is:

```text
obfuscation signal
+
dangerous sink
+
sensitive context
=
higher confidence
```

For example:

```text
encoded blob only
```

may be informational.

But:

```text
encoded blob -> decode -> exec
```

is high confidence.

## Test benign Unicode aggressively

For every Unicode detector, include safe regression cases:

```text
emoji ZWJ sequence
skin-tone emoji
flag
normal CJK text
accented Latin text
mixed-language documentation
```

Then add security cases:

```text
Bidi instruction hiding
hostname confusable
zero-width keyword splitting
mixed-script identifier
tag-character concealment
```

<KeyTakeaway>
Evasion detection is useful only if it can distinguish deception from normal representation complexity.
</KeyTakeaway>

That principle applies far beyond Unicode. It is the difference between a scanner that finds attacks and a scanner that merely dislikes unusual text.
