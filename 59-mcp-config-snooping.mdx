## MCP configuration is a topology map

MCP configuration can describe every tool server an environment knows about, including command lines, URLs, environment variables and authentication hints. Exposing raw configuration to an arbitrary skill is equivalent to handing it a map of the agent’s integration control plane.

Skills should consume host-provided MCP handles, not enumerate global server configuration. Discovery, credentials and server topology belong to the host control plane and should be exposed only through scoped interfaces. The original `skil` control model expresses the same idea as `READ_OR_ENUMERATE(MCP_SERVER_CONFIGURATION_OR_CREDENTIALS) outside declared scope`. That relation is more useful than a label such as “suspicious” because it specifies what must be evidenced and what a legitimate counterexample must break.

## Why raw config should not enter the skill workspace

Even redacted configs can disclose internal hostnames, server names, local executable paths and organizational tool choices. This information narrows an attacker’s search space and can help craft convincing tool-specific injection. The same model supports change detection: when identity, configuration or code changes, the platform can recompute the relation and show exactly which part of the previously reviewed assumption no longer holds.

## Credentials belong in a broker

OAuth tokens, API keys and environment secrets should remain in a credential broker. The model or skill can request a tool call without seeing the bearer token used to authorize that call. In an agentic environment this distinction becomes operational because model-generated plans can select the relevant value or capability at runtime. The host therefore needs evidence that can survive from code review into execution policy.

## Host-mediated discovery preserves least privilege

The host can advertise only the tools available to the current task or identity. This prevents a skill from learning about unrelated production, administrative or personal MCP servers merely because they exist in the global config. The design implication is that detection and authorization must remain separate: the scanner identifies the condition, while a policy layer decides whether the condition is permissible in this deployment context.

## Audience and issuer binding prevent credential reuse

Modern MCP authorization hardening emphasizes correct issuer relationships. Tokens should be bound to the intended resource/server and must not be reusable across unrelated MCP endpoints. This is a runtime authorization property, not something a prompt can enforce. This also improves explainability. Reviewers can see the specific security fact rather than receiving a generic severity label, and future tooling can compose that fact with independent findings without double-counting the same evidence.

## File-based detection remains valuable

Many real environments still use JSON/TOML/YAML configuration files. Static analysis can flag code that enumerates known MCP config paths or prints server records, while runtime filesystem policy blocks the access in production. A useful implementation records both the positive observation and the guard that would have made the path safe. That makes remediation testable and turns false-positive handling into explicit logic instead of a collection of suppressions.

## Host-mediated discovery

A deliberately small positive fixture from the source property illustrates the boundary:

```python
cfg = json.loads(Path.home().joinpath(".claude", "mcp.json").read_text())
print(cfg)
```

The safe counterexample changes the semantics rather than merely deleting a suspicious token:

```md
Use only the MCP server handles provided by the host. Do not enumerate global MCP configuration or credentials.
```

The purpose of pairing them is not to teach exploitation. It is to force the detector to explain which relation changes between the two cases. A scanner that fires on both has learned vocabulary; a scanner that can explain the difference has begun to model the security property.

## Static path detection and its limits

Detection quality depends on traceability. The scanner should preserve the raw location, the property-specific observation produced by MCP config path + enumeration/secret context detection, and the reasoning that turns it into `READ_OR_ENUMERATE(MCP_SERVER_CONFIGURATION_OR_CREDENTIALS) outside declared scope`. The native control surface is `SKIL-BOUNDARY-MCP-CONFIG`. Because the stated coverage is FULL, confidence must follow evidence completeness—not severity labels or lexical suspicion.

A compact machine-readable evidence record can retain the essentials without pretending to encode the entire analysis:

## False positives, ambiguity, and safe counterexamples

Administrative backup or migration tools may need to read MCP configuration. They should run with a distinct role and explicit contract. Ordinary skills should not inherit that exception simply because the same codebase contains an admin utility.

Static analysis has an epistemic boundary: it can only reason about the representation it sees. Dynamic DNS, runtime-generated code, reflection, remote configuration, credential brokers and policy decisions may exist outside that view. The correct result vocabulary therefore includes states such as `verified`, `partially_resolved`, `provider_backed`, `runtime_dependent`, and `not_observable`. This is not bureaucratic metadata; it prevents a consumer from interpreting an absent finding as proof that no risk exists.

## Administrative workflows

Keep MCP config directories outside agent workspaces, expose scoped server handles through the host, store credentials separately, validate token audience/issuer, and log server-discovery decisions.

Defense in depth is intentionally redundant. Authoring lint, static analysis, contract verification, supply-chain verification, runtime policy and audit telemetry answer different questions. A strong result from one layer should never be used as a reason to remove the others.

## Runtime architecture

A serious regression suite needs paired examples. Each positive fixture should have a near-neighbor negative case, and each new false positive should become a permanent test. Where the property depends on identity or time, tests should also change the resolved artifact or metadata between review and execution. Where it depends on data flow, fixtures should exercise aliases, wrappers and valid sanitizers. For **MCP Configuration Snooping**, the most valuable tests are those that preserve the surface appearance while changing the underlying security relation; that is how the suite verifies semantics instead of vocabulary.

For `skil`, implementation claims should be checked against the repository’s control matrix, external-control crosswalk, analyzer tests and any provider-specific tests. Provider-backed coverage—such as OSV or external rule packs—must state whether the provider actually ran.

## Architecture drill-down: from finding to enforceable boundary

For **MCP Configuration Snooping**, think in terms of a chain of custody for security meaning. The artifact creates an observation, MCP config path + enumeration/secret context detection converts that observation into a structured fact, contract or policy logic interprets the fact, and runtime enforcement decides whether the operation can proceed. Each handoff can lose context. The relation `READ_OR_ENUMERATE(MCP_SERVER_CONFIGURATION_OR_CREDENTIALS) outside declared scope` should therefore be represented explicitly in evidence rather than reconstructed from a human-readable message after the fact. Reviewers should inspect whether normalization is reversible for forensics, whether identity is immutable between review and use, whether policy is scoped to the task, and whether provider failures are visible. This turns a static finding into an assurance argument that can survive deployment changes.

The paired fixtures also serve as an architectural regression test. The unsafe example begins with `cfg = json.loads(Path.home().joinpath(".claude", "mcp.json").read_text())` while the safe example begins with `Use only the MCP server handles provided by the host. Do not enumerate global MCP configur`. The important difference is the security relation, not the cosmetic text. If a refactor causes both to produce the same result, the detector or policy has lost a meaningful distinction.

## Common implementation traps

Several implementation mistakes recur around **MCP Configuration Snooping**, even when the high-level policy is correct:

**1. Using a contract vocabulary that is too coarse to enforce.** A declaration such as 'network' is weak if the runtime cannot distinguish approved targets from arbitrary egress. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**2. Interpreting absence of static observation as proof that a capability is unused.** Dynamic frameworks, reflection and remote configuration require explicit coverage states and sometimes runtime evidence. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**3. Mounting global control-plane state for convenience.** Home directories, peer skill directories and MCP config files create ambient authority that bypasses the intended capability model. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

A useful review discipline is to turn every exception into a scoped, expiring artifact with an owner and rationale. Permanent blanket suppressions hide whether the architecture improved; narrow exceptions preserve the signal and make technical debt measurable.

## How this property composes with adjacent findings

**MCP config discovery plus token misuse.** Server enumeration becomes more serious if the same code can read credential-bearing environment variables or reuse tokens across endpoints. Linking config-snooping, secret-access, and authorization findings exposes a plausible control-plane attack path while preserving each detector’s independent evidence.

This composition model is deliberately graph-like: each detector contributes a typed fact and shared evidence identifiers allow a higher-level policy engine to connect them. That prevents one rule from becoming an overloaded catch-all and makes severity escalation explainable.

## Operational signals and measurable assurance

Measure raw MCP-config read attempts, host-mediated discovery usage, credential-bearing config exposure, token audience validation failures, and administrative exceptions. The desired architecture shifts discovery from files to audited host APIs.

Metrics should be tied to an explicit denominator and deployment profile. A low finding count may mean strong controls, weak coverage, or simply little exposure; telemetry and coverage state are needed to tell those cases apart. Trend the data over time and review unexpected changes in both positive findings and scanner-negative regression behavior.

## Engineering implications beyond the scanner

Capability and isolation properties become most valuable when compiled into runtime controls. A declaration can drive egress filters, filesystem mounts, process brokers, secret scopes and delegation edges. Static observations then test whether implementation and contract agree, while runtime denials expose behaviors the static analyzers could not resolve. This feedback loop turns the contract into a living security boundary instead of documentation that gradually drifts from reality.

The broader lesson is that an agentic skill is simultaneously text, code, configuration, a tool contract and a supply-chain artifact. Security review should follow the boundary that is actually crossed—data, authority, identity, execution, or control-plane visibility—rather than forcing every risk into the same detection template.

## Assurance tests

A reviewer should be able to answer four questions before accepting this property as controlled:

1. **What exact security relation is being asserted?** Here it is `READ_OR_ENUMERATE(MCP_SERVER_CONFIGURATION_OR_CREDENTIALS) outside declared scope`.
2. **What concrete evidence supports the relation?** The evidence must come from MCP config path + enumeration/secret context detection, not from a keyword alone.
3. **What near-neighbor safe case has been tested?** The paired negative fixture should differ in the property, not merely in spelling.
4. **What remains outside static visibility?** Runtime identity, dynamic values, provider state and policy decisions must be named explicitly.

## Conclusion

**MCP Configuration Snooping** is valuable only when it is treated as a falsifiable security property rather than a checklist term. The goal is not to declare an entire skill “malicious” or “safe.” The goal is to state what boundary may be crossed, show the evidence that supports that statement, preserve the coverage limits, and make the safe countercondition explicit. That produces findings engineers can test, reviewers can reproduce, and runtime policy can enforce.
