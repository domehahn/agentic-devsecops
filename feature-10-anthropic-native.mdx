Eine native Provider-Anbindung nutzt das spezifische API-Modell eines Anbieters direkt. Das erlaubt präzisere Konfiguration, bessere Fehlerbehandlung und Zugriff auf provider-spezifische Funktionen.

Das Feature ist damit nicht nur eine Komfortfunktion.

Es verändert, **welcher Kontext geprüft wird, welche Vertrauensgrenzen gelten und wie belastbar das Ergebnis später in CI/CD oder Security-Governance verwendet werden kann**.

## Was das Feature leistet

Statt eine generische Chat-Completions-Abstraktion zu erzwingen, bildet der Adapter native Nachrichtenformate, Modellparameter, Limits und Response-Strukturen ab. Dadurch kann der Scanner Providerfehler klar von Analysefehlern unterscheiden.

Für Security Workflows ist diese Trennung wertvoll: Ein Rate Limit, ein Policy-Block oder ein Timeout ist kein inhaltliches Urteil über das Artefakt und muss im Report anders dargestellt werden.

## Typischer Ablauf

Unabhängig von der konkreten Implementierung sollte der Ablauf klar getrennte Phasen besitzen:

```text
Input
  ↓
Validierung und Normalisierung
  ↓
Feature-spezifische Verarbeitung
  ↓
Security-Analyse
  ↓
Findings + Coverage + technischer Status
  ↓
Policy-Entscheidung
```

Diese Trennung ist wichtig, weil ein technischer Fehler bei Beschaffung, Parsing oder Providerzugriff nicht dieselbe Bedeutung hat wie ein tatsächlich unauffälliges Prüfergebnis.

## Negatives Beispiel

Eine Implementierung fängt jeden Providerfehler ab und liefert anschließend ein leeres Finding-Set:

```text
429 Too Many Requests
        ↓
findings = []
        ↓
PASS
```

Damit wird technische Nichtverfügbarkeit semantisch als „keine Risiken gefunden“ interpretiert. Das ist ein klassischer Fail-open-Fehler.

## Positives Beispiel

Der Providerzustand ist Teil des Ergebnisses:

```json
{
  "semantic_analysis": {
    "status": "degraded",
    "reason": "rate_limited",
    "findings": null
  }
}
```

Ein CI-Gate kann daraufhin bewusst entscheiden, ob ein statischer Scan genügt oder ob die semantische Stufe zwingend erfolgreich sein muss.

<KeyTakeaway>
Ein nativer Adapter schafft bessere Kontrolle über Providerzustand und Fähigkeiten. Entscheidend ist, technische Fehler niemals als Sicherheitsurteil zu maskieren.
</KeyTakeaway>

## Security- und Betriebsaspekte

API-Schlüssel gehören in Secret Stores und sollten weder in Reports noch in Debug-Logs erscheinen. Außerdem müssen Datenklassifizierung, Retention-Vorgaben und erlaubte Regionen mit der Provider-Nutzung abgestimmt werden.

Prompt- und Modellversionen sollten nachvollziehbar dokumentiert werden, damit Änderungen im Backend nicht unbemerkt die Bewertungslogik verändern.

Ein professioneller Betrieb sollte außerdem drei Zustände konsequent auseinanderhalten:

```text
clean      = geprüft, kein relevanter Befund
finding    = geprüft, mindestens ein relevanter Befund
incomplete = Prüfung technisch oder fachlich nicht vollständig
```

Gerade der dritte Zustand ist für DevSecOps entscheidend.

Ein Scanner darf fehlende Coverage nicht als positives Sicherheitsurteil darstellen.

## Wo das Feature sinnvoll eingesetzt wird

Native Anbindung lohnt sich, wenn provider-spezifische Funktionen, klare Telemetrie oder Supportability wichtig sind. Sie ist gut für produktive semantische Analyse mit festen Betriebsanforderungen.

Wer viele austauschbare Backends bedienen muss, kann zusätzlich eine kompatible Standardschnittstelle anbieten.

Die konkrete Aktivierung sollte deshalb aus dem gewünschten Trust-Modell abgeleitet werden und nicht allein aus technischer Verfügbarkeit.

## Integration in eine DevSecOps-Pipeline

In einer Pipeline sollte das Feature nicht isoliert betrachtet werden.

Ein belastbares Muster ist:

```text
Source / Artifact
      ↓
Input-Validierung
      ↓
Deterministische Analyse
      ↓
optionale erweiterte Analyse
      ↓
normalisierte Findings
      ↓
Policy Gate
      ↓
Report / Audit Evidence
```

Dabei sollte jeder Report mindestens folgende Informationen transportieren:

- Identität des analysierten Artefakts
- aktive Analyseverfahren
- übersprungene oder nicht verfügbare Prüfschritte
- stabile Regel- oder Finding-IDs
- Schweregrad und Evidenz
- Scanner- und Regelversion
- eindeutiger technischer Abschlussstatus

Damit wird das Feature nicht nur ausführbar, sondern **auditierbar**.

## Fazit

Ein nativer Adapter schafft bessere Kontrolle über Providerzustand und Fähigkeiten. Entscheidend ist, technische Fehler niemals als Sicherheitsurteil zu maskieren.

Der eigentliche Wert entsteht dann, wenn das Feature mit klaren Grenzen, reproduzierbaren Eingaben und transparenten Ergebnissen in den Entwicklungsprozess eingebettet wird.
