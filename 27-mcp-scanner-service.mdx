Ein Scanner als MCP-Service verändert den Workflow grundlegend. Ein Agent kann einen Skill prüfen, bevor er ihn installiert oder verwendet, und Security wird damit Teil des agentischen Kontrollflusses statt ein manueller Offline-Schritt.

Gleichzeitig wird der Scanner selbst zu einem Tool mit Eingaben, Netzwerk- und Dateisystemgrenzen. Seine Service-Oberfläche muss deshalb genauso sorgfältig gehärtet werden wie die Analyzer.

<Architecture>
Ein Scanner als MCP-Tool ist Teil der Agent Runtime. Security entsteht erst, wenn das Ergebnis an eine nicht vom Agenten umgehbare Policy- oder Installationsgrenze gekoppelt ist.
</Architecture>

## Was das Feature wirklich bedeutet

Ein MCP Security Service sollte nur klar definierte Roots lesen, Remote-Zugriffe kontrollieren, Authentisierung besitzen und keine beliebigen Hostpfade akzeptieren. Findings müssen als Daten zurückkommen; der gescannte Skill darf nie zu Instructions für den Scannerprozess werden.

Für Remote-Transport ist Loopback-Bindung plus Authentisierung ein sinnvoller Default.

## SkillSpector

SkillSpector kann als MCP-Server laufen. Die Dokumentation beschreibt stdio für lokale Agenten sowie HTTP/SSE-Transport auf `127.0.0.1`. Der Service soll Scanning als Tool bereitstellen, damit Agenten Installationen auf Scanergebnisse gaten können.

Damit wird die vorhandene CLI-Funktionalität in agentische Workflows eingebettet.

## `skil`

`skil` bietet einen begrenzten MCP Scanner Service über stdio oder bearer-authentifiziertes Loopback-HTTP. Der CLI-Help verlangt bei Serverbetrieb ein explizites Root-Verzeichnis. Das passt zum allgemeinen Design, Host-Capabilities möglichst eng zu halten.

Der Service ist damit eine First-Class-Schnittstelle, bleibt aber an eine definierte Dateisystem- und Transportgrenze gebunden.

## Praxisbeispiel

```text
Agent
  │
  │ MCP: scan_skill(path)
  ▼
Scanner Service
  │
  ├── bounded artifact loader
  ├── static analyzers
  └── policy/report
       │
       ▼
   allow / review / block
```

Der Agent sollte nicht selbst entscheiden dürfen, den Scan bei einem negativen Ergebnis einfach zu überspringen. Das Gate muss in Host-/Installationslogik verankert sein.

## Security- und DevSecOps-Einordnung

- MCP-Scanner nur auf definierte Roots zugreifen lassen.
- HTTP standardmäßig auf Loopback binden und authentisieren.
- Remote-Scanning nicht automatisch durch Toolparameter freischalten.
- Scannerresultat außerhalb des unvertrauenswürdigen Agent-Prompts als Policy-Signal verwenden.
- Tool-Aufrufe und Artefakt-Digests auditieren.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

## Typische Fehlinterpretation

„Wenn ein Agent vor Installation den Scanner aufruft, ist das ein Gate.“ Nur wenn die Installation technisch vom Ergebnis abhängt. Ein freiwilliger Tool-Aufruf ist noch keine Enforcement-Grenze.

## Einordnung in die Pipeline

Dieses Feature betrifft die **Integration und Laufzeit des Scanners selbst**. Damit wird nicht nur der Skill analysiert, sondern auch festgelegt, über welche Tool-, Prozess- oder Containergrenze Security-Funktionen erreichbar sind.

Für produktive Nutzung sollten Identität, Dateisystemzugriff, Netzwerk, Secrets und Auditlogs der Scanner-Runtime genauso behandelt werden wie bei jedem anderen sicherheitskritischen Service.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Beide Projekte bieten einen MCP Scanner Service. Der nächste Reifegrad liegt nicht in „MCP vorhanden“, sondern in der Frage, wie eng Root, Transport, Authentisierung und Installations-Gate technisch erzwungen werden.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
