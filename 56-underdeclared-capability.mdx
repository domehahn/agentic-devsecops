## A contract that omits authority is not a boundary

A capability contract exists so reviewers can understand what a skill is allowed to do without reverse-engineering every line of code. If the implementation can access network, files, processes or secrets that the contract omits, that contract becomes a misleading security boundary.

Underdeclaration is the set difference between observed and declared capability. The difficult part is building both sets with explicit granularity and coverage so the verifier can distinguish a real omission from an analyzer blind spot. The original `skil` control model expresses the same idea as `OBSERVED_CAPABILITIES − DECLARED_CAPABILITIES != ∅`. That relation is more useful than a label such as “suspicious” because it specifies what must be evidenced and what a legitimate counterexample must break.

## Property at a glance

| Dimension | Assessment |
| --- | --- |
| Security property | Underdeclared Capabilities |
| Relevant `skil` controls | `SKIL-CAP-DECLARATION-MISSING`, `SKIL-CAP-001` |

| Declared coverage character | VERIFY_ONLY for precise mismatches |
| Core security relation | `OBSERVED_CAPABILITIES − DECLARED_CAPABILITIES != ∅` |

## Set difference with explicit coverage

A deliberately small positive fixture from the source property illustrates the boundary:

```yaml
contract:
  network: []
# observed: requests.post("https://api.example")
```

The safe counterexample changes the semantics rather than merely deleting a suspicious token:

```yaml
contract:
  network:
    - https://api.example
# observed network access remains within declared target
```

The purpose of pairing them is not to teach exploitation. It is to force the detector to explain which relation changes between the two cases. A scanner that fires on both has learned vocabulary; a scanner that can explain the difference has begun to model the security property.

## Building a capability ontology

Different analyzers speak different languages: an HTTP POST, a socket connection and a cloud SDK upload are all network-related but carry different risk. A verifier needs a stable capability model with categories, targets, modes and side-effect semantics. The design implication is that detection and authorization must remain separate: the scanner identifies the condition, while a policy layer decides whether the condition is permissible in this deployment context.

## From AST and taint to observed capabilities

AST, taint and boundary analyzers can observe many capabilities statically, but dynamic imports, reflection and remote configuration may remain unresolved. The comparison should include coverage metadata so “not observed” is not confused with “proved absent.” This also improves explainability. Reviewers can see the specific security fact rather than receiving a generic severity label, and future tooling can compose that fact with independent findings without double-counting the same evidence.

## Target-level precision changes usefulness

A contract that declares “network” may be too coarse if the implementation contacts arbitrary domains. High-assurance systems should compare targets, protocols or resource classes where analyzers can resolve them, while reporting partial resolution honestly when they cannot. A useful implementation records both the positive observation and the guard that would have made the path safe. That makes remediation testable and turns false-positive handling into explicit logic instead of a collection of suppressions.

## Contract drift should fail loudly for high-risk classes

New process execution, secret access, external writes or production deployment capability should not appear silently in a refactor. CI can fail on an undeclared high-risk observation and require the contract change to be reviewed in the same pull request. The same model supports change detection: when identity, configuration or code changes, the platform can recompute the relation and show exactly which part of the previously reviewed assumption no longer holds.

## Runtime enforcement closes the semantic gap

The best contract is executable policy. If the static verifier missed a new network call, the runtime should still deny any target outside the declared network set. This turns the contract from documentation into defense in depth. In an agentic environment this distinction becomes operational because model-generated plans can select the relevant value or capability at runtime. The host therefore needs evidence that can survive from code review into execution policy.

## CI as a contract gate

Detection quality depends on traceability. The scanner should preserve the raw location, the property-specific observation produced by declared-vs-observed contract verification, and the reasoning that turns it into `OBSERVED_CAPABILITIES − DECLARED_CAPABILITIES != ∅`. The native control surface is `SKIL-CAP-DECLARATION-MISSING`, `SKIL-CAP-001`. Because the stated coverage is VERIFY_ONLY for precise mismatches, confidence must follow evidence completeness—not severity labels or lexical suspicion.

A compact machine-readable evidence record can retain the essentials without pretending to encode the entire analysis:

```yaml
property_order: 56
property: "underdeclared-capabilities"
controls: "SKIL-CAP-DECLARATION-MISSING, SKIL-CAP-001"
mechanism: "declared-vs-observed contract verification"
security_relation: "OBSERVED_CAPABILITIES − DECLARED_CAPABILITIES != ∅"
coverage: "VERIFY_ONLY for precise mismatches"
evidence:
  raw_location: true
  structured_observation: true
  context_resolved: true
  safe_countercase_tested: true
```

## False positives, ambiguity, and safe counterexamples

Generated code, dead code and platform-specific branches can produce observations that are not reachable in a given deployment. Findings should show the exact observation and allow reachability or deployment-profile evidence to qualify the result rather than suppressing the capability class globally.

Static analysis has an epistemic boundary: it can only reason about the representation it sees. Dynamic DNS, runtime-generated code, reflection, remote configuration, credential brokers and policy decisions may exist outside that view. The correct result vocabulary therefore includes states such as `verified`, `partially_resolved`, `provider_backed`, `runtime_dependent`, and `not_observable`. This is not bureaucratic metadata; it prevents a consumer from interpreting an absent finding as proof that no risk exists.

## Runtime policy compilation

Compile approved contracts into network, filesystem, process and secret policies. Log denied attempts as contract-violation evidence and feed them back into static coverage improvements.

Defense in depth is intentionally redundant. Authoring lint, static analysis, contract verification, supply-chain verification, runtime policy and audit telemetry answer different questions. A strong result from one layer should never be used as a reason to remove the others.

## Handling dead code and dynamic behavior

A serious regression suite needs paired examples. Each positive fixture should have a near-neighbor negative case, and each new false positive should become a permanent test. Where the property depends on identity or time, tests should also change the resolved artifact or metadata between review and execution. Where it depends on data flow, fixtures should exercise aliases, wrappers and valid sanitizers. For **Underdeclared Capabilities**, the most valuable tests are those that preserve the surface appearance while changing the underlying security relation; that is how the suite verifies semantics instead of vocabulary.

For `skil`, implementation claims should be checked against the repository’s control matrix, external-control crosswalk, analyzer tests and any provider-specific tests. Provider-backed coverage—such as OSV or external rule packs—must state whether the provider actually ran.

## Architecture drill-down: from finding to enforceable boundary

For **Underdeclared Capabilities**, think in terms of a chain of custody for security meaning. The artifact creates an observation, declared-vs-observed contract verification converts that observation into a structured fact, contract or policy logic interprets the fact, and runtime enforcement decides whether the operation can proceed. Each handoff can lose context. The relation `OBSERVED_CAPABILITIES − DECLARED_CAPABILITIES != ∅` should therefore be represented explicitly in evidence rather than reconstructed from a human-readable message after the fact. Reviewers should inspect whether normalization is reversible for forensics, whether identity is immutable between review and use, whether policy is scoped to the task, and whether provider failures are visible. This turns a static finding into an assurance argument that can survive deployment changes.

The paired fixtures also serve as an architectural regression test. The unsafe example begins with `contract:` while the safe example begins with `contract:`. The important difference is the security relation, not the cosmetic text. If a refactor causes both to produce the same result, the detector or policy has lost a meaningful distinction.

## Common implementation traps

Several implementation mistakes recur around **Underdeclared Capabilities**, even when the high-level policy is correct:

**1. Using a contract vocabulary that is too coarse to enforce.** A declaration such as 'network' is weak if the runtime cannot distinguish approved targets from arbitrary egress. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**2. Interpreting absence of static observation as proof that a capability is unused.** Dynamic frameworks, reflection and remote configuration require explicit coverage states and sometimes runtime evidence. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**3. Mounting global control-plane state for convenience.** Home directories, peer skill directories and MCP config files create ambient authority that bypasses the intended capability model. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

A useful review discipline is to turn every exception into a scoped, expiring artifact with an owner and rationale. Permanent blanket suppressions hide whether the architecture improved; narrow exceptions preserve the signal and make technical debt measurable.

## How this property composes with adjacent findings

**Undeclared capability plus actual use.** Observed capability is strongest when the analyzer can show a concrete call or source-to-sink path and the runtime later confirms the same class. Static and runtime evidence can be linked to demonstrate that the contract omitted authority actually exercised, not merely dead code.

This composition model is deliberately graph-like: each detector contributes a typed fact and shared evidence identifiers allow a higher-level policy engine to connect them. That prevents one rule from becoming an overloaded catch-all and makes severity escalation explainable.

## Operational signals and measurable assurance

Track undeclared capability classes by severity, percentage with concrete target resolution, CI failures requiring contract updates, runtime denials of undeclared actions, and analyzer coverage gaps responsible for late discovery.

Metrics should be tied to an explicit denominator and deployment profile. A low finding count may mean strong controls, weak coverage, or simply little exposure; telemetry and coverage state are needed to tell those cases apart. Trend the data over time and review unexpected changes in both positive findings and scanner-negative regression behavior.

## Engineering implications beyond the scanner

Capability and isolation properties become most valuable when compiled into runtime controls. A declaration can drive egress filters, filesystem mounts, process brokers, secret scopes and delegation edges. Static observations then test whether implementation and contract agree, while runtime denials expose behaviors the static analyzers could not resolve. This feedback loop turns the contract into a living security boundary instead of documentation that gradually drifts from reality.

The broader lesson is that an agentic skill is simultaneously text, code, configuration, a tool contract and a supply-chain artifact. Security review should follow the boundary that is actually crossed—data, authority, identity, execution, or control-plane visibility—rather than forcing every risk into the same detection template.

## Assurance criteria

A reviewer should be able to answer four questions before accepting this property as controlled:

1. **What exact security relation is being asserted?** Here it is `OBSERVED_CAPABILITIES − DECLARED_CAPABILITIES != ∅`.
2. **What concrete evidence supports the relation?** The evidence must come from declared-vs-observed contract verification, not from a keyword alone.
3. **What near-neighbor safe case has been tested?** The paired negative fixture should differ in the property, not merely in spelling.
4. **What remains outside static visibility?** Runtime identity, dynamic values, provider state and policy decisions must be named explicitly.

## Conclusion

**Underdeclared Capabilities** is valuable only when it is treated as a falsifiable security property rather than a checklist term. The goal is not to declare an entire skill “malicious” or “safe.” The goal is to state what boundary may be crossed, show the evidence that supports that statement, preserve the coverage limits, and make the safe countercondition explicit. That produces findings engineers can test, reviewers can reproduce, and runtime policy can enforce.
