# AI Agents: From Perception and Memory to Planning, Tools, and Bounded Action

The phrase *AI agent* is used so broadly that it can describe anything from a chatbot with one tool to a long-running software system that coordinates multiple services over hours. A useful definition must therefore focus on architecture rather than marketing.

An AI agent is a software system that maintains a goal-relevant state, observes information from an environment, selects actions, executes those actions through available capabilities, and uses the results to determine what to do next.

A compact abstraction is:

\[
Action_t = Agent(Goal, State_t, Observation_t)
\]

followed by:

\[
State_{t+1}=Update(State_t, Action_t, Observation_{t+1})
\]

The language model may be the central reasoning component, but **agency emerges from the loop around it**.

## A Model Is Not an Agent by Itself

A basic model interaction is:

```text
input
 ↓
model
 ↓
output
```

An agent adds continuity and effect:

```text
goal
 ↓
observe
 ↓
reason
 ↓
act
 ↓
observe result
 ↓
update state
 ↺
```

That distinction explains why a strong language model can still be used in a non-agentic application and why a relatively modest model can become operationally significant when connected to powerful tools.

## Agency Is a System Property

Agency depends on several dimensions:

```text
decision scope
tool authority
memory / persistence
execution duration
ability to replan
```

A useful mental model is a spectrum.

### Level 0 — Generative response

The model produces text only.

### Level 1 — Read-only tool use

The system can retrieve information.

### Level 2 — Reversible actions

It can create drafts, branches, or tickets.

### Level 3 — Multi-step orchestration

It can choose actions iteratively and recover from failures.

### Level 4 — Long-running broad authority

It can act for extended periods across consequential systems.

Risk normally grows with authority and irreversibility, not merely with model intelligence.

## Perception: Turning the Environment into Observations

The perception layer converts raw input into information the agent can use.

Inputs may include:

```text
user messages
API responses
source code
metrics
logs
images
browser state
events
```

Perception is not always an AI problem.

A JSON API should normally be parsed deterministically.

A screenshot may require a multimodal model.

A thousand-line log may first be reduced through structured filtering before it reaches the reasoning model.

Good agents do not use expensive semantic inference where ordinary parsing is sufficient.

## Observation Quality Limits Reasoning Quality

An agent can only reason over what the runtime exposes.

If file discovery omits a malicious script, the model cannot detect it.

If telemetry is stale, planning is stale.

If context loses provenance, the model may treat attacker-controlled text as policy.

Perception therefore needs:

```text
completeness
freshness
provenance
trust labels
normalization
```

The most capable reasoning model cannot compensate reliably for a broken observation layer.

## Working Memory: State for the Current Task

Working memory tracks information needed during the active run:

```text
current goal
plan
open questions
recent observations
intermediate artifacts
```

This may be represented partly in model context and partly in structured runtime state.

The runtime state should remain authoritative.

A long conversation transcript is a poor substitute for explicit state such as:

```yaml
stage: verifying
failed_tests: 2
approval_required: false
```

## Long-Term Memory: Persistence Across Runs

Long-term memory can store preferences, past outcomes, reusable facts, or summaries.

It can improve continuity.

It also introduces new problems:

```text
staleness
contradiction
privacy
poisoning
scope leakage
```

Persistent memory should have source provenance, scope, retention, and write policy.

A model-generated statement should not silently become an authoritative fact for future sessions.

## Procedural Memory: Skills and Runbooks

Another form of memory is procedural knowledge:

```text
how to perform security review
how to triage an incident
how to prepare a release
```

Agent Skills and runbooks can package these procedures without retraining the model.

They reduce the need to reconstruct institutional practice from generic model knowledge.

But they become supply-chain artifacts and must be versioned and reviewed.

## Reasoning and Planning: Choosing the Next Action

Planning decomposes a goal into steps.

For example:

```text
Goal: fix failing CI

1. inspect failure
2. identify likely cause
3. inspect relevant files
4. propose patch
5. run tests
6. evaluate result
```

A rigid plan can become stale after new evidence appears.

Strong agent loops therefore use **rolling planning**:

```text
plan
→ act
→ observe
→ replan
```

This resembles receding-horizon control more than executing a static checklist.

## ReAct: Interleaving Reasoning and Action

ReAct popularized a pattern in which reasoning-like steps and environment actions are interleaved.[^1]

The architectural contribution is not that an application must expose private chain-of-thought text. It is the control pattern:

```text
interpret current state
→ choose action
→ receive observation
→ update decision
```

The loop allows environmental evidence to correct an initial hypothesis.

Modern agents often implement similar control without surfacing hidden reasoning traces.

## Tools Are the Agent's Effectors

Tools connect planning to the world.

Examples:

```text
search
database query
Git
browser
shell
Kubernetes
email
ticketing
```

Tool design determines operational agency.

A model with `read_file` has a different risk profile from one with unrestricted shell and production credentials.

Therefore:

> **The tool surface is part of the agent's security policy.**

## Capability-Oriented Tools Reduce Accidental Authority

Prefer narrow semantic tools:

```text
read_pipeline(project, id)
create_draft_issue(project, finding)
run_tests(repository)
```

rather than universal primitives:

```text
shell(command)
http_request(any_url, any_method, any_body)
```

Generic tools maximize flexibility.

Semantic tools maximize control and interpretability.

A platform can expose both in different sandboxes and risk classes.

## The Action Layer Must Separate Proposal from Permission

The model may choose an action.

The runtime decides whether it is allowed.

```text
model proposal
   ↓
validation
   ↓
authorization
   ↓
policy
   ↓
execution
```

This is the single most important production boundary in agent architecture.

Never treat model confidence as permission.

## Feedback Turns a Tool User into a Control Loop

After a tool executes, the agent observes the result.

A test failure can lead to another patch.

A 403 response can lead to an escalation rather than repeated retries.

A missing document can trigger another search.

The quality of the feedback signal determines whether the agent improves or drifts.

Mechanical signals are especially valuable:

```text
compiler pass/fail
test result
schema validation
policy decision
health metric
```

They provide external anchors to probabilistic reasoning.

## Termination Is a First-Class Design Problem

An agent must know when to stop.

Stopping conditions can include:

```text
goal verified
no progress
budget exhausted
max steps reached
human escalation required
policy denied continuation
```

Without explicit termination, autonomous loops can waste compute or cause repeated side effects.

The runtime should enforce hard budgets even if the model believes another step might help.

## Agent Types Are Architectural Patterns, Not Species

Common labels include:

```text
reactive agent
planning agent
retrieval agent
coding agent
research agent
multi-agent system
```

These categories describe different control structures and tool environments rather than fundamentally different forms of intelligence.

A coding agent is largely a general agent with repository context, file/shell tools, software-engineering procedures, and code-specific evaluators.

## Agents Versus Deterministic Workflows

A deterministic workflow encodes the path before runtime.

An agent synthesizes part of the path from the current state.

```text
Workflow:
state → predefined transition

Agent:
state → model selects bounded transition
```

Production systems often combine both.

A flow can define mandatory stages while an agent chooses the local actions inside each stage.

## Agentic RAG Is a Specialized Agent Pattern

An Agentic RAG system uses its action loop primarily to gather knowledge.

```text
question
→ retrieve
→ evaluate evidence
→ search again
→ synthesize
```

Its authority is largely epistemic.

A general operational agent may additionally change external systems.

This distinction matters because epistemic agency and operational agency have different risk.

## Multi-Agent Systems: Specialization with Coordination Cost

Multiple agents can divide work:

```text
Planner
 ├─ Researcher
 ├─ Implementer
 └─ Reviewer
```

Potential benefits include parallelism, tool specialization, and independent context.

Costs include:

```text
handoff overhead
context duplication
role confusion
circular delegation
higher token usage
more failure surfaces
```

Use multiple agents when the separation has an engineering reason—not merely because organizational roles are intuitive metaphors.

## Handoffs Need Structured Contracts

A good handoff should include:

```yaml
objective: review patch
artifact: commit-sha
constraints:
  - read_only
expected_output: findings_schema
```

The receiving agent should not infer all task state from prose.

Structured handoffs improve reliability and security.

## Identity Makes the Agent a Non-Human Principal

An operational agent needs an identity model.

Avoid simply inheriting the developer's full credentials.

Use:

```text
workload identity
short-lived tokens
delegated scopes
resource-level authorization
```

The audit trail should preserve which human or system initiated the run and which agent performed each action.

## Sandboxing Contains Model and Tool Error

Agents that execute code should operate in isolated environments.

Controls include:

```text
ephemeral filesystem
restricted network
resource limits
credential isolation
timeouts
```

Sandboxing does not make the model correct.

It limits the consequence of being wrong.

## Human-in-the-Loop Should Follow Impact

A read-only search does not need approval every time.

A production database deletion does.

Risk-based approval is stronger than blanket human involvement.

Approval should present exact action parameters and evidence, not merely “the agent wants to continue.”

## Observability: The Agent Is a Trajectory

A conventional request log shows one call.

An agent run may contain dozens of decisions and effects.

Trace:

```text
goal
state transitions
context sources
model calls
tool calls
policy decisions
approvals
memory writes
results
```

This trajectory is the basic debugging and security evidence unit.

## Evaluation Must Include Process Quality

Final-answer correctness is insufficient.

Agent evaluation should measure:

```text
task success
steps taken
tool efficiency
cost
policy violations
recovery behavior
human intervention
side effects
```

Two agents can reach the same answer with radically different operational quality.

## Autonomy Should Expand Through Evidence

A safe adoption path is gradual.

```text
recommend only
→ read-only tools
→ reversible writes
→ bounded workflow control
→ high-impact actions with strong gates
```

Increase authority only when evaluation shows the system performs reliably under realistic and adversarial conditions.

Autonomy is a deployment parameter, not a badge of sophistication.

## The Future: Agentic Computing as a Software Architecture

Traditional applications ask developers to encode much of the control flow.

Agentic applications allow some control-flow selection to occur at runtime:

```text
Goal + State + Capabilities + Constraints
        ↓
Model-mediated decision
        ↓
Bounded action
```

This is a meaningful change in software architecture.

It does not eliminate deterministic software. It increases the importance of deterministic infrastructure around the probabilistic decision layer.

## Conclusion

AI agents are best understood as **goal-directed software systems that close a loop between perception, reasoning, action, and feedback**.

Their defining capabilities—memory, planning, tools, adaptation, and multi-step execution—do not come from the language model alone. They emerge from the runtime architecture around it.

That same architecture determines risk.

The mature design therefore keeps a clear separation:

```text
model decides what may be useful
runtime knows current state
authorization decides what is permitted
tools produce effects
verifiers determine whether the effect succeeded
```

The future of Agentic AI is not maximum autonomy for its own sake. It is **bounded action under explicit state, authority, evidence, and control**.
