## The difference between a tag and an identity

A container image tag looks like an identity but behaves like a pointer. `latest`, a branch tag, and even a semantic-version tag can be retargeted to different content. If an agent runtime approves a tag but executes whatever the registry serves later, review and execution are no longer bound to the same artifact.

Container trust requires immutable identity plus verified origin. Digest pinning answers what bytes are executed; signatures and provenance help establish who produced them and from which source/build process; admission policy ensures those claims are checked at the moment of execution. The original `skil` control model expresses the same idea as `CONTAINER_IMAGE_IDENTITY is mutable_or_unverified OR content_trust_disabled`. That relation is more useful than a label such as “suspicious” because it specifies what must be evidenced and what a legitimate counterexample must break.

## Provenance and the build path

A deliberately small positive fixture from the source property illustrates the boundary:

```yaml
image: registry.example/agent:latest
# or DOCKER_CONTENT_TRUST=0
```

The safe counterexample changes the semantics rather than merely deleting a suspicious token:

```yaml
image: registry.example/agent@sha256:<reviewed-digest>
```

The purpose of pairing them is not to teach exploitation. It is to force the detector to explain which relation changes between the two cases. A scanner that fires on both has learned vocabulary; a scanner that can explain the difference has begun to model the security property.

## Digest pinning

Tags are convenient release labels, not cryptographic identities. Pinning an image by digest prevents silent content substitution. Operational systems can still retain a human-friendly tag in metadata while enforcing the digest at admission. In an agentic environment this distinction becomes operational because model-generated plans can select the relevant value or capability at runtime. The host therefore needs evidence that can survive from code review into execution policy.

## Signatures and trusted subjects

Sigstore-style signing can bind an artifact digest to an identity and transparency log evidence. Verification policy must define which issuers and subjects are trusted; a valid signature from an arbitrary identity is not sufficient. The design implication is that detection and authorization must remain separate: the scanner identifies the condition, while a policy layer decides whether the condition is permissible in this deployment context.

## Provenance answers a different question

SLSA provenance links build outputs to source and build process. It complements signatures and digest pinning by making the production path reviewable. Provenance should be verified against expected repositories, builders and parameters. This also improves explainability. Reviewers can see the specific security fact rather than receiving a generic severity label, and future tooling can compose that fact with independent findings without double-counting the same evidence.

## Registry and transport policy still matter

Insecure registries, disabled verification, credential leakage and overly broad pull permissions can undermine an otherwise pinned deployment. Registry endpoints and authentication are part of the trust boundary, not mere plumbing. A useful implementation records both the positive observation and the guard that would have made the path safe. That makes remediation testable and turns false-positive handling into explicit logic instead of a collection of suppressions.

## Admission is the decisive control point

CI can validate an image, but production should revalidate identity and policy before starting the workload. This closes time-of-check/time-of-use gaps and prevents a later deployment path from bypassing earlier security evidence. The same model supports change detection: when identity, configuration or code changes, the platform can recompute the relation and show exactly which part of the previously reviewed assumption no longer holds.

## Admission as the final verification point

Detection quality depends on traceability. The scanner should preserve the raw location, the property-specific observation produced by trust-disable flags + mutable image identity detection, and the reasoning that turns it into `CONTAINER_IMAGE_IDENTITY is mutable_or_unverified OR content_trust_disabled`. The native control surface is `SKIL-CONTAINER-TRUST`, `SKIL-BOUNDARY-MUTABLE-IMAGE`. Because the stated coverage is FULL, confidence must follow evidence completeness—not severity labels or lexical suspicion.

A compact machine-readable evidence record can retain the essentials without pretending to encode the entire analysis:

## False positives, ambiguity, and safe counterexamples

Development environments may intentionally use mutable tags for iteration. The detector should distinguish local/test contexts from release manifests and escalate when mutable identity enters a production or privileged agent runtime.

Static analysis has an epistemic boundary: it can only reason about the representation it sees. Dynamic DNS, runtime-generated code, reflection, remote configuration, credential brokers and policy decisions may exist outside that view. The correct result vocabulary therefore includes states such as `verified`, `partially_resolved`, `provider_backed`, `runtime_dependent`, and `not_observable`. This is not bureaucratic metadata; it prevents a consumer from interpreting an absent finding as proof that no risk exists.

## Development exceptions without production drift

Enforce digest-pinned images, trusted signer identities, provenance policy, non-root execution and restricted capabilities. Keep image verification evidence alongside the agent task so audits can tie an autonomous action to the exact workload image that performed it.

Defense in depth is intentionally redundant. Authoring lint, static analysis, contract verification, supply-chain verification, runtime policy and audit telemetry answer different questions. A strong result from one layer should never be used as a reason to remove the others.

## Evidence and auditability

A serious regression suite needs paired examples. Each positive fixture should have a near-neighbor negative case, and each new false positive should become a permanent test. Where the property depends on identity or time, tests should also change the resolved artifact or metadata between review and execution. Where it depends on data flow, fixtures should exercise aliases, wrappers and valid sanitizers. For **Container Trust for Agentic Workloads**, the most valuable tests are those that preserve the surface appearance while changing the underlying security relation; that is how the suite verifies semantics instead of vocabulary.

For `skil`, implementation claims should be checked against the repository’s control matrix, external-control crosswalk, analyzer tests and any provider-specific tests. Provider-backed coverage—such as OSV or external rule packs—must state whether the provider actually ran.

## Architecture drill-down: from finding to enforceable boundary

For **Container Trust for Agentic Workloads**, think in terms of a chain of custody for security meaning. The artifact creates an observation, trust-disable flags + mutable image identity detection converts that observation into a structured fact, contract or policy logic interprets the fact, and runtime enforcement decides whether the operation can proceed. Each handoff can lose context. The relation `CONTAINER_IMAGE_IDENTITY is mutable_or_unverified OR content_trust_disabled` should therefore be represented explicitly in evidence rather than reconstructed from a human-readable message after the fact. Reviewers should inspect whether normalization is reversible for forensics, whether identity is immutable between review and use, whether policy is scoped to the task, and whether provider failures are visible. This turns a static finding into an assurance argument that can survive deployment changes.

The paired fixtures also serve as an architectural regression test. The unsafe example begins with `image: registry.example/agent:latest` while the safe example begins with `image: registry.example/agent@sha256:<reviewed-digest>`. The important difference is the security relation, not the cosmetic text. If a refactor causes both to produce the same result, the detector or policy has lost a meaningful distinction.

## Common implementation traps

Several implementation mistakes recur around **Container Trust for Agentic Workloads**, even when the high-level policy is correct:

**1. Assuming a name or version string uniquely identifies an artifact.** Registry, digest, publisher, platform variant and provenance may all be relevant to the reviewed identity. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**2. Running provider-backed checks without surfacing provider failure or staleness.** An unavailable advisory or reputation service must not be reported as a clean scan. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**3. Treating a supply-chain finding as timeless.** Reputation, tags, signatures and external artifacts change, so admission-time revalidation is part of the control. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

A useful review discipline is to turn every exception into a scoped, expiring artifact with an owner and rationale. Permanent blanket suppressions hide whether the architecture improved; narrow exceptions preserve the signal and make technical debt measurable.

## How this property composes with adjacent findings

**Mutable image plus privileged workload.** A mutable image reference becomes substantially more serious when the workload is privileged, mounts the container runtime socket, or receives production credentials. Image identity and workload authority are independent dimensions; combining them exposes the true blast radius without conflating the controls.

This composition model is deliberately graph-like: each detector contributes a typed fact and shared evidence identifiers allow a higher-level policy engine to connect them. That prevents one rule from becoming an overloaded catch-all and makes severity escalation explainable.

## Operational signals and measurable assurance

Track digest-pinned image coverage, signature/provenance verification success, mutable tags reaching production manifests, admission denials, and signer/issuer policy failures. Report development exceptions separately from production drift.

Metrics should be tied to an explicit denominator and deployment profile. A low finding count may mean strong controls, weak coverage, or simply little exposure; telemetry and coverage state are needed to tell those cases apart. Trend the data over time and review unexpected changes in both positive findings and scanner-negative regression behavior.

## Engineering implications beyond the scanner

Supply-chain properties are time-sensitive. Package reputation, advisory state, tags, signatures and provenance can change independently of source code. Production systems should therefore store the identity and evidence that was reviewed, re-resolve it at admission, and surface any delta. A clean repository scan from last week is not sufficient evidence for an artifact resolved from a mutable external namespace today.

The broader lesson is that an agentic skill is simultaneously text, code, configuration, a tool contract and a supply-chain artifact. Security review should follow the boundary that is actually crossed—data, authority, identity, execution, or control-plane visibility—rather than forcing every risk into the same detection template.

## A production hardening model

A reviewer should be able to answer four questions before accepting this property as controlled:

1. **What exact security relation is being asserted?** Here it is `CONTAINER_IMAGE_IDENTITY is mutable_or_unverified OR content_trust_disabled`.
2. **What concrete evidence supports the relation?** The evidence must come from trust-disable flags + mutable image identity detection, not from a keyword alone.
3. **What near-neighbor safe case has been tested?** The paired negative fixture should differ in the property, not merely in spelling.
4. **What remains outside static visibility?** Runtime identity, dynamic values, provider state and policy decisions must be named explicitly.

## Conclusion

**Container Trust for Agentic Workloads** is valuable only when it is treated as a falsifiable security property rather than a checklist term. The goal is not to declare an entire skill “malicious” or “safe.” The goal is to state what boundary may be crossed, show the evidence that supports that statement, preserve the coverage limits, and make the safe countercondition explicit. That produces findings engineers can test, reviewers can reproduce, and runtime policy can enforce.
