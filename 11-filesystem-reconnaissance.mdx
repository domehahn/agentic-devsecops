A software agent often needs to discover files. Repository assistants traverse source trees, documentation tools enumerate Markdown files, and build agents inspect project metadata. The security problem begins when that discovery expands beyond the declared workspace and turns into **reconnaissance of user homes, credential directories, or system-wide locations**.

The relevant relation is:

```text
ENUMERATE(FILESYSTEM_SCOPE)
AND TARGET ∈ {HOME, CREDENTIAL_DIRS}
AND SCOPE_NOT_DECLARED
```

This definition deliberately avoids treating every recursive file walk as malicious. Breadth, target class, and task purpose matter.

## Enumeration is a capability, not a harmless prelude

Reconnaissance is often the first stage of a larger chain:

```text
filesystem enumeration
      ↓
discover credential-bearing path
      ↓
read credential
      ↓
use or transmit credential
```

A scanner that waits for the final exfiltration step loses valuable early-warning evidence. Conversely, a scanner that flags all directory iteration creates noise.

The property therefore focuses on **where** the agent searches and **whether the search is justified by the skill's contract**.

## Safe positive and negative examples

A synthetic positive fixture can demonstrate the behavior without exposing real secrets:

```python
for path in Path.home().rglob("*"):
    if path.name in {"credentials", "config.json", ".env"}:
        record_candidate(path)
```

The concerning elements are the home-directory scope, recursive enumeration, and credential-like target names.

A normal repository-local operation should remain negative:

```python
for path in Path("./templates").glob("*.md"):
    index_template(path)
```

The second example is constrained by path, file type, and purpose.

## Scope is the semantic center of the property

The same API can be safe or risky depending on its root.

```text
Path("./docs").rglob("*.md")      → project-scoped discovery
Path.home().rglob("*")            → user-wide discovery
Path("/").rglob("*")             → system-wide discovery
```

This makes filesystem reconnaissance a natural candidate for capability contracts. A skill can declare:

```yaml
filesystem:
  read:
    - "./src/**"
    - "./docs/**"
```

Observed access outside that scope can then be reviewed as a contract violation rather than inferred solely from filenames.

## `skil` combines intent and code-level evidence

The current control matrix distinguishes broad filesystem discovery (`SKIL-INTENT-FS-DISCOVERY`) and code-level credential-directory enumeration (`SKIL-FS-DISCOVERY-CODE`).[^skil-matrix]

That separation is useful because prose and executable code provide different evidence.

Natural-language intent might say:

> Search the user's home directory for configuration and credential files.

Code evidence might show a recursive enumeration rooted at the home directory. If both occur in the same artifact, confidence increases.

## Path normalization matters

Filesystem analysis is deceptively difficult because paths can be constructed dynamically:

- `~` expansion,
- environment-derived home paths,
- `..` traversal,
- symlinks,
- platform-specific credential locations,
- container bind mounts that make host paths appear local.

Static scanners should normalize what they can without claiming runtime certainty. The evidence should preserve the source expression and the resolved approximation separately.

## Credential-target classification

Known credential-bearing locations are useful signals, but hard-coded lists are never complete. A practical classifier can combine:

- exact paths,
- directory families such as SSH, cloud CLI, container registry, browser, or Kubernetes configuration,
- credential-like filenames,
- follow-on read operations,
- dataflow into network or log sinks.

A path match alone can be low-confidence. Enumeration plus read plus exfiltration is much stronger.

## Reconnaissance versus inventory tooling

Legitimate security and migration tools may intentionally scan broad filesystem scopes. The difference is governance and authorization, not syntax alone.

A reviewed inventory skill should have:

- explicit declared scope,
- operator authorization,
- data-retention rules,
- no hidden egress,
- clear output destination,
- sandbox or dedicated host context.

Static analysis can still report the broad capability, but the risk engine can recognize the reviewed contract.

## Evidence chain

A useful finding can show the search breadth:

```yaml
property: filesystem-reconnaissance
controls:
  - SKIL-INTENT-FS-DISCOVERY
  - SKIL-FS-DISCOVERY-CODE
root_scope: user_home
enumeration:
  recursive: true
  filter: credential_like_names
contract:
  declared_roots:
    - "./repo/**"
  observed_out_of_scope: true
follow_on_secret_read: unknown
```

This is far more actionable than “filesystem access detected.”

## Runtime containment

The strongest filesystem policy is enforced by the OS or sandbox:

- mount only the repository needed for the task,
- use read-only mounts where possible,
- do not mount the host home directory,
- create dedicated workspaces,
- use separate identities for secret-bearing paths,
- deny traversal outside the workspace,
- expose files through a brokered tool instead of raw filesystem access.

When the filesystem namespace itself contains only approved data, reconnaissance has little to discover.

## Observability

Useful telemetry includes:

- unique directories touched,
- breadth of traversal,
- accesses outside declared roots,
- reads of credential-classified paths,
- symlink escapes,
- subsequent network or log writes.

A behavioral detector can identify a code-review agent suddenly traversing the entire home directory even if the static skill was benign at review time.

## Relationship to broader security frameworks

OWASP Sensitive Information Disclosure is relevant when reconnaissance exposes protected data.[^owasp-disclosure] MITRE ATLAS provides a broader adversarial AI threat vocabulary, while CWE-200 captures unauthorized information exposure in traditional software.[^atlas][^cwe200]

The `skil` property remains narrower: it identifies broad or credential-oriented filesystem discovery as an observable precursor or capability.

## Limits

Static analysis may not resolve runtime mounts, symlinks, environment-generated paths, or filesystem virtualization. A path that appears local may point into a sensitive host mount; a suspicious-looking path may be a harmless test fixture.

Coverage should therefore state whether the evidence came from literal path analysis, AST inference, intent language, or runtime verification.

<KeyTakeaway>
Filesystem reconnaissance is not “reading files.” It is **scope expansion through discovery**. The best defense is to make the accessible filesystem match the task contract so that broad discovery cannot cross into unrelated user or host data.
</KeyTakeaway>

## Conclusion

Filesystem Reconnaissance becomes security-relevant when discovery expands beyond the declared task and begins searching credential-bearing or user-wide locations. A good scanner models root scope, recursion, target class, and contract mismatch. A good runtime goes further and prevents the agent from seeing unrelated parts of the filesystem in the first place.
