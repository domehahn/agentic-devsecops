Nicht jedes Artefakt liegt in Git. Direkte HTTPS-Links zu Archiven, Textdateien oder veröffentlichten Paketen können deshalb eine sinnvolle Scanquelle sein. Die Flexibilität darf jedoch nicht in einen universellen URL-Fetcher ohne Sicherheitsgrenzen ausarten.

Das Feature ist damit nicht nur eine Komfortfunktion.

Es verändert, **welcher Kontext geprüft wird, welche Vertrauensgrenzen gelten und wie belastbar das Ergebnis später in CI/CD oder Security-Governance verwendet werden kann**.

## Was das Feature leistet

Bei einer generischen Remote-URL lädt der Scanner eine Ressource kontrolliert herunter, bestimmt ihren Typ und übergibt sie an die passende Analysepipeline. Der Downloader ist damit ein sicherheitskritischer Teil des Systems.

Relevante Eigenschaften sind Protokoll-Policy, Redirect-Verhalten, DNS-Auflösung, Größenlimits, Content-Type-Abgleich, Zertifikatsprüfung und optional ein erwarteter Digest. Die Herkunft sollte im Report als Provenienz erhalten bleiben.

## Typischer Ablauf

Unabhängig von der konkreten Implementierung sollte der Ablauf klar getrennte Phasen besitzen:

```text
Input
  ↓
Validierung und Normalisierung
  ↓
Feature-spezifische Verarbeitung
  ↓
Security-Analyse
  ↓
Findings + Coverage + technischer Status
  ↓
Policy-Entscheidung
```

Diese Trennung ist wichtig, weil ein technischer Fehler bei Beschaffung, Parsing oder Providerzugriff nicht dieselbe Bedeutung hat wie ein tatsächlich unauffälliges Prüfergebnis.

## Negatives Beispiel

Ein Dienst akzeptiert jede URL:

```text
http://169.254.169.254/latest/meta-data/
http://localhost:8080/admin
file:///etc/passwd
```

Der Scanner wird dadurch unfreiwillig zu einem SSRF-Proxy oder lokalen Dateileser. Selbst bei HTTPS können Redirects von einem erlaubten Host in private Netze führen.

Das Problem liegt nicht in der späteren Inhaltsanalyse, sondern in der unkontrollierten Beschaffung.

## Positives Beispiel

Eine sichere Remote-Fetch-Policy kann so aussehen:

```yaml
remote:
  enabled: true
  schemes: [https]
  allowed_hosts:
    - releases.example.invalid
  max_bytes: 52428800
  redirects: 2
  block_private_networks: true
```

Optional wird ein erwarteter Hash mitgegeben:

```text
url + sha256 -> fetch -> verify -> scan
```

Erst nach erfolgreicher Herkunfts- und Integritätsprüfung beginnt die eigentliche Analyse.

<KeyTakeaway>
Remote-URL-Support ist ein Beschaffungsfeature mit SSRF-Risiko. Sicherheit entsteht durch Protokoll-, Host-, Netzwerk- und Größenpolicy vor dem ersten Byte der Analyse.
</KeyTakeaway>

## Security- und Betriebsaspekte

Wichtig sind Schutz gegen DNS Rebinding, Redirect-Ketten, private IP-Bereiche, ungewöhnliche Ports und unbeschränkte Downloads. Der HTTP-Client sollte keine Browser-Cookies oder globale Zugangsdaten übernehmen.

Für sensitive Umgebungen kann ein dedizierter Fetcher in einem isolierten Netzwerksegment sinnvoll sein. Der Scanner erhält dann nur das bereits kontrolliert beschaffte Artefakt.

Ein professioneller Betrieb sollte außerdem drei Zustände konsequent auseinanderhalten:

```text
clean      = geprüft, kein relevanter Befund
finding    = geprüft, mindestens ein relevanter Befund
incomplete = Prüfung technisch oder fachlich nicht vollständig
```

Gerade der dritte Zustand ist für DevSecOps entscheidend.

Ein Scanner darf fehlende Coverage nicht als positives Sicherheitsurteil darstellen.

## Wo das Feature sinnvoll eingesetzt wird

Die Funktion eignet sich für Release-Artefakte, interne Downloadportale, Objekt-Storage oder statische Artefaktserver. Sie ist besonders nützlich, wenn ein standardisierter API-Aufruf beliebige unterstützte Dateiformate annehmen soll.

Wenn die Quelle aus Git stammt, liefert ein Git-spezifischer Modus bessere Provenienz. Für lokale Dateien sollte kein Netzwerkpfad verwendet werden.

Die konkrete Aktivierung sollte deshalb aus dem gewünschten Trust-Modell abgeleitet werden und nicht allein aus technischer Verfügbarkeit.

## Integration in eine DevSecOps-Pipeline

In einer Pipeline sollte das Feature nicht isoliert betrachtet werden.

Ein belastbares Muster ist:

```text
Source / Artifact
      ↓
Input-Validierung
      ↓
Deterministische Analyse
      ↓
optionale erweiterte Analyse
      ↓
normalisierte Findings
      ↓
Policy Gate
      ↓
Report / Audit Evidence
```

Dabei sollte jeder Report mindestens folgende Informationen transportieren:

- Identität des analysierten Artefakts
- aktive Analyseverfahren
- übersprungene oder nicht verfügbare Prüfschritte
- stabile Regel- oder Finding-IDs
- Schweregrad und Evidenz
- Scanner- und Regelversion
- eindeutiger technischer Abschlussstatus

Damit wird das Feature nicht nur ausführbar, sondern **auditierbar**.

## Fazit

Remote-URL-Support ist ein Beschaffungsfeature mit SSRF-Risiko. Sicherheit entsteht durch Protokoll-, Host-, Netzwerk- und Größenpolicy vor dem ersten Byte der Analyse.

Der eigentliche Wert entsteht dann, wenn das Feature mit klaren Grenzen, reproduzierbaren Eingaben und transparenten Ergebnissen in den Entwicklungsprozess eingebettet wird.
