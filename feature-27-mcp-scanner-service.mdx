Ein Scanner als MCP-Service macht Sicherheitsanalyse direkt für agentische Workflows verfügbar. Statt Shell-Kommandos zu konstruieren, kann ein Client eine klar beschriebene Tool-Schnittstelle mit typisierten Parametern aufrufen.

Das Feature ist damit nicht nur eine Komfortfunktion.

Es verändert, **welcher Kontext geprüft wird, welche Vertrauensgrenzen gelten und wie belastbar das Ergebnis später in CI/CD oder Security-Governance verwendet werden kann**.

## Was das Feature leistet

Der Service exponiert beispielsweise Operationen für Datei-, Verzeichnis- oder Textanalyse und liefert strukturierte Findings zurück. Das erlaubt kontrollierte Integration in Orchestratoren, Entwicklungsumgebungen und automatisierte Review-Flows.

Wichtig ist, dass MCP nur die Aufrufschnittstelle standardisiert. Dateizugriff, Netzwerkzugriff, Authentisierung und Mandantentrennung bleiben Aufgaben des Service-Designs.

## Typischer Ablauf

Unabhängig von der konkreten Implementierung sollte der Ablauf klar getrennte Phasen besitzen:

```text
Input
  ↓
Validierung und Normalisierung
  ↓
Feature-spezifische Verarbeitung
  ↓
Security-Analyse
  ↓
Findings + Coverage + technischer Status
  ↓
Policy-Entscheidung
```

Diese Trennung ist wichtig, weil ein technischer Fehler bei Beschaffung, Parsing oder Providerzugriff nicht dieselbe Bedeutung hat wie ein tatsächlich unauffälliges Prüfergebnis.

## Negatives Beispiel

Ein Tool akzeptiert einen beliebigen Serverpfad:

```json
{
  "path": "/"
}
```

und der Service läuft mit weitreichenden Dateirechten. Ein Client kann damit nicht nur das gewünschte Projekt, sondern das gesamte Dateisystem zur Analyse und damit potenziell zur Datenexposition bringen.

## Positives Beispiel

Der Service arbeitet mit expliziten Workspaces:

```text
workspace_id -> serverseitig freigegebener Root
requested_path -> muss innerhalb dieses Roots liegen
```

Das Tool-Schema erlaubt nur relative Pfade. Authentisierung, Quota und maximale Artefaktgröße werden vor dem Scan geprüft. Ergebnisse enthalten eine Job-ID und strukturierte Findings, keine internen absoluten Pfade.

<KeyTakeaway>
MCP macht den Scanner als Tool adressierbar, aber nicht automatisch sicher. Workspace-Grenzen, Authentisierung und ressourcenbezogene Policies bestimmen den tatsächlichen Trust Boundary.
</KeyTakeaway>

## Security- und Betriebsaspekte

MCP-Toolbeschreibungen sind selbst Teil der Prompt-Oberfläche. Beschreibungen sollten sachlich sein und keine dynamisch eingefügten untrusted Anweisungen enthalten. Server müssen zudem gegen Path Traversal, SSRF, Resource Exhaustion und Cross-Tenant-Leaks gehärtet werden.

Bei schreibenden Zusatzfunktionen sollte Least Privilege strikt gelten; ein Scanner benötigt in der Regel keinen Schreibzugriff auf den Quellworkspace.

Ein professioneller Betrieb sollte außerdem drei Zustände konsequent auseinanderhalten:

```text
clean      = geprüft, kein relevanter Befund
finding    = geprüft, mindestens ein relevanter Befund
incomplete = Prüfung technisch oder fachlich nicht vollständig
```

Gerade der dritte Zustand ist für DevSecOps entscheidend.

Ein Scanner darf fehlende Coverage nicht als positives Sicherheitsurteil darstellen.

## Wo das Feature sinnvoll eingesetzt wird

Geeignet für zentrale Security Services, AI-gestützte Entwicklungsumgebungen und orchestrierte Review-Prozesse. Der MCP-Service kann eine einheitliche Schnittstelle über lokale und entfernte Scans legen.

Für einfache CI-Läufe bleibt eine CLI oft leichter zu betreiben.

Die konkrete Aktivierung sollte deshalb aus dem gewünschten Trust-Modell abgeleitet werden und nicht allein aus technischer Verfügbarkeit.

## Integration in eine DevSecOps-Pipeline

In einer Pipeline sollte das Feature nicht isoliert betrachtet werden.

Ein belastbares Muster ist:

```text
Source / Artifact
      ↓
Input-Validierung
      ↓
Deterministische Analyse
      ↓
optionale erweiterte Analyse
      ↓
normalisierte Findings
      ↓
Policy Gate
      ↓
Report / Audit Evidence
```

Dabei sollte jeder Report mindestens folgende Informationen transportieren:

- Identität des analysierten Artefakts
- aktive Analyseverfahren
- übersprungene oder nicht verfügbare Prüfschritte
- stabile Regel- oder Finding-IDs
- Schweregrad und Evidenz
- Scanner- und Regelversion
- eindeutiger technischer Abschlussstatus

Damit wird das Feature nicht nur ausführbar, sondern **auditierbar**.

## Fazit

MCP macht den Scanner als Tool adressierbar, aber nicht automatisch sicher. Workspace-Grenzen, Authentisierung und ressourcenbezogene Policies bestimmen den tatsächlichen Trust Boundary.

Der eigentliche Wert entsteht dann, wenn das Feature mit klaren Grenzen, reproduzierbaren Eingaben und transparenten Ergebnissen in den Entwicklungsprozess eingebettet wird.
