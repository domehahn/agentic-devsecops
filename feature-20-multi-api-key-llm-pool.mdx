Ein Pool aus mehreren API-Keys kann Rate Limits verteilen, Mandanten trennen oder Failover ermöglichen. Gleichzeitig vervielfacht er die Anzahl sensibler Secrets und benötigt eine explizite Routing- und Auditstrategie.

Das Feature ist damit nicht nur eine Komfortfunktion.

Es verändert, **welcher Kontext geprüft wird, welche Vertrauensgrenzen gelten und wie belastbar das Ergebnis später in CI/CD oder Security-Governance verwendet werden kann**.

## Was das Feature leistet

Der Pool verwaltet mehrere Zugangsdaten für denselben oder verschiedene Modellendpunkte. Ein Scheduler wählt einen gültigen Schlüssel anhand von Quota, Fehlerzustand, Mandant oder Priorität.

Security-relevant ist, dass die Auswahl deterministisch erklärbar bleibt. Ein Finding sollte nicht den Secret-Wert enthalten, aber nachvollziehbar machen können, über welches Providerprofil oder welche logische Credential-ID der Request lief.

## Typischer Ablauf

Unabhängig von der konkreten Implementierung sollte der Ablauf klar getrennte Phasen besitzen:

```text
Input
  ↓
Validierung und Normalisierung
  ↓
Feature-spezifische Verarbeitung
  ↓
Security-Analyse
  ↓
Findings + Coverage + technischer Status
  ↓
Policy-Entscheidung
```

Diese Trennung ist wichtig, weil ein technischer Fehler bei Beschaffung, Parsing oder Providerzugriff nicht dieselbe Bedeutung hat wie ein tatsächlich unauffälliges Prüfergebnis.

## Negatives Beispiel

Mehrere Keys stehen als kommaseparierte Umgebungsvariable bereit:

```text
LLM_KEYS=key1,key2,key3,key4
```

Der Client wählt zufällig und loggt bei Fehlern die komplette Konfiguration. Ein einziger Debug-Stacktrace exponiert alle Zugangsdaten. Außerdem können Keys unterschiedlicher Mandanten vermischt werden.

## Positives Beispiel

Der Pool nutzt Secret-Referenzen und logische IDs:

```yaml
credentials:
  - id: team-a-primary
    secret_ref: vault://llm/team-a/primary
  - id: team-a-secondary
    secret_ref: vault://llm/team-a/secondary
```

Routing berücksichtigt Quota und Health, ohne Secrets in den Prozesslogs offenzulegen. Metriken arbeiten mit `credential_id`, nicht mit dem Schlüssel selbst.

<KeyTakeaway>
Mehr Zugangsdaten erhöhen Kapazität und Ausfallsicherheit, aber auch Secret-Risiko. Ein Key-Pool braucht Identität, Rotation, Isolation und erklärbares Routing.
</KeyTakeaway>

## Security- und Betriebsaspekte

Rotation, Revocation, Least Privilege und Tenant Isolation sind zentral. Keys sollten nicht gemeinsam in einer einzelnen Datei oder Environment-Variable liegen. Circuit Breaker verhindern, dass ein gesperrter Key bei jedem Request erneut versucht wird.

Ein Failover auf einen anderen Provider kann außerdem Datenresidenz oder Vertragsbedingungen ändern und sollte deshalb policy-gesteuert erfolgen.

Ein professioneller Betrieb sollte außerdem drei Zustände konsequent auseinanderhalten:

```text
clean      = geprüft, kein relevanter Befund
finding    = geprüft, mindestens ein relevanter Befund
incomplete = Prüfung technisch oder fachlich nicht vollständig
```

Gerade der dritte Zustand ist für DevSecOps entscheidend.

Ein Scanner darf fehlende Coverage nicht als positives Sicherheitsurteil darstellen.

## Wo das Feature sinnvoll eingesetzt wird

Sinnvoll bei hoher Parallelität, mehreren Teams, gestaffelten Quotas oder Verfügbarkeitsanforderungen. Für kleine lokale Workflows erhöht ein Key-Pool dagegen unnötig die Komplexität.

Wenn möglich, sind Workload-Identitäten oder kurzlebige Tokens langfristig robuster als große statische Key-Sammlungen.

Die konkrete Aktivierung sollte deshalb aus dem gewünschten Trust-Modell abgeleitet werden und nicht allein aus technischer Verfügbarkeit.

## Integration in eine DevSecOps-Pipeline

In einer Pipeline sollte das Feature nicht isoliert betrachtet werden.

Ein belastbares Muster ist:

```text
Source / Artifact
      ↓
Input-Validierung
      ↓
Deterministische Analyse
      ↓
optionale erweiterte Analyse
      ↓
normalisierte Findings
      ↓
Policy Gate
      ↓
Report / Audit Evidence
```

Dabei sollte jeder Report mindestens folgende Informationen transportieren:

- Identität des analysierten Artefakts
- aktive Analyseverfahren
- übersprungene oder nicht verfügbare Prüfschritte
- stabile Regel- oder Finding-IDs
- Schweregrad und Evidenz
- Scanner- und Regelversion
- eindeutiger technischer Abschlussstatus

Damit wird das Feature nicht nur ausführbar, sondern **auditierbar**.

## Fazit

Mehr Zugangsdaten erhöhen Kapazität und Ausfallsicherheit, aber auch Secret-Risiko. Ein Key-Pool braucht Identität, Rotation, Isolation und erklärbares Routing.

Der eigentliche Wert entsteht dann, wenn das Feature mit klaren Grenzen, reproduzierbaren Eingaben und transparenten Ergebnissen in den Entwicklungsprozess eingebettet wird.
