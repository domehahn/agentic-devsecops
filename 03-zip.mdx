ZIP-Dateien sind ein naheliegendes Distributionsformat für Agent Skills. Genau deshalb muss ein Security Scanner das Archiv **vor** Installation oder Extraktion in eine vertrauenswürdige Zielumgebung analysieren können.

Der Scanner schützt dabei nicht nur vor bösartigem Skill-Inhalt. Bereits die Archivstruktur selbst kann Angriffsfläche sein: Path Traversal, Symlinks, doppelte Einträge oder extreme Größenverhältnisse können einen unsicheren Loader kompromittieren.

<Architecture>
Der Archive Loader gehört zur Security Boundary des Scanners. Ein perfekter Analyzer hilft nicht, wenn das Entpacken des Prüflings bereits den Host kompromittieren kann.
</Architecture>

## Was das Feature wirklich bedeutet

Archive Security beginnt vor dem ersten Analyzer. Ein robustes Design trennt zwei Phasen: zuerst entsteht aus den unvertrauenswürdigen Bytes ein begrenztes, kanonisches Artefakt; erst danach laufen Prompt-, Code-, Dependency- oder Malware-Analysen.

Das klassische Beispiel ist Zip Slip: Ein Eintrag wie `../../.ssh/authorized_keys` darf niemals außerhalb eines temporären Extraktionsverzeichnisses geschrieben werden.

## SkillSpector

SkillSpector unterstützt lokale ZIP-Dateien und erkennt auch heruntergeladene ZIP-Inhalte. Der Input Handler prüft beim Entpacken, ob der aufgelöste Zielpfad innerhalb des Extraktionsverzeichnisses bleibt. Damit wird die zentrale Zip-Slip-Klasse abgefangen.

Die ZIP-Unterstützung ist direkt Teil des normalen `scan`-Workflows.

## `skil`

`skil` behandelt ZIP als eines der nativen Artefaktformate. Die Dokumentation nennt neben Path Traversal auch absolute Pfade, Symlinks, Duplikate, Case Collisions, Dateigrößen, Dateizahl und Dekompressionsbomben als Loader-Grenzen.

Das ist architektonisch bedeutsam: Die Archive-Härtung ist Teil des Artefaktmodells und nicht nur eine Vorstufe außerhalb des Scanners.

## Praxisbeispiel

```bash
skillspector scan ./release/my-skill.zip --no-llm
skil scan ./release/my-skill.zip --static-only
```

Ein CI-Job kann das tatsächlich veröffentlichte ZIP scannen, statt nur den Quellordner. Das entdeckt zusätzlich Packaging-Probleme: versehentlich eingepackte Secrets, generierte Binärartefakte oder Dateien, die lokal gar nicht Teil des erwarteten Skills waren.

## Security- und DevSecOps-Einordnung

- Das veröffentlichte Archiv scannen, nicht ausschließlich den Source Tree.
- Archivextraktion mit Pfad-, Link-, Größen- und Mengenlimits absichern.
- Digest des analysierten Pakets erfassen, damit Scan und ausgeliefertes Artefakt zusammengehören.
- Unterschiede zwischen Source Directory und Release Archive als Supply-Chain-Signal behandeln.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

## Typische Fehlinterpretation

„ZIP ist nur ein Transportcontainer; nach dem Entpacken ist alles gleich.“ Das ignoriert, dass die Extraktion selbst angegriffen werden kann und dass das veröffentlichte ZIP andere Dateien enthalten kann als der lokale Source Tree.

## Einordnung in die Pipeline

Dieses Feature gehört in die **Ingestion-Stufe** der Pipeline. Bevor Analyzer oder Policies überhaupt laufen, muss klar sein, welches Artefakt gelesen wird, wie es kanonisiert wird und welche zusätzlichen Fähigkeiten – insbesondere Netzwerk – dafür notwendig sind.

Ein belastbares Muster ist: Input auflösen → Digest/Manifest erzeugen → statisch analysieren → Report/Evidence speichern. Bei Remote-Eingaben sollte der Netzwerkzugriff in einem eigenen Job oder Runner-Profil aktiviert werden.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Beide unterstützen ZIP. `skil` dokumentiert einen breiteren Satz expliziter Loader-Grenzen; SkillSpector besitzt ebenfalls eine konkrete Zip-Slip-Prüfung. Für produktive Pipelines sollte das ZIP nach dem Build erneut analysiert werden.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
