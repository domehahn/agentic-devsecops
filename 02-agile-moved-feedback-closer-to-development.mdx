By the end of the twentieth century, software engineering had accumulated process, planning, modeling, testing, and project-management techniques. But software projects still faced a fundamental problem: teams could spend a long time implementing assumptions before discovering that those assumptions were wrong.

The Agile Manifesto, published in 2001, captured a different emphasis. Its four value statements favored individuals and interactions, working software, customer collaboration, and responding to change—without claiming that processes, documentation, contracts, or plans had no value.[^manifesto]

The principles behind the manifesto made the feedback objective even clearer: deliver valuable software early and continuously, deliver working software frequently, welcome changing requirements, and treat working software as the primary measure of progress.[^principles]

## The important change was feedback

The shift can be modeled as:

```text
plan
  ↓
large implementation phase
  ↓
integration
  ↓
customer feedback
```

becoming closer to:

```text
small change
  ↓
working software
  ↓
feedback
  ↓
next change
```

Shorter cycles reduce the amount of unvalidated work accumulated between decisions.

<KeyTakeaway>
Agile's most durable contribution was not a meeting format. It was the idea that software development should continuously produce evidence about whether the team is building the right thing.
</KeyTakeaway>

## Working software became a feedback mechanism

A specification can be reviewed.

A design can be discussed.

But working software exposes assumptions that documents can hide:

- integration problems,
- usability problems,
- incorrect requirements,
- performance constraints,
- missing edge cases,
- operational dependencies.

Frequent delivery therefore changes more than project management. It changes how knowledge is produced.

## Agile created pressure on engineering practices

If teams want to integrate and deliver frequently, several technical practices become increasingly important:

```text
version control
automated builds
automated testing
frequent integration
deployable environments
small changes
```

The Agile Manifesto itself does not prescribe a CI/CD implementation. But its principles create strong incentives for engineering practices that make frequent working software economically possible.[^principles]

## Continuous Integration fits the feedback model

Martin Fowler defines Continuous Integration as a practice in which team members merge changes into a shared codebase at least daily and automated builds and tests verify those integrations.[^fowler-ci]

That addresses an old software-engineering problem: integration risk.

Instead of discovering after weeks or months that two branches no longer fit together:

```text
change
change
change
change
     ↓
big integration event
```

teams continuously test:

```text
change → integrate → test
change → integrate → test
```

The principle is the same as Agile feedback: shorten the time between an action and evidence about its consequences.

## Agile did not solve operations

There was still a boundary.

A development team might become highly iterative while production deployment remained governed by a completely different operating model.

```text
Development
  rapid iteration
       │
       ▼
   handoff
       │
       ▼
Operations
  controlled change
```

That separation would become increasingly visible as internet services pushed teams toward much more frequent releases.

<Note>
Agile and DevOps overlap, but they are not synonyms. Agile primarily changed how teams organize software development and feedback. DevOps expanded the feedback loop into delivery and operation of running systems.
</Note>

## The path forward

Once frequent software changes became desirable, integration and release automation moved from optional productivity improvements to core engineering infrastructure.

That leads to the next step: Continuous Integration and Continuous Delivery, where frequent feedback becomes a technical property of the delivery system itself.
