A vulnerability scanner asks:

```text
Is this behavior dangerous?
```

Capability verification asks:

```text
Is this behavior authorized?
```

Those are different questions.

## Start with a contract

Suppose an artifact declares:

```yaml
capabilities:
  network:
    outbound: false

  commands:
    execute: true
    allow:
      - git
```

The declaration describes intended authority.

Static analysis then observes behavior.

```text
network outbound: false
commands execute: true
command: git
```

The verifier compares the two.

## Underdeclaration

If the code makes an HTTP request while the contract says:

```yaml
network:
  outbound: false
```

the artifact is underdeclared.

```text
declared: false
observed: true
```

That is a policy violation even when the network request itself is technically safe.

The problem is that the artifact performs behavior outside its declared authority.

## Overdeclaration

Now suppose the contract requests:

```yaml
network:
  outbound: true
```

but no network behavior is observed.

```text
declared: true
observed: false
```

That is overdeclaration.

It may be less severe, but it still matters.

Excess authority expands the blast radius of future changes or agent decisions.

<KeyTakeaway>
Least privilege applies to what an agent *could* do, not only to what the current implementation happens to do.
</KeyTakeaway>

## Findings are not observations

This distinction is subtle and critical.

Consider:

```python
subprocess.run(["git", "status"], shell=False)
```

A good code analyzer may decide this is not a vulnerability.

So:

```text
security findings = none
```

But the artifact clearly uses process execution.

Therefore:

```text
observed capability = commands.execute
```

If capability inference only reads security findings, it will incorrectly conclude that no command capability exists.

## Use two output channels

Analyzers should produce:

```text
Findings
+
Capability Observations
```

Conceptually:

```go
type AnalysisResult struct {
    Findings     []Finding
    Observations []CapabilityObservation
}
```

A capability observation might contain:

```yaml
capability: commands.execute
value: git
location: helpers/status.py:12
analyzer: python-ast
```

This is evidence of behavior, not evidence of insecurity.

## Allowlist verification becomes precise

Once observations include concrete values, policy can validate them:

```text
observed host
  ∈ declared network hosts?

observed command
  ∈ declared argv prefixes?

observed write path
  ∈ declared filesystem paths?
```

That produces actionable mismatches:

```text
outside allowlist:
  commands.execute: curl
```

instead of a generic "too many permissions" warning.

## Effective authority spans tools too

Capabilities can come from:

```text
code
MCP tools
runtime adapters
agent tools
network clients
filesystem APIs
```

Verification should eventually reason about the union:

```text
observed implementation authority
+
declared tool authority
+
runtime-exposed authority
```

A narrow code path does not make a wildcard tool grant least privilege.

## Verification needs a policy decision

Not every mismatch has the same severity.

A reasonable model is:

```text
underdeclared        → fail
outside allowlist    → fail
overdeclared         → warn or fail by policy
```

Production environments may choose stricter behavior.

The important part is that the mismatch is explicit and evidence-backed.

## Scanning and verification complement each other

Scanning says:

```text
shell=True with untrusted input is dangerous
```

Verification says:

```text
process execution was not declared
```

Both can apply to the same line.

One is a vulnerability property.

The other is an authorization property.

Agent security needs both.
