Eine Git-URL als Quelle macht es möglich, ein Repository direkt zu analysieren. Das ist praktisch für CI, Reviews und externe Artefakte, erweitert aber den Scanner um Netzwerk-, Authentifizierungs- und Provenienzrisiken.

Das Feature ist damit nicht nur eine Komfortfunktion.

Es verändert, **welcher Kontext geprüft wird, welche Vertrauensgrenzen gelten und wie belastbar das Ergebnis später in CI/CD oder Security-Governance verwendet werden kann**.

## Was das Feature leistet

Das Feature nimmt eine Git-URL entgegen, bezieht den gewünschten Stand und überführt ihn anschließend in denselben lokalen Prüfprozess wie ein Verzeichnis. Entscheidend ist, dass die Beschaffung klar von der Analyse getrennt bleibt.

Eine belastbare Implementierung unterstützt Referenzen wie Commit-SHA oder Tag, begrenzt Clone-Größe und Historie und dokumentiert den tatsächlich analysierten Commit. Dadurch kann ein späterer Scan denselben Stand reproduzieren.

## Typischer Ablauf

Unabhängig von der konkreten Implementierung sollte der Ablauf klar getrennte Phasen besitzen:

```text
Input
  ↓
Validierung und Normalisierung
  ↓
Feature-spezifische Verarbeitung
  ↓
Security-Analyse
  ↓
Findings + Coverage + technischer Status
  ↓
Policy-Entscheidung
```

Diese Trennung ist wichtig, weil ein technischer Fehler bei Beschaffung, Parsing oder Providerzugriff nicht dieselbe Bedeutung hat wie ein tatsächlich unauffälliges Prüfergebnis.

## Negatives Beispiel

Eine Pipeline scannt immer den beweglichen Branch `main`:

```bash
scanner scan https://git.example.invalid/team/repo.git
```

Am Montag ist der Branch sauber, am Dienstag enthält er einen neuen Commit. Der Report vom Montag nennt aber nur die URL. Niemand kann später eindeutig beweisen, welcher Stand analysiert wurde.

Zusätzlich erlaubt der Scanner beliebige Git-Hosts. Damit wird die Beschaffung selbst zu einer möglichen SSRF- oder Egress-Oberfläche.

## Positives Beispiel

Die Quelle wird mit einer unveränderlichen Referenz gebunden:

```text
repository: https://git.example.invalid/team/repo.git
commit: 4f3c2a1...
```

Der Scanner prüft Host-Policy, Protokoll, Größenlimit und Commit-ID und hält den resultierenden Digest fest.

```bash
scanner scan 'https://git.example.invalid/team/repo.git#4f3c2a1'
```

Der Report enthält Quelle, aufgelösten Commit und Artefakt-Hash. Dadurch sind Analyse und Provenienz miteinander verbunden.

<KeyTakeaway>
Eine Git-URL ist zugleich Quelle und Netzwerkoperation. Reproduzierbarkeit entsteht erst, wenn URL, aufgelöster Commit und analysierter Inhalt eindeutig miteinander gebunden sind.
</KeyTakeaway>

## Security- und Betriebsaspekte

Remote-Git sollte explizit freigeschaltet werden, weil Netzwerkzugriff den Trust Boundary verändert. Empfehlenswert sind Host-Allowlisten, blockierte private Zielnetze, deaktivierte Git-Hooks, restriktive Credential-Behandlung und shallow fetches.

Submodule benötigen eine eigene Policy. Sie können zusätzliche Hosts und Repositories einführen und sollten nicht stillschweigend mitgeladen werden.

Ein professioneller Betrieb sollte außerdem drei Zustände konsequent auseinanderhalten:

```text
clean      = geprüft, kein relevanter Befund
finding    = geprüft, mindestens ein relevanter Befund
incomplete = Prüfung technisch oder fachlich nicht vollständig
```

Gerade der dritte Zustand ist für DevSecOps entscheidend.

Ein Scanner darf fehlende Coverage nicht als positives Sicherheitsurteil darstellen.

## Wo das Feature sinnvoll eingesetzt wird

Die Funktion eignet sich für zentrale Review-Dienste, Pull-Request-Prüfungen und On-Demand-Scans externer Repositories. Besonders sinnvoll ist sie, wenn der Scanner nicht im selben Workspace wie der Quellcode läuft.

In hochrestriktiven Umgebungen ist ein vorheriger, kontrollierter Checkout durch die CI-Plattform oft die bessere Trennung.

Die konkrete Aktivierung sollte deshalb aus dem gewünschten Trust-Modell abgeleitet werden und nicht allein aus technischer Verfügbarkeit.

## Integration in eine DevSecOps-Pipeline

In einer Pipeline sollte das Feature nicht isoliert betrachtet werden.

Ein belastbares Muster ist:

```text
Source / Artifact
      ↓
Input-Validierung
      ↓
Deterministische Analyse
      ↓
optionale erweiterte Analyse
      ↓
normalisierte Findings
      ↓
Policy Gate
      ↓
Report / Audit Evidence
```

Dabei sollte jeder Report mindestens folgende Informationen transportieren:

- Identität des analysierten Artefakts
- aktive Analyseverfahren
- übersprungene oder nicht verfügbare Prüfschritte
- stabile Regel- oder Finding-IDs
- Schweregrad und Evidenz
- Scanner- und Regelversion
- eindeutiger technischer Abschlussstatus

Damit wird das Feature nicht nur ausführbar, sondern **auditierbar**.

## Fazit

Eine Git-URL ist zugleich Quelle und Netzwerkoperation. Reproduzierbarkeit entsteht erst, wenn URL, aufgelöster Commit und analysierter Inhalt eindeutig miteinander gebunden sind.

Der eigentliche Wert entsteht dann, wenn das Feature mit klaren Grenzen, reproduzierbaren Eingaben und transparenten Ergebnissen in den Entwicklungsprozess eingebettet wird.
