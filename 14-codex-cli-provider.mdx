Die Codex CLI kann bereits authentisiert und in den Entwicklungsworkflow integriert sein. SkillSpector kann diese lokale Laufzeit als semantischen Provider verwenden – ein attraktiver Weg für schnelle Scans ohne zusätzliche API-Konfiguration.

Aus Sicht eines Security Scanners ist eine Agent-CLI jedoch eine deutlich größere Komponente als ein minimaler Modellendpoint.

<KeyTakeaway>
Mehr Providerkompatibilität ist nicht automatisch mehr Sicherheit. Entscheidend ist, welche Fähigkeiten der Providerprozess neben der eigentlichen Inference besitzt.
</KeyTakeaway>

## Was das Feature wirklich bedeutet

Der entscheidende Unterschied heißt **Capability Surface**. Eine reine Inference-API erhält Request-Daten und liefert eine Antwort. Eine lokale Coding-Agent-Laufzeit existiert dagegen in einem Dateisystem, hat lokale Konfiguration und kann prinzipiell weitere Fähigkeiten besitzen.

Je stärker unvertrauenswürdige Skill-Inhalte an so eine Laufzeit weitergereicht werden, desto wichtiger ist die Frage, welche Schutzmechanismen tatsächlich technisch erzwungen werden.

## SkillSpector

SkillSpector führt `codex_cli` als Provider und nutzt die vorhandene lokale Codex-Anmeldung. Damit wird semantische Analyse besonders niederschwellig für Entwickler, die Codex bereits installiert haben.

Das Feature ist bewusst auf Developer Convenience und Provider-Vielfalt ausgerichtet.

## `skil`

`skil` schließt lokale authentisierte Agent-CLIs für den Semantic Provider aus. Der Grund ist derselbe wie bei Claude CLI: Der Providervertrag soll keine Shell-, Tool- oder Host-State-Fähigkeiten enthalten. Eine komplexe lokale Agent Runtime passt nicht in diese minimale Boundary.

Wer lokale Modelle nutzen möchte, kann stattdessen einen expliziten OpenAI-kompatiblen Endpoint mit Private-Allowance verwenden.

## Praxisbeispiel

```bash
# SkillSpector
export SKILLSPECTOR_PROVIDER=codex_cli
skillspector scan ./skill
```

Ein sinnvolles Einsatzmodell ist der lokale Pre-Review. Für ein zentrales Gate sollte die Organisation dagegen festlegen, ob Developer-CLI-State überhaupt Teil des Security-Control-Pfads sein darf.

## Security- und DevSecOps-Einordnung

- Lokale Agent Runtime nicht mit einem passiven Modellendpoint gleichsetzen.
- Authentisierungszustand und lokale Konfiguration als Security State behandeln.
- CI reproduzierbar halten; persönliche CLI-Sessions sind dafür meist ungeeignet.
- Alternative: dedizierter lokaler/remote Inference-Server mit begrenztem Netzwerkvertrag.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

## Direkter Vergleich

| Aspekt | SkillSpector | `skil` |
| --- | --- | --- |
| Feature vorhanden | ja | nein / nicht als gleichwertiges Feature |
| Schwerpunkt | Integration und Scanner-Ergonomie | explizite Trust Boundaries und Evidence |
| Bewertung | SkillSpector-only | SkillSpector-only |

**Bewertung aus der Vergleichsmatrix:** SkillSpector-only.

## Typische Fehlinterpretation

„Wenn der Scanner die CLI nur für Inference nutzt, sind Agent-Fähigkeiten irrelevant.“ Entscheidend ist, was der gestartete Prozess technisch kann – nicht nur, was der aufrufende Code beabsichtigt.

## Einordnung in die Pipeline

Dieses Feature gehört in eine **optionale semantische Analyse-Stufe hinter dem deterministischen Gate**. So bleiben Pull-Request-Checks schnell und reproduzierbar, während modellgestützte Analyse gezielt für risikoreiche Skills, Release-Kandidaten oder Nightly-Scans zugeschaltet werden kann.

Pipeline-seitig sollten Provider, Modell, Endpoint und Credential aus vertrauenswürdiger Konfiguration stammen. Der Skill selbst darf diese Parameter nicht überschreiben. Ein Providerfehler muss als fehlende Coverage sichtbar bleiben.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Wie beim Claude-CLI-Provider bietet SkillSpector mehr unmittelbare Integration. `skil` entscheidet sich gegen diese Capability, um seinen semantischen Analysekanal kleiner und technisch klarer zu halten.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
