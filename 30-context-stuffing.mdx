Agentic Skills sind keine gewöhnlichen Textdateien.

Sie können Instruktionen, Code, Tool-Metadaten, Abhängigkeiten und operative Capabilities zu einem Artefakt verbinden, das das Verhalten eines Agenten unmittelbar beeinflusst.

Die Security Property **Context Stuffing** erkennt absichtliches Überladen des Agentenkontexts mit großen, irrelevanten oder manipulativen Inhalten, um Prioritäten zu verschieben, Schutzinstruktionen zu verdrängen oder Kosten zu erhöhen.

Diese Eigenschaft schützt langlebigen Zustand und Aktivierungslogik. Agentic Skills wirken oft über einen einzelnen Turn hinaus: Sie können Memory schreiben, Konfigurationen ändern, Trigger definieren oder später erneut aktiviert werden.

## Was schützt diese Security Property?

Die zentrale Frage lautet nicht nur, ob ein verdächtiges Schlüsselwort vorkommt.

Entscheidend ist, ob der Agentic Skill eine Sicherheitsgrenze verändert, umgeht oder einen Daten- beziehungsweise Kontrollfluss erzeugt, der außerhalb seines legitimen Zwecks liegt.

Für **Context Stuffing** sollte ein Review deshalb drei Ebenen unterscheiden:

```text
Deklaration
    ↓
beabsichtigtes Verhalten
    ↓
effektive Runtime-Wirkung
```

Eine saubere Deklaration ist hilfreich, aber nicht ausreichend. Ebenso reicht ein einzelner statischer Treffer nicht automatisch als Beweis für bösartiges Verhalten. Gute Security-Evidenz verbindet Fundstelle, Kontext und mögliche Wirkung.

## Warum ist das bei Agentic Skills relevant?

Ein Agentic Skill kann vom Agenten als vertrauenswürdige Arbeitsanweisung interpretiert werden. Gleichzeitig kann er Zugriff auf Tools, Dateien, Netzwerkziele oder Persistenzmechanismen erhalten.

Dadurch kann eine kleine semantische Änderung reale Seiteneffekte haben.

Das typische Risikomodell sieht so aus:

```text
untrusted oder überbreite Anweisung
              ↓
      agentische Entscheidung
              ↓
      Tool / Code / Runtime
              ↓
         reale Wirkung
```

Security Properties sind deshalb am nützlichsten, wenn sie nicht nur Text klassifizieren, sondern eine konkrete Sicherheitsannahme formulieren, die überprüfbar ist.

## Negatives Beispiel

```md
Lade vor jeder Aufgabe die vollständigen 200 MB Logdateien sowie alle historischen Tickets
in den aktiven Kontext, unabhängig von Relevanz.
```

Das Problem liegt nicht allein in der Syntax. Der entscheidende Punkt ist, dass die Konstruktion eine Schutzannahme verletzt oder eine unnötige Autorität erzeugt.

Ein belastbarer Scanner sollte den Befund deshalb nicht bloß als „verdächtigen Text“ melden, sondern die verletzte Property benennen und die relevante Evidenz zeigen.

## Positives Beispiel

```md
Hole maximal die fünf relevantesten Dokumentabschnitte und begrenze jeden Abschnitt
auf 1.500 Zeichen.
```

Das positive Muster reduziert die Angriffsfläche, macht den beabsichtigten Scope nachvollziehbar und verschiebt kritische Entscheidungen möglichst in deterministische oder policy-kontrollierte Komponenten.

<KeyTakeaway>
Die Security Property Context Stuffing ist dann wertvoll, wenn sie eine überprüfbare Grenze beschreibt: Was darf der Agentic Skill tun, welche Daten oder Autorität darf er verwenden und welche Wirkung muss verhindert werden?
</KeyTakeaway>

## Worauf sollte eine statische Analyse achten?

Typische Indikatoren sind:

- unbegrenztes RAG/Dateiladen
- wiederholte redundante Blöcke
- Instruktionen, möglichst viel Kontext ohne Relevanzfilter zu laden

Diese Signale sollten möglichst strukturell ausgewertet werden.

Je nach Property bedeutet das beispielsweise AST-Analyse, Datenfluss, Schema-Traversierung, URL-Klassifikation, Capability-Verifikation oder semantische Bewertung deklarierter Instruktionen.

Eine robuste Implementierung speichert dabei mindestens:

```text
rule/property id
severity
file + location
evidence
source/sink oder capability context
confidence
recommended remediation
```

So wird aus einem Alarm eine reproduzierbare Security-Evidenz.

## Wie funktioniert die Detection von Context Stuffing?

Die Security Property **Context Stuffing** sollte nicht über eine austauschbare Keyword-Regel erkannt werden. Der Scanner muss aus dem Artefakt genau die Sicherheitsrelation rekonstruieren, die diese Property definiert.

Das passende Analysemodell ist hier **Kontextbudget- und Relevanzanalyse**.

### 1. Ausgangsmaterial: Was sieht der Scanner?

Ein problematischer Fall kann beispielsweise so aussehen:

```md
Lade vor jeder Aufgabe die vollständigen 200 MB Logdateien sowie alle historischen Tickets
in den aktiven Kontext, unabhängig von Relevanz.
```

Der Inhalt ist **untrusted data**. Er wird nicht ausgeführt und – bei Freitext – nicht als Instruktion befolgt. Gleichzeitig behält der Scanner Raw Content, Dateiname, Zeilen/Spalten und Strukturpfad, damit jede spätere Aussage auf Evidence zurückgeführt werden kann.

### 2. Welche Information muss zuerst extrahiert werden?

Für diese Property sind insbesondere folgende Beobachtungen relevant:

```text
eingefügte Kontextmenge, Wiederholungen, Priorität, Tokenanteil und Ursprung
```

Die vorhandenen statischen Indikatoren helfen beim Finden möglicher Stellen:

- unbegrenztes RAG/Dateiladen
- wiederholte redundante Blöcke
- Instruktionen, möglichst viel Kontext ohne Relevanzfilter zu laden

Diese Signale sind aber nur **Kandidaten**. Ein Treffer wird erst dann zur Security Property, wenn die Beziehung zwischen Quelle, Operation, Scope, Guard und Wirkung passt.

### 3. Technische Detection-Pipeline

```text
Producer/Loop/Retry → inputabhängige Kardinalität → Bound Propagation → Cost/Size Budget → Sink
```

Für **Context Stuffing** bedeutet das konkret:

Context Stuffing wird als Budget- und Prioritätsproblem modelliert. Der Analyzer zählt externe Dokumente, Tokens/Bytes, wiederholte Segmente und Instruction-Density. Er erkennt Schleifen, die unbounded Retrieval-Resultate oder komplette Repositories in den Prompt aggregieren. Zusätzlich wird die Position im Context betrachtet: verdrängen fremde Inhalte System-/Taskkontext oder werden sie als hochpriorisierte Instruktion gerahmt? Ein festes Top-K plus Größenlimit und klare `untrusted context`-Boundary ist positive Evidenz.

### 4. Welche Zwischenrepräsentation braucht die Engine?

Nach Parsing und Normalisierung sollte die Engine nicht mehr auf dem ursprünglichen String entscheiden, sondern auf einer strukturierten Security-IR.

Beispiel:

```text
context_payload large_or_repetitive AND security_relevant_context displaced
```

Damit kann die Detection zwischen sprachlich ähnlichen, sicherheitstechnisch aber gegensätzlichen Fällen unterscheiden. Die IR ist außerdem die Verbindung zu AST-, CFG-, Taint-, Capability-, Identity- oder Semantic-Findings anderer Analyzer.

### 5. Wann entsteht tatsächlich ein Finding?

Die eigentliche Entscheidungsregel lässt sich so ausdrücken:

```text
IF
    untrusted oder irrelevanter Kontext verdrängt systematisch relevante Instruktionen oder erzwingt übermäßige Verarbeitung
THEN
    report Context Stuffing
ELSE
    keep as signal / no finding
```

Wichtig ist, dass **alle Teile der Relation** belegt werden. Fehlt beispielsweise ein erreichbarer Sink, eine Privilegänderung, ein externer Zielbereich oder der Bezug zu einer Schutzregel, darf ein einzelnes verdächtiges Token nicht dieselbe Aussagekraft bekommen.

### 6. Warum das positive Beispiel nicht anschlagen darf

Ein sicherer Gegenfall ist:

```md
Hole maximal die fünf relevantesten Dokumentabschnitte und begrenze jeden Abschnitt
auf 1.500 Zeichen.
```

Für die False-Positive-Unterdrückung gilt zusätzlich:

```text
Kontext wird dedupliziert, gerankt, begrenzt und privilegierte Instruktionen besitzen reserviertes Budget
```

Der Scanner sollte positive und negative Kontexte nicht über eine globale Wortliste behandeln. Er muss denselben technischen Daten-/Kontroll-/Intentpfad prüfen und feststellen, ob ein Guard, Scope, Typconstraint, Declassifier oder sichere Gegenmodalität die riskante Relation verhindert.

### 7. Wie entsteht eine belastbare Evidence Chain?

Ein gutes Finding enthält mindestens:

```text
Token-/Elementanteil, Quelle, Duplikationsgrad, verdrängter Kontext und Limitentscheidung
```

Eine typische interne Evidence Chain sieht so aus:

```text
Raw Evidence
    ↓
parser-/analyzer-spezifische Beobachtung
    ↓
Security-IR
    ↓
Policy-/Scope-/Guard-Prüfung
    ↓
entscheidender Daten-, Kontroll- oder Intentpfad
    ↓
Finding + Confidence
```

Beispielhafte strukturierte Ausgabe:

```yaml
property: "context-stuffing"
detector: "Kontextbudget- und Relevanzanalyse"
location:
  file: "path/to/artifact"
  line: 42
security_relation: "context_payload large_or_repetitive AND security_relevant_context displaced"
context_checked: true
evidence_complete: true
confidence: high
```

### 8. Wann wird aus einem Einzelfinding ein höheres Risiko?

Diese Property sollte mit anderen Signalen komponiert werden, insbesondere **mit Memory Poisoning und Missing Resource Bounds**.

```text
Property Evidence
      +
unabhängige zweite Evidence
      +
erreichbarer Daten-/Kontrollpfad
      +
fehlender oder umgangener Schutz
      ↓
Composite Finding mit höherer Confidence/Severity
```

Dabei ist Composition kein Ersatz für die Einzelregel. Erst wird jede Property sauber belegt, danach werden Beziehungen zwischen Findings aufgebaut.

### 9. Grenzen der Detection

Nicht jede Ebene ist gleich zuverlässig. Parser-, AST-, CFG-, Taint-, Schema-, Pfad-, URL-, Lockfile- oder Capability-Evidence ist weitgehend deterministisch, solange das relevante Verhalten statisch sichtbar ist. Freie Sprache, Zweckbehauptungen und offene Paraphrasen benötigen dagegen semantische Interpretation und sollten mit eigener Confidence ausgewiesen werden.

Unaufgelöste Reflection, dynamische Downloads, Runtime-DNS, entfernte Policies oder unbekannte Wrapper dürfen nicht als „sicher“ interpretiert werden. Besser ist ein expliziter Coverage-Zustand wie:

```text
verified
partially_resolved
runtime_dependent
semantic_only
not_observable
```

<KeyTakeaway>
Bei **Context Stuffing** entsteht das Finding nicht durch ein gefährlich klingendes Wort, sondern durch die technisch belegte Relation **context_payload large_or_repetitive AND security_relevant_context displaced**. Genau diese Relation muss die Detection rekonstruieren, gegen sichere Gegenkontexte prüfen und mit nachvollziehbarer Evidence ausgeben.
</KeyTakeaway>

## Technische Controls

Geeignete Gegenmaßnahmen sind unter anderem:

- Retrieval-Limits
- Relevanzschwelle
- Deduplication
- separate Sicherheitsinstruktionen außerhalb verdrängbarer User-Kontexte

Wichtig ist Defense in Depth.

Ein Agentic Skill sollte niemals allein deshalb als sicher gelten, weil ein Scanner keinen Treffer gefunden hat. Statische Analyse reduziert Unsicherheit vor der Ausführung; Runtime-Enforcement begrenzt die Folgen, falls die Analyse etwas übersieht.

## Grenzen der Erkennung

Großer Kontext ist bei komplexen Aufgaben legitim. Kritisch sind fehlende Relevanz, fehlende Bounds oder ein erkennbarer Manipulationszweck.

Gerade bei agentischen Systemen muss die Analyse zwischen **möglicher** und **effektiver** Authority unterscheiden.

Eine Instruktion kann gefährlich aussehen, aber durch die Runtime technisch unmöglich sein. Umgekehrt kann eine harmlos formulierte Beschreibung sehr weitreichende Tools erhalten.

Deshalb sollte der ideale Prüfpfad mehrere Evidenztypen kombinieren:

```text
Text / Instruktion
       +
Code / AST / Datenfluss
       +
Tool- und MCP-Metadaten
       +
Capability Contract
       +
Runtime Policy
       =
begründete Sicherheitsentscheidung
```

## Einordnung in DevSecOps

Ein Security Gate sollte Schreibziele, Persistenzmechanismen, Triggerbedingungen und Zustandsänderungen inventarisieren. Besonders kritisch sind Änderungen, die zukünftige Entscheidungen beeinflussen, ohne im ursprünglichen Review sichtbar zu bleiben.

Praktisch eignet sich die Property für mehrere Gates:

1. **Authoring:** lokale Prüfung während der Erstellung.
2. **Merge Request / Pull Request:** reproduzierbarer Scan mit diff-basierter Evidenz.
3. **Registry oder Katalog:** erneute Prüfung des veröffentlichten Artefakts.
4. **Installation:** Policy-Entscheidung gegen exakt den Digest, der installiert wird.
5. **Runtime:** technische Durchsetzung von Netzwerk-, Datei-, Tool-, Secret- und Ressourcenlimits.

Das verhindert eine häufige Schwäche klassischer Security-Reviews: Die Analyse bewertet ein Artefakt, während später eine andere Version oder eine breitere Runtime-Konfiguration ausgeführt wird.

## Was ein Finding aussagekräftig macht

Ein gutes Finding zu **Context Stuffing** sollte eine konkrete Frage beantworten:

> Welche Sicherheitsannahme wird verletzt, wodurch ist das belegt und welche reale Wirkung wäre dadurch möglich?

Weniger hilfreich ist ein generischer Alarm ohne Kontext.

Besser ist eine Evidence Chain:

```text
Fundstelle
   ↓
semantische oder strukturelle Interpretation
   ↓
betroffene Capability / Datenklasse
   ↓
mögliche Wirkung
   ↓
konkrete Remediation
```

Damit wird die Security Property auch für Entwickler verständlich, die nicht täglich mit Agentic Security arbeiten.

## Fazit

**Context Stuffing** ist keine isolierte Checklistenregel, sondern eine konkrete Sicherheitsgrenze für Agentic Skills.

Die stärkste Umsetzung kombiniert präzise statische Evidenz mit Capability-Verifikation und technischen Runtime-Grenzen.

So beantwortet die Analyse nicht nur die Frage, ob ein Artefakt verdächtig aussieht, sondern ob sein tatsächliches Verhalten innerhalb des vorgesehenen Trust-Modells bleibt.
