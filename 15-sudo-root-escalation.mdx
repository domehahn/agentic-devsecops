A process running as an unprivileged user and the same process running as `root` are not two equivalent execution modes. They have different blast radii, different access to host resources, and different consequences when an AI agent makes a mistake.

The **sudo/root escalation** property therefore focuses on the privilege transition itself:

```text
COMMAND_EXECUTION
AND PRIVILEGE_TRANSITION(to=root|setuid)
```

The exact payload is secondary. Once a skill requests elevation, the security boundary has changed.

## Privilege is part of the input to every threat model

An agent can generate the same buggy command in two environments. Under a restricted account, the impact may be contained. Under root, it may affect system configuration, credentials, other users, services, or security controls.

This is why privilege should be treated as a first-class parameter of agent execution:

```text
risk = f(model_behavior, tool_surface, data_access, privilege, isolation)
```

Prompt security alone cannot compensate for root authority.

## Safe scanner fixtures

A positive fixture can remain operationally harmless while still exercising the control:

```bash
sudo sh -c 'run-maintenance-task'
```

The finding is caused by the explicit elevation mechanism, not by what `run-maintenance-task` does.

A negative fixture can perform a user-scoped installation:

```bash
install -m 0755 ./tool "$HOME/.local/bin/tool"
```

No privilege transition occurs.

## Shell analysis should model elevation primitives

`skil` maps shell privilege escalation to `SKIL-SH-002`.[^skil-matrix]

A shell-aware analyzer can identify classes such as:

- `sudo` or equivalent elevation wrappers,
- explicit UID/GID transitions,
- setuid-related operations,
- commands that modify privilege policy,
- privileged shell execution.

The scanner need not explain how to exploit these mechanisms. It only needs to establish that the artifact attempts to execute with higher authority.

## Why string matching is not enough

Shell syntax includes quoting, command substitution, variables, functions, pipelines, and wrappers. A naïve search for the word `sudo` can flag documentation or comments while missing dynamically constructed invocations.

A stronger implementation parses shell where possible and records:

```yaml
property: sudo-root-escalation
control: SKIL-SH-002
execution_primitive: shell
privilege_transition: root
source_location: "script.sh:42"
defensive_context: false
```

## Root is often a design smell, not automatically a vulnerability

Some installation or systems-management tasks legitimately require elevated privileges. The correct response is not always “ban root.” Instead ask:

- Why is elevation required?
- Can the privileged operation be isolated?
- Can a dedicated service perform it instead?
- Can a narrow Linux capability replace UID 0?
- Is the action approved independently?
- Is the elevated phase minimal and auditable?

CWE-269 emphasizes careful privilege management, least privilege, explicit trust zones, and separation of privilege.[^cwe269]

## Capability-specific authority is often safer

Linux capabilities can split parts of root authority, though they also require careful design. The principle is to grant only the kernel privilege required for one operation rather than unrestricted UID 0.

For agentic workloads, an even stronger pattern is often a broker:

```text
agent proposes privileged operation
        ↓
trusted broker validates arguments and policy
        ↓
broker performs narrow operation
        ↓
agent receives result, not root shell
```

This prevents the model from obtaining general-purpose elevation.

## Approval should surround the privilege boundary

A human approval gate is most useful **before** the privilege transition, not after a root-capable command has already been assembled and partially executed.

The approval UI should show:

- requested operation,
- target resource,
- expected side effects,
- reason elevation is required,
- rollback plan where applicable.

A generic “Allow?” button hides too much context.

## Runtime containment

Defensive controls include:

- run agent workers as non-root,
- avoid passwordless broad sudo rules,
- isolate privileged helpers,
- use immutable base images where practical,
- prevent agents from modifying sudoers/PolicyKit rules,
- apply seccomp/AppArmor/SELinux policies,
- separate build and production identities,
- log privilege transitions as security events.

OWASP Excessive Agency is relevant because unnecessary privilege amplifies damage from manipulated outputs.[^owasp-agency]

## Root inside a container is not the same as root on the host—but still matters

Container namespaces can limit the effect of container UID 0. However, privileged containers, host namespaces, host mounts, or Docker socket access can collapse that isolation. Therefore, root escalation findings should be composed with container-boundary properties rather than interpreted in isolation.

```text
root_in_restricted_container      < risk
root + privileged workload       < higher risk
root + host control-plane socket < highest authority class
```

The exact ordering depends on runtime hardening, but the composition principle is robust.

## Evidence and severity

A scanner can report the privilege transition independently of exploitability. Severity can then incorporate:

- host versus container context,
- privileged mode,
- mounted host paths,
- tool exposure,
- production versus test environment,
- approval controls.

This avoids overstating a static shell finding while preserving an important boundary signal.

## False positives

Documentation, build instructions, installer examples, and tests may contain elevated commands legitimately. Context guards should recognize fenced examples and defensive prose, but reviewed exceptions should remain visible when the actual skill executes privileged operations.

## Validation

Test fixtures should cover:

- direct elevation wrappers,
- nested shell execution,
- benign textual mentions,
- explicit prohibition of elevation,
- user-local alternatives,
- containerized contexts,
- privilege-policy modification attempts.

## Limits

Static analysis cannot know whether `sudo` is configured, whether a password is required, whether the process already runs as root, or whether a sandbox blocks the effect. It also cannot fully infer Linux capability semantics from every runtime.

The correct claim is simply that the artifact contains an execution path requesting a privilege transition.

<KeyTakeaway>
Privilege escalation is a **threat-model transition**. Once an agent moves from a restricted identity to root-level authority, every subsequent model error or prompt-injection consequence must be evaluated under the larger blast radius.
</KeyTakeaway>

## Conclusion

Root and sudo escalation should be treated as a change in security domain, not just another shell command. Static detection can identify the transition, but the production defense is to avoid general-purpose elevation, broker narrow privileged actions, require independent approval, and preserve strong isolation so that the model never becomes the authority deciding its own privilege level.
