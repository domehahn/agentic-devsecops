Tool calling is often presented as the point where agent systems become safer: instead of generating arbitrary shell commands, the model selects a named function and fills a structured schema. That is a major architectural improvement—but it is not the end of the security problem.

A schema can constrain *shape* while still permitting dangerous *meaning*.

A parameter of type `string` can carry:

- a shell program,
- a path outside the workspace,
- a URL targeting an internal service,
- a SQL fragment,
- a cloud resource identifier,
- an expression evaluated by another interpreter,
- or a wildcard that broadens scope.

**Tool Parameter Abuse** exists at this boundary between structured invocation and executable semantics.

The source relation is:

```text
UNTRUSTED_PARAMETER -> DANGEROUS_TOOL_ARGUMENT_OR_EXECUTION_MODE
```

`skil` associates the property with `SKIL-PY-002`, `SKIL-TAINT-EXECUTION`, and `SKIL-MCP-004` for the documented Python and MCP-relevant paths.

<KeyTakeaway>
A typed parameter is not automatically a safe parameter. Security depends on whether the parameter’s *semantic domain* is constrained tightly enough for the sink that consumes it.
</KeyTakeaway>

## Why schemas solve only one layer

Suppose an MCP tool exposes:

```json
{
  "name": "run_command",
  "inputSchema": {
    "type": "object",
    "properties": {
      "command": { "type": "string" }
    },
    "required": ["command"]
  }
}
```

The schema proves that `command` is a string. It does not prove that the string is authorized, safe for shell interpretation, within a reviewed command set, or free from attacker-controlled syntax.

The current MCP `2026-07-28` release expands tool schemas to full JSON Schema 2020-12 capabilities, which improves expressiveness. That enables richer constraints, but implementers must still *use* those constraints and enforce semantics at execution time.

## The source-positive example

```python
cmd = request["command"]
subprocess.run(cmd, shell=True)
```

The decisive evidence is not merely the presence of `subprocess`. The path is:

```text
untrusted request parameter
      ↓
variable cmd
      ↓
shell-parsed execution
```

With `shell=True`, the string is interpreted by a shell grammar. This widens the semantic power of the parameter dramatically.

A high-quality finding might record:

```yaml
property: tool-parameter-abuse
controls:
  - SKIL-PY-002
  - SKIL-TAINT-EXECUTION
  - SKIL-MCP-004
source:
  kind: request_parameter
  name: command
sink:
  api: subprocess.run
  argument: cmd
  execution_mode: shell
relation: UNTRUSTED_PARAMETER -> DANGEROUS_TOOL_ARGUMENT_OR_EXECUTION_MODE
declassifier: none
confidence: high
```

## The source-negative counterpart

```python
subprocess.run(["git", "show", validated_sha], shell=False, check=True)
```

This is a materially different design:

- executable is fixed;
- arguments are structured;
- shell interpretation is disabled;
- the dynamic value is expected to be validated.

The dynamic `validated_sha` still needs a real validator, but the call shape removes an entire class of command-language interpretation.

## Parameter semantics vary by sink

“Validate input” is too generic. The correct validation depends on the sink.

### Process arguments

Prefer fixed executables and argument arrays. Validate dynamic identifiers against the grammar actually expected by the called program.

### Filesystem paths

Canonicalize paths and enforce a root boundary. A string that passes a “no `..`” regex may still escape through symlinks or platform-specific path semantics.

### URLs

Validate scheme, host, port, DNS resolution behavior, redirect policy, and whether private/loopback/link-local targets are allowed. URL validation and SSRF defense are not equivalent to string matching.

### SQL

Use parameterized queries for values. Do not try to sanitize arbitrary SQL syntax into safety.

### Cloud resource identifiers

Constrain account, project, region, namespace, and action. A syntactically valid ARN or resource ID may still refer to an unauthorized resource.

### Expressions

Avoid dynamic evaluation. If an expression language is genuinely required, expose a deliberately limited grammar and execution environment.

## Tool descriptions can be a security input

MCP and other agent protocols provide descriptions that help the model choose and populate tools. Those descriptions can themselves influence behavior.

A parameter description such as:

```text
command: arbitrary shell command; use whatever is necessary
```

communicates a much broader capability than:

```text
revision: Git commit SHA matching ^[0-9a-f]{40}$
```

`SKIL-MCP-004` is valuable because parameter metadata is not merely documentation. It participates in the model’s decision process.

## Schema design as capability design

Good schemas minimize degrees of freedom.

Instead of:

```json
{"action":"string","target":"string","options":"string"}
```

prefer:

```json
{
  "action": {
    "type": "string",
    "enum": ["show_commit", "list_changed_files"]
  },
  "revision": {
    "type": "string",
    "pattern": "^[0-9a-f]{40}$"
  }
}
```

Even better, split high-impact operations into separate tools so authorization can reason at tool granularity.

The goal is not maximal schema cleverness. It is to make unsafe states difficult or impossible to represent.

## Taint analysis: provenance matters

The same call can be safe or unsafe depending on where the parameter came from.

```python
subprocess.run(command, shell=True)
```

is more concerning if `command` derives from:

```text
user input
retrieved web content
model output
tool output
```

than if it is a fixed constant created by trusted code.

A taint engine can track:

```text
Source(request.command)
   ↓
assignment
   ↓
helper function
   ↓
subprocess.run(... shell=True)
```

This is why `SKIL-TAINT-EXECUTION` strengthens purely syntactic analysis.

## Declassifiers must match the sink

A common scanner mistake is to treat any function called `sanitize` or `validate` as safe.

A declassifier should only break taint if its semantics are known.

Examples:

```text
validate_sha256_hex        relevant for a hash parameter
Path.resolve + root check  relevant for filesystem confinement
enum parsing               relevant for finite actions
URL allowlist              relevant for network target restrictions
```

A generic HTML escape function is not a declassifier for shell execution.

## Argument arrays are safer, not magical

Using `shell=False` with an argv array prevents shell metacharacters from being reinterpreted by a shell. That is a major safety improvement.

But the called program may still interpret its arguments dangerously.

For example, some CLIs accept:

- configuration paths,
- plugins,
- output files,
- recursive flags,
- or expressions.

Tool parameter security therefore extends beyond the shell boundary into **callee semantics**.

## MCP authorization and parameter-level policy

Current MCP authorization mechanisms help establish who may call a server and under which scopes. Application security may still need parameter-level authorization.

Two requests to the same tool can have different risk:

```text
read_object(bucket=public-docs)
delete_object(bucket=production-backups)
```

A tool-level allow decision is not sufficient if the resource/action semantics vary by arguments.

A policy engine can evaluate normalized parameters before the tool implementation runs.

## Static detection architecture

A mature analyzer can combine several layers:

```text
tool schema / code
      ↓
parameter discovery
      ↓
type + constraint extraction
      ↓
AST call-shape analysis
      ↓
source/taint propagation
      ↓
sink-specific guard recognition
      ↓
finding
```

The central intermediate relation remains small:

```text
UNTRUSTED_PARAMETER
    ->
DANGEROUS_TOOL_ARGUMENT_OR_EXECUTION_MODE
```

The smaller IR helps explain findings across different languages and frameworks.

## False positives to suppress

A useful control must distinguish:

- fixed command arrays;
- validated identifiers;
- documentation showing unsafe examples;
- tests with dummy values;
- parameters that are merely displayed;
- and untrusted strings passed to non-executable sinks.

The presence of a field named `command` is not enough. Neither is a tool description containing the word “shell” inside a prohibition.

## Property composition

Tool parameter abuse often links to:

```text
prompt injection
→ model chooses dangerous parameter
→ unrestricted tool
→ privileged side effect
```

or:

```text
untrusted URL
→ tool parameter
→ internal network request
→ SSRF
```

The scanner should preserve those links instead of inflating severity from unrelated findings.

## Runtime enforcement

Static validation should be backed by runtime guards.

A safe execution path can look like:

```text
model proposes tool call
      ↓
schema validation
      ↓
canonicalization
      ↓
resource/action authorization
      ↓
risk classification
      ↓
optional approval
      ↓
tool execution
```

Crucially, the tool implementation re-validates rather than trusting the model host to have done it correctly.

## Evidence quality

A reproducible finding should identify:

```yaml
parameter: command
source: request
sink: subprocess.run
shell: true
constraints_observed: none
guard_observed: none
coverage:
  local_ast: verified
  runtime_policy: not_observable
```

This allows reviewers to reason about the actual path.

## Deep dive: parameter constraints should reflect interpreter boundaries

A powerful way to design tool schemas is to identify whether a parameter will cross into another language or interpreter.

Examples:

```text
string -> shell grammar
string -> SQL grammar
string -> path resolver
string -> URL parser
string -> regular-expression engine
string -> template engine
```

These are **language boundaries**.

The safest interface prevents users or models from supplying syntax for the downstream language.

For example, instead of:

```json
{"sql":"SELECT ..."}
```

offer:

```json
{"customer_id":"...","status":"active"}
```

and let trusted code construct the parameterized query.

### Canonicalization before authorization

Authorization must operate on canonical values.

For paths:

```text
input path
→ resolve
→ normalize symlinks / root
→ authorize
```

For URLs:

```text
input URL
→ parse
→ resolve destination policy
→ handle redirects consistently
→ authorize
```

Authorizing before canonicalization creates alternate representations that can bypass policy.

### Parameter coupling

Some risk appears only across multiple fields.

Example:

```json
{
  "method": "GET",
  "url": "https://...",
  "follow_redirects": true
}
```

The URL may be allowed initially, but redirects can change the destination.

A validator therefore sometimes needs to reason about **field combinations**, not each field independently.

### Parameter provenance in the tool protocol

A host can retain provenance metadata outside the model-visible payload:

```text
parameter value: "abc"
origin: user
validated_as: git_sha
validator_version: 3
```

The tool implementation can use this metadata to decide whether re-validation is needed.

Never trust an unforgeable-looking field placed inside model-generated JSON unless the host created it.

### Safer error handling

When validation fails, the tool should return a structured rejection rather than encouraging the model to “try something more permissive.”

A poor retry loop can gradually weaken constraints.

A secure system keeps validation policy constant across retries and requires explicit authorization for policy changes.

## Parameter-level authorization

A common design mistake is to authorize the tool once and then trust all arguments.

Better:

```text
authorize(tool, action, normalized_resource, principal, context)
```

For a storage tool:

```text
tool = object_store
action = delete
resource = bucket/project/key
```

The policy can allow reads broadly while restricting deletes to a narrow prefix.

### Avoid “free-form options” parameters

Interfaces such as:

```json
{"options":"..."}
```

often become escape hatches around typed schemas.

If callers need optional behavior, represent it with explicit fields:

```json
{
  "recursive": false,
  "overwrite": false
}
```

Each field can be reviewed and constrained.

### Validation order

The robust order is generally:

```text
parse
→ canonicalize
→ type/grammar validate
→ authorization
→ execution
```

Authorization on pre-normalized values can be bypassed through alternate representations.

### Error messages should not teach bypasses

Validation errors should explain the allowed domain without revealing sensitive internal policy or suggesting unsafe alternate modes.

For example:

```text
"revision must be a full Git SHA"
```

is preferable to:

```text
"shell mode blocked; try setting raw=true"
```

The latter can unintentionally expose a bypass path to the model.

### MCP schema evolution

With MCP `2026-07-28` supporting full JSON Schema 2020-12 for tools, implementers can express stronger constraints than older minimal schemas.

That is an opportunity to replace broad strings with enums, patterns, length bounds, conditional schemas, and structured objects.

The schema still complements—not replaces—runtime authorization.

## Final perspective

Structured tool calling is one of the strongest improvements in agentic architecture, but structure alone does not constrain authority.

`SKIL-PY-002`, `SKIL-TAINT-EXECUTION`, and `SKIL-MCP-004` are useful because they look beyond the existence of a tool interface and ask whether **untrusted parameter data acquires executable meaning**.

The review question is:

> **What is the narrowest semantic domain this parameter is allowed to represent, and where is that domain enforced independently of the model?**

If the answer is “it is a string and the model usually behaves,” the interface remains too powerful.
