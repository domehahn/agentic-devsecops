DevOps and DevSecOps made software delivery increasingly automated, observable, and repeatable.

Machine learning introduced a new problem:

```text
the behavior of the system
is not determined by code alone
```

A production ML system also depends on data, training logic, model artifacts, features, and changing real-world distributions.

## The code can stay the same while behavior changes

Traditional software roughly follows:

```text
code
  ↓
build
  ↓
behavior
```

Machine learning adds more variables:

```text
code
+
training data
+
features
+
parameters
+
model
+
runtime data
        ↓
     behavior
```

That changes what must be versioned, tested, monitored, and reproduced.

## Research exposed the engineering gap

Google researchers described this problem in the 2015 paper **"Hidden Technical Debt in Machine Learning Systems."**[^debt] The title itself captures the key point: successful model experimentation is not the same thing as building a maintainable production system.

In 2017, another Google paper, **"The ML Test Score,"** presented 28 tests and monitoring needs aimed at production readiness and technical-debt reduction for ML systems.[^ml-test]

The engineering challenge was moving beyond:

```text
Does the model work in an experiment?
```

toward:

```text
Can the complete ML system be operated reliably?
```

## CI/CD is necessary but incomplete

For ordinary software, a source change is a common trigger for a new build.

For ML, a new model may also be triggered by:

```text
new data
data correction
feature change
training configuration
model code
performance degradation
drift
```

This motivates an additional concept:

```text
Continuous Training
```

Google Cloud's MLOps guidance explicitly describes CI, Continuous Delivery, and Continuous Training as automation concerns for ML systems.[^google-mlops]

<Architecture>
MLOps extends the delivery pipeline from managing source changes to managing changes in data, training, models, and production behavior.
</Architecture>

## Testing becomes multidimensional

A production ML lifecycle may need to test:

```text
software
data
features
model quality
model bias
serving compatibility
performance
drift
```

A unit test cannot answer whether the data distribution has changed.

A model metric cannot prove that the serving code is secure.

Both forms of engineering evidence are needed.

## Monitoring changes meaning

Traditional monitoring asks:

```text
Is the service healthy?
```

ML monitoring adds:

```text
Are predictions still useful?
Has input distribution changed?
Has model quality degraded?
Is retraining necessary?
```

A system can return HTTP 200 while its model is no longer fit for purpose.

<KeyTakeaway>
For ML systems, operational correctness includes statistical behavior—not only software availability.
</KeyTakeaway>

## Reproducibility becomes a first-class requirement

To understand a model release, an organization may need to reconstruct:

```text
source revision
dataset version
feature logic
training configuration
dependencies
model artifact
evaluation result
```

That resembles software supply-chain provenance, but with additional artifacts.

This is one reason MLOps is best understood as an extension of engineering practices rather than a replacement for DevOps.

## The next step is broader than MLOps

MLOps focuses strongly on machine-learning lifecycle concerns.

But real AI systems also involve:

- systems architecture,
- human interaction,
- robustness,
- safety,
- security,
- governance,
- changing operational environments.

By 2019 and the early 2020s, organizations such as Carnegie Mellon's Software Engineering Institute were explicitly framing these concerns under **AI Engineering**.
