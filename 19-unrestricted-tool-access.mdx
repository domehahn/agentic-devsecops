Tools convert language-model output into effects. Once an agent can query databases, alter repositories, send messages, provision infrastructure, or trigger deployments, the security question changes from “what can the model say?” to **“what authority can the system exercise on the model's behalf?”**

Unrestricted Tool Access is the failure mode in which the callable capability set is much broader than the task requires. The simplest manifestation is a wildcard allowlist, but the deeper issue is effective reachability: dynamic discovery, inherited permissions, shared credentials, or permissive tool brokers can create a de facto wildcard even when no literal `*` appears.

The invariant is:

```text
AGENT_TOOL_SET = ALL_AVAILABLE_TOOLS
AND PURPOSE_REQUIRES_SUBSET
```

A more general formulation is:

```text
EFFECTIVE_CAPABILITIES ⊃ JUSTIFIED_CAPABILITIES
```

This is the agentic version of least privilege.

## The attack surface is the product of model uncertainty and tool authority

A model may be extremely capable and still make mistakes. A prompt injection may redirect its objective. A tool description may be misleading. A retrieved document may contain adversarial instructions. The damage from any of these conditions depends heavily on the actions the runtime exposes.

```text
uncertain decision process
          ×
reachable tools
          ×
credential scope
          ×
autonomy
          =
possible impact
```

This is why OWASP's Excessive Agency guidance separates **excessive functionality, excessive permissions, and excessive autonomy**.[^owasp-agency] The same principle appears in the OWASP Top 10 for Agentic Applications, where tool misuse and identity/privilege abuse are treated as first-class agentic risks.[^owasp-agentic]

## A wildcard permission is easy to detect—and should be treated as a design smell

A synthetic positive fixture can be as small as:

```yaml
allowedTools:
  - "*"
```

The finding is not that every tool will be abused. The finding is that the task contract has delegated the authorization decision to the model at runtime instead of constraining it beforehand.

A better counterpart is explicit:

```yaml
allowedTools:
  - repository.read_file
  - repository.search
  - tests.run
```

Even this is only the beginning. The argument schemas and underlying credentials also need to be scoped.

## Tool names are not capabilities; parameters and resources matter

Suppose an agent is allowed to call `read_file`. If that tool accepts any absolute path, the apparent read capability may include the entire host filesystem. Likewise, a `query_database` tool can be narrow or extremely powerful depending on tenant, database, SQL grammar, and execution identity.

A useful capability model therefore has several dimensions:

```text
capability = operation
           × resource set
           × tenant / principal
           × parameter constraints
           × time window
           × rate / budget
           × side-effect class
```

For example:

```yaml
capability:
  operation: repository.read_file
  resources:
    repository: current
    paths:
      - "src/**"
      - "docs/**"
  side_effect: none
  expires_with_run: true
```

This is materially stronger than `filesystem:*`.

## MCP makes tool metadata explicit—but metadata is not a trust boundary

The Model Context Protocol defines structured tool discovery and invocation. A server can publish tool names, descriptions, and JSON Schema inputs, allowing a client to present those tools to a model.[^mcp-tools]

The current MCP specification also warns implementations not to treat tool annotations as inherently trusted. Servers are expected to validate tool inputs and access controls, while clients should preserve user visibility and confirmation around sensitive operations.[^mcp-tools]

That has two implications for Unrestricted Tool Access:

1. **discovery must not equal authorization**, and
2. **schema availability must not equal permission to execute**.

A client may know that a tool exists while still withholding it from a particular agent, user, tenant, or run.

## `skil`: `SKIL-AGENCY-TOOLS` and `SKIL-MCP-001`

The current security matrix maps unrestricted/wildcard tool access to `SKIL-AGENCY-TOOLS` and MCP wildcard exposure to `SKIL-MCP-001`.[^skil-matrix]

The property can be evaluated through both prose and structured manifests:

```text
artifact
  ↓
tool declaration / permission candidate
  ↓
wildcard or broad-scope classification
  ↓
purpose / contract comparison
  ↓
negative context and policy checks
  ↓
finding
```

Structured fields should receive stronger confidence than a phrase such as “use any tools you need” embedded in an explanatory paragraph, although that phrase can still be relevant intent evidence.

## Dynamic discovery creates a moving authorization surface

Modern agent runtimes often support tools that appear and disappear at runtime. This flexibility creates a security problem if the agent's permission model is based only on discovery-time availability.

Imagine:

```text
09:00  client connects to MCP server
09:01  server advertises read-only tools
10:30  server configuration changes
10:31  new destructive tool becomes discoverable
10:32  agent sees it automatically
```

If discovery and authorization are conflated, the agent's authority silently expands. A mature runtime therefore needs a **capability snapshot or policy evaluation** that binds allowed tools to a reviewed identity/version/schema state.

This is related to MCP rug-pull and mutable-identity concerns, but the property here remains narrower: the agent must not automatically inherit every newly visible capability.

## Schema constraints are part of least privilege

A tool with a constrained schema can reduce risk before application-level authorization even runs.

For example, a deployment tool can expose:

```text
deploy(environment ∈ {dev, staging}, artifact_digest, change_id)
```

rather than:

```text
execute(command: string)
```

The first interface encodes allowed semantic actions. The second delegates interpretation to an unrestricted execution surface.

A strong tool contract constrains:

- enumerated operations,
- resource identifiers,
- tenant context,
- maximum batch size,
- destination domains,
- write scope,
- dangerous combinations of parameters.

The authorization layer must still validate those fields. JSON Schema is input structure, not an authorization system.

## OAuth scopes and resource binding

For remote MCP deployments, current authorization guidance builds on OAuth and requires resource-aware token use. The specification requires clients to use resource indicators and servers to validate that tokens were issued for the correct audience, and explicitly forbids token passthrough.[^mcp-auth]

This aligns with RFC 9700's broader OAuth security guidance around restricted tokens and least-privilege authorization.[^rfc9700]

For agentic tools, the practical lesson is simple: **do not give every tool the same bearer token with every scope**. Capability separation at the tool layer is undermined if all calls execute under one unconstrained identity.

## From static allowlist to policy decision

A scalable enterprise design usually needs a policy function:

```text
allow(
  agent_identity,
  user_identity,
  tool_identity,
  operation,
  resource,
  arguments,
  purpose,
  environment,
  approval_state
)
```

The model can propose a tool call. The policy engine decides whether that exact call is authorized.

This creates a clean separation:

```text
LLM:       "I would like to call tool X with arguments Y."
Policy:    "This principal may call X only for resource R under condition C."
Executor:  performs call only after authorization
```

The LLM is an untrusted planner inside the authorization architecture, not the authorization architecture itself.

<Architecture>
Goal → candidate tool call → schema validation → policy authorization → optional approval → execution → result filtering → audit trail
</Architecture>

## Tool minimization improves reliability as well as security

Restricting the tool set is not merely defensive. Large tool catalogs can also make routing harder, increase prompt/context overhead, and create ambiguous affordances.

A router that presents only tools relevant to the current task can improve:

- tool-selection precision,
- context efficiency,
- reviewability,
- deterministic policy evaluation,
- blast-radius containment.

The key is to ensure that the router itself is policy-bound. “The model chose these tools” is not sufficient evidence that they are authorized.

## False positives and legitimate generic agents

Some platforms intentionally expose broad tools to privileged operators. That may be legitimate in a controlled administrative agent, but it changes the trust model.

The scanner should distinguish:

- wildcard tool access with no reviewed contract,
- broad access in an explicitly privileged administrative profile,
- documentation describing wildcard risks,
- policy code that rejects wildcard declarations,
- a narrow tool list whose individual parameters remain unconstrained.

A privileged profile may still deserve a finding; the difference may be **accepted risk** rather than “not a risk.” Findings and policy decisions should not be conflated.

## Evidence chain

A useful result can explain both declared and effective scope:

```yaml
property: unrestricted-tool-access
controls:
  - SKIL-AGENCY-TOOLS
  - SKIL-MCP-001
declared:
  tools:
    - "*"
purpose:
  required_tools:
    - repository.read_file
    - tests.run
assessment:
  overbroad: true
runtime_authorization:
  observable: false
coverage:
  manifest: deterministic
  effective_identity: runtime_dependent
```

That is more actionable than “wildcard found.”

## Runtime observability

Once agents are deployed, useful metrics include:

- number of discoverable tools versus authorized tools,
- tool calls denied by policy,
- privilege-escalation requests,
- new tools appearing during long-running sessions,
- parameter-scope violations,
- calls requiring human approval,
- calls executed under break-glass credentials,
- tool-call frequency and cost budgets.

These metrics can identify permission drift even when the source artifacts remain unchanged.

## Validation matrix

A serious test suite should include:

- literal wildcard permissions,
- natural-language “use all tools” intent,
- explicit allowlists,
- tool groups that indirectly contain broad capabilities,
- dynamic MCP discovery,
- schema changes between versions,
- overbroad parameters on otherwise allowed tools,
- tenant/resource constraints,
- defensive documentation,
- administrative profiles with explicit risk acceptance.

Tool authorization is multidimensional; test data should reflect that.

## Limits

Static scanning cannot normally prove the effective runtime permission set when it depends on:

- remote server configuration,
- OAuth grants,
- dynamic policy,
- tenant membership,
- user approvals,
- server-side argument validation,
- tool behavior that differs from its declaration.

Coverage metadata should state which layers were actually observed.

<KeyTakeaway>
A tool catalog is not an authorization model. The secure agentic pattern is to expose the smallest task-relevant capability set, constrain resource and argument scope, bind credentials to those capabilities, and let an independent policy layer authorize each consequential call.
</KeyTakeaway>

## Conclusion

Unrestricted Tool Access is a capability-design failure, not merely a wildcard-syntax problem. The mature control compares effective authority with task need across operation, resource, tenant, arguments, identity, and time. Static analysis can identify broad declarations and suspicious intent; runtime policy must ultimately ensure that the model can propose only those effects that an independent authorization layer is prepared to permit.
