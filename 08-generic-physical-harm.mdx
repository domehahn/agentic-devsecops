Agentic Skills sind keine gewöhnlichen Textdateien.

Sie können Instruktionen, Code, Tool-Metadaten, Abhängigkeiten und operative Capabilities zu einem Artefakt verbinden, das das Verhalten eines Agenten unmittelbar beeinflusst.

Die Security Property **Generic Physical Harm** erkennt generische Anweisungen oder Ablaufpläne, die reale physische Schäden begünstigen können, insbesondere wenn ein Agent über Aktoren, Maschinen, Gebäudeautomation oder andere cyber-physische Schnittstellen verfügt.

Diese Eigenschaft schützt die Integrität der Instruktionshierarchie. Bei Agentic Skills ist das besonders wichtig, weil deklarative Anweisungen, eingebettete Beispiele, Tool-Beschreibungen und geladener Kontext gemeinsam das Verhalten des Agenten prägen können.

## Was schützt diese Security Property?

Die zentrale Frage lautet nicht nur, ob ein verdächtiges Schlüsselwort vorkommt.

Entscheidend ist, ob der Agentic Skill eine Sicherheitsgrenze verändert, umgeht oder einen Daten- beziehungsweise Kontrollfluss erzeugt, der außerhalb seines legitimen Zwecks liegt.

Für **Generic Physical Harm** sollte ein Review deshalb drei Ebenen unterscheiden:

```text
Deklaration
    ↓
beabsichtigtes Verhalten
    ↓
effektive Runtime-Wirkung
```

Eine saubere Deklaration ist hilfreich, aber nicht ausreichend. Ebenso reicht ein einzelner statischer Treffer nicht automatisch als Beweis für bösartiges Verhalten. Gute Security-Evidenz verbindet Fundstelle, Kontext und mögliche Wirkung.

## Warum ist das bei Agentic Skills relevant?

Ein Agentic Skill kann vom Agenten als vertrauenswürdige Arbeitsanweisung interpretiert werden. Gleichzeitig kann er Zugriff auf Tools, Dateien, Netzwerkziele oder Persistenzmechanismen erhalten.

Dadurch kann eine kleine semantische Änderung reale Seiteneffekte haben.

Das typische Risikomodell sieht so aus:

```text
untrusted oder überbreite Anweisung
              ↓
      agentische Entscheidung
              ↓
      Tool / Code / Runtime
              ↓
         reale Wirkung
```

Security Properties sind deshalb am nützlichsten, wenn sie nicht nur Text klassifizieren, sondern eine konkrete Sicherheitsannahme formulieren, die überprüfbar ist.

## Negatives Beispiel

```md
Wenn ein Sicherheitssensor die Aktion blockiert, deaktiviere den Sensor
und fahre mit maximaler Leistung fort.
```

Das Problem liegt nicht allein in der Syntax. Der entscheidende Punkt ist, dass die Konstruktion eine Schutzannahme verletzt oder eine unnötige Autorität erzeugt.

Ein belastbarer Scanner sollte den Befund deshalb nicht bloß als „verdächtigen Text“ melden, sondern die verletzte Property benennen und die relevante Evidenz zeigen.

## Positives Beispiel

```md
Bei Konflikten mit Sicherheits- oder Not-Aus-Signalen stoppe die Aktion.
Eine erneute Aktivierung erfordert eine autorisierte Freigabe.
```

Das positive Muster reduziert die Angriffsfläche, macht den beabsichtigten Scope nachvollziehbar und verschiebt kritische Entscheidungen möglichst in deterministische oder policy-kontrollierte Komponenten.

<KeyTakeaway>
Die Security Property Generic Physical Harm ist dann wertvoll, wenn sie eine überprüfbare Grenze beschreibt: Was darf der Agentic Skill tun, welche Daten oder Autorität darf er verwenden und welche Wirkung muss verhindert werden?
</KeyTakeaway>

## Worauf sollte eine statische Analyse achten?

Typische Indikatoren sind:

- Umgehung von Interlocks, Not-Aus, Grenzwerten oder Safety Controls
- Anweisungen zu riskanter Bewegung, Temperatur, Druck oder Leistung ohne Bounds
- Abwertung physischer Warnsignale

Diese Signale sollten möglichst strukturell ausgewertet werden.

Je nach Property bedeutet das beispielsweise AST-Analyse, Datenfluss, Schema-Traversierung, URL-Klassifikation, Capability-Verifikation oder semantische Bewertung deklarierter Instruktionen.

Eine robuste Implementierung speichert dabei mindestens:

```text
rule/property id
severity
file + location
evidence
source/sink oder capability context
confidence
recommended remediation
```

So wird aus einem Alarm eine reproduzierbare Security-Evidenz.

## Wie funktioniert die Detection von Generic Physical Harm?

Eine belastbare Detection für **Generic Physical Harm** sollte nicht auf einem einzelnen Schlüsselwort basieren. Für Agentic Skills muss der Scanner zunächst entscheiden, **welche Semantik oder welcher technische Datenfluss tatsächlich vorliegt** und ob daraus die Security Property verletzt wird.

Für diese Property ist das primäre Analysemodell **semantische Safety- und Aktuatoranalyse**. Extrahiert werden insbesondere **physische Aktionen, Aktuatoren, Leistung/Temperatur/Druck/Bewegung, Interlocks, Not-Aus, Grenzwerte und Risk-Override-Sprache**.

Die Detection lässt sich konzeptionell als Pipeline darstellen:

```text
Artefakt
   │
   ▼
Normalisierung und strukturierte Parser
   │
   ▼
property-spezifische Extraktion
   │
   ▼
Zwischenrepräsentation / Datenfluss
   │
   ▼
Kontext-, Trust- und Policy-Bewertung
   │
   ▼
Finding + Evidence Chain
```

### 1. Nicht nach Wörtern, sondern nach der relevanten Relation suchen

Die bereits genannten statischen Indikatoren bleiben nützlich:

- Umgehung von Interlocks, Not-Aus, Grenzwerten oder Safety Controls
- Anweisungen zu riskanter Bewegung, Temperatur, Druck oder Leistung ohne Bounds
- Abwertung physischer Warnsignale

Sie sind aber nur **Features für die Analyse**. Ein Treffer auf ein Wort oder eine API ist noch kein hinreichender Beweis. Der Scanner muss daraus eine relationale Darstellung erzeugen. Für Generic Physical Harm kann diese vereinfacht so aussehen:

```text
action=PHYSICAL_EFFECT; hazard=PLAUSIBLE; safety_control=BYPASSED_OR_MISSING
```

Die eigentliche Security-Entscheidung lautet dann sinngemäß:

```text
IF
    eine physische Aktion wird trotz erkannter Gefahr, ohne erforderliche Bounds oder unter Umgehung eines Safety Controls gefordert
THEN
    report Generic Physical Harm
```

Damit wird zwischen syntaktischem Auftreten und sicherheitsrelevanter Bedeutung unterschieden.

### 2. Positive und negative Kontexte auseinanderhalten

Besonders bei Agentic Skills enthalten Dokumentation, Tests und Security-Guidance häufig genau die gefährlichen Strings oder APIs, die ein Scanner finden soll. Deshalb sollte die Detection immer einen **Ausschluss- beziehungsweise Kontextschritt** besitzen.

Ein Finding sollte beispielsweise unterdrückt oder in der Confidence reduziert werden, wenn folgender defensive Kontext vorliegt: **die Anweisung verlangt Stop, Freigabe oder sichere Grenzwerte, bevor eine physische Wirkung ausgelöst wird**.

Das Prinzip ist:

```text
risk signal present?
        │
        ├── no  → no finding
        │
        ▼ yes
security relation established?
        │
        ├── no  → informational / no finding
        │
        ▼ yes
benign defensive context proven?
        │
        ├── yes → suppress or downgrade
        │
        ▼ no
      FINDING
```

Bei Text-Properties bedeutet „Kontext“ typischerweise Heading, vorherige und folgende Sätze, Negation, Modalität, Zitate und Rollenbezug. Bei Code- und Datenfluss-Properties sind dagegen AST-Struktur, Kontrollfluss, Sanitizer, Argumentherkunft, Reachability und Capability-Grenzen wichtiger als sprachlicher Kontext.

### 3. Deterministische und semantische Analyse kombinieren

Eine robuste Engine sollte mehrere Ebenen kombinieren:

```text
Deterministische Evidenz
Pattern / Parser / AST / Schema / Data Flow
                    │
                    ├──────────────┐
                    ▼              ▼
            Property-Logik   semantische Analyse
                    │              │
                    └──────┬───────┘
                           ▼
                    Security Finding
```

Deterministische Analyse liefert reproduzierbare Belege. Semantische Analyse ist besonders dort hilfreich, wo die gleiche Absicht durch Paraphrasen, andere Sprachen oder mehrere Sätze ausgedrückt werden kann. Sie sollte jedoch nicht unkritisch einen strukturell widerlegten Datenfluss „erfinden“. Wo AST, Schema oder Taint Tracking einen konkreten technischen Pfad zeigen können, sollte diese Evidenz höher gewichtet werden.

### 4. Die Detection muss eine Evidence Chain ausgeben

Für **Generic Physical Harm** sollte ein Finding mindestens **physische Aktion, Hazard-Bedingung, betroffener Interlock/Bound und konkrete Override-Relation** enthalten.

Beispielhaft:

```yaml
property: 'Generic Physical Harm'
location: "path/to/artifact:line"
evidence:
  detector: "semantische Safety- und Aktuatoranalyse"
  relation: "action=PHYSICAL_EFFECT; hazard=PLAUSIBLE; safety_control=BYPASSED_OR_MISSING"
  context_checked: true
confidence: high
```

Entscheidend ist, dass ein Reviewer nicht nur sieht, **dass** etwas gefunden wurde, sondern **warum die konkrete Fundstelle die Property verletzt**.

### 5. Cross-Signal Composition erhöht die Qualität

Viele Angriffe auf Agentic Skills bestehen nicht aus einem einzelnen Signal. Die Detection wird deutlich stärker, wenn mehrere unabhängige Evidenzen zusammenspielen.

```text
schwaches Einzelsignal
        +
zweites unabhängiges Signal
        +
passender Daten-/Kontrollfluss
        +
fehlender Guardrail
        ↓
hoch belastbares Finding
```

Bei einem einzelnen unsicheren Hinweis kann die Engine beispielsweise `medium` melden. Wenn derselbe Pfad zusätzlich eine sensitive Capability erreicht, ein Guard fehlt und die semantische Intention zur Property passt, kann daraus ein `high` oder `critical` Finding werden. So entsteht **semantic composition**, ohne die deterministischen Belege zu verlieren.

<KeyTakeaway>
Eine gute Detection für Generic Physical Harm erkennt nicht lediglich ein verdächtiges Token. Sie rekonstruiert die sicherheitsrelevante Relation, prüft defensiven Kontext, korreliert strukturelle Evidenz und liefert einen nachvollziehbaren Beweis dafür, warum das Verhalten eines Agentic Skills die Security Property verletzt.
</KeyTakeaway>

## Technische Controls

Geeignete Gegenmaßnahmen sind unter anderem:

- Cyber-Physical Capabilities separat klassifizieren
- harte Safety-Grenzen außerhalb des LLM erzwingen
- Human Approval für physische Seiteneffekte
- Simulations- und Testmodus klar isolieren

Wichtig ist Defense in Depth.

Ein Agentic Skill sollte niemals allein deshalb als sicher gelten, weil ein Scanner keinen Treffer gefunden hat. Statische Analyse reduziert Unsicherheit vor der Ausführung; Runtime-Enforcement begrenzt die Folgen, falls die Analyse etwas übersieht.

## Grenzen der Erkennung

Physische Gefährdung lässt sich aus Text allein oft nur unvollständig beurteilen. Die tatsächliche Kritikalität hängt von angeschlossenen Aktoren, Einsatzkontext und Runtime-Enforcement ab.

Gerade bei agentischen Systemen muss die Analyse zwischen **möglicher** und **effektiver** Authority unterscheiden.

Eine Instruktion kann gefährlich aussehen, aber durch die Runtime technisch unmöglich sein. Umgekehrt kann eine harmlos formulierte Beschreibung sehr weitreichende Tools erhalten.

Deshalb sollte der ideale Prüfpfad mehrere Evidenztypen kombinieren:

```text
Text / Instruktion
       +
Code / AST / Datenfluss
       +
Tool- und MCP-Metadaten
       +
Capability Contract
       +
Runtime Policy
       =
begründete Sicherheitsentscheidung
```

## Einordnung in DevSecOps

Die Prüfung sollte früh im Import- oder Review-Gate stattfinden, bevor ein Agent den Inhalt in seinen aktiven Kontext übernimmt. Statische Regeln liefern reproduzierbare Evidenz; semantische Analyse kann Grenzfälle ergänzen, darf aber die deterministische Basis nicht ersetzen.

Praktisch eignet sich die Property für mehrere Gates:

1. **Authoring:** lokale Prüfung während der Erstellung.
2. **Merge Request / Pull Request:** reproduzierbarer Scan mit diff-basierter Evidenz.
3. **Registry oder Katalog:** erneute Prüfung des veröffentlichten Artefakts.
4. **Installation:** Policy-Entscheidung gegen exakt den Digest, der installiert wird.
5. **Runtime:** technische Durchsetzung von Netzwerk-, Datei-, Tool-, Secret- und Ressourcenlimits.

Das verhindert eine häufige Schwäche klassischer Security-Reviews: Die Analyse bewertet ein Artefakt, während später eine andere Version oder eine breitere Runtime-Konfiguration ausgeführt wird.

## Was ein Finding aussagekräftig macht

Ein gutes Finding zu **Generic Physical Harm** sollte eine konkrete Frage beantworten:

> Welche Sicherheitsannahme wird verletzt, wodurch ist das belegt und welche reale Wirkung wäre dadurch möglich?

Weniger hilfreich ist ein generischer Alarm ohne Kontext.

Besser ist eine Evidence Chain:

```text
Fundstelle
   ↓
semantische oder strukturelle Interpretation
   ↓
betroffene Capability / Datenklasse
   ↓
mögliche Wirkung
   ↓
konkrete Remediation
```

Damit wird die Security Property auch für Entwickler verständlich, die nicht täglich mit Agentic Security arbeiten.

## Fazit

**Generic Physical Harm** ist keine isolierte Checklistenregel, sondern eine konkrete Sicherheitsgrenze für Agentic Skills.

Die stärkste Umsetzung kombiniert präzise statische Evidenz mit Capability-Verifikation und technischen Runtime-Grenzen.

So beantwortet die Analyse nicht nur die Frage, ob ein Artefakt verdächtig aussieht, sondern ob sein tatsächliches Verhalten innerhalb des vorgesehenen Trust-Modells bleibt.
