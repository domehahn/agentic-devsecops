Ein AI Skill ist nur selten eine einzelne Datei. Neben `SKILL.md` liegen dort Skripte, Konfigurationen, Package-Manifeste, MCP-Definitionen, Referenzen und Assets. Wer ausschließlich die zentrale Markdown-Datei betrachtet, sieht deshalb nur einen Ausschnitt der tatsächlichen Angriffsfläche.

Der Directory Scan ist die Grundlage für eine realistische Sicherheitsanalyse: Der Scanner muss ein Verzeichnis als **zusammenhängendes Artefakt** verstehen und alle relevanten Dateien in denselben Analysekontext aufnehmen.

<Architecture>
Der Directory Scan definiert die erste Trust Boundary: Aus einem potenziell feindlichen Dateibaum muss ein kanonisches, nicht ausgeführtes Analyseartefakt werden.
</Architecture>

## Was das Feature wirklich bedeutet

Ein guter Directory Scan beantwortet nicht nur die Frage, welche Dateien existieren. Er muss auch sicherstellen, dass das Einlesen selbst keine neue Vertrauensverletzung erzeugt. Besonders wichtig sind stabile relative Pfade, Größenlimits, eine nachvollziehbare Dateiliste und die Trennung zwischen *Lesen* und *Ausführen*.

Das ist bei Skills relevant, weil sich Verhalten über mehrere Dateien verteilt. Eine harmlose Anweisung in `SKILL.md` kann beispielsweise auf `scripts/run.py` verweisen, während erst dort Netzwerkzugriff oder Prozessausführung sichtbar wird. Cross-File-Analyse ist deshalb wichtiger als ein isolierter Textscan.

## SkillSpector

SkillSpector akzeptiert lokale Verzeichnisse direkt und normalisiert unterschiedliche Eingabeformen auf einen lokalen Scan-Kontext. Die Analyzer erhalten damit den Inhalt des Skills, ohne dass der Skill zur Analyse ausgeführt werden muss.

Für die Praxis bedeutet das: Ein Entwickler kann den Skill-Ordner vor Installation oder Merge direkt prüfen. Der Directory Scan ist damit die natürliche Eingabeform für lokale Entwicklung und CI.

## `skil`

`skil` lädt Verzeichnisse ebenfalls als Artefakt und erstellt dabei ein Manifest mit stabilen Pfaden und SHA-256-Bezug. Ein wichtiges Detail ist `.skilignore`: generierte Dateien können bewusst ausgeschlossen werden, aber `skil` übernimmt nicht automatisch `.gitignore`. Sicherheitsrelevante Dateien sollen nicht nur deshalb aus einem Scan verschwinden, weil Git sie ignoriert.

Zusätzlich wird der Analyseumfang über Coverage und ein Inspection Ledger sichtbar. Damit lässt sich unterscheiden, ob eine Datei analysiert, übersprungen oder für einen Analyzer nicht relevant war.

## Praxisbeispiel

```bash
# SkillSpector
skillspector scan ./skills/deploy-helper --no-llm

# skil
skil scan ./skills/deploy-helper --static-only
```

Angenommen, `SKILL.md` beschreibt einen Deployment-Workflow, `scripts/deploy.py` liest Umgebungsvariablen und `mcp.json` erlaubt mehrere Tools. Der Verzeichnisscan kann diese Informationen gemeinsam betrachten. Ein Scan nur von `SKILL.md` würde die Code- und Toolseite dagegen ausblenden.

## Security- und DevSecOps-Einordnung

- Verzeichnisse als unvertrauenswürdige Artefakte behandeln, nicht als ausführbare Projekte.
- Scanumfang und ausgeschlossene Dateien auditierbar machen.
- Cross-File-Beziehungen berücksichtigen, weil Risiken häufig erst über mehrere Dateien sichtbar werden.
- CI sollte immer denselben Wurzelpfad und dieselben Ausschlussregeln verwenden.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

## Typische Fehlinterpretation

„Wenn `SKILL.md` sauber ist, ist der Skill sauber.“ Das übersieht Code, Konfiguration, Dependencies und Tooldefinitionen im selben Verzeichnis. Der Directory Scan ist gerade deshalb wertvoll, weil er diese künstliche Dateigrenze aufhebt.

## Einordnung in die Pipeline

Dieses Feature gehört in die **Ingestion-Stufe** der Pipeline. Bevor Analyzer oder Policies überhaupt laufen, muss klar sein, welches Artefakt gelesen wird, wie es kanonisiert wird und welche zusätzlichen Fähigkeiten – insbesondere Netzwerk – dafür notwendig sind.

Ein belastbares Muster ist: Input auflösen → Digest/Manifest erzeugen → statisch analysieren → Report/Evidence speichern. Bei Remote-Eingaben sollte der Netzwerkzugriff in einem eigenen Job oder Runner-Profil aktiviert werden.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Funktional herrscht Gleichstand: Beide Scanner können komplette Skill-Verzeichnisse analysieren. Für eine DevSecOps-Pipeline ist weniger entscheidend, *dass* ein Directory Scan existiert, sondern wie transparent der tatsächliche Analyseumfang dokumentiert wird.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
