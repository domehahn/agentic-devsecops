The most dangerous transition in many agent systems is almost invisible in an architecture diagram. A model produces text. A framework treats that text as a command, script, SQL fragment, expression, or tool argument. A representation that was **data one moment becomes executable authority the next**.

That transition is the subject of the **Output → Execution** property.

The central relation is:

```text
MODEL_OR_TOOL_OUTPUT -> EXECUTION_SINK ∧ VALIDATION=ABSENT
```

`skil` maps the property to `SKIL-OUTPUT-EXECUTION`, with structural reinforcement from `SKIL-PY-001` and `SKIL-TAINT-EXECUTION` when the behavior is visible in Python code.

This is a more fundamental issue than “the model might write bad code.” Models are supposed to generate code in many legitimate workflows. The security failure happens when **untrusted generative output crosses directly into an interpreter or privileged executor without a deterministic boundary**.

<KeyTakeaway>
Model output should be treated like untrusted network input. Fluency, JSON formatting, confidence, or the fact that the same model produced the surrounding plan does not raise its trust level.
</KeyTakeaway>

## A code/data boundary, not an AI-specific superstition

The underlying principle predates LLMs. Secure systems have always separated data from code:

- SQL parameters should not become SQL syntax.
- User strings should not become shell programs.
- Templates should not evaluate arbitrary expressions.
- Serialized data should not select unrestricted object constructors.
- Network input should not be passed to `eval`.

Agentic systems reintroduce the same class of risk through a new source: **model and tool outputs**.

A dangerous flow can be summarized as:

```text
untrusted or probabilistic source
          │
          ▼
      model/tool output
          │
          ▼
  parsing / transformation
          │
          ▼
    execution boundary
          │
          ▼
 shell | eval | interpreter | dynamic import | privileged tool
```

The transformation layer is important. A flow may remain dangerous even if the raw output is first placed in JSON, Base64, Markdown fences, or a temporary file. Encoding is not validation.

## The direct positive example

The source article uses:

```python
code = model_response.text
exec(code)
```

This is a strong positive because the relation is explicit. The model output is the source; Python `exec` is the sink; there is no allowlist, parser, schema, or sandbox boundary between them.

A good finding can therefore explain itself:

```yaml
property: output-execution
controls:
  - SKIL-OUTPUT-EXECUTION
  - SKIL-PY-001
  - SKIL-TAINT-EXECUTION
source:
  kind: model_output
  symbol: model_response.text
sink:
  kind: dynamic_code_execution
  call: exec
path:
  - model_response.text
  - code
  - exec(code)
declassifier: none
security_relation: MODEL_OR_TOOL_OUTPUT -> EXECUTION_SINK ∧ VALIDATION=ABSENT
confidence: high
```

This is qualitatively better than “found `exec(` on line 42,” because it proves that the *argument* derives from the untrusted source.

## A safe design uses a narrow intermediate language

The source-negative pattern is more interesting:

```python
plan = json.loads(model_response.text)
validated = PlanSchema.model_validate(plan)
execute_allowed_actions(validated)
```

This can be safe **if** `PlanSchema` actually narrows the language and `execute_allowed_actions` does not reintroduce arbitrary interpretation.

The pattern is conceptually:

```text
free-form model output
        │
        ▼
     parse data
        │
        ▼
 validate schema
        │
        ▼
 map to finite action set
        │
        ▼
 policy / authorization
        │
        ▼
 implementation
```

The security gain comes from reducing a potentially Turing-complete output space to a small, typed command language.

For example:

```yaml
action: read_file
path: docs/architecture.md
```

can be validated against an enum of actions, a workspace path policy, and a read-only permission set. The model never gets to emit shell syntax at all.

## Why “JSON mode” is not a security boundary

Structured generation is valuable, but it is frequently misunderstood.

A JSON object such as:

```json
{
  "command": "..."
}
```

is still dangerous if `command` is later passed to a shell. JSON guarantees syntax, not semantics.

Similarly, an MCP tool definition can constrain a parameter to `string` while leaving its security meaning completely open. A parameter named `query`, `path`, `url`, or `expression` may still carry syntax for another interpreter.

The real control must therefore exist at the **semantic boundary**:

- enums instead of unconstrained strings where possible;
- path canonicalization and root confinement;
- URL scheme/host allowlists;
- prepared statements for database operations;
- argument arrays rather than shell command strings;
- command identifiers mapped to fixed implementations;
- and explicit authorization for side effects.

## Three distinct execution patterns

A useful detector should distinguish at least three families.

### Direct dynamic execution

Examples include `exec`, `eval`, dynamic `Function` construction, or equivalent interpreter APIs. When the argument is model-derived, the source-to-sink path is direct.

### Shell or process execution

The model produces a command or command fragment, and code passes it to a shell/process API. Risk depends heavily on whether shell parsing is enabled and whether arguments are structured.

### Tool-mediated execution

The model selects a high-impact tool and supplies parameters that themselves carry executable semantics. This is common in agent frameworks, because “execution” may occur outside the language runtime.

The last category is why output handling and excessive agency interact. A model does not need access to `exec` if it can call a deployment, database, terminal, or automation tool with equivalent authority.

## Validation is only valid when it narrows behavior

Security documentation often says “validate model output.” That phrase is too vague.

Validation is meaningful only if it removes dangerous states from the input space. A regex such as `.*` is validation in name only. A JSON schema with every property defined as arbitrary string provides structure but little authority reduction.

Strong validation tends to have these properties:

```text
finite action vocabulary
+ typed parameters
+ bounded lengths
+ resource allowlists
+ canonicalized identifiers
+ side-effect classification
+ authorization checks
```

The validator should be deterministic. Asking the same or another LLM “is this command safe?” may be useful as an additional signal, but it is not a substitute for enforcement.

## Taint analysis: following provenance instead of words

The source files correctly emphasize taint analysis because output-to-execution is a **flow property**.

A bounded taint engine can label sources such as:

```text
model response
tool response
retrieved document
user input
environment secret
```

and propagate those labels through assignments, containers, selected function summaries, and transformations.

A finding occurs when taint reaches a sink such as:

```text
exec / eval
subprocess with shell parsing
dynamic code loader
script interpreter
high-impact tool parameter
```

without passing through a recognized declassifier.

The important caveat is that declassification must be security-specific. `str(value)` is a transformation, not a declassifier. `json.loads` is a parser, not by itself a declassifier. A schema plus an action allowlist may be.

## Sandboxing: essential, but not permission to skip validation

Some systems respond to output execution risk by placing code in a container or sandbox. That is good defense in depth, but it changes the consequence rather than the underlying trust error.

A sandbox must itself be constrained:

- no ambient cloud credentials;
- no host filesystem mounts beyond what is required;
- no Docker socket;
- no privileged mode;
- controlled network egress;
- CPU, memory, process, and wall-clock limits;
- disposable state;
- and explicit output channels.

Otherwise “sandboxed execution” becomes an alternate path to the host.

## Cross-language examples

The security relation is independent of language.

Python:

```python
exec(model_text)
```

JavaScript:

```typescript
new Function(modelText)()
```

Shell:

```bash
sh generated-script.sh
```

Database:

```python
cursor.execute(model_generated_sql)
```

Infrastructure:

```text
model output -> generated Terraform -> unattended apply
```

The last example is not automatically unsafe. Generated infrastructure code can be reviewed, policy-checked, planned, and approved. The dangerous version is the absence of gates between generation and privileged execution.

## False positives and semantic context

A robust detector must not flag every appearance of dangerous APIs.

Scanner-negative examples include:

```python
example = "Never call exec(model_output)"
```

or a security test fixture that intentionally contains `exec`.

Even executable code can be safe in context:

```python
subprocess.run(["git", "status", "--short"], shell=False, check=True)
```

The call starts a process, but the command and arguments are fixed and do not derive from untrusted model output.

This is why parser-based evidence is stronger than regex. A syntax tree can distinguish a comment, a string literal, and an actual call expression. Taint adds the provenance question on top.

## Composition with other properties

Output-to-execution often becomes critical when combined with other findings.

```text
indirect prompt injection
        +
untrusted tool output
        +
cross-context promotion
        +
output-to-execution
        =
remote influence over execution
```

Severity should increase only when the paths compose. Two independent findings in unrelated files do not automatically form an exploit chain.

The scanner therefore benefits from retaining a graph:

```text
source → transformations → trust boundary → sink
```

rather than only a flat list of rule IDs.

## Runtime architecture: the executor should distrust the planner

The cleanest pattern is to separate roles.

The LLM planner can propose intent:

```json
{"action":"restart_service","service":"api"}
```

A deterministic executor then:

1. validates the schema;
2. normalizes the service identifier;
3. checks whether `restart_service` is allowed for this workflow;
4. checks whether `api` is within the authorized resource scope;
5. evaluates approval requirements;
6. executes a fixed implementation;
7. records evidence.

The planner never emits shell syntax. This makes the privilege boundary explicit.

## Testing strategy

A serious control suite should cover:

- direct `exec`/`eval`;
- aliases to dangerous functions;
- model output copied through intermediate variables;
- decoded/parsed output that still reaches execution;
- safe structured plans;
- safe fixed process calls;
- security documentation containing dangerous terms;
- test fixtures;
- model output used only for display;
- sanitized paths versus unchecked paths;
- tool calls where parameter schemas are narrow versus arbitrary strings.

Mutation tests can be particularly valuable: take a scanner-negative fixture and remove exactly one guard. The result should become positive. This demonstrates that the detector understands the guard rather than merely the surrounding syntax.

## The broader design principle

OWASP’s Improper Output Handling category captures the application-level problem: model output must not be trusted merely because the model is internal. Agentic systems intensify that principle because output can trigger real-world side effects.

The most durable rule is:

> **Generative output may propose; deterministic code must dispose.**

A model can select from a constrained plan space. It should not get a transparent path from arbitrary text generation into unrestricted execution.

## Deep dive: build a small execution language instead of sanitizing a large one

One of the most powerful defensive techniques is to avoid accepting a general-purpose language from the model at all.

Suppose an agent needs to interact with Git. The unsafe interface is:

```json
{"command": "git ..."}
```

The safe direction is a task-specific intermediate representation:

```json
{
  "operation": "show_commit",
  "revision": "a1b2c3d4..."
}
```

The executor maps that structure to a fixed implementation.

This changes the problem dramatically. Instead of trying to prove an arbitrary shell program safe, the system validates:

```text
operation ∈ finite enum
revision ∈ Git-SHA grammar
```

The command syntax never enters the model output space.

### Treat generated code as an artifact

Developer agents legitimately generate code. A secure pipeline can preserve the data/code boundary by treating generated code as an **artifact under review** before execution:

```text
model generates patch
   ↓
write to isolated workspace
   ↓
static analysis / lint / type check
   ↓
diff policy
   ↓
tests in sandbox
   ↓
human or policy approval
   ↓
promotion
```

This is different from:

```text
model generates code -> exec immediately
```

The former turns execution into a supply-chain workflow with evidence.

### Plan validation should be capability-aware

A schema that validates action names can still allow an unsafe sequence.

Example:

```json
[
  {"action":"read_secret"},
  {"action":"send_http"}
]
```

Each action might be valid individually. Their composition creates a prohibited flow.

Therefore the validator can inspect the **plan graph**:

```text
secret source
   ↓
network sink
```

and reject the sequence before execution.

### Deterministic policy is stronger than model self-critique

An LLM can review its own generated command and say “this looks safe.” That can be useful for usability, but it should not be the authorization step.

Deterministic policy can answer concrete questions:

```text
Is this action in the allowlist?
Is this resource within the workspace?
Does this action require approval?
Does any sensitive source flow to an external sink?
```

Those questions can be tested exhaustively far more reliably than a natural-language judgment.

## Execution evidence as a chain of custody

For generated artifacts, record:

```text
model/version
prompt/task id
artifact digest
scanner results
test results
approval identity
execution environment digest
result
```

The goal is not bureaucratic logging. It is to make the path from probabilistic generation to deterministic execution **reconstructable**.

If an incident occurs, investigators can identify whether the failure came from generation, validation, approval, or the executor.

This is the difference between “the AI ran something bad” and a security system that can explain exactly where a trust boundary failed.
