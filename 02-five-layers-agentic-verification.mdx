There is no single scan that can answer whether an autonomous artifact is safe.

The reason is simple: agentic behavior exists across multiple layers. Structure, source code, natural-language intent, runtime behavior, and actual permissions are related, but they are not the same thing.

A practical verification architecture separates them.

## Layer 1: Structural verification

Structural verification answers:

```text
Can I parse and reason about this artifact reliably?
```

Typical checks include:

- required metadata exists
- schemas are valid
- referenced files exist
- permission declarations are syntactically valid
- archives are canonical and bounded
- ambiguous layouts are rejected

This layer should be deterministic and cheap.

It is not a security verdict. A malicious artifact can be perfectly valid.

## Layer 2: Static semantic verification

This is the traditional scanning layer.

It inspects content without executing it:

```text
instructions
code
dependencies
tool metadata
configuration
```

It can detect properties such as:

- prompt injection
- anti-refusal instructions
- secret access
- dangerous execution
- wildcard permissions
- unpinned dependencies
- Unicode deception
- unsafe MCP metadata

Static analysis is scalable and suitable for CI, but it operates on what can be inferred from the artifact.

## Layer 3: Behavioral verification

Behavioral verification asks:

```text
What does the agent actually do when given a task?
```

This requires controlled execution.

Examples:

- Does a read-only task attempt a write?
- Does the agent call undeclared network destinations?
- Does it request secrets it does not need?
- Does it follow a malicious tool response?
- Does it ask for confirmation before a destructive operation?

This layer measures behavior rather than source properties.

## Layer 4: Adversarial verification

A system that behaves correctly on the happy path can still fail under pressure.

Adversarial verification introduces intentionally hostile conditions:

```text
malicious tool output
prompt injection
ambiguous instructions
conflicting context
unexpected dependency metadata
Unicode deception
permission boundary probes
```

The goal is not to prove invulnerability. It is to test whether the controls fail safely when assumptions are challenged.

<KeyTakeaway>
Behavioral evaluation asks "does it work?" Adversarial evaluation asks "does it stay within bounds when something tries to make it misbehave?"
</KeyTakeaway>

## Layer 5: Runtime verification and enforcement

The final layer operates at the point of action.

The agent may request:

```text
read file
write file
send HTTP request
run command
access secret
invoke tool
```

A trusted gateway decides whether the request is allowed.

```text
Agent request
     ↓
Policy
     ↓
Capability gate
     ↓
Trusted implementation
```

This is fundamentally different from scanning.

A prompt that says "do not access secrets" is guidance.

A gateway that does not expose a secret-read operation is a security boundary.

<Architecture>
The strongest agent policy is one the agent does not have the technical ability to violate.
</Architecture>

## The layers answer different questions

| Layer | Question |
| --- | --- |
| Structural | Is the artifact valid and inspectable? |
| Static | What risks can be inferred without execution? |
| Behavioral | What does it actually do? |
| Adversarial | What happens under hostile conditions? |
| Runtime | What actions are technically possible? |

Collapsing these layers creates misleading claims.

For example:

```text
static scan passed
```

does not imply:

```text
runtime behavior is safe
```

Likewise:

```text
policy says network=false
```

does not imply:

```text
network access is impossible
```

unless the runtime enforces it.

## Evidence should flow forward

A mature pipeline connects the layers:

```text
artifact digest
      │
      ├── validation result
      ├── scan result
      ├── capability observations
      ├── behavioral metrics
      ├── adversarial results
      └── enforcement coverage
              │
              ▼
           policy
```

Every result should be bound to the same artifact identity. Otherwise a clean scan of one version can accidentally authorize another.

## Do not aim for one perfect scanner

The engineering objective is not:

```text
build a scanner that knows everything
```

It is:

```text
combine independent controls
so that failure in one layer
does not become system compromise
```

That is the same principle that made defense in depth useful long before agents existed.

The difference is that agentic systems make the gap between "instruction" and "enforcement" impossible to ignore.
