Static-only bedeutet, dass ein Scan vollständig mit deterministischen Parsern, Regeln, Signaturen und Heuristiken durchgeführt wird. Es findet keine semantische Bewertung durch ein Sprachmodell statt.

Das Feature ist damit nicht nur eine Komfortfunktion.

Es verändert, **welcher Kontext geprüft wird, welche Vertrauensgrenzen gelten und wie belastbar das Ergebnis später in CI/CD oder Security-Governance verwendet werden kann**.

## Was das Feature leistet

Der Modus ist für reproduzierbare Security Gates wichtig. Gleicher Input, gleiche Regelversion und gleiche Konfiguration sollen zu demselben Ergebnis führen. Dadurch lassen sich Findings leichter testen, versionieren und in Compliance-Prozesse integrieren.

Statische Analyse kann Syntax, gefährliche APIs, verdächtige Strings, bekannte Muster, Abhängigkeiten, Metadaten und strukturelle Policy-Verstöße sehr zuverlässig erkennen. Ihre Grenze liegt bei Bedeutung, impliziten Absichten und komplexen semantischen Zusammenhängen.

## Typischer Ablauf

Unabhängig von der konkreten Implementierung sollte der Ablauf klar getrennte Phasen besitzen:

```text
Input
  ↓
Validierung und Normalisierung
  ↓
Feature-spezifische Verarbeitung
  ↓
Security-Analyse
  ↓
Findings + Coverage + technischer Status
  ↓
Policy-Entscheidung
```

Diese Trennung ist wichtig, weil ein technischer Fehler bei Beschaffung, Parsing oder Providerzugriff nicht dieselbe Bedeutung hat wie ein tatsächlich unauffälliges Prüfergebnis.

## Negatives Beispiel

Ein Build ist so konfiguriert, dass jeder Scan zwingend eine externe semantische Analyse benötigt. Bei einem Provider-Ausfall kann kein Release geprüft werden. Außerdem variieren Begründungen zwischen Läufen, obwohl der Quellstand identisch ist.

```text
CI -> externer Provider nicht erreichbar -> Scan abgebrochen -> Release blockiert
```

Für einen deterministischen Basisschutz ist diese Kopplung unnötig.

## Positives Beispiel

Die Pipeline nutzt einen statischen Baseline-Scan als verlässliches Gate:

```bash
scanner scan ./artifact --static-only
```

Regeln erkennen beispielsweise:

```text
- verdächtige Shell-Ausführung
- geheime Schlüssel im Text
- unsichere URLs
- bekannte Schwachstellen
- YARA-Treffer
- Policy-Verstöße
```

Semantische Analyse kann separat als zusätzliche Stufe laufen, ohne die deterministische Mindestprüfung zu ersetzen.

<KeyTakeaway>
Determinismus ist ein Sicherheitsmerkmal. Static-only schafft eine reproduzierbare Baseline, deren Grenzen klar benannt und gezielt durch weitere Analyseformen ergänzt werden können.
</KeyTakeaway>

## Security- und Betriebsaspekte

Static-only reduziert Datenabfluss, externe Abhängigkeiten und Variabilität. Es ist daher oft die richtige Wahl für vertraulichen Quellcode, air-gapped Umgebungen und harte CI-Gates.

Gleichzeitig darf der Modus nicht als vollständiges Sicherheitsurteil dargestellt werden. Semantische Täuschung, mehrdeutige Dokumentation oder verteilte Absichten können außerhalb statischer Regeln liegen. Coverage sollte explizit beschrieben werden.

Ein professioneller Betrieb sollte außerdem drei Zustände konsequent auseinanderhalten:

```text
clean      = geprüft, kein relevanter Befund
finding    = geprüft, mindestens ein relevanter Befund
incomplete = Prüfung technisch oder fachlich nicht vollständig
```

Gerade der dritte Zustand ist für DevSecOps entscheidend.

Ein Scanner darf fehlende Coverage nicht als positives Sicherheitsurteil darstellen.

## Wo das Feature sinnvoll eingesetzt wird

Geeignet für Pre-Commit, Pull Requests, Offline-Scans, reproduzierbare Regressionstests und Compliance-Nachweise. Auch als erste Stufe eines mehrschichtigen Scans ist der Modus stark.

Bei neuartigen, kontextabhängigen Angriffsmustern kann eine nachgelagerte semantische Analyse zusätzliche Evidenz liefern.

Die konkrete Aktivierung sollte deshalb aus dem gewünschten Trust-Modell abgeleitet werden und nicht allein aus technischer Verfügbarkeit.

## Integration in eine DevSecOps-Pipeline

In einer Pipeline sollte das Feature nicht isoliert betrachtet werden.

Ein belastbares Muster ist:

```text
Source / Artifact
      ↓
Input-Validierung
      ↓
Deterministische Analyse
      ↓
optionale erweiterte Analyse
      ↓
normalisierte Findings
      ↓
Policy Gate
      ↓
Report / Audit Evidence
```

Dabei sollte jeder Report mindestens folgende Informationen transportieren:

- Identität des analysierten Artefakts
- aktive Analyseverfahren
- übersprungene oder nicht verfügbare Prüfschritte
- stabile Regel- oder Finding-IDs
- Schweregrad und Evidenz
- Scanner- und Regelversion
- eindeutiger technischer Abschlussstatus

Damit wird das Feature nicht nur ausführbar, sondern **auditierbar**.

## Fazit

Determinismus ist ein Sicherheitsmerkmal. Static-only schafft eine reproduzierbare Baseline, deren Grenzen klar benannt und gezielt durch weitere Analyseformen ergänzt werden können.

Der eigentliche Wert entsteht dann, wenn das Feature mit klaren Grenzen, reproduzierbaren Eingaben und transparenten Ergebnissen in den Entwicklungsprozess eingebettet wird.
