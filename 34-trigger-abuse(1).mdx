Before an agentic skill can misuse a tool, leak data, or overreach its scope, the system must first decide **to activate it**.

That routing decision is often driven by natural-language descriptions, trigger words, manifest fields, classifier output, or model-based skill selection. Poorly designed triggers create an unexpectedly large activation surface: the skill runs for requests that were never intended to invoke it.

The source models Trigger Abuse as:

```text
TRIGGER_SET is overly broad -> unintended activation surface
```

with `SKIL-TRIGGER-GENERIC` and `SKIL-TA-001` covering the documented patterns.

<KeyTakeaway>
Trigger design is part of authorization. A skill that activates for “anything” effectively asks the router for ambient relevance across the entire application.
</KeyTakeaway>

## Routing is a security decision

Skill routing is usually described as a UX or performance problem:

> Which skill best matches this request?

From a security perspective the question is:

> Which capabilities become available because the router selected this skill?

A broad trigger may expose a powerful capability in contexts where users and reviewers did not expect it.

## The obvious positive case

```yaml
triggers:
  - "help"
  - "any request"
```

These phrases are semantically generic. They match a huge portion of normal user behavior.

A finding should capture the activation problem:

```yaml
property: trigger-abuse
controls:
  - SKIL-TRIGGER-GENERIC
  - SKIL-TA-001
trigger_set:
  - help
  - any request
scope: overbroad
effect: unintended_activation_surface
relation: TRIGGER_SET is overly broad -> unintended activation surface
confidence: high
```

## A scoped negative example

```yaml
triggers:
  - "scan-agentic-skill"
  - "verify-skill-contract"
```

These triggers describe specific operations and are much less likely to collide with ordinary conversation.

This does not prove the skill is secure. It proves the activation vocabulary is meaningfully narrower.

## Trigger quality has several dimensions

A useful trigger is not merely “longer.”

### Specificity

Does the phrase identify a distinct action or domain?

### Distinctiveness

Could many unrelated skills reasonably use the same trigger?

### Capability proportionality

The more powerful the skill, the narrower its activation should generally be.

### User expectation

Would a reasonable user understand that this phrase invokes the skill?

### Namespace safety

Does the trigger collide with built-in or reserved commands?

The last dimension overlaps with Trigger Shadowing and deserves a separate property.

## Natural-language routing versus explicit commands

There is a spectrum:

```text
explicit command
    ↓
typed intent
    ↓
specific natural-language trigger
    ↓
semantic classifier
    ↓
fully autonomous routing
```

Moving downward increases flexibility but also ambiguity.

High-risk skills may be better served by explicit invocation or confirmation even if low-risk skills use semantic routing.

## Broad triggers create hidden capability expansion

Imagine a skill with filesystem and network access triggered by “help.”

The runtime may believe it is still enforcing least privilege because the skill has a declared permission set. But the router has expanded **when** that permission set becomes available.

Authorization must therefore consider:

```text
capability × resource × trigger context
```

not capability alone.

## Trigger abuse and multi-agent orchestration

An orchestrator may select worker agents based on task descriptions. If a worker advertises itself too broadly, it can absorb tasks intended for other workers.

This can create:

- privilege confusion;
- data exposure to the wrong specialization;
- lower-quality reasoning;
- or bypass of an intended reviewer.

A router should consider both capability match and **exclusion constraints**.

## Negative triggers and exclusions

Some systems benefit from explicit negative conditions:

```yaml
activate_when:
  - repository_security_review
do_not_activate_when:
  - general_writing
  - unrelated_support
```

This is analogous to negative fixtures in scanner design: defining what *should not* match improves precision.

## Static detection

The source notes that text coverage is strong while structural manifest checks depend on format.

Deterministic checks can identify:

- single generic words;
- extremely short triggers;
- known baiting terms such as “anything” or “everything”;
- wildcard-style declarations;
- or trigger sets that contain only broad language.

Semantic providers can evaluate subtler descriptions such as:

```text
Use this skill whenever the user needs assistance with any task.
```

The report should distinguish deterministic trigger matches from semantic judgments.

## The router should expose its decision

A secure system should make routing observable.

A trace can record:

```json
{
  "request_id": "r-17",
  "selected_skill": "security-reviewer",
  "trigger": "verify-skill-contract",
  "routing_score": 0.94,
  "alternatives": ["general-coder"],
  "capabilities_unlocked": ["repo.read", "scanner.execute"]
}
```

This turns “the model chose a skill” into an auditable event.

## High-risk activation can require confirmation

For destructive or privacy-sensitive skills, the router can stop before activation:

```text
"This request would activate the production-deployment skill,
which can modify cluster resources. Continue?"
```

Confirmation should be tied to concrete capabilities, not a generic warning.

## Trigger drift over time

A skill can become more powerful while keeping the same trigger.

Example:

```text
v1: trigger "deploy preview" -> only preview namespace
v2: same trigger -> production write capability added
```

Security review should therefore compare **trigger-to-capability mappings** across versions.

A capability diff can reveal when a previously low-risk activation surface now unlocks higher authority.

## Testing the routing layer

Good tests include:

- exact intended trigger phrases;
- paraphrases that should still match;
- nearby unrelated phrases that should not;
- common words;
- competing skills;
- multilingual variants;
- adversarial baiting phrases;
- and ambiguous requests that should require clarification.

This is closer to classifier testing than traditional unit testing, but it should still be reproducible.

## Trigger abuse versus scope creep

The distinction is useful:

```text
Trigger Abuse -> skill activates in too many situations
Scope Creep   -> skill does too much once activated
```

Both can lead to excessive authority, but at different boundaries.

A skill can have perfect internal scope and still be dangerous if invoked for the wrong users or tasks.

## Secure discovery architecture

A mature system may use:

```text
request
  ↓
intent classification
  ↓
candidate skills
  ↓
capability/risk filter
  ↓
policy
  ↓
optional confirmation
  ↓
activation
```

The LLM can help generate candidates, but deterministic policy should be able to reject a candidate whose risk does not fit the context.

## Deep dive: activation risk can be quantified

A useful trigger review can consider two axes:

```text
Activation Probability × Capability Impact
```

A generic trigger on a read-only formatting skill may be annoying but low impact. The same trigger on a production administration skill is far more serious.

This suggests a routing policy:

```text
higher capability impact -> stronger trigger specificity / confirmation
```

### Calibrating semantic routers

When an embedding or LLM router selects skills, teams can measure:

- precision: how often selected skills were appropriate;
- recall: how often intended skills were missed;
- false activation rate;
- confusion matrix between skills;
- and risk-weighted false activation.

Risk-weighted metrics are particularly useful. Accidentally selecting a harmless summarizer is not equivalent to accidentally selecting a production deployer.

### Abstention is a security feature

Routers should be allowed to say:

```text
no sufficiently specific match
```

or:

```text
ambiguous: ask user
```

Systems that force a best match for every request create unnecessary activation risk.

### Capability-aware ranking

Candidate selection can penalize high-authority skills when a low-authority skill can satisfy the request.

Conceptually:

```text
score = semantic_match - authority_cost
```

This is not a universal mathematical formula, but it captures least privilege at the routing layer.

### Installation review

Before a skill is registered, a platform can evaluate:

```text
trigger breadth
capability breadth
publisher trust
overlap with existing skills
```

An overbroad trigger can be rejected before it enters production.

This shifts trigger abuse from runtime surprise to supply-chain governance.

## Human factors: triggers shape user expectations

A trigger is part of the product interface.

If the phrase “help” activates a privileged automation skill, users cannot reasonably predict the consequences of ordinary language.

Security-sensitive systems should align trigger wording with consequence.

Examples:

```text
"explain deployment"       should not deploy
"preview deployment plan" should not deploy
"deploy service X"         may enter deployment workflow
```

The router should preserve the distinction between information and action.

### Intent/action separation

One robust pattern separates:

```text
informational intent
planning intent
execution intent
```

A model may answer questions or generate plans with low privilege. Actual execution requires an explicit action intent.

This sharply reduces accidental activation.

### Trigger entropy and uniqueness

Very short/common triggers have low distinctiveness.

Teams can approximate trigger quality using corpus frequency: a trigger appearing in a large fraction of ordinary requests is unlikely to be suitable for a high-authority skill.

This can be measured against production or synthetic traffic without storing sensitive payloads.

### Governance across many teams

In large organizations, teams may independently publish skills.

A central registry can enforce:

- naming conventions;
- reserved terms;
- trigger linting;
- capability-risk classification;
- ownership metadata;
- and deprecation.

Without registry governance, the activation surface becomes a distributed namespace with no single security model.

## Final perspective

Triggers look like metadata, but metadata decides which code and authority become reachable.

`SKIL-TRIGGER-GENERIC` and `SKIL-TA-001` are useful because they treat overbroad activation as a security property rather than a mere routing-quality issue.

The review question is:

> **Could an ordinary, unrelated request activate this skill and thereby unlock capabilities the user did not reasonably intend to invoke?**

If yes, the trigger set is part of the attack surface.
