# Agentic Artificial Intelligence: From Reactive Language Models to Governed Autonomous Systems

The most consequential shift in applied artificial intelligence is not that language models have become better at producing text. It is that models are increasingly embedded inside systems that **observe state, pursue goals, choose actions, invoke tools, maintain memory, evaluate outcomes, and decide what to do next**.

That shift changes the engineering problem.

A conventional language-model application can often be understood as a bounded transformation:

```text
input → model inference → output
```

An agentic system is closer to a controlled process:

```text
state_t
   ↓
interpretation
   ↓
decision / plan
   ↓
action
   ↓
environment transition
   ↓
observation
   ↓
evaluation
   ↓
state_(t+1)
```

The difference is not cosmetic. Once an AI system can affect external state, the model stops being merely a content generator and becomes part of a **control architecture**. Reliability now depends not only on model quality, but on state management, tool contracts, authorization, planning, evaluation, observability, failure recovery, resource limits, and governance.

The original paper behind this essay correctly identifies the central transition: agentic AI moves from reactive answer generation toward systems that can pursue explicit goals, take actions, and evaluate results. It also sketches a layered architecture spanning perception/context, agentic control, execution, and feedback, and names logical roles such as planner, executor, critic, memory manager, and safety controller. Those ideas are the right foundation. The deeper engineering question is how these parts interact, where trust boundaries sit, and which responsibilities must remain deterministic even when the model itself is probabilistic.

This essay develops that architecture into a production-oriented theory of agentic systems.

## 1. Agentic AI Is Not a Model Class

One of the first conceptual mistakes in discussions about agentic AI is treating *agentic* as if it were a property of a single model architecture.

It is usually more accurate to describe agentic behavior as an **emergent property of a system configuration**.

A transformer model does not become an agent merely because it can reason well. A model with function calling does not automatically become an agent either. Agency appears when a software system gives a model some degree of control over a workflow and lets it use observations to determine subsequent actions.

OpenAI describes agents as systems that independently accomplish tasks on behalf of users and emphasizes two core characteristics: the model manages workflow execution, and it can select tools while operating within defined guardrails.[^1] Anthropic makes a closely related but useful distinction between **workflows** and **agents**: workflows follow predefined code paths, while agents dynamically direct their own processes and tool use.[^2]

That distinction prevents the word *agent* from becoming meaningless.

Consider three systems.

### System A: LLM as a function

```text
user request
   ↓
prompt template
   ↓
LLM
   ↓
response
```

The control flow is deterministic. The model produces content but does not determine what happens next.

### System B: model-assisted workflow

```text
user request
   ↓
classifier
   ↓
fixed branch A / B / C
   ↓
LLM step
   ↓
fixed validation
   ↓
result
```

The model may influence local decisions, but the workflow topology remains primarily encoded in software.

### System C: agent

```text
goal
   ↓
model interprets state
   ↓
model chooses next capability
   ↓
tool executes
   ↓
observation returns
   ↓
model replans
   ↓
repeat until termination
```

Here the model participates directly in control-flow selection.

The boundary between B and C is not mathematically sharp. Agentic AI is therefore better understood as a **continuum of delegated decision authority**.

A useful engineering metric is not simply:

```text
agent = yes / no
```

but:

```text
degree_of_agency =
    scope_of_decisions_delegated_to_model
    × external_effect_of_available_actions
    × duration_of_autonomous_execution
    × uncertainty_of_environment
```

A coding assistant that proposes a patch but cannot write to a repository has lower effective agency than an identical model that can modify files, open pull requests, trigger CI pipelines, and deploy changes.

This leads to a central thesis:

> **Autonomy is not produced by intelligence alone. It is produced by intelligence combined with authority.**

## 2. From Classical Agent Theory to LLM-Based Agents

Agentic AI did not begin with large language models.

Artificial-intelligence research has long defined agents as entities that perceive an environment and act upon it. Classical formulations emphasize rational action: an agent chooses actions expected to improve performance relative to its observations and objectives. Modern LLM-based agents inherit this framing but replace parts of explicit symbolic decision logic with learned language-model inference.

Several theoretical traditions converge in contemporary agent architectures.

### 2.1 Rational-agent models

A minimal abstraction describes an agent policy:

```text
π : S → A
```

where:

- `S` is a representation of state,
- `A` is the action space,
- `π` maps observed state to an action.

In realistic systems, however, the agent rarely observes the complete world state. What it receives is an observation `o_t`, not necessarily the true state `s_t`.

That moves the model closer to a partially observable setting:

```text
o_t = observation(s_t)
```

The system must infer enough hidden state from:

- current input,
- prior observations,
- memory,
- tool responses,
- environment events.

This is one reason context management is not optional. The agent needs a usable internal representation of what has already happened.

### 2.2 Control theory

The original paper correctly connects agentic AI to control theory.

The simplest feedback controller has the form:

```text
desired state
     ↓
compare with observed state
     ↓
error
     ↓
controller
     ↓
action
     ↓
system
     ↓
new observation
```

Agentic AI uses an analogous pattern, but the controller is partly probabilistic and semantic.

```text
goal
  ↓
current state estimate
  ↓
LLM-based decision
  ↓
tool/action
  ↓
external system
  ↓
observation
  ↓
evaluation
  ↺
```

The control-theoretic analogy is important because it changes how failures are interpreted.

If an LLM produces one poor sentence, the error is local.

If an agent makes one poor decision inside a feedback loop, the result may alter the environment and therefore influence every subsequent decision.

This is **error propagation through state**.

### 2.3 Planning systems

Classical AI planning asks how a sequence of actions can transform an initial state into a goal state.

In symbolic form:

```text
S_0 --a_1--> S_1 --a_2--> ... --a_n--> S_goal
```

LLM-based agents often approximate planning in natural language rather than constructing a formally verified action sequence.

They may:

- decompose a task,
- choose intermediate objectives,
- query tools,
- revise plans after failures,
- abandon unsuccessful branches.

ReAct demonstrated an influential pattern in which reasoning and actions are interleaved rather than separated into one monolithic plan followed by execution.[^3]

A practical agent therefore does not necessarily compute a complete plan at time `t=0`.

It can use **receding-horizon planning**:

```text
observe
→ choose near-term step
→ execute
→ observe result
→ revise
```

This is often more robust in uncertain environments because the system does not commit to an obsolete plan after the world changes.

### 2.4 Reinforcement-learning intuition without online RL

The original paper is also right to separate the *conceptual* relation to reinforcement learning from the claim that every agent performs reinforcement learning.

Many deployed agents do not update model weights during operation.

Instead, the system may use:

- externally supplied objectives,
- binary task success,
- unit tests,
- API responses,
- user corrections,
- evaluator-model scores,
- policy checks.

Reflexion illustrates one approach in which an agent incorporates linguistic feedback into episodic memory rather than changing model weights.[^4]

This distinction matters:

```text
learning from feedback
≠
online gradient-based reinforcement learning
```

An agent can adapt behavior within a session through memory and replanning while the underlying model parameters remain unchanged.

## 3. A More Precise Definition of an Agentic System

A useful production definition should be architectural rather than anthropomorphic.

An agentic AI system is a software system in which a model participates in selecting actions over multiple steps in pursuit of an explicit objective, using observations from tools or an environment to update subsequent decisions.

We can express this as:

```text
Goal G

for t = 0 ... T:
    C_t = build_context(S_t, M_t, O_t)
    D_t = model_decision(G, C_t)
    A_t = authorize(D_t)
    R_t = execute(A_t)
    E_t = evaluate(R_t, G, policy)
    S_(t+1), M_(t+1) = update(S_t, M_t, R_t, E_t)

    if terminate(E_t):
        break
```

This pseudocode is more revealing than the vague phrase “AI that acts autonomously.”

It separates five fundamentally different responsibilities:

1. **Context construction**
2. **Model inference**
3. **Authorization**
4. **Execution**
5. **Evaluation and termination**

Only some of them should be delegated to the model.

In high-assurance systems:

```text
model proposes
policy decides
runtime enforces
telemetry records
```

That separation is foundational.

## 4. Why the Simple LLM-versus-Agent Table Needs Nuance

The source paper contrasts conventional LLM applications with agentic AI along dimensions such as control flow, goal orientation, self-evaluation, tool use, and autonomy.

That is pedagogically useful, but production systems are less binary.

A more precise table is:

| Dimension | Basic LLM Application | Agentic Workflow | Model-Directed Agent |
| --- | --- | --- | --- |
| Control flow | Mostly fixed | Programmed graph with LLM nodes | Model influences next-step selection |
| Goal representation | Often implicit in prompt | Explicit workflow objective | Explicit objective plus evolving state |
| Tool use | Optional | Predefined | Dynamically selected within policy |
| Memory | Prompt-local | Workflow state | Short-/long-term state may influence future actions |
| Evaluation | Usually final-response only | Step-specific checks | Continuous or event-driven |
| Recovery | User retries | Coded fallback path | Replan, retry, escalate, or terminate |
| Autonomy | Low | Bounded | Variable; depends on permissions |
| External effects | Often none | Controlled | Potentially broad |
| Governance burden | Moderate | High | Potentially very high |

The critical variable is not whether the model “has tools.”

The critical variable is:

> **Who controls sequencing, and how much authority is available at each step?**

## 5. A Production Reference Architecture

The source paper proposes four layers:

1. perception/context,
2. agentic control,
3. action/execution,
4. evaluation/feedback.

That is an excellent conceptual skeleton.

For production systems, however, two additional planes should be made explicit:

- **policy and governance**, which cuts across the stack;
- **observability and evidence**, which makes behavior inspectable.

A richer architecture therefore looks like this:

```text
┌────────────────────────────────────────────────────────────┐
│                    User / Environment                      │
└────────────────────────────┬───────────────────────────────┘
                             │
                             ▼
┌────────────────────────────────────────────────────────────┐
│ 1. Perception & Context                                    │
│ prompts · events · retrieval · tool results · system state │
└────────────────────────────┬───────────────────────────────┘
                             │
                             ▼
┌────────────────────────────────────────────────────────────┐
│ 2. Cognitive / Control Layer                               │
│ goal interpretation · planning · routing · state machine   │
│ model inference · decomposition · replanning               │
└────────────────────────────┬───────────────────────────────┘
                             │ proposal
                             ▼
┌────────────────────────────────────────────────────────────┐
│ 3. Policy & Authorization                                  │
│ capabilities · identity · scopes · approvals · budgets     │
└────────────────────────────┬───────────────────────────────┘
                             │ authorized action
                             ▼
┌────────────────────────────────────────────────────────────┐
│ 4. Execution                                               │
│ tools · MCP · APIs · code sandboxes · databases · systems  │
└────────────────────────────┬───────────────────────────────┘
                             │ observation
                             ▼
┌────────────────────────────────────────────────────────────┐
│ 5. Evaluation & Verification                               │
│ tests · schemas · policy checks · graders · assertions     │
└────────────────────────────┬───────────────────────────────┘
                             │
                             ▼
┌────────────────────────────────────────────────────────────┐
│ 6. Memory & State                                          │
│ working state · episodic memory · semantic memory          │
└────────────────────────────────────────────────────────────┘

Cross-cutting:
Observability · provenance · audit · cost · safety · governance
```

This architecture intentionally separates the *cognitive* layer from the *authority* layer.

An LLM can decide that sending an email is useful.

It should not automatically decide that it is authorized.

## 6. Perception and Context: The Agent Never Sees “The World”

An agent acts on representations.

Its environment may contain databases, repositories, websites, users, files, APIs, cloud infrastructure, and other agents. The model receives only a selected projection of that environment.

That projection becomes context.

### Context sources

A production agent may combine:

- user instructions;
- developer/system instructions;
- retrieved documents;
- workspace files;
- API results;
- memory records;
- tool descriptions;
- task metadata;
- policy constraints;
- prior actions;
- structured state.

We can express context construction as:

```text
C_t =
    I_system
  + I_user
  + S_task
  + R_t
  + M_t
  + O_t
  + P_t
```

where:

- `I_system` = privileged instructions,
- `I_user` = user intent,
- `S_task` = structured task state,
- `R_t` = retrieved information,
- `M_t` = memory,
- `O_t` = observations,
- `P_t` = policy-relevant context.

The model sees only `C_t`.

If context is wrong, incomplete, stale, poisoned, or overlong, decision quality degrades even when the underlying model is strong.

### Context is also an attack surface

AgentDojo demonstrates why this matters for security: agents that execute tools over untrusted data are vulnerable to prompt injection carried through tool outputs and external content.[^5]

This means perception is not neutral.

A retrieved web page is **data**, but it may contain language that resembles instructions.

A secure architecture therefore labels provenance:

```text
system instruction      → privileged
user request            → authorized intent
retrieved document      → untrusted data
tool output             → untrusted or capability-scoped data
memory                  → persisted data with provenance
```

The model may read all of them, but the runtime should not treat them as equal sources of authority.

## 7. The Agentic Control Layer: Planning Is Only One Function

The source paper lists goal definition, task decomposition, decision logic, and state management as central control-layer functions.

That is correct, but the control layer is better understood as a collection of **decision responsibilities**.

### 7.1 Goal interpretation

User instructions are frequently underspecified.

“Prepare the release” may imply:

- update version numbers,
- run tests,
- generate changelog,
- create tag,
- publish package,
- deploy.

The agent needs to infer a goal representation.

A robust system should externalize that inference:

```yaml
goal:
  objective: "prepare release candidate"
  allowed_effects:
    - repository.read
    - repository.write_branch
    - ci.run
  forbidden_effects:
    - production.deploy
    - package.publish
  completion_criteria:
    - tests_pass
    - changelog_generated
    - pull_request_opened
```

This is more governable than keeping the goal entirely inside hidden model state.

### 7.2 Task decomposition

A planner maps a high-level objective into subproblems.

```text
Goal
 ├─ inspect current state
 ├─ identify required changes
 ├─ implement
 ├─ verify
 └─ present result
```

The value of decomposition is not merely cognitive.

It creates **control checkpoints**.

A system can assign different permissions and verification requirements to different stages.

### 7.3 Routing

Sometimes the right next step is not another reasoning step but choosing a specialist capability:

```text
request
  ├─ documentation question → retrieval
  ├─ code change → coding tool
  ├─ deployment request → approval gate
  └─ ambiguous intent → user clarification
```

Routing can be model-based, deterministic, or hybrid.

### 7.4 Replanning

A static plan is fragile.

Real systems fail:

- tests fail,
- APIs return errors,
- files change,
- credentials expire,
- users modify requirements.

A useful agent should treat plans as hypotheses, not commitments.

```text
plan_t
   ↓
action
   ↓
observation
   ↓
plan_(t+1)
```

### 7.5 Termination

Termination is one of the least glamorous and most important design problems.

Without explicit stopping logic, an agent can:

- loop,
- retry indefinitely,
- consume unbounded tokens,
- generate repetitive tool calls,
- escalate cost.

Termination should therefore combine model judgment with deterministic constraints:

```text
terminate if:
    success_criteria_met
 OR max_steps_reached
 OR max_cost_reached
 OR policy_violation
 OR repeated_failure_threshold
 OR user_interrupt
```

## 8. Logical Agent Roles Are Architectural Responsibilities, Not Necessarily Separate Agents

The original paper lists:

- Goal Manager,
- Planner,
- Executor,
- Critic,
- Memory Manager,
- Safety Controller.

This is a useful decomposition.

But there is a crucial implementation nuance:

> A logical role does not imply a separate model process.

A single agent can implement all six responsibilities.

```text
single model
   ├─ interpret goal
   ├─ plan
   ├─ choose tool
   ├─ evaluate result
   └─ update memory
```

Alternatively:

```text
orchestrator
   ├─ planning model
   ├─ coding model
   ├─ evaluator
   └─ policy engine
```

The second architecture may improve separation of concerns, but it also introduces:

- more latency,
- more tokens,
- more failure modes,
- more coordination state,
- more attack surfaces.

Multi-agent design should therefore not be treated as a maturity level.

Anthropic explicitly recommends starting with the simplest architecture that works and increasing complexity only when the task requires it.[^2]

A useful design rule is:

```text
introduce another agent only if it provides
    independent context
 OR independent capability
 OR parallelism
 OR independent evaluation
 OR administrative separation
```

Otherwise, another agent may simply duplicate uncertainty.

## 9. Memory: Persistence Is an Information-Architecture Problem

The original paper correctly states that agentic systems need explicit memory mechanisms.

However, “memory” is not one thing.

### 9.1 Working memory

Working memory contains information needed for the current execution.

Examples:

- current plan,
- unfinished subtasks,
- temporary calculations,
- recent observations.

It is usually short-lived.

### 9.2 Episodic memory

Episodic memory records prior experiences.

```text
task X
→ action Y
→ failure Z
→ recovery strategy Q
```

Reflexion uses an episodic memory buffer to preserve verbal feedback for later attempts.[^4]

### 9.3 Semantic memory

Semantic memory stores reusable knowledge rather than specific events.

Examples:

- repository conventions,
- domain rules,
- user preferences,
- architectural facts.

This is often implemented through retrieval systems.

### 9.4 Procedural memory

A fourth useful category is procedural knowledge:

- workflows,
- skills,
- tool-use instructions,
- runbooks.

In modern agent ecosystems, procedural knowledge may exist as skill files, prompts, policy packages, or executable tools.

### 9.5 Memory should have governance metadata

A production memory record should not be just text.

```yaml
memory:
  id: mem-384
  content: "Service A requires header X"
  type: semantic
  source: documentation/service-a.md
  created_at: 2026-08-27T10:00:00Z
  trust: repository_document
  sensitivity: internal
  expires_at: null
  scope:
    project: payments
```

This enables:

- provenance,
- deletion,
- retention,
- access control,
- conflict resolution,
- freshness checks.

### 9.6 Memory can be wrong

Persistence amplifies mistakes.

A hallucinated statement in one response is temporary.

A hallucinated statement written into long-term memory can affect future sessions.

Therefore:

```text
write_memory
```

should often be treated as a privileged operation.

Memory requires the same questions as a database:

- Who can write?
- Who can read?
- How long is data retained?
- What is the provenance?
- Can it be corrected?
- Can it be deleted?
- Can untrusted content become authoritative?

The “memory manager” is therefore not just an optimization component. It is part of the security and governance architecture.

## 10. Tools Turn Language into Effects

Without tools, a language model primarily produces information.

With tools, generated decisions can become state transitions.

Tools may:

- search the web,
- read files,
- write code,
- call APIs,
- query databases,
- send messages,
- modify tickets,
- execute shell commands,
- deploy infrastructure.

This changes the safety model from:

```text
Is the output correct?
```

to:

```text
Is the action authorized?
Is the parameter valid?
Is the effect reversible?
Is the evidence sufficient?
```

### Tool contracts

A tool should expose a narrow semantic capability.

Prefer:

```text
create_issue(project, title, body)
```

over:

```text
http_request(method, url, headers, body)
```

The second tool gives the model a much larger authority surface.

### Model Context Protocol

The Model Context Protocol has become an important integration layer for tools and context. The current specification revision `2026-07-28` moves the protocol toward a stateless core, adds header-based routing and cacheable list results, and strengthens authorization behavior.[^6]

This matters architecturally because standardized tool integration does **not** eliminate the need for policy.

Protocol interoperability answers:

```text
How can the client call the capability?
```

Security must answer:

```text
Should this principal be allowed to call it?
With which parameters?
For which resource?
Under which approval state?
```

These are different questions.

## 11. Evaluation: Self-Reflection Is Not Verification

The original paper identifies internal evaluation as a distinguishing feature of agentic systems.

That is directionally correct, but the phrase *self-evaluation* can create a dangerous impression.

A model evaluating its own output is not an independent source of truth.

The evaluator may share:

- the same blind spots,
- the same incorrect assumptions,
- the same poisoned context,
- the same model family.

A mature agent therefore uses a hierarchy of verification mechanisms.

### Level 1: deterministic validation

Examples:

- JSON Schema validation,
- type checks,
- syntax parsing,
- unit tests,
- compiler output,
- policy rules.

### Level 2: environment feedback

Examples:

- API status,
- build result,
- deployment health check,
- database constraint.

### Level 3: independent model evaluation

A second model can score or critique the result.

Useful, but still probabilistic.

### Level 4: human review

Required where consequences exceed the system's delegated authority.

The strongest possible verification is domain-specific.

For code:

```text
tests > model confidence
```

For authorization:

```text
policy engine > model confidence
```

For financial limits:

```text
ledger constraints > model confidence
```

For production deployment:

```text
approval workflow > model confidence
```

This is a general principle:

> **Use models for judgment where judgment is required; use deterministic systems where correctness can be mechanically checked.**

## 12. Evaluation Must Measure Trajectories, Not Only Final Answers

Agent evaluation is harder than chatbot evaluation.

A chatbot can be scored on one response.

An agent produces a trajectory:

```text
τ = (s_0, a_0, o_1, a_1, o_2, ..., a_n)
```

Two agents can reach the same final answer through radically different paths.

One may:

- use 3 tool calls,
- cost $0.10,
- respect policy.

Another may:

- use 80 tool calls,
- expose sensitive data,
- accidentally modify state,
- eventually return the same answer.

Final-answer accuracy misses the difference.

Agent evaluation should include:

### Task success

Did the system achieve the objective?

### Path efficiency

How many steps, tokens, calls, retries, and seconds were required?

### Policy compliance

Did the system remain within delegated authority?

### Recovery quality

What happened when a tool failed?

### Safety

Did untrusted content alter privileged behavior?

### State integrity

Did the system leave the environment in a correct condition?

### Evidence quality

Can reviewers reconstruct why the action occurred?

AgentDojo is useful precisely because it evaluates agents in dynamic tool-using environments and includes adversarial security cases rather than scoring only static answers.[^5]

## 13. Observability: The Missing Layer in Many Agent Diagrams

Traditional distributed systems need logs, metrics, and traces.

Agentic systems need all three plus **semantic execution evidence**.

An agent run should be observable as a trace:

```text
Run: release-preparation-172
│
├─ Goal interpretation
├─ Retrieval
├─ Plan creation
├─ Tool call: read repository
├─ Tool call: edit file
├─ Test execution
├─ Evaluation
├─ Approval requested
└─ Final result
```

Useful metadata includes:

- model/version,
- prompts or prompt hashes where policy permits,
- tool name,
- arguments,
- result status,
- token usage,
- latency,
- policy decisions,
- approvals,
- memory reads/writes,
- retries,
- error classes.

OpenAI's agent tooling explicitly emphasizes tracing and workflow observability as production requirements.[^7]

Observability serves four purposes:

1. debugging,
2. evaluation,
3. security investigation,
4. compliance evidence.

Without it, an autonomous system becomes operationally opaque.

## 14. Governance: Controlled Autonomy, Not Unlimited Independence

The original paper's strongest sentence is the idea that agentic AI should mean **controlled autonomy**, not unrestricted independence.

That principle deserves to be made architectural.

The runtime should define an **autonomy envelope**.

```yaml
autonomy:
  max_steps: 20
  max_runtime_minutes: 15
  max_cost_usd: 2.00

capabilities:
  repository_read: allow
  repository_write_branch: allow
  issue_create: allow
  production_deploy: approval_required
  secrets_read: deny
```

The agent may choose freely **inside** the envelope.

It may not redefine the envelope.

### NIST risk management

NIST's AI Risk Management Framework organizes risk-management activities around the functions Govern, Map, Measure, and Manage, with governance operating across the lifecycle.[^8]

Applied to agents:

```text
Govern
→ define authority, accountability, policies

Map
→ identify use case, users, environment, harms

Measure
→ evaluate task success, safety, robustness

Manage
→ deploy controls, monitor, respond, improve
```

This lifecycle view is more appropriate than bolting “safety checks” onto the final output.

## 15. Security: Agents Create a New Attack Surface Through Composition

The OWASP Top 10 for Agentic Applications 2026 reflects an important reality: agentic risks are not simply chatbot risks with more tools.[^9]

The system now has interacting attack surfaces:

```text
instructions
+
tools
+
identity
+
memory
+
external data
+
supply chain
+
execution
```

OWASP highlights categories including:

- Agent Goal Hijack,
- Tool Misuse and Exploitation,
- Identity and Privilege Abuse,
- Agentic Supply Chain Vulnerabilities,
- Unexpected Code Execution.[^9]

These risks are compositional.

A malicious document alone may be harmless.

A broad tool alone may be legitimate.

A powerful identity alone may be required.

But:

```text
untrusted document
   +
prompt injection
   +
broad tool
   +
privileged credential
   =
high-impact compromise path
```

Security must therefore focus on **trust boundaries and capability chains**.

### The model is not the security boundary

The most important architectural rule is:

```text
LLM output is a proposal, not authorization.
```

Authorization belongs in deterministic infrastructure:

- capability brokers,
- policy engines,
- IAM,
- sandboxing,
- network controls,
- approval gates.

This makes the system robust against both malicious instructions and ordinary model mistakes.

## 16. Human-in-the-Loop Is a Control Mechanism, Not a UX Feature

Human approval is sometimes added as a modal dialog after an agent has already decided what it wants to do.

That is a weak design.

A meaningful approval gate needs:

- a clear action description,
- exact resource,
- exact scope,
- material parameters,
- predicted impact,
- irreversible effects,
- evidence needed for review.

Good approval:

```text
Deploy version 2.4.1
to production cluster eu-central-1
using image digest sha256:...
change set: 3 manifests
estimated downtime: none
```

Weak approval:

```text
Agent wants to continue. Allow?
```

Approval should be bound to the specific action.

If parameters change after approval, authorization should be invalidated.

Anthropic's discussion of trustworthy agents emphasizes user control through tool permissions and action-specific approval requirements.[^10]

---

## 17. Non-Linear Control Flow: State Machines, Graphs, and Agent Loops

The original paper notes that agentic systems use loops, conditional branches, returns, and explicit termination.

There are several useful formal models.

### 17.1 Finite-state machine

Useful when states are known.

```text
RECEIVED
   ↓
PLANNED
   ↓
EXECUTING
   ├─ failure → RECOVERY
   ├─ approval → WAITING
   └─ success → VERIFYING
                     ↓
                  COMPLETE
```

Advantages:

- explainable,
- testable,
- easy to constrain.

### 17.2 Directed acyclic graph

Useful for workflow systems with known dependency structure.

```text
extract
  ├─ analyze code
  ├─ analyze tests
  └─ analyze dependencies
         ↓
      synthesize
```

Parallelism is easier.

### 17.3 Cyclic graph / stateful workflow

Allows retries and replanning.

### 17.4 Model-directed loop

The model dynamically determines the next step.

This offers flexibility but makes formal reasoning harder.

Production systems often combine all four:

```text
deterministic outer state machine
        ↓
bounded model-directed loop
        ↓
deterministic verification
```

This hybrid pattern is often more robust than unrestricted autonomy.

## 18. Failure Modes Are Architectural Signals

Agentic systems fail differently from static software.

### Hallucinated state

The model believes an action succeeded when it did not.

Mitigation:

```text
do not infer success from prose
read success from tool result
```

### Plan drift

The agent gradually pursues a related but different objective.

Mitigation:

- explicit goal representation,
- periodic goal re-grounding,
- scope checks.

### Retry amplification

A transient error triggers uncontrolled retries.

Mitigation:

- retry budget,
- exponential backoff,
- idempotency,
- circuit breakers.

### Context degradation

The context becomes too large or filled with irrelevant history.

Mitigation:

- structured state,
- summarization,
- retrieval,
- bounded memory.

### Tool misuse

A legitimate capability is used with dangerous parameters.

Mitigation:

- typed contracts,
- authorization,
- parameter policy.

### Evaluation collapse

The same model incorrectly validates its own incorrect result.

Mitigation:

- external verifiers,
- deterministic tests,
- independent evidence.

## 19. Cost and Latency Are Part of Correctness

The source paper correctly lists latency and system complexity as limitations.

In agents, cost and latency are architectural properties.

If an agent requires:

```text
5 planning calls
+ 12 tool calls
+ 4 evaluator calls
+ 3 retries
```

its economics differ dramatically from a single inference.

A useful cost model is:

```text
C_run =
    Σ model_cost_i
  + Σ tool_cost_j
  + infrastructure_cost
  + evaluation_cost
  + human_review_cost
```

Latency:

```text
L_run =
    critical_path(model + tools + approvals + retries)
```

This is why parallelization matters.

Independent subproblems can execute concurrently.

But parallelism also increases:

- state synchronization,
- rate limits,
- concurrency hazards,
- cost spikes.

Resource budgets should therefore be part of agent state.

## 20. Multi-Agent Systems: Coordination Is Not Automatically Intelligence

The future outlook in the source document points to multi-agent coordination.

That is plausible, but multi-agent architectures deserve skepticism.

A multi-agent system can provide real value when tasks require:

- independent specializations,
- context isolation,
- parallel investigation,
- adversarial review,
- organizational separation.

Example:

```text
Orchestrator
   ├─ Security Analyst
   ├─ Architecture Analyst
   ├─ Test Engineer
   └─ Reviewer
```

But every interaction adds another probabilistic boundary.

Potential failure modes include:

- conflicting plans,
- duplicated work,
- circular delegation,
- inconsistent memory,
- authority confusion,
- prompt injection across agents.

The system therefore needs explicit coordination semantics.

```yaml
agent: security-reviewer
can:
  - read_patch
  - create_review_comment
cannot:
  - modify_code
  - merge
```

Multi-agent security is partly an IAM problem.

## 21. Where Agentic AI Actually Adds Value

The source paper lists research assistants, software engineering, business-process automation, compliance analysis, and decision support.

Those domains are plausible because they share a common structure:

```text
high task complexity
+
multiple information sources
+
nontrivial tool interaction
+
uncertain intermediate state
+
need for adaptation
```

However, complexity alone is not sufficient.

Agentic systems are a poor fit when:

- rules are stable,
- workflow is deterministic,
- errors are expensive,
- verification is impossible,
- latency must be extremely low.

A tax calculation governed by explicit law may be better implemented by deterministic software.

An agent can help interpret documents or collect missing evidence, while the final calculation remains deterministic.

This is the correct relationship:

> Agentic AI should complement deterministic systems where uncertainty and interpretation are unavoidable, not replace deterministic software simply because a model is available.

## 22. A Practical Decision Framework: Should This Be an Agent?

Before building an agent, ask five questions.

### 1. Is the workflow genuinely variable?

If every request follows the same steps, use a workflow.

### 2. Does the system need environment feedback?

If not, one or a few model calls may be enough.

### 3. Can success be verified?

If success cannot be measured, autonomy becomes difficult to govern.

### 4. Can authority be bounded?

If the only available tool is effectively “do anything,” the architecture is unsafe.

### 5. Does flexibility justify the operational cost?

Agentic systems trade predictability for adaptability.

Anthropic explicitly recommends using the simplest design that meets the requirement because agentic systems often trade latency and cost for task performance.[^2]

## 23. Production Readiness Requires More Than a Strong Model

A production-grade agent should have explicit answers for:

### Identity

Who is the agent acting for?

### Authority

What may it do?

### State

What does it know about the current task?

### Memory

What persists beyond the current step?

### Planning

How are actions selected?

### Execution

Where do side effects occur?

### Verification

How is success established?

### Recovery

What happens after failure?

### Observability

Can the trajectory be reconstructed?

### Governance

Who is accountable?

### Security

Which trust boundaries exist?

### Termination

When must the system stop?

If one of these questions has no architectural answer, the missing component will eventually appear as an operational incident.

## 24. A Reference Execution Pattern

A robust execution loop can be expressed as:

```text
1. Accept goal
2. Normalize goal into structured task state
3. Load only relevant context and memory
4. Ask model for proposed next action
5. Validate proposal against capability contract
6. Require approval if policy demands it
7. Execute through constrained tool broker
8. Record observation and provenance
9. Run deterministic verification where possible
10. Update task state
11. Replan or terminate
```

In pseudocode:

```python
while not task.done:
    if task.steps >= policy.max_steps:
        stop("step budget exceeded")

    context = context_builder.build(task)

    proposal = model.decide(
        goal=task.goal,
        state=task.state,
        context=context,
        allowed_capabilities=policy.visible_capabilities,
    )

    decision = policy_engine.authorize(
        actor=task.identity,
        proposal=proposal,
        state=task.state,
    )

    if decision.requires_human:
        decision = approval_service.request(decision)

    if not decision.allowed:
        task.record_denial(decision)
        break

    result = tool_broker.execute(decision.bound_action)

    evidence = verifier.evaluate(
        goal=task.goal,
        action=decision.bound_action,
        result=result,
    )

    task.update(result, evidence)

    telemetry.record(task, proposal, decision, result, evidence)
```

The crucial line is not the model call.

It is:

```text
policy_engine.authorize(...)
```

That is where useful autonomy becomes controlled autonomy.

## 25. The Future: From Agent Demos to Agent Infrastructure

The next stage of agentic AI will likely be less about inventing increasingly anthropomorphic “agents” and more about building infrastructure that makes delegated machine action reliable.

Several directions are already visible.

### Standardized tool and context protocols

MCP's continued evolution toward stateless, routable, authorized infrastructure reflects a broader shift from ad hoc tool integrations toward standardized agent middleware.[^6]

### Better evaluation

Static benchmarks are insufficient. Agents need environment-based, adversarial, trajectory-level evaluation.

### Stronger policy enforcement

Organizations will increasingly separate model reasoning from authorization.

### Formal verification of bounded components

It is unrealistic to formally verify arbitrary natural-language reasoning end to end.

It is entirely realistic to verify:

- schemas,
- state transitions,
- permissions,
- budget constraints,
- deployment policies,
- invariants around critical actions.

### Hybrid neuro-symbolic systems

Symbolic solvers, compilers, theorem provers, policy engines, and deterministic planners can constrain or verify model proposals.

### Agent identity and delegation

As agents act across systems, questions of delegated identity become central:

```text
user
   ↓ delegates
agent
   ↓ invokes
tool
   ↓ acts on
resource
```

Each edge requires explicit authority.

## Conclusion: Agentic AI Is a Systems-Engineering Discipline

Agentic artificial intelligence is often described as the next step after chatbots.

That description is too shallow.

The real shift is from **model-centric AI** to **system-centric AI**.

The model remains important, but production behavior emerges from the interaction of:

- goals,
- context,
- planning,
- memory,
- tools,
- identity,
- policy,
- verification,
- feedback,
- observability.

The architecture can be summarized as:

```text
Goal
  ↓
Context
  ↓
Model proposes
  ↓
Policy authorizes
  ↓
Runtime acts
  ↓
Environment responds
  ↓
Verifier evaluates
  ↓
State and memory update
  ↺
```

This loop is the essence of agentic computing.

Its value comes from the ability to adapt to uncertain, multi-step environments.

Its risk comes from exactly the same property.

The engineering challenge is therefore not to maximize autonomy.

It is to find the smallest, most useful autonomy envelope in which the system can act effectively while remaining **bounded, observable, verifiable, interruptible, and accountable**.

That is the point at which agentic AI stops being a compelling demo and becomes reliable infrastructure.
