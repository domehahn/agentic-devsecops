Markdown ist das natürliche Format für Git-basierte Reviews. Ein Scannerreport kann direkt als Pipeline-Artefakt, Pull-Request-Kommentar oder Dokumentationsseite veröffentlicht werden – ohne proprietären Viewer.

Das macht Findings sichtbar und diskutierbar. Für automatisierte Policy-Entscheidungen sollte Markdown trotzdem nicht die primäre Schnittstelle sein.

<KeyTakeaway>
Markdown macht Security Evidence konsumierbar. Enforcement sollte trotzdem auf strukturierten Daten und stabilen Exit Codes basieren.
</KeyTakeaway>

## Was das Feature wirklich bedeutet

Markdown optimiert auf Menschen. Tabellen, Überschriften und Codeblöcke sind ideal für Review und Nachvollziehbarkeit. Maschinen sollten dagegen JSON oder SARIF verwenden, weil Formatierungsänderungen sonst Integrationen brechen.

Zudem müssen Scanner Markdown-Sonderzeichen und eingebettete untrusted Strings korrekt neutralisieren.

## SkillSpector

SkillSpector unterstützt `--format markdown` und kann den Report direkt in eine Datei schreiben. Das eignet sich für Security Review Notes oder automatisierte Dokumentation eines Skill-Releases.

Batch-Scans unterstützen ebenfalls menschenlesbare Ausgabeformen.

## `skil`

`skil` bietet Markdown sowohl für Einzel- als auch Collection-Reports. Bei Collection Scans entsteht eine kompakte Übersicht über Skill, Status, Verdict, Finding-Anzahl und Inspection-Completeness.

Damit eignet sich das Format gut als Management- oder Review-Layer über den detaillierteren JSON-Evidenzen.

## Praxisbeispiel

```bash
skillspector scan ./skill --no-llm   --format markdown --output security-review.md

skil scan ./skill --static-only   --format markdown --output security-review.md
```

In einem PR kann die Pipeline die Datei als Artefakt verlinken. Für das eigentliche Merge-Gate sollte jedoch der Exit Code oder ein strukturiertes Reportfeld maßgeblich sein.

## Security- und DevSecOps-Einordnung

- Markdown niemals per Regex als Policy-API verwenden.
- Untrusted Inhalte escapen, damit Findings keine Reportstruktur manipulieren.
- Report zusammen mit Scanner-Version und Artefakt-Digest archivieren.
- Menschenlesbaren Report als Review-Sicht, JSON/SARIF als Maschinen-Sicht behandeln.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

| Aspekt | SkillSpector | `skil` |

| Feature vorhanden | ja | ja |
| Schwerpunkt | Integration und Scanner-Ergonomie | explizite Trust Boundaries und Evidence |
| Bewertung | gleich | gleich |

**Bewertung aus der Vergleichsmatrix:** gleich.

## Typische Fehlinterpretation

„Markdown eignet sich als Maschineninterface, weil es strukturiert aussieht.“ Markdown ist für Menschen. Tabellen und Überschriften können sich ändern; Policy sollte auf JSON, SARIF oder Exit Codes basieren.

## Einordnung in die Pipeline

Dieses Feature gehört in die **Reporting- und Integrationsstufe**. Ein guter Pipeline-Lauf erzeugt mindestens eine menschenlesbare Sicht und eine maschinenlesbare Evidence. So können Entwickler Findings verstehen, während Policy Engines und Dashboards stabile Strukturen konsumieren.

Das Ausgabeformat darf nicht bestimmen, ob ein Gate greift: Exit Code, strukturierter Status und Policy-Ergebnis sollten die technische Entscheidung tragen.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Gleichstand. Beide decken Markdown als dokumentationsfreundliche Oberfläche ab. Der Wert liegt in Review und Kommunikation, nicht in der technischen Enforcement-Schnittstelle.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
