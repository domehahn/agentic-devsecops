## Names are security-sensitive identities

Package managers optimize for convenience: a short name is enough to pull executable code from a vast public registry. Attackers exploit the same convenience by registering names that are one transposition, omitted character, homoglyph or prefix away from a trusted dependency.

Typosquatting detection is an identity-assurance problem. String similarity is useful for candidate generation, but a high-confidence decision also needs ecosystem context, publisher or provenance evidence, popularity/reputation context and review of newly introduced dependencies. The original `skil` control model expresses the same idea as `PACKAGE_NAME suspiciously_similar_to TRUSTED_POPULAR_NAME ∧ identity differs`. That relation is more useful than a label such as “suspicious” because it specifies what must be evidenced and what a legitimate counterexample must break.

## Unicode and near-name collisions

A deliberately small positive fixture from the source property illustrates the boundary:

```text
requsets==2.0.0
```

The safe counterexample changes the semantics rather than merely deleting a suspicious token:

```text
requests==2.32.4
```

The purpose of pairing them is not to teach exploitation. It is to force the detector to explain which relation changes between the two cases. A scanner that fires on both has learned vocabulary; a scanner that can explain the difference has begun to model the security property.

## Similarity is candidate generation, not proof

Levenshtein distance catches simple misspellings such as transpositions, but attackers can use prefix/suffix patterns, separators, scoped-package confusion and Unicode confusables. A practical detector combines several similarity features rather than relying on one threshold. A useful implementation records both the positive observation and the guard that would have made the path safe. That makes remediation testable and turns false-positive handling into explicit logic instead of a collection of suppressions.

## Registry and namespace context

Similarity is meaningful only relative to a reference set. Popular-package lists, organization allowlists and previously approved dependencies provide different signals. The reference set should be versioned so findings are reproducible and changes can be audited. The same model supports change detection: when identity, configuration or code changes, the platform can recompute the relation and show exactly which part of the previously reviewed assumption no longer holds.

## Registry namespace matters

The same spelling can have different ownership semantics across npm, PyPI, Maven or internal registries. Dependency confusion introduces another dimension: an internal package name may collide with a public package. Security review must include registry source and resolution precedence, not just the package string. In an agentic environment this distinction becomes operational because model-generated plans can select the relevant value or capability at runtime. The host therefore needs evidence that can survive from code review into execution policy.

## Publisher and provenance can break ties

A near-name package maintained by the expected organization may be legitimate; an exact-looking package from an unrelated publisher may be riskier. Signed provenance, verified publisher programs and repository linkage provide stronger evidence than popularity alone. The design implication is that detection and authorization must remain separate: the scanner identifies the condition, while a policy layer decides whether the condition is permissible in this deployment context.

## Agents can introduce dependencies at machine speed

Code-generation agents may select a package based on plausibility without human familiarity. Dependency additions should therefore be explicit capability-changing events: the diff should surface package identity, registry, maintainer context, similarity warnings and provenance before installation. This also improves explainability. Reviewers can see the specific security fact rather than receiving a generic severity label, and future tooling can compose that fact with independent findings without double-counting the same evidence.

## False positives, ambiguity, and safe counterexamples

Legitimate forks, language bindings and plugin ecosystems often use similar names. Findings should explain the compared trusted name and similarity features, then allow a reviewed exception tied to exact package identity rather than a broad suppression.

Coverage should be treated as first-class security data. Deterministic syntax and configuration observations can often be reproduced exactly, while intent, future identity and runtime targets may remain uncertain. A mature scanner reports those asymmetries instead of collapsing them into one confidence score. This is particularly important in agentic systems, where the model may choose arguments and tools only after deployment.

## Reviewing machine-selected packages

Restrict registries, require allowlisted scopes for internal packages, verify lockfile source URLs, and block runtime package installation by untrusted agent code. The strongest mitigation is to make package selection a reviewed build-time action.

Defense in depth is intentionally redundant. Authoring lint, static analysis, contract verification, supply-chain verification, runtime policy and audit telemetry answer different questions. A strong result from one layer should never be used as a reason to remove the others.

## Runtime and build restrictions

True-positive fixtures should cover canonical violations, while true-negative fixtures should intentionally reuse similar tokens and syntax so the detector proves it understands context. Boundary cases should change one security-relevant fact at a time. Mutation tests can vary scope, target, normalization, version, guard, or sink. Holdout fixtures protect against overfitting to the public examples. For **Typosquatting in Agentic Skill Supply Chains**, the most valuable tests are those that preserve the surface appearance while changing the underlying security relation; that is how the suite verifies semantics instead of vocabulary.

For `skil`, implementation claims should be checked against the repository’s control matrix, external-control crosswalk, analyzer tests and any provider-specific tests. Provider-backed coverage—such as OSV or external rule packs—must state whether the provider actually ran.

## Architecture drill-down: from finding to enforceable boundary

A design review for this software supply chain property should begin by drawing the trust boundary rather than opening with a rule ID. Identify who controls the input, which component interprets it, what authority is available at that point, and which deterministic guard is expected to stop an unsafe transition. Then map `PACKAGE_NAME suspiciously_similar_to TRUSTED_POPULAR_NAME ∧ identity differs` onto that diagram. The purpose of ecosystem-aware edit-distance/reputation comparison is to provide one or more observable edges in that model; it is not a substitute for the model itself. Reviewers should ask whether the same relation can be created indirectly through wrappers, generated configuration, aliases, cached metadata, transitive dependencies, or delegated tools. If so, the implementation needs either deeper static summaries or a runtime control at the unresolved boundary. Finally, confirm that evidence identifiers survive across CI, packaging and runtime so an observed denial or drift event can be traced back to the assumption approved in code review.

The paired fixtures also serve as an architectural regression test. The unsafe example begins with `requsets==2.0.0` while the safe example begins with `requests==2.32.4`. The important difference is the security relation, not the cosmetic text. If a refactor causes both to produce the same result, the detector or policy has lost a meaningful distinction.

## Common implementation traps

Several implementation mistakes recur around **Typosquatting in Agentic Skill Supply Chains**, even when the high-level policy is correct:

**1. Assuming a name or version string uniquely identifies an artifact.** Registry, digest, publisher, platform variant and provenance may all be relevant to the reviewed identity. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**2. Running provider-backed checks without surfacing provider failure or staleness.** An unavailable advisory or reputation service must not be reported as a clean scan. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**3. Treating a supply-chain finding as timeless.** Reputation, tags, signatures and external artifacts change, so admission-time revalidation is part of the control. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

A useful review discipline is to turn every exception into a scoped, expiring artifact with an owner and rationale. Permanent blanket suppressions hide whether the architecture improved; narrow exceptions preserve the signal and make technical debt measurable.

## How this property composes with adjacent findings

**Near-name package plus new dependency introduction.** A typosquatting signal is strongest on a newly added package that is one edit away from an already approved dependency, comes from an unexpected publisher, and introduces install-time execution. Each signal can be tested separately and then composed into a higher-confidence supply-chain finding.

This composition model is deliberately graph-like: each detector contributes a typed fact and shared evidence identifiers allow a higher-level policy engine to connect them. That prevents one rule from becoming an overloaded catch-all and makes severity escalation explainable.

## Operational signals and measurable assurance

Useful indicators include near-name additions per thousand dependency changes, reviewer confirmation rate, unexpected-registry resolutions, new-publisher events, and the number of runtime install attempts blocked before review.

Metrics should be tied to an explicit denominator and deployment profile. A low finding count may mean strong controls, weak coverage, or simply little exposure; telemetry and coverage state are needed to tell those cases apart. Trend the data over time and review unexpected changes in both positive findings and scanner-negative regression behavior.

## Engineering implications beyond the scanner

Supply-chain properties are time-sensitive. Package reputation, advisory state, tags, signatures and provenance can change independently of source code. Production systems should therefore store the identity and evidence that was reviewed, re-resolve it at admission, and surface any delta. A clean repository scan from last week is not sufficient evidence for an artifact resolved from a mutable external namespace today.

The broader lesson is that an agentic skill is simultaneously text, code, configuration, a tool contract and a supply-chain artifact. Security review should follow the boundary that is actually crossed—data, authority, identity, execution, or control-plane visibility—rather than forcing every risk into the same detection template.

## Testing for false positives

A reviewer should be able to answer four questions before accepting this property as controlled:

1. **What exact security relation is being asserted?** Here it is `PACKAGE_NAME suspiciously_similar_to TRUSTED_POPULAR_NAME ∧ identity differs`.
2. **What concrete evidence supports the relation?** The evidence must come from ecosystem-aware edit-distance/reputation comparison, not from a keyword alone.
3. **What near-neighbor safe case has been tested?** The paired negative fixture should differ in the property, not merely in spelling.
4. **What remains outside static visibility?** Runtime identity, dynamic values, provider state and policy decisions must be named explicitly.

## Conclusion

**Typosquatting in Agentic Skill Supply Chains** is valuable only when it is treated as a falsifiable security property rather than a checklist term. The goal is not to declare an entire skill “malicious” or “safe.” The goal is to state what boundary may be crossed, show the evidence that supports that statement, preserve the coverage limits, and make the safe countercondition explicit. That produces findings engineers can test, reviewers can reproduce, and runtime policy can enforce.
