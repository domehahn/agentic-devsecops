# When the Dockerfile Is Not the Bug: Diagnosing Enterprise Build Failures with RAG and MCP

A developer reports a simple problem:

> “There is an error in the Dockerfile.”

The application has a Spring Boot backend, a TypeScript frontend, and a Docker-based build. The organization routes external dependencies through a corporate proxy and Artifactory remote repositories. Internal Confluence documentation defines the approved remote URLs and proxy conventions.

The Dockerfile may indeed contain an error.

But the actual failure could be somewhere else:

```text
wrong base-image registry
public registry used instead of Artifactory remote
missing Maven proxy settings
missing npm proxy/registry configuration
apt/apk cannot reach upstream
repository URL wrong
Docker daemon proxy missing
TLS trust chain missing
```

This case is useful because it demonstrates the real difference between a **pre-retrieved evidence architecture** and an **adaptive diagnostic agent**.

## The User's Diagnosis Is an Input, Not Ground Truth

The phrase “the Dockerfile is broken” is a hypothesis.

A diagnostic system should preserve the user's observation while separating it from verified evidence.

A useful initial state is:

```yaml
symptom:
  docker_build: failing
user_hypothesis:
  dockerfile_bug: possible
unknowns:
  - exact error log
  - failing build stage
  - registry path
  - proxy configuration
  - Artifactory policy
```

This avoids anchoring on the first explanation.

## Enterprise Builds Add Hidden Network Architecture

On a personal workstation, a Dockerfile might legitimately use:

```dockerfile
FROM eclipse-temurin:21-jdk
```

and download dependencies directly from Maven Central or npmjs.

In an enterprise, outbound access may be deliberately mediated:

```text
Developer / CI
    ↓
Corporate Proxy / Firewall
    ↓
Artifactory Remote Repository
    ↓
External Registry / Package Source
```

JFrog remote repositories act as caching proxies for external repositories. They can centralize upstream access, reduce repeated downloads, provide governance, and shield clients from direct public-registry dependencies.[^1]

The build therefore depends on organizational architecture that is not visible from the Dockerfile alone.

## Failure Class 1: The Base Image Bypasses the Approved Registry

The Dockerfile may contain:

```dockerfile
FROM node:22-alpine
```

while organization policy expects an internal virtual or remote path such as:

```text
artifactory.company.example/docker-remote/node:22-alpine
```

Depending on Docker registry configuration and network policy, the direct public reference may fail with DNS, proxy, TLS, authorization, or denied-egress errors.

The Dockerfile syntax is valid.

The architecture is wrong for the environment.

## Failure Class 2: Docker Daemon Proxy and Build-Step Proxy Are Different

Docker proxy behavior has multiple layers.

The daemon may need proxy configuration to reach remote registries. Docker documents daemon proxy configuration through daemon settings or environment configuration, with platform-specific differences.[^2]

Inside a build stage, package managers may independently require:

```text
HTTP_PROXY / HTTPS_PROXY
npm registry/proxy
Maven settings.xml proxy/repository mirrors
apt / apk proxy configuration
```

A system that simply scans Dockerfile syntax may miss this entirely.

## Failure Class 3: Maven and npm Need Repository Governance

A Spring Boot build may use Maven or Gradle.

A TypeScript frontend may use npm, pnpm, or yarn.

Organizations often route these through Artifactory virtual repositories that aggregate local and remote repositories.

The correct configuration may live in:

```text
settings.xml
.npmrc
gradle.properties
CI variables
Docker build args
corporate documentation
```

Diagnosis therefore requires **cross-artifact reasoning**.

## How a Classical RAG System Approaches the Problem

A RAG orchestrator receives:

```text
"There is an error in the Dockerfile."
```

Before generation, it decides which evidence to retrieve.

A well-designed retriever might gather:

```text
Dockerfile
recent build log
Confluence proxy documentation
Artifactory remote repository policy
project Maven/npm configuration
```

Then it constructs context for the LLM.

```text
User request
+
Dockerfile
+
internal Artifactory rules
+
build-log excerpt
       ↓
LLM
       ↓
diagnosis
```

This can work extremely well.

The critical dependency is **retrieval coverage**.

## The Classical RAG Failure Mode: Missing the Hidden Dependency

Suppose the retriever sees “Dockerfile” and loads only:

```text
Dockerfile
Docker documentation
```

The model may inspect syntax and conclude that the file looks correct.

It never sees the company-specific rule that base images must use Artifactory.

The problem is not model intelligence.

The relevant evidence was never provided.

This is a classic retrieval miss caused by a weak query-to-source mapping.

## How an MCP-Enabled Agent Changes the Investigation

An agent with carefully scoped capabilities can gather evidence iteratively.

Initial tools might be:

```text
read_project_file(path)
read_latest_build_log()
search_internal_docs(query)
get_artifactory_repository_policy(ecosystem)
```

The flow can become:

```text
1. Read Dockerfile
2. Read actual build error
3. Observe registry/proxy failure
4. Search internal documentation for Docker/Artifactory policy
5. Compare observed URL with approved remote URL
6. Inspect npm/Maven configuration if failure occurs later
7. Produce diagnosis with evidence
```

The agent does not need to know in advance that the Confluence proxy page is relevant. It can discover that relevance from the build error.

## MCP Is Not the Source of Intelligence

It is important not to attribute the reasoning improvement to the protocol itself.

MCP standardizes how a host can expose tools and resources. The **agent control loop** decides to use them.

The same adaptive diagnostic logic could technically be built with direct API calls or custom function calling.

MCP contributes interoperability, typed contracts, discovery, and a place to apply consistent governance.

## Semantic Tools Are Better Than Generic Infrastructure Tools

Compare:

```text
confluence.search(query)
```

with:

```text
get_build_network_policy(ecosystem="docker")
```

The first is flexible but may return large, noisy search results.

The second expresses business intent and can internally query Confluence, Artifactory configuration, and policy metadata.

For enterprise agents, semantic capabilities often reduce context and policy complexity.

## Build Evidence Should Drive the Search Tree

A diagnostic agent should classify errors before searching widely.

For example:

```text
Could not resolve host
  → network / DNS / proxy path

401 / 403 registry response
  → authentication / repository policy

x509 certificate error
  → corporate CA / TLS configuration

manifest unknown
  → image path / tag / remote repository mapping

npm ETIMEDOUT
  → registry / proxy / network

Maven transfer failed
  → mirror / proxy / repository config
```

This converts generic “reasoning” into a structured evidence strategy.

## RAG Remains Valuable Inside the Agent

The adaptive agent should not replace every knowledge lookup with raw tool calls.

Stable enterprise knowledge is still an excellent RAG workload:

```text
Artifactory guidelines
proxy policy
Docker best practices
Maven/npm configuration standards
```

A hybrid flow can be:

```text
Agent
  ↓
read live build evidence
  ↓
RAG search over internal docs
  ↓
compare policy with runtime observation
  ↓
propose remediation
```

MCP can expose both the live tools and the RAG/search service.

## The Diagnostic Trust Boundary

A troubleshooting agent often needs sensitive information:

```text
build logs
repository contents
internal URLs
CI variables
Artifactory configuration
```

It should not receive raw credentials merely to diagnose access.

A secure tool can return:

```yaml
authentication:
  configured: true
  credential_type: workload_token
  valid: false
```

rather than exposing the token itself.

This follows a broader design rule: **give the agent evidence about secrets, not the secrets, whenever possible.**

## Do Not Let the Agent “Fix” Production Directly

Diagnosis and remediation are separate authority classes.

The agent may propose:

```diff
-FROM node:22-alpine
+FROM artifactory.company.example/docker/node:22-alpine
```

or a change to `.npmrc` or Maven settings.

A safe workflow should create a branch or merge request, run the build, and require policy checks before merge.

```text
Diagnosis
  ↓
Patch proposal
  ↓
Sandbox build
  ↓
CI verification
  ↓
Review
  ↓
Merge
```

The model handles diagnosis; the delivery system establishes correctness.

## Observability Makes Diagnosis Auditable

The trace should show:

```text
which files were read
which logs were queried
which internal docs were retrieved
which URLs were compared
which hypothesis was rejected
which fix was proposed
```

This is far more useful than an opaque statement:

```text
"The AI believes the proxy is wrong."
```

Evidence turns troubleshooting into an inspectable process.

## A Hybrid Reference Architecture

```text
Developer / CI Event
        ↓
Diagnostic Agent
        ↓
Read-Only Capability Broker
  ├─ repository files
  ├─ CI build logs
  ├─ Artifactory metadata
  └─ service configuration
        ↓
Enterprise RAG
  ├─ Confluence
  ├─ runbooks
  └─ platform standards
        ↓
Evidence State
        ↓
Root-Cause Hypothesis
        ↓
Patch Proposal
        ↓
CI + Policy Verification
```

This design combines live state with stable knowledge.

## Conclusion

The Dockerfile case demonstrates why enterprise AI troubleshooting is fundamentally an **evidence-acquisition problem**.

The user sees a failing Docker build and reasonably points at the Dockerfile. The real cause may be an invisible organizational dependency: Artifactory remote repositories, corporate proxy rules, registry governance, package-manager configuration, or TLS trust.

Classical RAG succeeds when its retrieval policy already knows which evidence matters. An MCP-enabled agent can improve the investigation when relevance must be discovered dynamically. The strongest design uses both: RAG for stable internal knowledge, controlled tools for live state, and deterministic CI/policy for verification.

The final lesson is broader than Docker:

> **In enterprise systems, the file where the error appears is often not the system where the cause lives.**

Agentic diagnosis is valuable when it can cross those architectural boundaries without crossing security boundaries.
