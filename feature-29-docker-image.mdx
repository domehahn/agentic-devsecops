Ein Docker-Image verpackt Scanner, Laufzeit und native Abhängigkeiten in ein versioniertes Auslieferungsartefakt. Das reduziert Unterschiede zwischen Entwicklerrechnern und CI-Runnern und erleichtert reproduzierbare Deployments.

Das Feature ist damit nicht nur eine Komfortfunktion.

Es verändert, **welcher Kontext geprüft wird, welche Vertrauensgrenzen gelten und wie belastbar das Ergebnis später in CI/CD oder Security-Governance verwendet werden kann**.

## Was das Feature leistet

Das Image sollte eine klar definierte Entry-Point-Schnittstelle besitzen und möglichst ohne Root-Rechte laufen. Scanziele werden read-only gemountet; Reports können in ein separates Output-Verzeichnis geschrieben werden.

Für Reproduzierbarkeit ist ein Digest stärker als ein beweglicher Tag. `latest` beschreibt eine Absicht, ein Image-Digest eine konkrete Identität.

## Typischer Ablauf

Unabhängig von der konkreten Implementierung sollte der Ablauf klar getrennte Phasen besitzen:

```text
Input
  ↓
Validierung und Normalisierung
  ↓
Feature-spezifische Verarbeitung
  ↓
Security-Analyse
  ↓
Findings + Coverage + technischer Status
  ↓
Policy-Entscheidung
```

Diese Trennung ist wichtig, weil ein technischer Fehler bei Beschaffung, Parsing oder Providerzugriff nicht dieselbe Bedeutung hat wie ein tatsächlich unauffälliges Prüfergebnis.

## Negatives Beispiel

Eine Pipeline verwendet:

```yaml
image: scanner:latest
```

und mountet zusätzlich den Docker Socket:

```text
/var/run/docker.sock
```

Der Scanprozess läuft als root. Ein kompromittierter Scanner oder Parser hätte damit faktisch Host-Kontrolle. Gleichzeitig ändert sich das Image hinter `latest` ohne Änderung der Pipeline.

## Positives Beispiel

Die Pipeline pinnt einen Digest und beschränkt Rechte:

```text
image: scanner@sha256:<digest>
user: non-root
workspace mount: read-only
no docker socket
network: disabled unless required
```

Reports werden in ein separates, beschreibbares Volume geschrieben. Die Image-Version erscheint im Report und kann mit SBOM und Signatur verifiziert werden.

<KeyTakeaway>
Ein Container standardisiert die Laufzeit, ersetzt aber keine Isolation. Gepinnte Digests, read-only Mounts und minimale Rechte machen das Image zu einem belastbaren DevSecOps-Baustein.
</KeyTakeaway>

## Security- und Betriebsaspekte

Container sind keine vollständige Sandbox. Capabilities, Seccomp/AppArmor, Netzwerk, Mounts und User Namespace bestimmen die Isolation. Besonders riskant sind Host-Sockets, privileged mode und schreibbare Repository-Mounts.

Das Scanner-Image selbst braucht Supply-Chain-Kontrollen: minimales Base Image, regelmäßige Updates, SBOM, Signatur und bekannte Digest-Referenz.

Ein professioneller Betrieb sollte außerdem drei Zustände konsequent auseinanderhalten:

```text
clean      = geprüft, kein relevanter Befund
finding    = geprüft, mindestens ein relevanter Befund
incomplete = Prüfung technisch oder fachlich nicht vollständig
```

Gerade der dritte Zustand ist für DevSecOps entscheidend.

Ein Scanner darf fehlende Coverage nicht als positives Sicherheitsurteil darstellen.

## Wo das Feature sinnvoll eingesetzt wird

Ideal für CI/CD, reproduzierbare lokale Tests und zentrale Runner. Containerisierung vereinfacht die Verteilung nativer Abhängigkeiten und sorgt für konsistente Versionen.

In sehr restriktiven Umgebungen kann zusätzlich eine stärkere Sandbox oder VM-Isolation notwendig sein.

Die konkrete Aktivierung sollte deshalb aus dem gewünschten Trust-Modell abgeleitet werden und nicht allein aus technischer Verfügbarkeit.

## Integration in eine DevSecOps-Pipeline

In einer Pipeline sollte das Feature nicht isoliert betrachtet werden.

Ein belastbares Muster ist:

```text
Source / Artifact
      ↓
Input-Validierung
      ↓
Deterministische Analyse
      ↓
optionale erweiterte Analyse
      ↓
normalisierte Findings
      ↓
Policy Gate
      ↓
Report / Audit Evidence
```

Dabei sollte jeder Report mindestens folgende Informationen transportieren:

- Identität des analysierten Artefakts
- aktive Analyseverfahren
- übersprungene oder nicht verfügbare Prüfschritte
- stabile Regel- oder Finding-IDs
- Schweregrad und Evidenz
- Scanner- und Regelversion
- eindeutiger technischer Abschlussstatus

Damit wird das Feature nicht nur ausführbar, sondern **auditierbar**.

## Fazit

Ein Container standardisiert die Laufzeit, ersetzt aber keine Isolation. Gepinnte Digests, read-only Mounts und minimale Rechte machen das Image zu einem belastbaren DevSecOps-Baustein.

Der eigentliche Wert entsteht dann, wenn das Feature mit klaren Grenzen, reproduzierbaren Eingaben und transparenten Ergebnissen in den Entwicklungsprozess eingebettet wird.
