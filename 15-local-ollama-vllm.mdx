Lokale Modelle sind attraktiv, wenn Skill-Inhalte das eigene Netzwerk nicht verlassen sollen. Ollama, vLLM oder llama.cpp können eine OpenAI-kompatible API bereitstellen und damit semantische Analyse ohne öffentlichen SaaS-Provider ermöglichen.

„Lokal“ bedeutet aber nicht automatisch sicher. Ein Scanner, der `localhost` oder private Netze kontaktieren darf, besitzt eine SSRF-relevante Fähigkeit.

<Warning>
Privacy und SSRF-Schutz sind zwei verschiedene Ziele. Ein lokaler Endpoint schützt Datenresidenz, erweitert aber gleichzeitig die Netzwerk-Capability des Scanners.
</Warning>

## Was das Feature wirklich bedeutet

Bei einem rein lokalen Modell treffen zwei Ziele aufeinander: Datenschutz und Netzwerkisolation. Einerseits bleiben Inhalte im eigenen System; andererseits muss der Scanner Verbindungen zu Loopback oder RFC1918-Zielen öffnen, die bei unkontrollierter URL-Konfiguration missbraucht werden könnten.

Die sichere Lösung ist eine explizite, vertrauenswürdige Providerkonfiguration außerhalb des Prüflings.

## SkillSpector

SkillSpector nutzt lokale Modelle über den normalen OpenAI-kompatiblen Provider. Die README zeigt Ollama mit `OPENAI_BASE_URL=http://localhost:11434/v1` und einem lokalen Modellnamen. Damit ist der lokale Pfad sehr direkt.

Dasselbe Prinzip funktioniert für andere OpenAI-kompatible Inference-Server wie vLLM.

## `skil`

`skil` unterstützt ebenfalls OpenAI-kompatible lokale Endpoints, blockiert private, Loopback- und ähnliche Zielnetze jedoch standardmäßig. Erst `--semantic-allow-private` öffnet diese Grenze.

Damit bleibt SSRF-Schutz der Default, während lokale Inference als bewusste Ausnahme möglich ist.

## Praxisbeispiel

```bash
# SkillSpector + Ollama
export SKILLSPECTOR_PROVIDER=openai
export OPENAI_API_KEY=ollama
export OPENAI_BASE_URL=http://localhost:11434/v1
export SKILLSPECTOR_MODEL=llama3.1:8b
skillspector scan ./skill

# skil: private Zieladresse bewusst freigeben
skil scan ./skill   --semantic   --semantic-provider openai   --semantic-model llama3.1:8b   --semantic-allow-private
```

In CI sollte der lokale Modellserver auf einem dedizierten Interface laufen und der Scanner nur genau dieses Ziel erreichen können.

## Security- und DevSecOps-Einordnung

- Private Endpoint-Allowance nur aus vertrauenswürdiger Pipeline-Konfiguration setzen.
- Modellserver nicht auf unnötig breite Interfaces exponieren.
- API-/Model-Endpoint nicht aus dem gescannten Skill ableiten.
- Auch lokal Modellversion und Prompt-/Provider-Coverage dokumentieren.
- Container-Netzwerke so segmentieren, dass andere interne Dienste nicht erreichbar sind.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

## Typische Fehlinterpretation

„Lokales LLM bedeutet null Netzwerk-Risiko.“ Der Scanner muss zumindest Loopback oder ein privates Netz erreichen. Ohne Zielkontrolle kann daraus eine SSRF- oder Seitwärtsbewegungsfläche werden.

## Einordnung in die Pipeline

Dieses Feature gehört in eine **optionale semantische Analyse-Stufe hinter dem deterministischen Gate**. So bleiben Pull-Request-Checks schnell und reproduzierbar, während modellgestützte Analyse gezielt für risikoreiche Skills, Release-Kandidaten oder Nightly-Scans zugeschaltet werden kann.

Pipeline-seitig sollten Provider, Modell, Endpoint und Credential aus vertrauenswürdiger Konfiguration stammen. Der Skill selbst darf diese Parameter nicht überschreiben. Ein Providerfehler muss als fehlende Coverage sichtbar bleiben.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Beide können lokale OpenAI-kompatible Modelle nutzen. `skil` macht die zusätzliche Vertrauensentscheidung sichtbar, indem private Zielnetze standardmäßig blockiert sind. SkillSpector ist im lokalen Setup unmittelbarer.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
