# Vector Search: The Mechanics of Semantic Retrieval

Vector search is often summarized as:

> “Search by meaning instead of words.”

That sentence is useful for product explanations and inadequate for engineering.

A vector retrieval system does not directly compare meaning. It compares numerical representations produced by a learned model. The real chain is:

```text
information
   ↓
representation model
   ↓
high-dimensional vector
   ↓
similarity function
   ↓
nearest-neighbor algorithm
   ↓
candidate set
```

Every stage imposes assumptions.

The representation model decides which distinctions survive compression.

The distance function decides how geometric closeness is measured.

The index decides which points are examined.

The retrieval policy decides which candidates are eligible.

The downstream ranker decides which results matter most.

Vector search is therefore best understood as **learned representation plus geometric retrieval**, not as a database that magically understands semantics.

---

## The Representation Problem Comes Before the Search Problem

Suppose two sentences express a similar operational issue:

```text
"The GitLab Runner cannot start container jobs."

"The Docker executor on the CI runner fails before creating the container."
```

A lexical method may see limited overlap.

A well-trained embedding model may map both into nearby regions.

Formally:

\[
e_q=f_\theta(q)
\]

\[
e_d=f_\theta(d)
\]

The retrieval system then compares \(e_q\) with stored document embeddings.

The quality of the entire search is bounded by \(f_\theta\).

A perfect nearest-neighbor algorithm operating on a representation that collapses important distinctions will return the wrong neighbors perfectly.

This gives a practical hierarchy:

```text
representation quality
   ↓
candidate search quality
   ↓
ranking quality
```

Index tuning should never be used to avoid evaluating the embedding model.

---

## Embeddings Compress Information

A document may contain thousands of tokens, several entities, negations, exceptions, versions, and relationships.

A single-vector encoder compresses this into \(d\) numbers.

That compression is powerful because it enables fast comparison.

It is also lossy.

Two documents may become geometrically close for broad topical reasons while differing on the exact fact that matters.

Example:

```text
Document A:
GitLab Runner 18.7 requires custom CA installation in path X.

Document B:
GitLab Runner 18.6 had a certificate issue in path Y.
```

A dense embedding may consider both highly similar.

For a version-specific troubleshooting task, the distinction may be decisive.

This is one reason modern retrieval architectures increasingly combine dense search with lexical and late-interaction signals.

---

## Cosine Similarity Is Geometry, Not Confidence

Cosine similarity compares direction:

\[
\cos(q,d)
=
\frac{q\cdot d}
{\|q\|\|d\|}
\]

If embeddings are normalized:

\[
\|q\|=\|d\|=1
\]

then:

\[
\cos(q,d)=q\cdot d
\]

This makes cosine and inner-product ranking equivalent under normalization.

But a score such as:

```text
0.86
```

does not answer:

```text
Is this document relevant?
Is it correct?
Is it current?
Is it safe?
```

Similarity thresholds are model- and domain-dependent.

A score distribution for legal documents may look very different from one for source code.

Thresholds should be learned empirically from labeled retrieval data.

---

## Euclidean Distance Encodes Another Geometry

Euclidean distance:

\[
d(q,x)=
\sqrt{
\sum_i(q_i-x_i)^2
}
\]

measures absolute geometric distance.

This can matter when vector magnitude carries signal.

Some embedding models are trained explicitly around cosine-like objectives, others around inner product or distance functions.

The database metric and training objective should be aligned.

A mismatch can quietly degrade ranking even if the index is correctly implemented.

---

## Exact Search Defines What “Nearest” Means Operationally

For \(N\) stored vectors, exact search evaluates every candidate:

\[
score_i=sim(q,v_i)
\]

and sorts the results.

Complexity is approximately:

\[
O(Nd)
\]

This may be entirely acceptable for:

- tens of thousands of vectors;
- offline evaluation;
- small tenant partitions;
- low-query-rate systems.

Exact search has another role: it establishes the reference ranking used to evaluate ANN indexes.

Without that baseline, teams may tune HNSW or IVF against final answer quality only and miss index-specific recall loss.

---

## ANN Search Changes the Objective

Approximate search asks:

> Can we retrieve nearly the same useful neighbors without evaluating the entire space?

The important word is *useful*.

A mathematically exact top-10 may not equal the semantically best top-10 because the embedding model itself is imperfect.

That yields two different notions of recall.

### ANN recall

Did the approximate index reproduce the exact vector neighbors?

\[
Recall^{ANN}@K
=
\frac{
ANN_K \cap Exact_K
}{K}
\]

### Relevance recall

Did the retrieval system return the documents judged relevant to the information need?

\[
Recall^{rel}@K
=
\frac{
RelevantRetrieved_K
}{
AllRelevant
}
\]

These metrics should not be conflated.

## HNSW Trades Graph Memory for Navigability

HNSW represents vectors as a hierarchy of proximity graphs.[^1]

The upper layers contain sparse long-range structure.

Lower layers contain denser local neighborhoods.

A query enters high in the hierarchy and descends while following promising connections.

The mechanism resembles navigable small-world structures rather than partition-based indexing.

Practical implementations expose two especially important classes of tuning.

### Construction effort

More effort during index construction can produce better graph connectivity.

The cost is slower builds and more compute.

### Query effort

More candidate exploration can improve recall.

The cost is higher latency.

Therefore:

```text
higher recall
↔
more work
```

The optimal point depends on latency SLO and workload.

---

## Why HNSW Works Well—and Where It Hurts

HNSW is attractive because it often provides a strong speed/recall trade-off.[^1]

Its cost profile includes:

- graph edges;
- index memory;
- slower builds;
- maintenance overhead;
- interaction with filters and deletes.

In memory-constrained environments, the graph can be more expensive than the vectors themselves.

Delete-heavy or frequently changing corpora may need special operational attention depending on the implementation.

The right question is not:

> Is HNSW fast?

It is:

> Is HNSW economical under our write rate, memory budget, filtering pattern, and recall target?

---

## IVF Is Coarse Quantization as Search Pruning

Inverted-file approaches partition the space around coarse centroids.

At query time, only the nearest regions are searched.

Conceptually:

\[
q
\rightarrow
nearest\ centroids
\rightarrow
selected\ lists
\rightarrow
candidate\ distances
\]

The central parameter is how broadly to probe.

Probe too few clusters:

```text
low latency
low recall
```

Probe many:

```text
higher latency
higher recall
```

Unlike HNSW, IVF-based indexes typically require a training or clustering step before the index can represent the corpus efficiently.

The pgvector documentation reflects this distinction between HNSW and IVFFlat in operational terms.[^2]

---

## Product Quantization Separates Candidate Search from Exact Representation

Product Quantization divides vectors into subspaces and replaces each subvector with a codebook entry.

A simplified model:

\[
x=
[x^{(1)},x^{(2)},...,x^{(m)}]
\]

Each subvector becomes:

\[
x^{(j)}
\rightarrow
c^{(j)}_{k}
\]

Instead of storing full floats, the index stores compact code references.

This reduces memory and often increases cache efficiency.

The trade-off is approximation error.

A strong architecture may use quantized search for candidate generation and a higher-fidelity representation for reranking.

---

## The Curse of Dimensionality Is Not Just a Textbook Phrase

As dimensionality increases, geometric intuition from two or three dimensions becomes unreliable.

Distances can concentrate.

Neighborhood structure becomes harder to separate.

Index efficiency changes.

However, modern embedding spaces are not random high-dimensional clouds. They contain learned structure.

Therefore the practical question is not whether the curse of dimensionality “applies” in the abstract.

It is whether:

- the representation separates relevant from irrelevant items;
- the chosen index can exploit that structure;
- recall remains acceptable at production scale.

Empirical retrieval evaluation wins over geometric slogans.

---

## Bi-Encoders Make Large-Scale Retrieval Possible

A bi-encoder independently encodes the query and the document.

\[
q=f_Q(query)
\]

\[
d=f_D(document)
\]

The document vector is precomputed.

At query time only \(q\) needs to be generated.

This makes ANN retrieval practical.

The price is interaction compression: the query and document do not jointly attend to one another during the initial score.

This is why bi-encoders are often excellent candidate generators but not always optimal final rankers.

---

## Cross-Encoders Recover Fine-Grained Interaction

A cross-encoder receives query and document together:

```text
[query] [SEP] [document]
```

and produces a relevance score.

Because the model can jointly attend across both sequences, it can capture subtle interactions that one-vector similarity may miss.

But the cost scales with the number of query-document pairs.

Therefore:

```text
millions of documents
→ impossible to cross-encode directly

top 50 candidates
→ feasible
```

This naturally creates multi-stage ranking.

---

## Late Interaction Occupies a Middle Ground

ColBERT introduced a late-interaction approach where query and document are encoded independently into token-level vectors, then matched through a fine-grained interaction function.[^3]

This preserves more local semantic detail than a single-vector representation while retaining substantial precomputation.

ColBERTv2 further reduces storage through compression while preserving retrieval quality.[^4]

Conceptually:

```text
single-vector bi-encoder:
document → one vector

late interaction:
document → many token-level vectors
```

The second representation is more expensive but can improve exact term/concept alignment without running a full cross-encoder over every candidate.

---

## Sparse Learned Retrieval Blurs the Lexical/Semantic Boundary

Dense embeddings are not the only learned retrieval representation.

SPLADE learns sparse token-space representations and expansion weights.[^5]

This matters architecturally because the classic distinction:

```text
BM25 = lexical
Vector Search = semantic
```

is becoming less binary.

Modern retrieval includes:

```text
classical sparse
learned sparse
dense
multi-vector
cross-encoder
graph
```

The production problem is increasingly *signal composition*, not choosing one “best search technology.”

---

## Multilingual Retrieval Is Representation Transfer

Multilingual embedding models can place semantically related text from different languages into a shared space.

This enables:

```text
German query
→ English document
```

without explicit translation in every retrieval path.

But performance is rarely uniform across all language pairs.

Benchmarks should segment by:

- source language;
- query language;
- technical vocabulary;
- domain.

A multilingual model that performs well on common conversational text may perform poorly on mixed German-English DevSecOps terminology.

---

## Multimodal Vector Search Extends the Same Retrieval Principle

The retrieval object does not have to be text.

Embedding models can map:

```text
image
audio
video
code
text
```

into compatible or modality-specific representation spaces.

This supports:

```text
text → image
image → image
text → code
audio → similar audio
```

The same infrastructure concerns remain:

- representation versioning;
- metric choice;
- ANN recall;
- filtering;
- access control.

The modality changes.

The retrieval discipline does not.

---

## Vector Search in RAG Is Candidate Selection for Context Construction

In RAG:

```text
user question
   ↓
query embedding
   ↓
vector search
   ↓
candidate chunks
   ↓
reranker
   ↓
context builder
   ↓
LLM
```

The search stage does not answer the question.

It selects evidence candidates.

This distinction matters because RAG quality can fail in four separate ways:

```text
1. relevant evidence not indexed
2. relevant evidence not retrieved
3. retrieved evidence not ranked high enough
4. evidence reaches LLM but is misinterpreted
```

A single final-answer score cannot localize these failures.

---

## Top-K Is a Budget Parameter

A larger `K` can increase recall.

It can also increase:

- context tokens;
- irrelevant information;
- contradiction;
- prompt-injection exposure;
- reranking compute.

The best `K` is workload-specific.

A system may retrieve 100 candidates for reranking and pass only five sections into the LLM.

That is fundamentally different from putting all 100 chunks into context.

---

## Exact Identifiers Expose Dense Retrieval Weaknesses

A vector model may embed:

```text
CVE-2026-12345
```

near other vulnerability identifiers.

But the user usually wants this exact identifier.

The same problem occurs with:

```text
commit hashes
ticket IDs
resource names
package versions
error codes
```

Semantic similarity is not identity.

This is one of the strongest practical arguments for hybrid retrieval.

---

## Metadata Filtering Is Part of Retrieval Semantics

Suppose the nearest documents are:

```text
1. another tenant's incident
2. an expired policy
3. a public blog
4. the user's valid internal runbook
```

Pure vector similarity would rank 1–3 above 4.

A production query must apply constraints:

```text
tenant = current_tenant
classification <= principal_clearance
validity = current
source_type in allowed_sources
```

Retrieval relevance is conditional on admissibility.

---

## Temporal Awareness Must Be Explicit

Semantic search has no natural sense of “current.”

A five-year-old policy can be nearly identical to the current policy.

Store and filter:

```text
valid_from
valid_until
superseded_by
version
updated_at
```

The application should be able to distinguish:

```text
similar
```

from:

```text
applicable now
```

---

## Poisoning Targets Retrieval Probability

An attacker does not necessarily need to compromise the vector database.

They can manipulate an upstream document so that it becomes highly retrievable for target queries.

PoisonedRAG formalized this as a knowledge-corruption attack against RAG systems and demonstrated high attack success in evaluated settings.[^6]

This means the attack surface includes:

```text
source authoring
document ingestion
embedding
ranking
context construction
```

Security cannot begin at the vector index.

---

## Vector Search in Agentic AI Becomes Semantic Routing

A tool-capable agent can use vector retrieval for:

```text
knowledge
memory
skills
tools
sub-agents
historical cases
```

Example:

```text
task:
"Investigate a TLS error in GitLab Runner"

vector retrieval:
- runbook: custom CA
- memory: similar incident
- skill: pipeline troubleshooting
- tool: inspect_runner_logs
```

The vector search is now influencing *what the agent does next*.

This elevates retrieval from information retrieval to control-plane support.

---

## Tool Discovery Needs Safety Metadata

Embedding a tool description is easy.

Safe tool routing is harder.

A retrieved capability should carry:

```json
{
  "tool": "inspect_runner_logs",
  "risk": "read_only",
  "owner": "platform-team",
  "version": "3.2.1",
  "allowed_environments": ["dev", "test", "prod"],
  "requires_approval": false
}
```

The vector score answers relevance.

Policy answers authority.

---

## Evaluation Must Use Real Information Needs

A meaningful retrieval benchmark contains:

```yaml
query: "Why is the runner failing x509 validation?"
relevant:
  - runbook-custom-ca
  - incident-184
irrelevant_but_similar:
  - generic-tls-overview
  - expired-ca-policy
```

This allows the system to test not just topical similarity but answer-bearing retrieval.

Metrics include:

\[
Precision@K
\]

\[
Recall@K
\]

\[
MRR
\]

\[
NDCG@K
\]

For approximate indexes, also measure ANN recall against exact search.

---

## Evaluation Should Be Sliced

Aggregate retrieval metrics can hide severe failures.

Useful slices:

```text
exact identifiers
long natural-language questions
short queries
German queries
English queries
code search
security queries
recent documents
ACL-heavy queries
```

A model can achieve strong average NDCG while failing badly on CVE identifiers.

That failure may be unacceptable in a security assistant.

---

## Retrieval Traces Make Search Debuggable

For every query, record:

```text
query
embedding model
index version
filters
candidate ids
raw scores
reranker scores
final context
latency
```

This turns “the model answered incorrectly” into a diagnosable pipeline.

Example:

```text
failure:
relevant document never entered top 100

root cause:
dense embedding failed exact identifier matching

fix:
hybrid lexical+dense retrieval
```

Without traceability, teams frequently tune the wrong layer.

---

## Embedding Upgrades Are Behavioral Changes

Changing an embedding model changes the neighborhood graph of information.

The same query may retrieve different:

- documents;
- memories;
- tools;
- skills.

Therefore treat embedding upgrades as production releases.

Use:

```text
dual index
offline benchmark
shadow traffic
canary
rollback
```

The fact that the model does not generate text does not make it operationally harmless.

---

## Storage Economics Matter More at Multi-Vector Scale

A single 1536-dimensional Float32 vector is roughly 6 KB.

Late-interaction models may store many vectors per document.

This can increase storage by an order of magnitude.

Compression, lower precision, quantization, pruning, or specialized indexing become architectural choices.

ColBERTv2 explicitly addresses this storage problem through residual compression.[^4]

Retrieval quality cannot be separated from representation cost.

---

## The Right Mental Model

Vector search is not:

```text
semantic SQL
```

It is closer to:

```text
learned feature extraction
+
geometric candidate selection
```

The output is a ranked hypothesis about relevance.

That hypothesis must still pass:

- authorization;
- provenance;
- freshness;
- reranking;
- domain validation.

---

## Conclusion

Vector search gives modern AI systems a powerful capability: the ability to navigate information spaces using learned similarity rather than exact lexical identity.

Its strength comes from compression.

Its limitations come from the same compression.

A mature retrieval architecture therefore treats vector search as one stage in a larger system:

```text
representation
→ ANN
→ filters
→ fusion
→ reranking
→ context
→ verification
```

Use dense vectors for semantic reach.

Use lexical retrieval for identity.

Use late interaction when finer matching justifies the cost.

Use policy for admissibility.

And evaluate every layer separately.

Vector search does not “understand meaning.”

It makes learned semantic geometry operational.
