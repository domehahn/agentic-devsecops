## Unused permission is still attack surface

Security teams often focus on code that secretly does more than declared. The opposite mismatch is quieter but strategically important: a skill asks for filesystem, network or tool authority it does not appear to need. That unused authority expands the blast radius of future bugs, prompt injection and compromised dependencies.

Overdeclaration is a least-privilege property. It compares declared authority with observed need while acknowledging that static analysis cannot prove every capability is unused. The result should drive review and reduction, not pretend to be a perfect liveness proof. The original `skil` control model expresses the same idea as `DECLARED_CAPABILITIES − OBSERVED_CAPABILITIES != ∅`. That relation is more useful than a label such as “suspicious” because it specifies what must be evidenced and what a legitimate counterexample must break.

## Reverse capability comparison

An unused permission may have no effect today, but it can be exploited by a later injection or vulnerable dependency without another authorization change. Removing unused authority reduces the number of conditions an attacker must satisfy. This also improves explainability. Reviewers can see the specific security fact rather than receiving a generic severity label, and future tooling can compose that fact with independent findings without double-counting the same evidence.

## Coverage-aware absence

If an analyzer does not understand a framework, the absence of an observation is weak evidence. The verifier should mark which capability categories have strong static coverage and downgrade claims where dynamic behavior could explain the gap. A useful implementation records both the positive observation and the guard that would have made the path safe. That makes remediation testable and turns false-positive handling into explicit logic instead of a collection of suppressions.

## Category and item granularity differ

It may be safe to say “network capability appears unused” while being unsafe to claim “this particular allowlisted domain is unnecessary” if the analyzer cannot resolve all dynamic targets. Findings should match the granularity the evidence can support. The same model supports change detection: when identity, configuration or code changes, the platform can recompute the relation and show exactly which part of the previously reviewed assumption no longer holds.

## Operational traces can complement static analysis

Production or test traces can demonstrate which permissions are exercised under realistic workloads. Traces are not complete proof either, but combined with static observations they can support more confident contract reduction. In an agentic environment this distinction becomes operational because model-generated plans can select the relevant value or capability at runtime. The host therefore needs evidence that can survive from code review into execution policy.

## Overdeclaration is also a governance smell

Broad permissions often reveal unclear ownership, cargo-culted templates or fear of breaking automation. Treating the finding as an architecture issue encourages teams to design narrower interfaces instead of accumulating permanent exceptions. The design implication is that detection and authorization must remain separate: the scanner identifies the condition, while a policy layer decides whether the condition is permissible in this deployment context.

## Category versus item precision

A deliberately small positive fixture from the source property illustrates the boundary:

```yaml
contract:
  filesystem:
    write: ["/**"]
  network: ["*"]
# observed: only reads ./docs
```

The safe counterexample changes the semantics rather than merely deleting a suspicious token:

```yaml
contract:
  filesystem:
    read: ["./docs/**"]
# observed: reads only ./docs
```

The purpose of pairing them is not to teach exploitation. It is to force the detector to explain which relation changes between the two cases. A scanner that fires on both has learned vocabulary; a scanner that can explain the difference has begun to model the security property.

## Feature flags and exceptional paths

For this property, a finding is defensible only when the scanner can reconstruct the relation `DECLARED_CAPABILITIES − OBSERVED_CAPABILITIES != ∅` from observable evidence. The relevant implementation controls are `SKIL-CAP-001`. The mechanism—reverse declared-vs-observed verification—should therefore emit more than a Boolean match: reviewers need location, the structured observation, context resolution, the decision path, and the coverage state. The source material characterizes current coverage as PARTIAL for per-item allowlists; strong at category level; that statement should travel with the finding rather than being lost in presentation.

A compact machine-readable evidence record can retain the essentials without pretending to encode the entire analysis:

## False positives, ambiguity, and safe counterexamples

Feature flags and rarely used recovery paths can legitimately require permissions absent from ordinary tests. The contract should document those cases explicitly, ideally with targeted verification fixtures, rather than keeping unexplained wildcards.

Coverage should be treated as first-class security data. Deterministic syntax and configuration observations can often be reproduced exactly, while intent, future identity and runtime targets may remain uncertain. A mature scanner reports those asymmetries instead of collapsing them into one confidence score. This is particularly important in agentic systems, where the model may choose arguments and tools only after deployment.

## Task-scoped authority

Issue task-scoped or short-lived capabilities where possible. Even when a contract retains a broad category for exceptional workflows, runtime policy can mint narrower tokens or mounts for each actual task.

Defense in depth is intentionally redundant. Authoring lint, static analysis, contract verification, supply-chain verification, runtime policy and audit telemetry answer different questions. A strong result from one layer should never be used as a reason to remove the others.

## Governance implications

True-positive fixtures should cover canonical violations, while true-negative fixtures should intentionally reuse similar tokens and syntax so the detector proves it understands context. Boundary cases should change one security-relevant fact at a time. Mutation tests can vary scope, target, normalization, version, guard, or sink. Holdout fixtures protect against overfitting to the public examples. For **Overdeclared Capabilities**, the most valuable tests are those that preserve the surface appearance while changing the underlying security relation; that is how the suite verifies semantics instead of vocabulary.

For `skil`, implementation claims should be checked against the repository’s control matrix, external-control crosswalk, analyzer tests and any provider-specific tests. Provider-backed coverage—such as OSV or external rule packs—must state whether the provider actually ran.

## Architecture drill-down: from finding to enforceable boundary

A design review for this capability and isolation boundary property should begin by drawing the trust boundary rather than opening with a rule ID. Identify who controls the input, which component interprets it, what authority is available at that point, and which deterministic guard is expected to stop an unsafe transition. Then map `DECLARED_CAPABILITIES − OBSERVED_CAPABILITIES != ∅` onto that diagram. The purpose of reverse declared-vs-observed verification is to provide one or more observable edges in that model; it is not a substitute for the model itself. Reviewers should ask whether the same relation can be created indirectly through wrappers, generated configuration, aliases, cached metadata, transitive dependencies, or delegated tools. If so, the implementation needs either deeper static summaries or a runtime control at the unresolved boundary. Finally, confirm that evidence identifiers survive across CI, packaging and runtime so an observed denial or drift event can be traced back to the assumption approved in code review.

The paired fixtures also serve as an architectural regression test. The unsafe example begins with `contract:` while the safe example begins with `contract:`. The important difference is the security relation, not the cosmetic text. If a refactor causes both to produce the same result, the detector or policy has lost a meaningful distinction.

## Common implementation traps

Several implementation mistakes recur around **Overdeclared Capabilities**, even when the high-level policy is correct:

**1. Using a contract vocabulary that is too coarse to enforce.** A declaration such as 'network' is weak if the runtime cannot distinguish approved targets from arbitrary egress. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**2. Interpreting absence of static observation as proof that a capability is unused.** Dynamic frameworks, reflection and remote configuration require explicit coverage states and sometimes runtime evidence. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

**3. Mounting global control-plane state for convenience.** Home directories, peer skill directories and MCP config files create ambient authority that bypasses the intended capability model. The remediation should be encoded in tests or runtime policy so the same mistake cannot quietly return in a later refactor.

A useful review discipline is to turn every exception into a scoped, expiring artifact with an owner and rationale. Permanent blanket suppressions hide whether the architecture improved; narrow exceptions preserve the signal and make technical debt measurable.

## How this property composes with adjacent findings

**Overdeclaration plus injection exposure.** Excess authority increases the consequences of prompt injection, compromised dependencies, and tool-selection errors. A permission that is unused during normal operation may be exactly the capability an attacker wants. Least-privilege findings become more actionable when risk analysis shows which threat paths the permission would enable.

This composition model is deliberately graph-like: each detector contributes a typed fact and shared evidence identifiers allow a higher-level policy engine to connect them. That prevents one rule from becoming an overloaded catch-all and makes severity escalation explainable.

## Operational signals and measurable assurance

Measure unused high-risk permissions, contract reductions after review, permissions justified by exceptional-path tests, runtime token scopes versus declared maxima, and time-bounded exceptions that expire as planned.

Metrics should be tied to an explicit denominator and deployment profile. A low finding count may mean strong controls, weak coverage, or simply little exposure; telemetry and coverage state are needed to tell those cases apart. Trend the data over time and review unexpected changes in both positive findings and scanner-negative regression behavior.

## Engineering implications beyond the scanner

Capability and isolation properties become most valuable when compiled into runtime controls. A declaration can drive egress filters, filesystem mounts, process brokers, secret scopes and delegation edges. Static observations then test whether implementation and contract agree, while runtime denials expose behaviors the static analyzers could not resolve. This feedback loop turns the contract into a living security boundary instead of documentation that gradually drifts from reality.

The broader lesson is that an agentic skill is simultaneously text, code, configuration, a tool contract and a supply-chain artifact. Security review should follow the boundary that is actually crossed—data, authority, identity, execution, or control-plane visibility—rather than forcing every risk into the same detection template.

## How to test least privilege

A reviewer should be able to answer four questions before accepting this property as controlled:

1. **What exact security relation is being asserted?** Here it is `DECLARED_CAPABILITIES − OBSERVED_CAPABILITIES != ∅`.
2. **What concrete evidence supports the relation?** The evidence must come from reverse declared-vs-observed verification, not from a keyword alone.
3. **What near-neighbor safe case has been tested?** The paired negative fixture should differ in the property, not merely in spelling.
4. **What remains outside static visibility?** Runtime identity, dynamic values, provider state and policy decisions must be named explicitly.

## Conclusion

**Overdeclared Capabilities** is valuable only when it is treated as a falsifiable security property rather than a checklist term. The goal is not to declare an entire skill “malicious” or “safe.” The goal is to state what boundary may be crossed, show the evidence that supports that statement, preserve the coverage limits, and make the safe countercondition explicit. That produces findings engineers can test, reviewers can reproduce, and runtime policy can enforce.
