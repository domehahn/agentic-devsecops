Agent Skills besitzen häufig Netzwerktools. Dadurch wird Server-Side Request Forgery auch in Agent Workflows relevant: Ein manipulierter URL-Parameter kann den Agenten dazu bringen, interne Admin-APIs, lokale Services oder Cloud Metadata zu kontaktieren.

Dieser SSRF-Artikel unterscheidet sich vom ersten Beitrag zu „Generic Remote URL“: Dort ging es um die **Netzwerkgrenze des Scanners selbst**. Hier geht es um SSRF-Verhalten **im gescannten Skill**.

<KeyTakeaway>
Vulnerability Patterns sind keine bloße Liste verdächtiger Strings. Sie beschreiben **Sicherheitsproperties und Trust-Boundary-Verletzungen**, die bei agentischen Artefakten aus natürlicher Sprache, Code, Metadaten, Tools und Runtime-Capabilities entstehen.
</KeyTakeaway>

## Die Pattern-Familie

Dieser Beitrag betrachtet `SSRF1`, `SSRF2`, `SSRF3` im SkillSpector-Snapshot `2.5.0` beziehungsweise Commit `34f6030`.

| Rule | Pattern | Bedeutung |
| --- | --- | --- |
| `SSRF1` | Cloud Metadata Access | Greift auf Instance Metadata oder vergleichbare Cloud-Credential-Endpunkte zu. |
| `SSRF2` | Internal Network Request | Sendet Requests an Loopback, Link-Local oder private Netzwerkziele. |
| `SSRF3` | Dynamic Request Target | Konstruiert Zielhost oder URL aus dynamischen beziehungsweise untrusted Werten. |

Die Rule IDs sind vor allem als stabile Triage-Signale nützlich. Für eine Freigabeentscheidung sollten zusätzlich Finding-Text, Datei, Zeile, Confidence, Analyzer-Coverage und das konkrete Artefakt berücksichtigt werden.

## Das Sicherheitsmodell dahinter

SSRF1 schützt hochkritische Metadata/Credential Endpoints. SSRF2 erweitert die Grenze auf interne und lokale Services. SSRF3 erkennt die Voraussetzung für attacker-controlled Routing: Der Host wird dynamisch aus Input gebaut.

Ein sicheres Netzwerkmodell benötigt daher sowohl Destination Policy als auch Dataflow Validation.

<Architecture>
Ein Scan kann gefährliche Eigenschaften sichtbar machen. Die eigentliche Sicherheitsgrenze sollte trotzdem außerhalb des unvertrauenswürdigen Skills liegen: in Tool-Gateways, Filesystem-Isolation, Network Policy, Identity, Approval und Runtime Enforcement.
</Architecture>

## Verständliches Beispiel

```python title="safe-fetch.py"
ALLOWED_HOSTS = {"api.example.com"}

host = parse_host(user_url)
if host not in ALLOWED_HOSTS:
    raise ValueError("destination not allowed")

response = fetch(user_url)
```

Noch stärker ist ein Host Gateway, bei dem der Skill gar keine freie URL übergeben kann, sondern nur eine benannte, freigegebene Destination.

Das Beispiel zeigt das zentrale Prinzip: Nicht jede verwendete API oder Formulierung ist automatisch bösartig. Relevant ist, **welche Autorität ein Skill erhält, welche Daten er verarbeiten kann und welche Boundary er überschreiten soll**.

## Wie SkillSpector das erkennt

SkillSpector besitzt dedizierte SSRF-Patterns für Cloud Metadata, private/loopback/link-local Targets und dynamische Requestziele. Diese Regeln ergänzen E1: Nicht jeder Netzwerkrequest ist Exfiltration, und nicht jeder SSRF-Request sendet sensitive Daten nach außen.

SSRF ist eine **Destination-Trust**-Frage.[^module]

SkillSpector arbeitet dabei nicht mit einer einzigen monolithischen „AI Security“-Regel. Die Analyzer sind getrennte Nodes, die Findings erzeugen und im aktuellen Workflow über ein Inspection Ledger beziehungsweise Analyzer-Status sichtbar machen, welche Analyse tatsächlich ausgeführt wurde.[^registry]

## False Positives, False Negatives und Kontext

Private Netze sind nicht pauschal verboten. Ein legitimer interner Operations-Skill kann interne APIs benötigen. Dann braucht er eine präzise Allowlist und Workload Identity.

Dynamische URLs sind ebenfalls häufig normal; riskant werden sie, wenn Nutzerinput Zielautorität ohne Hostvalidierung bestimmt.

Das ist besonders wichtig bei Agent Skills. Dieselbe Zeichenfolge kann in drei Rollen vorkommen:

```text
Dokumentation:     beschreibt ein gefährliches Muster
Test/Eval:         enthält absichtlich eine Angriffsprobe
Produktivskill:    weist den Agenten tatsächlich zu diesem Verhalten an
```

Ein professionelles Review bewertet deshalb nicht nur den Match, sondern **Dateirole, Ausführbarkeit, deklarierte Capability, Datenfluss und Kontext**.

<Warning>
„Pattern gefunden“ bedeutet nicht automatisch „Skill ist bösartig“. Umgekehrt bedeutet „kein Pattern gefunden“ nicht, dass ein Skill sicher ist. Pattern Detection ist eine Evidence-Schicht innerhalb eines mehrstufigen Assurance-Prozesses.
</Warning>

## Sichere Gegenmaßnahmen

- Freie URL-Ziele vermeiden; benannte Destinations bevorzugen.
- Private, Loopback-, Link-Local- und Metadata-Netze standardmäßig blockieren.
- DNS-Rebinding und Redirects berücksichtigen.
- Cloud Metadata über Plattformmechanismen härten beziehungsweise Workload Identity verwenden.
- Network Egress unabhängig vom Skilltext erzwingen.

Eine gute Remediation entfernt nicht nur den konkreten String, der einen Scanner auslöst. Sie reduziert die zugrunde liegende Fähigkeit. Sonst kann dieselbe Sicherheitsverletzung mit anderer Syntax wieder erscheinen.

## Einordnung in DevSecOps und CI/CD

SSRF-Findings sollten mit Runtime Egress Policy verknüpft werden. Ein Scan zeigt verdächtige Absicht; NetworkPolicy, Proxy/Gateway und DNS-/IP-Validierung verhindern die tatsächliche Seitwärtsbewegung.

Ein belastbarer Workflow kann so aussehen:

```text
untrusted skill
      │
      ▼
bounded loader
      │
      ▼
static patterns + AST + taint + dependency/MCP analysis
      │
      ▼
coverage + findings + artifact identity
      │
      ▼
environment-specific policy
      │
      ├── allow
      ├── require review
      └── block
```

Der zentrale Punkt ist die Trennung zwischen **Detection** und **Decision**. Ein Scanner liefert Evidenz. Eine Policy entscheidet, welche Evidenz in Development, Sandbox, CI oder Produktion akzeptabel ist.

## Review-Fragen

Bei einem Finding aus dieser Pattern-Familie sollte ein Reviewer mindestens prüfen:

- Entspricht das beobachtete Verhalten dem dokumentierten Zweck des Skills?
- Ist die betroffene Capability überhaupt erforderlich?
- Kann dieselbe Funktion mit engeren Pfaden, Tools, Domains, Commands oder Rechten umgesetzt werden?
- Ist der Treffer tatsächlicher ausführbarer beziehungsweise handlungsleitender Inhalt oder nur Dokumentation/Testmaterial?
- Welche Daten können die betroffene Boundary passieren?
- Wird die Sicherheitsgrenze technisch durch den Host erzwungen oder nur textuell im Prompt beschrieben?
- Ist das analysierte Artefakt eindeutig per Version beziehungsweise Digest identifizierbar?
- Muss das Finding blockieren, einen Human Review auslösen oder als dokumentierte Ausnahme behandelt werden?

## Warum das für Agentic DevSecOps relevant ist

Klassisches DevSecOps betrachtet Source Code, Dependencies, Images, IaC und Runtime-Konfiguration. Agentic DevSecOps erweitert diese Oberfläche um **Instruktionslogik und delegierte Autorität**.

Ein Skill kann formal nur Markdown sein und trotzdem operative Wirkung besitzen. Er beeinflusst, welche Tools ein Agent wählt, welche Informationen er als relevant betrachtet, welche Side Effects er auslöst und welche Grenzen er respektiert. Deshalb müssen natürliche Sprache und Toolmetadaten mit denselben Prinzipien behandelt werden, die wir bei Code bereits kennen:

- Least Privilege
- Untrusted Input
- Explicit Trust Boundaries
- Reproducible Artifacts
- Policy as Code
- Auditability
- Defense in Depth

## Fazit

SSRF-Findings sollten mit Runtime Egress Policy verknüpft werden. Ein Scan zeigt verdächtige Absicht; NetworkPolicy, Proxy/Gateway und DNS-/IP-Validierung verhindern die tatsächliche Seitwärtsbewegung.

Die Pattern-Familie `SSRF1`, `SSRF2`, `SSRF3` ist vor allem dann wertvoll, wenn sie nicht isoliert betrachtet wird. Ihr Nutzen entsteht durch die Kombination aus präzisem Finding, nachvollziehbarer Coverage, Kontextreview und einer Runtime, die unerlaubte Aktionen auch dann verhindert, wenn die statische Analyse etwas übersieht.

<KeyTakeaway>
Die entscheidende Frage ist nicht „Hat der Skill einen Treffer?“, sondern: **Welche Trust Boundary würde dieses Verhalten überschreiten, und welche unabhängige Kontrolle verhindert den unerlaubten Effekt?**
</KeyTakeaway>
