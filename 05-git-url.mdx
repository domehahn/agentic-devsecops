Ein Git-URL-Scan ist ideal für Reviews, Security-Bots und CI: Statt ein Repository manuell auszuchecken, bekommt der Scanner eine URL und analysiert den aktuellen Inhalt. Gleichzeitig verschiebt sich die Trust Boundary. Der Scanner verarbeitet nun nicht nur unvertrauenswürdige Dateien, sondern führt auch **Netzwerkzugriff und Git-Operationen** aus.

Damit wird Remote-Scanning zu einem Infrastrukturthema.

<Warning>
Eine Git-URL ist nicht nur ein Pfad. Sie ist eine Anweisung an den Scanner, Netzwerk und Git als zusätzliche Angriffsfläche zu aktivieren.
</Warning>

## Was das Feature wirklich bedeutet

Sicheres Git-Scanning sollte mindestens vier Risiken adressieren: SSRF auf interne Ziele, Credential Leakage, unkontrollierte Git-Protokolle und rekursive Inhalte wie Submodule. Zusätzlich sollten Clone-Tiefe, Timeout und Datenmenge begrenzt sein.

Aus Security-Sicht ist die wichtigste Designfrage: Darf eine bloße Eingabe-URL automatisch Netzwerkverkehr auslösen?

## SkillSpector

SkillSpector erkennt Git-URLs und führt einen flachen Clone aus. Der Input Handler besitzt eine Allowlist für verbreitete Git-Hosts sowie Schutz vor privaten/reservierten Zieladressen. `git clone` wird ohne Shell und mit Timeout aufgerufen.

Der Remote-Zugriff ist Teil des normalen Komfortmodells: Eine passende Git-URL kann direkt an `skillspector scan` übergeben werden.

## `skil`

`skil` verlangt für Remote-Quellen ausdrücklich `--allow-remote`. Ohne diese Freigabe bleibt ein Scan offline. Bei Git werden unter anderem flache Clones, deaktivierte Submodule, deaktivierte lokale/ext-Protokolle, keine interaktive Credential-Abfrage, keine Redirects und Größenlimits verwendet.

Das Ergebnis ist funktional ähnlich, aber das Trust-Modell ist restriktiver: Netzwerkzugriff ist eine bewusste Capability des Aufrufs.

## Praxisbeispiel

```bash
# SkillSpector
skillspector scan https://github.com/acme/deploy-skill

# skil: Netzwerkzugriff explizit erlauben
skil scan https://github.com/acme/deploy-skill.git --allow-remote
```

In einer gehärteten CI-Umgebung ist diese Differenz relevant. Ein Job, der normalerweise nur lokale Artefakte prüft, kann bei `skil` nicht versehentlich durch eine geänderte Eingabe in einen Remote-Client verwandelt werden.

## Security- und DevSecOps-Einordnung

- Remote-Scanning als separate Capability behandeln und in CI bewusst freigeben.
- Git-Credentials nicht aus Benutzerkonfiguration oder interaktiven Helpers übernehmen.
- Submodule und alternative Git-Protokolle standardmäßig deaktivieren.
- DNS/IP-Ziele gegen interne, Loopback-, Link-Local- und Metadata-Netze absichern.
- Clone-Größe und Laufzeit begrenzen.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

| Aspekt | SkillSpector | `skil` |

| Feature vorhanden | ja | ja |
| Schwerpunkt | Integration und Scanner-Ergonomie | explizite Trust Boundaries und Evidence |
| Bewertung | gleich, skil restriktiver | gleich, skil restriktiver |

**Bewertung aus der Vergleichsmatrix:** gleich, skil restriktiver.

## Typische Fehlinterpretation

„Git-URL-Scanning ist nur Checkout plus Directory Scan.“ Der Clone aktiviert Netzwerk, Git-Konfiguration, DNS-Auflösung und gegebenenfalls Credential-Mechanismen – also eine deutlich größere Trust Boundary.

## Einordnung in die Pipeline

Dieses Feature gehört in die **Ingestion-Stufe** der Pipeline. Bevor Analyzer oder Policies überhaupt laufen, muss klar sein, welches Artefakt gelesen wird, wie es kanonisiert wird und welche zusätzlichen Fähigkeiten – insbesondere Netzwerk – dafür notwendig sind.

Ein belastbares Muster ist: Input auflösen → Digest/Manifest erzeugen → statisch analysieren → Report/Evidence speichern. Bei Remote-Eingaben sollte der Netzwerkzugriff in einem eigenen Job oder Runner-Profil aktiviert werden.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Beide können Git-Repositories direkt scannen. SkillSpector optimiert stärker auf Ergonomie, `skil` auf explizite Autorisierung des Netzwerkzugriffs. Welche Variante besser passt, hängt davon ab, ob Remote-Scanning der Normalfall oder eine privilegierte Ausnahme sein soll.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
