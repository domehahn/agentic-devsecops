Environment variables are convenient because they make configuration available to a process without hard-coding values. That same convenience can turn an agent runtime into a high-value credential reservoir.

A skill that reads one declared configuration variable is normal. A skill that enumerates the entire environment looking for names containing `TOKEN`, `SECRET`, `PASSWORD`, or similar markers is performing a very different operation: **credential discovery and collection**.

The property relation is:

```text
READ(SECRET_SOURCE)
AND (BULK_ENUMERATION | EXTERNAL_SINK | UNJUSTIFIED_SCOPE)
```

This formulation deliberately avoids classifying every environment read as suspicious.

## The environment is a shared process capability

In many application stacks, the process environment contains more than ordinary configuration. Depending on the deployment, it may hold:

- API credentials,
- cloud access tokens,
- database passwords,
- signing keys or key references,
- CI/CD tokens,
- package-registry credentials,
- webhook secrets.

An agent that can execute arbitrary code inside that process may therefore inherit visibility into secrets unrelated to the task.

This is a classic least-privilege problem with an agentic twist: untrusted natural-language instructions may influence code or tools that can inspect the environment.

## Harvesting versus legitimate configuration access

Compare:

```python
endpoint = os.environ.get("SERVICE_URL")
if endpoint is None:
    raise RuntimeError("SERVICE_URL is required")
```

with the abstract harvesting pattern:

```python
for key, value in os.environ.items():
    if looks_like_credential_name(key):
        collected[key] = value
```

The first reads one named, non-secret configuration value for a declared purpose. The second searches broadly for credential-like material.

The scanner therefore needs more than a source list. It needs to model **breadth and purpose**.

## Three escalation stages

Secret harvesting becomes progressively more serious across three stages.

### Stage 1: sensitive read

The artifact reads a credential-bearing value.

### Stage 2: collection

Multiple secrets are enumerated, aggregated, or serialized.

### Stage 3: disclosure or use

The collected material reaches an external sink, a log, a file, or an unauthorized tool.

Keeping these stages distinct improves triage. A legitimate service may need Stage 1. Stage 2 is rarer and requires stronger justification. Stage 3 often represents a direct confidentiality breach.

## How `skil` composes secret detection and taint

The current control matrix maps contextual secret access to `SKIL-SEC-001`, while the taint engine can compose secret sources with network sinks through `SKIL-TAINT-NETWORK`.[^skil-matrix][^skil-crosswalk]

A finding can therefore evolve from:

```text
secret source observed
```

into:

```text
secret source → collected object → external network sink
```

without forcing a single rule to encode the entire attack chain.

## Source classification should be conservative and explainable

Environment-variable names are heuristic. `TOKEN_COUNT` is not necessarily a credential; `PASSWORD_POLICY_URL` may not contain a password. Conversely, a secret may have an innocuous name.

A robust scanner can combine:

- exact known secret names,
- suffix/prefix patterns,
- manifest declarations,
- use context,
- downstream sink behavior.

Confidence should increase when multiple signals align.

## The best defense is not giving the process the secret

Static detection is valuable, but the strongest runtime control is reducing ambient authority.

Instead of injecting dozens of credentials into a long-lived agent process, production systems can use:

- workload identity,
- short-lived scoped tokens,
- secret brokers,
- per-tool credential isolation,
- sidecars or proxies that attach credentials only to approved requests,
- separate service accounts per capability.

This changes the threat model. If the agent cannot read a raw secret, prompt injection cannot trivially harvest it.

## Secret brokers versus direct environment access

A secret broker can expose an operation such as:

```text
call approved API as service X
```

without returning the underlying credential to the model or agent process. This follows capability-security principles: grant the operation, not the transferable bearer secret.

OAuth security best practice makes a related point by emphasizing least privilege, audience restriction, and sender-constrained tokens to reduce the impact of leakage.[^oauth-bcp]

For MCP over HTTP, the authorization specification similarly requires resource indicators and audience validation, and explicitly forbids token passthrough between resource boundaries.[^mcp-auth]

## Logs are an overlooked sink

A collected secret does not need to leave through HTTP to create a breach. It may be printed into:

- CI logs,
- agent traces,
- error messages,
- analytics events,
- model transcripts.

A mature taint engine should therefore distinguish multiple sink classes, including log output. Runtime logging should redact secrets before serialization, not rely on the model to avoid printing them.

## Evidence design

A useful finding might contain:

```yaml
property: env-secret-harvesting
controls:
  - SKIL-SEC-001
observed_sources:
  - kind: environment_enumeration
    credential_name_pattern: true
collection:
  breadth: multiple_values
  aggregate_symbol: collected
sinks:
  network: none_observed
  log: none_observed
scope_justification: not_found
```

This distinguishes harvesting from completed exfiltration.

## False positives

Legitimate cases may include:

- secret-management tooling specifically designed to inventory credentials,
- test harnesses using fake secrets,
- migration tools with explicit operator authorization,
- environment-debug utilities in isolated development environments.

The scanner should still report sensitive behavior where appropriate, but context can reduce severity or mark a reviewed exception. “False positive” should not become shorthand for “the behavior is dangerous but intentional.”

## Contract verification

Agentic skills benefit from explicit capability contracts:

```yaml
capabilities:
  environment:
    read:
      - SERVICE_URL
      - BUILD_ID
```

A scan can compare observed reads with declared scope. This turns least privilege into a machine-checkable property.

For secrets, a stricter contract can prohibit raw reads entirely and require access through a dedicated tool.

## Runtime detection

Useful telemetry includes:

- number of environment keys read,
- attempts to enumerate the full environment,
- secret-broker requests,
- secret-to-network or secret-to-log flows,
- policy denials,
- destination identities.

A sudden broad environment enumeration by a documentation or code-review skill is a strong anomaly even if static analysis missed the relevant code path.

## Relationship to OWASP and CWE

OWASP Sensitive Information Disclosure covers the broader risk of exposing confidential data.[^owasp-disclosure] CWE-200 provides a traditional software-security framing for unauthorized information exposure.[^cwe200] The `skil` property narrows this to a pre-exfiltration behavior: credential-source discovery and collection.

## Limits

Secrets can appear in nonstandard locations, be fetched dynamically, or be represented as opaque handles. Static scanners also cannot always determine whether a particular variable is sensitive.

Coverage should therefore be described in terms of known source forms and observed compositions rather than claiming universal secret discovery.

<KeyTakeaway>
Environment Secret Harvesting is best understood as **unjustified expansion of data visibility**. The ideal defense is to eliminate ambient secret access; the scanner then becomes a verification layer rather than the last line of protection.
</KeyTakeaway>

## Conclusion

Environment Secret Harvesting is not defined by a single API call. It is the combination of secret-source access, breadth of collection, unjustified scope, and—at higher severity—movement into logs or external sinks. The most robust architecture reduces ambient secrets, scopes identities, and uses brokers or short-lived tokens so that a manipulated agent cannot simply enumerate credentials that it never needed to possess.
