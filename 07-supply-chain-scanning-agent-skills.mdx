An agent skill can have a perfectly clean prompt and still be dangerous because of what it installs.

Dependencies are executable trust.

## The dependency surface is broader than Python

A scanner for agentic artifacts should expect mixed ecosystems:

```text
requirements.txt
pyproject.toml
poetry.lock
uv.lock
package.json
package-lock.json
go.mod
Cargo.toml
Cargo.lock
Gemfile.lock
pom.xml
```

The first task is deterministic inventory.

Do not install packages to learn what the artifact depends on.

Parse manifests and lockfiles as data.

## Pinning is reproducibility security

Consider:

```text
requests
```

versus:

```text
requests==2.32.4
```

The first delegates version selection to the future environment.

That makes later installation potentially resolve a different artifact than the one reviewed.

The same principle applies to:

```text
Git branches
mutable tags
container :latest tags
remote URLs without immutable digest
```

<KeyTakeaway>
If the artifact you reviewed cannot be reproduced, your security evidence is attached to an idea rather than to software.
</KeyTakeaway>

## Known vulnerabilities are one signal

A vulnerability service can answer:

```text
package + version
      ↓
known advisory?
```

That is useful, but it should remain explicit coverage.

Network lookup may be:

```text
completed
offline cache
degraded
not requested
failed
```

A scanner should not silently treat an unavailable vulnerability feed as "no known vulnerabilities."

## Typosquatting is a different problem

Packages such as:

```text
popular-library
popular-librarry
```

may have no known vulnerability.

The risk is identity confusion.

Useful heuristics can compare package names against trusted ecosystem names using:

- edit distance
- normalization
- common prefix/suffix tricks
- character substitution
- namespace similarity

This is heuristic by nature, so confidence and evidence matter.

## Abandoned packages require provenance

"Abandoned" is not a property that a scanner should invent from vibes.

A defensible implementation needs reviewed evidence such as:

```yaml
package: example
ecosystem: PyPI
status: abandoned
source: reviewed-dataset
observed_at: 2026-07-01
```

Offline reputation can be valuable when the provenance is versioned and auditable.

## Direct URLs deserve scrutiny

A dependency may point directly to:

```text
Git URL
archive URL
private registry
mutable branch
```

Questions include:

```text
Is the source pinned?
Is the transport trusted?
Is the commit immutable?
Is the host allowlisted?
Is the expected digest known?
```

These are supply-chain properties even if the package contains no known CVE.

## Generate an SBOM from the same inventory

Once dependencies are normalized, generating an SBOM is a natural next step.

The key is identity binding:

```text
artifact digest
      │
      ├── dependency inventory
      └── SBOM
```

The SBOM should describe the artifact that was actually scanned.

Not a later rebuild.

## Provenance closes another gap

Dependency scanning asks:

```text
What is inside?
```

Provenance asks:

```text
Where did this package come from?
Who built it?
From which source revision?
```

A mature install gate can require:

```text
artifact digest
package signature
attestation
provenance
policy approval
```

before making the skill available to an agent.

## Supply chain is part of agent security

Agentic systems often pull executable capability from:

```text
packages
containers
MCP servers
remote scripts
plugins
tools
```

That means the supply chain is not adjacent to prompt security.

It is one of the ways prompt-level intent becomes real-world action.

The scanner should therefore treat dependencies and external execution sources as first-class parts of the same behavioral artifact.
