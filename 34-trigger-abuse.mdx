Agentic Skills sind keine gewöhnlichen Textdateien.

Sie können Instruktionen, Code, Tool-Metadaten, Abhängigkeiten und operative Capabilities zu einem Artefakt verbinden, das das Verhalten eines Agenten unmittelbar beeinflusst.

Die Security Property **Trigger Abuse** verhindert Triggerdefinitionen, die zu breit, zu häufig, extern manipulierbar oder für privilegierte Aktionen ungeeignet sind.

Diese Eigenschaft schützt langlebigen Zustand und Aktivierungslogik. Agentic Skills wirken oft über einen einzelnen Turn hinaus: Sie können Memory schreiben, Konfigurationen ändern, Trigger definieren oder später erneut aktiviert werden.

## Was schützt diese Security Property?

Die zentrale Frage lautet nicht nur, ob ein verdächtiges Schlüsselwort vorkommt.

Entscheidend ist, ob der Agentic Skill eine Sicherheitsgrenze verändert, umgeht oder einen Daten- beziehungsweise Kontrollfluss erzeugt, der außerhalb seines legitimen Zwecks liegt.

Für **Trigger Abuse** sollte ein Review deshalb drei Ebenen unterscheiden:

```text
Deklaration
    ↓
beabsichtigtes Verhalten
    ↓
effektive Runtime-Wirkung
```

Eine saubere Deklaration ist hilfreich, aber nicht ausreichend. Ebenso reicht ein einzelner statischer Treffer nicht automatisch als Beweis für bösartiges Verhalten. Gute Security-Evidenz verbindet Fundstelle, Kontext und mögliche Wirkung.

## Warum ist das bei Agentic Skills relevant?

Ein Agentic Skill kann vom Agenten als vertrauenswürdige Arbeitsanweisung interpretiert werden. Gleichzeitig kann er Zugriff auf Tools, Dateien, Netzwerkziele oder Persistenzmechanismen erhalten.

Dadurch kann eine kleine semantische Änderung reale Seiteneffekte haben.

Das typische Risikomodell sieht so aus:

```text
untrusted oder überbreite Anweisung
              ↓
      agentische Entscheidung
              ↓
      Tool / Code / Runtime
              ↓
         reale Wirkung
```

Security Properties sind deshalb am nützlichsten, wenn sie nicht nur Text klassifizieren, sondern eine konkrete Sicherheitsannahme formulieren, die überprüfbar ist.

## Negatives Beispiel

```yaml
on:
  issue_comment:
    types: [created]
# Jeder beliebige Kommentar kann anschließend einen produktiven Deployment-Pfad aktivieren.
```

Das Problem liegt nicht allein in der Syntax. Der entscheidende Punkt ist, dass die Konstruktion eine Schutzannahme verletzt oder eine unnötige Autorität erzeugt.

Ein belastbarer Scanner sollte den Befund deshalb nicht bloß als „verdächtigen Text“ melden, sondern die verletzte Property benennen und die relevante Evidenz zeigen.

## Positives Beispiel

```yaml
on:
  workflow_dispatch: {}
# Der privilegierte Pfad prüft zusätzlich Actor, Environment und Approval.
```

Das positive Muster reduziert die Angriffsfläche, macht den beabsichtigten Scope nachvollziehbar und verschiebt kritische Entscheidungen möglichst in deterministische oder policy-kontrollierte Komponenten.

<KeyTakeaway>
Die Security Property Trigger Abuse ist dann wertvoll, wenn sie eine überprüfbare Grenze beschreibt: Was darf der Agentic Skill tun, welche Daten oder Autorität darf er verwenden und welche Wirkung muss verhindert werden?
</KeyTakeaway>

## Worauf sollte eine statische Analyse achten?

Typische Indikatoren sind:

- untrusted Events starten privilegierte Aktionen
- Wildcard-Schedules/Events
- fehlende Actor-/Branch-/Environment-Checks

Diese Signale sollten möglichst strukturell ausgewertet werden.

Je nach Property bedeutet das beispielsweise AST-Analyse, Datenfluss, Schema-Traversierung, URL-Klassifikation, Capability-Verifikation oder semantische Bewertung deklarierter Instruktionen.

Eine robuste Implementierung speichert dabei mindestens:

```text
rule/property id
severity
file + location
evidence
source/sink oder capability context
confidence
recommended remediation
```

So wird aus einem Alarm eine reproduzierbare Security-Evidenz.

## Technische Controls

Geeignete Gegenmaßnahmen sind unter anderem:

- Trigger-Authentizität prüfen
- privilegierte Pfade separat schützen
- Rate Limits
- Actor-/Scope-Filter

Wichtig ist Defense in Depth.

Ein Agentic Skill sollte niemals allein deshalb als sicher gelten, weil ein Scanner keinen Treffer gefunden hat. Statische Analyse reduziert Unsicherheit vor der Ausführung; Runtime-Enforcement begrenzt die Folgen, falls die Analyse etwas übersieht.

## Grenzen der Erkennung

Breite Trigger sind für Triage- oder Analyseaufgaben sinnvoll. Risiko entsteht aus der Kombination von Trigger und nachfolgender Autorität.

Gerade bei agentischen Systemen muss die Analyse zwischen **möglicher** und **effektiver** Authority unterscheiden.

Eine Instruktion kann gefährlich aussehen, aber durch die Runtime technisch unmöglich sein. Umgekehrt kann eine harmlos formulierte Beschreibung sehr weitreichende Tools erhalten.

Deshalb sollte der ideale Prüfpfad mehrere Evidenztypen kombinieren:

```text
Text / Instruktion
       +
Code / AST / Datenfluss
       +
Tool- und MCP-Metadaten
       +
Capability Contract
       +
Runtime Policy
       =
begründete Sicherheitsentscheidung
```

## Einordnung in DevSecOps

Ein Security Gate sollte Schreibziele, Persistenzmechanismen, Triggerbedingungen und Zustandsänderungen inventarisieren. Besonders kritisch sind Änderungen, die zukünftige Entscheidungen beeinflussen, ohne im ursprünglichen Review sichtbar zu bleiben.

Praktisch eignet sich die Property für mehrere Gates:

1. **Authoring:** lokale Prüfung während der Erstellung.
2. **Merge Request / Pull Request:** reproduzierbarer Scan mit diff-basierter Evidenz.
3. **Registry oder Katalog:** erneute Prüfung des veröffentlichten Artefakts.
4. **Installation:** Policy-Entscheidung gegen exakt den Digest, der installiert wird.
5. **Runtime:** technische Durchsetzung von Netzwerk-, Datei-, Tool-, Secret- und Ressourcenlimits.

Das verhindert eine häufige Schwäche klassischer Security-Reviews: Die Analyse bewertet ein Artefakt, während später eine andere Version oder eine breitere Runtime-Konfiguration ausgeführt wird.

## Was ein Finding aussagekräftig macht

Ein gutes Finding zu **Trigger Abuse** sollte eine konkrete Frage beantworten:

> Welche Sicherheitsannahme wird verletzt, wodurch ist das belegt und welche reale Wirkung wäre dadurch möglich?

Weniger hilfreich ist ein generischer Alarm ohne Kontext.

Besser ist eine Evidence Chain:

```text
Fundstelle
   ↓
semantische oder strukturelle Interpretation
   ↓
betroffene Capability / Datenklasse
   ↓
mögliche Wirkung
   ↓
konkrete Remediation
```

Damit wird die Security Property auch für Entwickler verständlich, die nicht täglich mit Agentic Security arbeiten.

## Fazit

**Trigger Abuse** ist keine isolierte Checklistenregel, sondern eine konkrete Sicherheitsgrenze für Agentic Skills.

Die stärkste Umsetzung kombiniert präzise statische Evidenz mit Capability-Verifikation und technischen Runtime-Grenzen.

So beantwortet die Analyse nicht nur die Frage, ob ein Artefakt verdächtig aussieht, sondern ob sein tatsächliches Verhalten innerhalb des vorgesehenen Trust-Modells bleibt.
