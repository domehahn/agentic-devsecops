Container sind ein ideales Auslieferungsmodell für Security Scanner: Runtime, Dependencies und Versionen werden reproduzierbar paketiert, während CI-Runners den Scanner ohne lokale Installation starten können.

Ein Container ist jedoch keine automatische Sandbox. Mounts, Netzwerk, Secrets und Linux Capabilities bestimmen weiterhin, wie groß die tatsächliche Host-Oberfläche ist.

<Warning>
Ein Scanner-Container mit `/var/run/docker.sock`, Host-Root-Mount oder unnötigem Netzwerkzugriff ist keine starke Isolation – unabhängig davon, wie sicher das Image selbst gebaut ist.
</Warning>

## Was das Feature wirklich bedeutet

Für Skill-Scanning sollte das Image möglichst non-root laufen, nur das zu prüfende Verzeichnis read-only mounten und Netzwerk standardmäßig deaktivieren, wenn keine externen Provider benötigt werden. Reports können über einen separaten beschreibbaren Output-Mount geschrieben werden.

Je weniger Runtime-Dependencies im Image liegen, desto kleiner werden Patch- und Supply-Chain-Fläche.

## SkillSpector

SkillSpector enthält einen Dockerfile und dokumentiert den Build über `make docker-build` beziehungsweise `docker build`. Das Image basiert auf Python 3.12 slim. Lokale Verzeichnisse werden in `/scan` gemountet; LLM-Credentials können bei Bedarf über Environment oder Env-File übergeben werden.

Damit lässt sich der Scanner ohne lokale Python-Installation einsetzen.

## `skil`

`skil` bietet einen non-root Multi-Stage-Container-Build. `make docker-build` erzeugt das Image, `make docker-smoke` prüft den CLI-Entrypoint. Der native Go-Ansatz und die eingebaute Malware-Schicht reduzieren den Bedarf an zusätzlichen Runtime-Komponenten im Standardpfad.

Externe YARA- oder Providerfunktionen können weiterhin zusätzliche Anforderungen erzeugen.

## Praxisbeispiel

```bash
# SkillSpector – statischer Scan, Verzeichnis read-only
docker run --rm --network none   -v "$PWD:/scan:ro"   skillspector scan ./my-skill --no-llm

# skil – analoges Muster
docker run --rm --network none   -v "$PWD:/scan:ro"   skil scan /scan/my-skill --static-only
```

Für Reports kann ein zweites Verzeichnis schreibbar gemountet werden, statt den gesamten Source Tree zu beschreiben.

## Security- und DevSecOps-Einordnung

- Image mit Digest pinnen statt nur `latest` verwenden.
- Scanner-Source read-only mounten.
- `--network none` für rein statische Jobs nutzen.
- Keine Docker Socket- oder Host-Root-Mounts an den Scanner geben.
- SBOM, Signatur und Scanner-Version für das Image selbst prüfen.
- Non-root und minimale Capabilities bevorzugen.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

## Typische Fehlinterpretation

„Im Container ist der Scanner automatisch isoliert.“ Ein privilegierter Container mit Host-Mounts und Netzwerk kann mehr Zugriff besitzen als ein normaler lokaler Prozess.

## Einordnung in die Pipeline

Dieses Feature betrifft die **Integration und Laufzeit des Scanners selbst**. Damit wird nicht nur der Skill analysiert, sondern auch festgelegt, über welche Tool-, Prozess- oder Containergrenze Security-Funktionen erreichbar sind.

Für produktive Nutzung sollten Identität, Dateisystemzugriff, Netzwerk, Secrets und Auditlogs der Scanner-Runtime genauso behandelt werden wie bei jedem anderen sicherheitskritischen Service.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Beide lassen sich als Docker-Image betreiben. SkillSpector liefert eine Python-basierte Containerlaufzeit; `skil` setzt auf einen non-root Multi-Stage-Build. In beiden Fällen entscheidet die Runtime-Konfiguration darüber, ob der Container tatsächlich eine sinnvolle zusätzliche Boundary bildet.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
