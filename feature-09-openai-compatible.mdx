Ein OpenAI-kompatibles API-Schema ist zu einem verbreiteten Integrationsmuster für gehostete und lokale Modellendpunkte geworden. Für Scanner bedeutet das: eine gemeinsame Client-Schnittstelle kann unterschiedliche Backends ansprechen.

Das Feature ist damit nicht nur eine Komfortfunktion.

Es verändert, **welcher Kontext geprüft wird, welche Vertrauensgrenzen gelten und wie belastbar das Ergebnis später in CI/CD oder Security-Governance verwendet werden kann**.

## Was das Feature leistet

Das Feature abstrahiert typischerweise Basis-URL, Modellname, API-Key, Timeout und optionale Request-Parameter. Dadurch kann dieselbe semantische Analyse gegen verschiedene kompatible Services laufen, ohne die fachliche Scanlogik zu ändern.

Kompatibilität auf HTTP-Ebene bedeutet jedoch nicht identisches Verhalten. Modelle unterscheiden sich bei Kontextfenster, Tool-Unterstützung, JSON-Modus, Rate Limits und Sicherheitsfiltern. Diese Eigenschaften gehören in die Provider-Konfiguration.

## Typischer Ablauf

Unabhängig von der konkreten Implementierung sollte der Ablauf klar getrennte Phasen besitzen:

```text
Input
  ↓
Validierung und Normalisierung
  ↓
Feature-spezifische Verarbeitung
  ↓
Security-Analyse
  ↓
Findings + Coverage + technischer Status
  ↓
Policy-Entscheidung
```

Diese Trennung ist wichtig, weil ein technischer Fehler bei Beschaffung, Parsing oder Providerzugriff nicht dieselbe Bedeutung hat wie ein tatsächlich unauffälliges Prüfergebnis.

## Negatives Beispiel

Ein Team ändert nur die Base URL und geht davon aus, dass sich jedes kompatible Backend identisch verhält:

```yaml
provider:
  base_url: https://llm.example.invalid/v1
  model: default
```

Der neue Endpoint ignoriert einen erwarteten strukturierten Output-Modus. Der Parser fällt auf Freitext zurück, wodurch Findings uneinheitlich werden. Technische API-Kompatibilität wurde mit semantischer Gleichwertigkeit verwechselt.

## Positives Beispiel

Die Integration beschreibt explizite Fähigkeiten:

```yaml
provider:
  base_url: https://llm.example.invalid/v1
  model: security-model
  timeout_seconds: 30
  structured_output: true
  max_context_tokens: 32000
```

Beim Start wird die Konfiguration validiert. Der Report dokumentiert Provider-Typ, Modellkennung und Analyseprofil, sodass Ergebnisse später eingeordnet werden können.

<KeyTakeaway>
API-Kompatibilität standardisiert den Transport, nicht das Vertrauen. Host-Policy, Modellfähigkeiten und Ergebnisformat müssen trotzdem explizit verifiziert werden.
</KeyTakeaway>

## Security- und Betriebsaspekte

Eine frei konfigurierbare Base URL ist sicherheitsrelevant. Secrets dürfen nur an erlaubte Hosts gesendet werden; Redirects sollten keinen Credential-Wechsel ermöglichen. TLS-Verifikation, Proxy-Verhalten und private Netzwerkziele benötigen klare Policies.

Darüber hinaus sollte der Scanner keine provider-spezifischen Debug-Responses mit sensiblen Prompt-Inhalten ungefiltert protokollieren.

Ein professioneller Betrieb sollte außerdem drei Zustände konsequent auseinanderhalten:

```text
clean      = geprüft, kein relevanter Befund
finding    = geprüft, mindestens ein relevanter Befund
incomplete = Prüfung technisch oder fachlich nicht vollständig
```

Gerade der dritte Zustand ist für DevSecOps entscheidend.

Ein Scanner darf fehlende Coverage nicht als positives Sicherheitsurteil darstellen.

## Wo das Feature sinnvoll eingesetzt wird

Das Feature ist sinnvoll für Unternehmen mit API-Gateways, Self-Hosted-Backends oder mehreren kompatiblen Modellservices. Es reduziert Integrationsaufwand und erleichtert Providerwechsel.

Für native APIs mit spezifischen Funktionen kann ein dedizierter Adapter mehr Kontrolle und bessere Fehlerdiagnose bieten.

Die konkrete Aktivierung sollte deshalb aus dem gewünschten Trust-Modell abgeleitet werden und nicht allein aus technischer Verfügbarkeit.

## Integration in eine DevSecOps-Pipeline

In einer Pipeline sollte das Feature nicht isoliert betrachtet werden.

Ein belastbares Muster ist:

```text
Source / Artifact
      ↓
Input-Validierung
      ↓
Deterministische Analyse
      ↓
optionale erweiterte Analyse
      ↓
normalisierte Findings
      ↓
Policy Gate
      ↓
Report / Audit Evidence
```

Dabei sollte jeder Report mindestens folgende Informationen transportieren:

- Identität des analysierten Artefakts
- aktive Analyseverfahren
- übersprungene oder nicht verfügbare Prüfschritte
- stabile Regel- oder Finding-IDs
- Schweregrad und Evidenz
- Scanner- und Regelversion
- eindeutiger technischer Abschlussstatus

Damit wird das Feature nicht nur ausführbar, sondern **auditierbar**.

## Fazit

API-Kompatibilität standardisiert den Transport, nicht das Vertrauen. Host-Policy, Modellfähigkeiten und Ergebnisformat müssen trotzdem explizit verifiziert werden.

Der eigentliche Wert entsteht dann, wenn das Feature mit klaren Grenzen, reproduzierbaren Eingaben und transparenten Ergebnissen in den Entwicklungsprozess eingebettet wird.
