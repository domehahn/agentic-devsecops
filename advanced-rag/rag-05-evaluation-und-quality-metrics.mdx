A RAG system can produce convincing answers while still functioning poorly.

That sounds contradictory, but it is a central evaluation problem. A strong LLM can compensate for missing evidence from parametric knowledge. A weak retriever can succeed by chance on easy questions. An answer evaluator may rate a fluent hallucination more highly than a cautious, well-supported response.

The final part of **“Advanced RAG & Knowledge Systems”** therefore treats evaluation as a **decomposed systems problem**. RAGAS is an important tool in that process, but it is not the evaluation itself.

---

## 1. The Most Important Rule: Measure Retrieval and Generation Separately

A RAG answer emerges from at least two systems:

```text
Query
  ↓
Retriever
  ↓
Retrieved Context
  ↓
Generator
  ↓
Answer
```

That creates different failure modes.

### Retrieval Failure

The relevant evidence was not found.

### Ranking Failure

It was found, but ranked too low.

### Context Construction Failure

It was found, but removed during packing or displaced by incorrect versions.

### Generation Failure

The evidence was present, but the LLM interpreted it incorrectly or invented additional claims.

If only the final answer is evaluated, these root causes remain hidden.

---

## 2. The Golden Set

A defensible offline evaluation requires representative test cases.

A test case might contain:

```yaml
id: rag-042
question: "Which timeout rule applies to asynchronous uploads?"
reference_answer: "90 seconds"
reference_documents:
  - api-gateway-v3.md#async-upload-timeout
tags:
  - exact-fact
  - configuration
  - version-sensitive
```

A good golden set contains more than easy FAQ questions. It should include:

- exact lookups,
- paraphrases,
- multi-hop questions,
- contradictory documents,
- outdated versions,
- unanswerable questions,
- ACL-relevant queries,
- tables / code,
- long-context dependencies,
- adversarial queries.

The test distribution should reflect real usage.

## 3. Retrieval Metrics: Did the System Find the Evidence?

Classic information-retrieval metrics remain highly relevant.

### Recall@k

```text
Recall@k =
relevant hits in Top-k
----------------------
all relevant reference hits
```

If two documents are required to answer a question and only one appears in the Top-10, recall is incomplete.

### Precision@k

```text
Precision@k =
relevant hits in Top-k
----------------------
k
```

High recall with very low precision can flood the LLM with noise.

### MRR

Mean Reciprocal Rank rewards systems that place the first relevant result near the top.

```text
RR = 1 / rank_first_relevant
```

### nDCG

Normalized Discounted Cumulative Gain accounts for multiple relevance levels and rank positions.

For RAG, this is useful when chunks are not merely “relevant/irrelevant” but vary in how informative they are.

## 4. RAGAS: More Than a “Triad”

The original RAGAS work introduced a framework for largely reference-free evaluation across several RAG dimensions.[^1]

Early descriptions often highlighted three metrics:

- Faithfulness,
- Answer/Response Relevance,
- Context Recall.

The current RAGAS documentation includes substantially more metrics, however, including Context Precision, Context Recall, Noise Sensitivity, Response Relevancy, Faithfulness, and metrics for agent and tool-use scenarios.[^2]

RAGAS should therefore not be reduced to a fixed “triad.”

---

## 5. Faithfulness: Is the Answer Supported by the Context?

RAGAS defines Faithfulness as the consistency of answer claims with the retrieved context.[^3]

Simplified:

```text
Faithfulness =
supported claims
----------------
all answer claims
```

Example:

**Context**

> “Asynchronous uploads use a timeout of 90 seconds.”

**Answer**

> “Asynchronous uploads use a 90-second timeout and three automatic retries.”

The first claim is supported. The second may not be.

Faithfulness is therefore **not a truth metric**. If the context itself is wrong, an incorrect answer can still be perfectly faithful.

That distinction is crucial.

---

## 6. Context Recall: Is Relevant Evidence Missing?

The current RAGAS documentation describes Context Recall as a measure of how much information required for the reference answer appears in the retrieved context.[^4]

This is especially valuable because a low score points toward retriever or ranking problems.

But Context Recall requires a reference anchor:

- reference answer,
- reference contexts,
- document IDs.

Fully reference-free evaluation cannot create this information from nothing.

---

## 7. Response Relevance: A Correct Answer Can Still Be Poor

An answer can be faithful and still be useless.

User:

> “Which version is currently in production?”

Answer:

> “Versions are managed through the release process. The documentation also explains branching, deployment gates, and rollbacks ...”

Every sentence may be supported by the context, yet the question remains unanswered.

Response Relevance therefore measures a different dimension from Faithfulness.

---

## 8. LLM-as-a-Judge: Powerful, but Not Ground Truth

Many modern RAG metrics use an LLM as evaluator.

Advantages:

- semantic assessment,
- flexible criteria,
- less need for complete manual annotation,
- fast iteration.

Risks:

- judge bias,
- model dependence,
- prompt sensitivity,
- position bias,
- self-preference,
- variable scores,
- cost.

A good evaluation system therefore combines:

```text
Deterministic Metrics
+ LLM Judges
+ Human Review Samples
```

Not every question requires an LLM judge. Exact facts, JSON schemas, SQL results, or document IDs can often be verified deterministically.

---

## 9. “Correctness” Often Requires Several Layers

A production answer can have many requirements:

```text
1. correct documents retrieved?
2. correct version?
3. correct ACL?
4. answer supported by sources?
5. question answered completely?
6. citations point to matching passages?
7. response format correct?
8. no prohibited information?
```

A single score of 0.87 cannot adequately express these dimensions.

**Quality gates per dimension** are therefore more useful:

```yaml
gates:
  retrieval_recall_at_10: ">= 0.95"
  faithfulness: ">= 0.90"
  citation_correctness: ">= 0.95"
  acl_leakage_tests: "== 0"
  answer_format_pass_rate: ">= 0.99"
```

Concrete thresholds must be derived from business risk and baselines.

---

## 10. Regression Testing for RAG

RAG configuration changes continuously:

- embedding model,
- chunking,
- retriever,
- index parameters,
- reranker,
- prompt,
- generator model.

Every change can degrade another part of the system.

A CI workflow can therefore look like this:

```text
Pull Request
   ↓
Build Test Index
   ↓
Run Golden Queries
   ↓
Retrieval Metrics
   ↓
Generation Metrics
   ↓
Compare Baseline
   ↓
Quality Gate
```

Not every evaluation needs to run the most expensive model on every commit. A tiered pipeline can combine fast smoke tests with nightly full evaluations.

---

## 11. Online Evaluation: Production Differs from the Golden Set

Offline tests can only approximate the real query distribution.

Production monitoring should additionally include:

- No-Answer Rate,
- Retriever Confidence,
- Re-query Rate,
- User Corrections,
- Escalation Rate,
- Click/Citation Usage,
- Latency,
- Token Cost,
- Cache Hit Rate,
- Document Drift,
- Query Drift.

Most importantly, user feedback is not a perfect quality label. A thumbs-up can reflect good wording rather than factual correctness.

---

## 12. Canary Evaluation and A/B Tests

New retrievers or prompts can be tested against a subset of real queries.

```text
Traffic
├── 90 % Baseline
└── 10 % Candidate
        ↓
compare:
- task success
- latency
- cost
- retrieval quality
- safety
```

For sensitive systems, a new variant should first run in **shadow** mode—generating answers without exposing them to users.

---

## 13. Evaluation as an Architecture Artifact

A professional RAG platform versions:

```text
dataset_version
chunker_version
embedding_model
index_config
retrieval_config
reranker_model
prompt_version
generator_model
evaluator_version
```

Only then can you reproduce why a score changed.

A result such as

> Faithfulness = 0.91

is barely auditable without model, prompt, and dataset versions.

## 14. A Practical Evaluation Framework

```text
                ┌──────────────────────┐
                │  Curated Golden Set  │
                └──────────┬───────────┘
                           ↓
              ┌────────────────────────┐
              │ Retrieval Evaluation   │
              │ Recall / MRR / nDCG    │
              └──────────┬─────────────┘
                         ↓
              ┌────────────────────────┐
              │ Generation Evaluation  │
              │ Faithfulness / Relev.  │
              └──────────┬─────────────┘

              ┌────────────────────────┐
              │ Deterministic Checks   │
              │ ACL / Schema / Cite    │
              └──────────┬─────────────┘
                         ↓
              ┌────────────────────────┐
              │ Human Review Samples   │
              └──────────┬─────────────┘
                         ↓
                    Release Gate
```

## 15. Measure Citation Correctness Separately

An answer can be correct while pointing to the wrong source.

Citation systems should therefore check at least:

```text
Citation Completeness:
Are claims that require evidence cited?

Citation Entailment:
Does the cited passage support the claim?

Citation Quality:
Is the source authoritative and current?
```

A link to the correct document is not enough if the cited passage does not support the claim.

---

## 16. No-Answer and Unanswerable Tests

A golden set needs intentionally unanswerable questions.

```yaml
question: "What is the root password of System X?"
expected_behavior: refuse_or_no_evidence
```

Or:

```yaml
question: "Which feature was removed in version 9.2?"
reference: no_information_in_corpus
```

A RAG system that confidently answers such queries has a grounding problem even if its normal QA scores are high.

---

## 17. Robustness Against Contradictory Sources

Enterprise corpora contain versions.

```text
Runbook v1: timeout = 30s
Runbook v3: timeout = 90s
```

Evaluation should test whether:

- the current version is prioritized,
- the answer recognizes the conflict,
- the source is cited correctly,
- the two values are not silently merged.

This is often more important than synthetic standard QA.

---

## 18. Evaluator Drift

The judge changes too.

If an evaluation model is updated, scores can rise or fall even when the RAG system itself is unchanged.

Therefore version:

```text
evaluator_model
evaluator_prompt
evaluator_temperature
metric_version
```

and perform a **re-baseline** after major changes.

## Conclusion of the Series

A powerful knowledge system is not created by simply connecting a vector database to an LLM.

The five parts of this series trace a chain of decisions:

1. **Chunking and representation** determine what becomes searchable.
2. **GraphRAG** adds explicit structure to semantic proximity.
3. **RAG, fine-tuning, and long context** address different memory and behavior problems.
4. **Hybrid search and reranking** optimize candidate recall and ranking precision.
5. **Evaluation** makes improvements measurable and regressions visible.

The “perfect memory” remains intentionally metaphorical. RAG systems are probabilistic information systems with measurable errors. They become professional not by promising to eliminate those errors, but by being able to **locate, quantify, and systematically reduce them**.
