Vector search answers one class of questions extremely well: *Which passages are semantically similar to my query?* That formulation is powerful, but it is not the same as asking: *Which systems depend indirectly on database X? Which actors connect two events? Which themes dominate an entire corpus?*

Those questions require more than similarity. They require **structure**.

The second part of the **“Advanced RAG & Knowledge Systems”** series therefore examines GraphRAG and hybrid knowledge systems. The central point is not to pit graph databases against vector databases. In production systems they serve different purposes: vectors model semantic proximity; graphs model explicit entities, relationships, and hierarchies.

---

## 1. Why Similarity Is Not a Relationship

Assume a company has architecture and incident documentation for several systems:

```text
Service A → calls Service B
Service B → writes to Database X
Service C → reads event stream from Service A
```

The question

> “Which components are transitively affected by Database X?”

may not have any single passage in which the complete answer appears verbatim.

Dense retrieval can find individual relevant segments:

- Service B uses Database X.
- Service A calls Service B.
- Service C depends on Service A.

But the answer requires **composing several relationships**. This is a multi-hop problem.

A knowledge graph can represent the same information explicitly:

```text
(Service A)-[:CALLS]->(Service B)
(Service B)-[:WRITES_TO]->(Database X)
(Service C)-[:CONSUMES_FROM]->(Service A)
```

Graph traversal can now expose relationships that are not fully expressed in any single chunk.

---

## 2. What Microsoft Means by GraphRAG

Microsoft Research published the GraphRAG paper *From Local to Global* in 2024, extending RAG with a graph extracted from text, community detection, and hierarchical summaries.[^1]

The current Microsoft implementation describes GraphRAG as a **structured, hierarchical alternative or complement to simple semantic chunk search**.[^2]

At a high level, the indexing pipeline contains several stages:

```text
Raw Text
   ↓
Text Units / Chunks
   ↓
Entity & Relationship Extraction
   ↓
Knowledge Graph
   ↓
Community Detection
   ↓
Community Reports / Summaries
   ↓
Index artifacts for different query modes
```

Importantly, the graph does not emerge “objectively” from the documents. An LLM or extraction system interprets text and generates entities and relationships. This introduces new classes of error:

- entity duplication,
- incorrect relationship types,
- missed relationships,
- extraction hallucinations,
- inconsistent entity names,
- temporally outdated edges.

GraphRAG therefore does not replace uncertainty with truth. It moves part of the interpretation into the **indexing phase**.

---

## 3. Local Search: Entities as Entry Points

For concrete questions about an entity, GraphRAG can construct local graph neighborhoods.

```text
                ┌──────────────┐
                │  Database X  │
                └──────┬───────┘
                       │
          ┌────────────┴────────────┐
          ↓                         ↓
     Service B                  Incident 42
          ↓                         ↓
     Service A                  Team Alpha
```

The query no longer has to be answered solely through vector similarity against text chunks. The system can combine entities, relationships, claims, community information, and associated source passages.

Microsoft describes **Local Search** precisely for entity-centered questions where structured and unstructured information are assembled into the context together.[^2]

This is particularly useful for:

- architecture dependencies,
- company and person relationships,
- incident correlations,
- research knowledge bases,
- asset and threat-intelligence graphs.

---

## 4. Global Search: Questions Across the Entire Corpus

A classic Top-\(k\) retriever performs poorly on questions such as:

> “Which three strategic risks are discussed most frequently across all 8,000 reports?”

Why? Because the query vector selects individual similar passages. It has no natural mechanism for covering the entire corpus evenly.

GraphRAG therefore creates communities in the graph and summarizes their contents in advance. Microsoft describes **Global Search** as a mechanism for “whole dataset reasoning” over such community reports.[^3]

Conceptually:

```text
Community 1 → Summary
Community 2 → Summary
Community 3 → Summary
      ↓
Map / Partial Analyses
      ↓
Reduce / Synthesis
      ↓
Global Answer
```

This is not a free quality improvement. Community construction, LLM-based extraction, and summaries create substantial indexing costs. The official GraphRAG documentation explicitly warns that indexing alone can consume significant LLM resources.[^4]

---

## 5. DRIFT Search: Combining Global Context with Local Exploration

In addition to Local and Global Search, the current Microsoft implementation includes **DRIFT Search**. DRIFT starts from a specific query but uses community information to expand the search space and derive follow-up questions.[^5]

This creates an interesting middle ground:

```text
User Query
   ↓
relevant community contexts
   ↓
local entities / relationships
   ↓
Follow-up Queries
   ↓
broader Evidence Set
```

For analytical research, this can be more powerful than a single retrieval step. At the same time, it increases the risk that an early misinterpretation sends subsequent searches in the wrong direction.

---

## 6. “GraphRAG” Is Not the Same as “Knowledge Graph + LLM”

The term GraphRAG is now used very broadly. At least three architectures are commonly conflated:

### A. Graph as the Retrieval Index

The graph is traversed directly:

```text
MATCH (s:Service)-[:DEPENDS_ON*1..3]->(db:Database {name:"X"})
RETURN s
```

### B. Graph + Vector Index

Nodes or passages additionally carry embeddings:

```text
Query
├── Vector Search → semantic candidates
└── Graph Traversal → relational candidates
            ↓
         Fusion
```

### C. Microsoft-Style GraphRAG

LLM-based entity/relationship extraction, community hierarchy, community reports, and specialized query modes.

These approaches have different cost and failure profiles. An existing curated CMDB or dependency graph, for example, does not need LLM-based entity extraction to answer relational questions.

---

## 7. The Most Important Architectural Distinction: Ground Truth vs. Derived Graph

Enterprise systems should distinguish between two types of edges:

```text
AUTHORITATIVE:
Service A --deployed_on--> Cluster 7
Source: CMDB / Kubernetes API

INFERRED:
Service A --business_critical_for--> Checkout
Source: LLM extraction from documentation
Confidence: 0.72
```

This distinction is fundamental.

A knowledge graph built from authoritative system sources has a different trust level from a graph whose relationships were extracted from free text by a language model. Nodes and edges should therefore carry provenance metadata:

- `source_id`
- `source_version`
- `extracted_at`
- `extractor_model`
- `confidence`
- `valid_from`
- `valid_to`
- `tenant`
- `security_label`

Without provenance, a graph quickly becomes an apparently precise but difficult-to-audit knowledge layer.

## 8. Hybrid Knowledge Systems: Vector + Graph + Lexical Search

The strongest architecture is often not “graph instead of vector,” but a **query router**.

```text
                         ┌─ BM25 / Lexical Search
User Query → Classifier ─┼─ Dense Vector Search
                         ├─ Graph Traversal
                         └─ GraphRAG Global/DRIFT
                                 ↓
                           Evidence Fusion
                                 ↓
                              Rerank
                                 ↓
                               LLM
```

Examples:

| Query Type | Primary Path |
|---|---|
| “Where is `maxPoolSize` explained?” | Lexical + Dense |
| “Which component resembles architecture X?” | Dense |
| “Which services depend on X?” | Graph |
| “Which themes dominate all reports?” | Global GraphRAG |
| “Explain X including neighboring dependencies” | Hybrid |

The router does not have to be an LLM. In known domains, rules, query templates, or classification models can be more deterministic and less expensive.

---

## 9. Cost Model: The Price of Structure

Vector RAG typically indexes chunks and embeddings. GraphRAG may additionally require:

- entity extraction,
- relationship extraction,
- claim extraction,
- community detection,
- community summaries,
- additional embeddings,
- periodic re-indexing.

Operational effort increases further when the corpus changes frequently.

A highly dynamic knowledge base with millions of documents changing every day may therefore be a poor fit for full GraphRAG. A more stable research archive, by contrast, may benefit from expensive precomputation.

---

## 10. When GraphRAG Is a Bad Idea

GraphRAG is probably over-engineered when:

- questions are almost always answered by individual passages,
- the corpus is small,
- relationships are not important,
- content changes extremely frequently,
- low latency matters more than global synthesis,
- indexing budgets are tightly constrained.

In such cases, classic hybrid search with good chunking and reranking may be simpler, cheaper, and easier to test.

<KeyTakeaway>
**Graphs do not solve a generic “RAG problem.”** They add another representation for questions whose answers substantially depend on relationships, aggregation, or hierarchical structure.
</KeyTakeaway>

---

## 11. Temporal Relationships: Graphs Need a Time Dimension

In real systems, relationships are rarely valid forever.

```text
Service A --DEPENDS_ON--> Database X
valid_from: 2025-01-01
valid_to:   2026-03-17
```

Without a time dimension, a query can return a dependency that is historically correct but currently false. Incident analysis, organizational structures, and software architecture in particular should therefore support **bitemporal or at least validity-based metadata**.

A question such as

> “Which services depended on Database X at the time of the incident?”

is not equivalent to

> “Which services depend on it today?”

Vector RAG has the same versioning problem, but graphs make the consequence more explicit: one incorrect edge can contaminate several traversal steps.

---

## 12. Entity Resolution Is Often Harder Than Graph Traversal

Graph algorithms are rarely the bottleneck. A harder question is whether two textual mentions refer to the same entity.

```text
"Postgres Prod"
"prod-postgresql"
"DB-P01"
"payments database"
```

If all four names refer to the same database, naive extraction creates four nodes.

Depending on the domain, entity resolution may require:

- canonical IDs,
- aliases,
- fuzzy matching,
- embedding similarity,
- external master data,
- human review,
- merge/split history.

For enterprise knowledge graphs, an existing asset identifier is often more valuable than a sophisticated LLM prompt.

---

## 13. How GraphRAG Should Be Evaluated

A GraphRAG evaluation needs more than answer quality.

### Extraction Quality

- Entity Precision / Recall
- Relationship Precision / Recall
- Duplicate Entity Rate
- Unsupported Edge Rate

### Graph Quality

- proportion of orphaned nodes,
- inconsistent types,
- missing provenance,
- stale edges.

### Query Quality

- Path Accuracy
- Evidence Coverage
- Global Summary Faithfulness
- cost per query mode.

This makes it possible to distinguish whether a poor answer originated in **Extraction**, **Graph Construction**, **Retrieval**, or **Generation**.

## Conclusion

Vector spaces answer proximity. Graphs answer structure. Modern knowledge systems can combine both.

Microsoft GraphRAG demonstrates how unstructured text can be transformed into a hierarchical knowledge representation that supports both local entity-centered questions and global corpus-level questions. The architecture is especially powerful for multi-hop and aggregation queries—but it pays for that capability with more complex indexing, additional LLM cost, and new failure modes.

The next part addresses a different strategic question: **Should knowledge be retrieved at all—or should it move into fine-tuning or long context?**
