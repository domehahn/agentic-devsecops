Retrieval-Augmented Generation is often framed as a language-model problem: choose a powerful LLM, place a vector database beside it, and expect relevant enterprise information to reliably appear in the answer. In practice, however, a large share of failures arises much earlier—at the question of **what unit of information is indexed in the first place**.

That is the core of the chunking problem. A retriever does not search “documents” in the abstract. It searches representations of concrete segments that were previously constructed from documents. If a paragraph is split so that cause and effect are separated, a table row is detached from its header, or a pronoun loses its referent, the later vector search is already operating with lost information. The LLM can sometimes compensate for this loss—but it cannot reliably reconstruct knowledge that was never represented in a useful form during indexing.

The first part of the **“Advanced RAG & Knowledge Systems”** series therefore treats chunking not as a cosmetic preprocessing step, but as a **representation decision**. We examine fixed-size, structural, semantic, and hierarchical methods, late chunking, metadata, and vector geometry—and above all, how to choose a strategy empirically instead of guessing from generic token counts.

---

## 1. RAG Is an Information System—Not a Magical Context Channel

The original RAG concept combines the parametric knowledge of a language model with an explicit non-parametric memory from which relevant passages are retrieved at runtime.[^1] Modern implementations differ substantially from the original research setup, but the basic chain is similar:

```text
Document
   ↓
Parsing / Normalization
   ↓
Segmentation (Chunking)
   ↓
Embedding / Indexing
   ↓
Query → Retrieval
   ↓
Context Selection
   ↓
LLM Generation
```

Every stage changes the amount of information available to the next. Chunking is especially consequential because it turns one coherent source into several independent retrieval units.

Formally, a chunk \(c_i\) can be viewed as a segment of a document \(D\), and an embedding model as a function

```text
e: c_i → ℝ^d
```

that maps each segment to a vector in a \(d\)-dimensional space. The retrieval decision is then no longer based directly on the original document, but on the similarity between the query representation \(e(q)\) and the chunk representations \(e(c_i)\).

This creates an unavoidable trade-off:

- **Very small chunks** can produce precise hits but lose context.
- **Very large chunks** preserve more context but compress multiple topics into a single representation.
- **Overlap** reduces hard boundary failures but increases index size, redundancy, and cost.
- **Semantic or structural boundaries** can be more natural but depend on the data and parser.

The right chunk size is therefore not a universal constant.

---

## 2. Why Fixed-Size Chunking Is Not “Wrong”

A common criticism is that fixed-size chunking inevitably destroys semantics. That is too absolute. Fixed windows are first and foremost a **baseline method**: simple, deterministic, fast, and easy to reproduce. With uniform text, they can be surprisingly competitive.

Fixed-size chunking becomes problematic where the semantic structure of the material does not correlate with the chosen window length.

```text
Chunk A:
"The outage was initially attributed to the load balancer.
However, the logs showed that ..."

                 [boundary]

Chunk B:
"... the database connection pool was completely exhausted.
As a result, requests timed out."
```

A query about the *cause of the outage* may now require both chunks. If only Chunk A is retrieved, the cause is missing; if only Chunk B is retrieved, the reference to the specific outage may be absent.

Overlap is a pragmatic countermeasure:

```text
Chunk 1: Token 0–500
Chunk 2: Token 450–950
Chunk 3: Token 900–1400
```

But overlap does not create genuine semantics. It merely shifts the probability that a relationship remains fully contained in at least one segment. At the same time, high overlap leads to duplicated indexed information, more retrieval candidates, and potentially redundant context.

<Note>
**Engineering rule:** Fixed-size chunking should be treated as a measurable baseline candidate—not as an anti-pattern and not as a best practice.
</Note>

## 3. Structure-Aware Chunking: The Document Often Knows Its Own Boundaries

Many professional documents already contain a hierarchy:

```text
Document
├── Chapter
│   ├── Section
│   │   ├── Paragraph
│   │   └── Table
│   └── Section
└── Appendix
```

Markdown headings, HTML DOM structures, PDF layout information, code symbols, tables, and lists are often better boundary signals than a rigid token count.

This is particularly important for technical material. A Java method should, where possible, not be split in the middle of its control flow; a Kubernetes resource should keep its `kind`, metadata, and relevant `spec` fields together; a table should not lose the relationship between headers and rows.

A structure-aware chunker might use rules such as:

```text
if heading_level <= 2:
    begin_new_section()

if code_symbol == "function":
    keep_symbol_body_together()

if table:
    repeat_header_for_each_table_chunk()
```

The result is not automatically better. A 20-page section remains too large even if its heading marks a natural boundary. Structure is therefore usually the first step in **multi-stage segmentation**.

---

## 4. Semantic Chunking: Deriving Boundaries from Changes in Meaning

Semantic chunking attempts to infer segment boundaries from topical transitions. A common heuristic is:

1. Split text into sentences or small units.
2. Compute an embedding for each unit.
3. Measure similarity between adjacent units.
4. Create a boundary when similarity drops sharply.

Simplified:

```text
s1 ── sim=0.92 ── s2 ── sim=0.88 ── s3 ── sim=0.31 ── s4
                                      ↑
                               possible boundary
```

This method can respect topic changes better than rigid windows. But it has its own hyperparameters: sentence segmentation, embedding model, similarity metric, threshold, and minimum/maximum size.

Moreover, semantic proximity is not the same as logical dependence. Two sentences can have different vectors and still be causally linked; conversely, many similarly worded sentences can be redundant.

Semantic chunking should therefore not be understood as an “intelligent solution” to every boundary problem, but as a **segmentation heuristic that must be evaluated**.

---

## 5. Parent-Child Retrieval: Search Precisely, Read Generously

A particularly robust architecture pattern separates **retrieval granularity** from **context granularity**.

```text
Parent: section with 1,500 tokens
├── Child A: 200 tokens
├── Child B: 200 tokens
├── Child C: 200 tokens
└── Child D: 200 tokens
```

The small child chunks are indexed because shorter segments often have a more precise semantic signature. If the retriever finds Child C, the prompt does not necessarily receive only Child C. Instead, the system can load the associated parent section.

This separates two objectives:

- **Recall/Ranking:** small units
- **LLM context:** coherent information

This pattern is especially useful for manuals, policies, source code, and longer technical specifications. It does, however, increase the risk that the same parent enters the context multiple times through several child hits. Deduplication and context packing therefore become part of the design.

---

## 6. Late Chunking: Context Before Segmentation

A fundamental problem in classic chunking pipelines is the order of operations:

```text
Document
→ split first
→ embed each chunk independently
```

The embedding model therefore sees only the local excerpt. Expressions such as “this method,” “he,” “the server,” or “this limitation” can be poorly represented without preceding context.

Jina AI proposed **Late Chunking** in 2024.[^2] The order is reversed:

```text
Document
→ run the whole document / long context through embedding transformer
→ contextualized token representations
→ apply segment boundaries afterward
→ pool token representations per chunk
```

The advantage is that token states have already seen the surrounding document context before they are aggregated into a chunk vector. Jina now also describes the method in its current embedding documentation as an available technique for contextual chunk embeddings.[^3]

Late chunking does not eliminate the chunking problem, however. It shifts part of the context loss: retrieval units remain chunks, and very long documents can still exceed the embedding model's context limit. Indexing compute and memory costs also increase.

---

## 7. Contextual Retrieval: Context as a Text Prefix

An alternative or complementary idea is to add short contextual information to each chunk before embedding.

Instead of:

```text
"The default value is 30 seconds."
```

use, for example:

```text
"Document: API Gateway Operations Guide.
Section: Upstream Timeout.
This section describes the default value for upstream requests.

The default value is 30 seconds."
```

Anthropic published experiments in 2024 on such a **Contextual Retrieval** approach, in which chunks were enriched with additional document context for both embedding and BM25 search. In its own tests, the combination of contextualized embeddings, BM25, and reranking substantially reduced retrieval failure rates.[^4] This is useful evidence, but it should be read as a vendor evaluation rather than a universal law.

Context prefixes also have costs: they lengthen every chunk, can introduce dominant metadata, and may need to be recomputed when source context changes.

---

## 8. Vector Spaces: Chunking and Embedding Cannot Be Optimized Separately

A chunk is only as useful as the representation the embedding model creates from it.

For normalized vectors, cosine similarity is commonly used:

```text
cos(q, d) = (q · d) / (||q|| ||d||)
```

The geometric interpretation can tempt us to treat “similar meaning” as an objective property. In reality, the space was learned from training data, a loss function, and a model architecture. Domain terminology, numbers, IDs, code, and multilingual content can be represented very differently depending on the embedding model.

The following decisions therefore belong in the same evaluation:

- chunking method,
- chunk length,
- overlap,
- embedding model,
- query/passage mode of the embedding model,
- distance metric,
- ANN index parameters,
- metadata filters,
- Top-\(k\).

Changing only chunk size often measures just one small part of the retrieval pipeline.

---

## 9. Special Cases: Tables, Code, and Multimodal Documents

Plain-text chunking quickly reaches its limits with structured data.

### Tables

A table row without its header can be semantically useless:

```text
| Service | Timeout | Retries |
| API-A   | 30s     | 3       |
```

If only `API-A | 30s | 3` is indexed, the column meanings are missing. A parser should therefore repeat headers or serialize the row into descriptive text.

### Source Code

For code, syntactic boundaries are often more important than token windows:

```text
Repository
→ File
→ Class / Module
→ Function / Method
→ optional Block
```

Additional metadata such as symbol name, file path, language, imports, and call-graph relationships can substantially improve search.

### PDF and Layout

With PDFs, text order must not be blindly inferred from the raw character stream. Multi-column layouts, footnotes, headers, and tables require layout parsing; otherwise semantically incorrect chunks can be created.

## 10. How to Actually Choose a Chunking Strategy

A defensible choice is based on a representative query set.

For each variant, measure:

```text
Chunker A + Embedding X
Chunker B + Embedding X
Chunker C + Embedding Y
            ↓
       Evaluation Set
            ↓
Recall@k / nDCG / MRR
+ End-to-End Answer Quality
+ Cost / Latency
```

It is important to separate retrieval from generation. A retriever can return the correct chunk even if the LLM produces a poor answer from it. Conversely, a strong LLM can formulate a good answer even when retrieval relevance is weak.

A useful experiment therefore does not vary ten parameters at once. Start with a simple baseline, change one dimension, measure the effect, and document the result.

<Architecture>
**Pragmatic starting point for Enterprise RAG:**

1. Structure-aware parsing.
2. Moderate child chunks with explicit parent IDs.
3. Metadata for source, version, section, and authorization domain.
4. Add hybrid retrieval and reranking only after a clean baseline test.
5. Evaluate late chunking or contextual retrieval where references and document-wide dependencies are common.
6. Treat chunking parameters as versioned configuration.
</Architecture>

---

## Conclusion

Chunking is neither a trivial text split nor the sole determinant of a RAG system. It is the point where a document is translated into **retrievable units of information**. Errors introduced here propagate through embeddings, ranking, and context assembly all the way to the final answer.

The key takeaway is therefore not “use semantic chunking” or “use 500 tokens.” It is:

> **Treat chunking as part of the retrieval model and evaluate it together with embeddings, ranking, and the actual queries your system receives.**
