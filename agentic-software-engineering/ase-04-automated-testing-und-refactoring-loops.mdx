Coding agents differ from traditional code generators because of their loop: they can modify files, run tests, read errors, and try again. That feedback loop makes them powerful—and dangerous when the feedback channel is designed poorly.

An agent whose only objective is “make all tests green” can theoretically choose between two paths:

```text
A) Fix the code
B) Delete the test
```

For a human, it is obvious that B is usually not acceptable. For an optimization system, that boundary must become **explicit**.

Automated testing in agentic engineering therefore means more than allowing the model to run `npm test`. It means connecting **deterministic verifiers, protected acceptance criteria, and controlled modification scopes** into a stable loop.

---

## 1. TDD Fits Agents Surprisingly Well

Kent Beck’s Red-Green-Refactor cycle provides a clear external objective function:[^1]

```text
RED      -> test describes desired behavior and fails
GREEN    -> minimal implementation satisfies the test
REFACTOR -> improve structure while tests stay green
```

This is attractive for agents because every state is observable. Still, it should not be dogmatically required that the agent write every baseline test itself. For critical requirements, at least the central acceptance tests should be protected **separately from the implementation target**.

---

## 2. The Verifier Must Be Harder to Manipulate Than the Solution

A robust repository separates:

```text
Agent-editable:
  src/**
  tests/unit/generated/**

Protected:
  tests/acceptance/**
  security/policies/**
  ci/required-checks/**
```

Branch protection or sandbox policies can prevent an agent from modifying protected files.

This is a general principle for verifiable agent systems:

> The objective function must not live in the same unprotected modification space as the solution.

---

## 3. Compilers, Type Checkers, and Linters Are Excellent Agent Tools

LLMs are probabilistic. Compilers are not.

A good loop therefore uses as many deterministic signals as possible:

```text
Patch
 ↓
Formatter
 ↓
Compiler / Typecheck
 ↓
Unit Tests
 ↓
Integration Tests
 ↓
SAST / Dependency / Secret Scan
 ↓
Acceptance Tests
```

The agent receives structured failures and may iterate.

Example:

```json
{
  "stage": "typecheck",
  "status": "failed",
  "errors": [
    {
      "file": "src/user.ts",
      "line": 41,
      "code": "TS2322"
    }
  ]
}
```

Structured tool output reduces context requirements and makes automatic classification easier.

---

## 4. Tests Check Examples—Invariants Check Classes of Errors

A unit test can cover one concrete input. Agents also benefit from property-based testing.

Example:

```text
Invariant:
For every valid token t:
verify(sign(t)) == true

For every modified payload t':
verify(t') == false
```

Fuzzing, property tests, and schema validation expand the solution space that an agent cannot simply overfit to a handful of known examples.

This is particularly important when the agent can read all existing tests.

---

## 5. Refactoring Needs Semantic Boundaries

An LLM can generate a textual diff. For large-scale refactoring, AST-based transformations are often more robust.

```text
Source
 ↓ parse
AST
 ↓ transform
AST'
 ↓ print
Source'
```

Examples include:

- API renames,
- import migrations,
- adding annotations,
- syntactically defined modernization.

The agent can decide **which transformation** is required while a deterministic AST tool performs it. This reduces formatting errors and unintended changes.

---

## 6. Diagnose Instead of Blindly Retrying

A bad agent loop looks like this:

```text
Test failed -> change random code -> rerun -> failed -> change more
```

A good loop classifies the failure:

```text
Failure
  ├─ compile
  ├─ deterministic test regression
  ├─ environment / dependency
  ├─ flaky test
  ├─ permission / sandbox
  └─ spec ambiguity
```

Each class requires a different response. A network failure must not be “fixed” by changing business logic.

---

## 7. Flaky Tests Are Especially Dangerous for Autonomous Loops

Humans often recognize that a test fails sporadically. An agent may interpret a random red test as proof of a code defect and make unnecessary changes.

Agent platforms should therefore know test history and flakiness:

```text
Test fails
 ↓
Known flaky?
 ├─ yes -> controlled retry + mark evidence
 └─ no  -> diagnose code
```

Retries must not become a blanket mechanism for hiding problems. Their number should be bounded and visible.

---

## 8. Stop Conditions Prevent Infinite Loops

Autonomous repair requires budgets:

```yaml
max_iterations: 8
max_wall_time: 30m
max_changed_files: 20
max_model_cost: 10.00
```

When the budget is exhausted, the agent escalates with evidence:

```text
Attempted fixes: 5
Remaining failures: 2
Suspected cause: ambiguous schema migration
Files changed: ...
Recommended human decision: ...
```

“Not solved” is a valid outcome. An agent must not be forced to claim success.

---

## 9. Evals Test the Loop Itself

Anthropic points out that agents are harder to evaluate because of their multi-step nature and that realistic evals are central to reliable deployment decisions.[^2]

For coding agents, the final test status should not be the only metric:

- Did the agent modify existing tests?
- How many irrelevant files were changed?
- Were root causes classified correctly?
- How many iterations were required?
- Was a security check bypassed?
- Was the result understandable to a reviewer?

“Green CI” is therefore only one quality dimension among several.

---

## 10. Evidence-Based Completion

An agent should not report completion as an unsupported claim:

> “I tested everything and it works.”

Better:

```json
{
  "status": "complete",
  "evidence": {
    "typecheck": {"exit_code": 0},
    "unit_tests": {"passed": 412, "failed": 0},
    "integration_tests": {"passed": 38, "failed": 0},
    "sast": {"new_high_findings": 0},
    "diff": "sha256:..."
  }
}
```

The platform can independently validate the evidence before a merge is even offered.

---

## 11. A Safe Agentic Refactoring Loop

Combined:

```text
Task + Protected Spec
       ↓
Agent proposes patch
       ↓
Sandbox applies diff
       ↓
Static Verifiers
       ↓
Tests + Security Scans
       ↓
Pass?
 ├─ no -> structured diagnosis -> bounded retry
 └─ yes
       ↓
Independent diff review
       ↓
Evidence package
       ↓
Human / Policy gate
```

Autonomy here does not mean allowing the agent to “do whatever it wants.” It means allowing it to **iterate independently inside a strongly verified environment**.

---

## 12. Mutation Testing: Does the Test Actually Check the Desired Property?

A green test proves only that the current code satisfies that test. It does not prove that the test is sensitive to relevant errors. Mutation testing deliberately changes the code—for example `>` to `>=`, `true` to `false`, or removes a validation—and expects at least one test to fail.

```text
Production Code
   ↓ mutate
Variant 1 -> tests fail  -> mutation killed
Variant 2 -> tests pass  -> surviving mutation
```

This is especially interesting for agentic engineering because a model may otherwise generate tests that merely confirm its own implementation. Surviving mutations reveal areas where verification is weak.

Mutation testing is compute-intensive and need not run on every small commit. For security-critical modules or larger autonomous refactors, however, it can provide a stronger signal than coverage percentages alone.

---

## 13. Refactoring and Feature Changes Should Be Separated

Coding agents tend toward opportunistic “cleanup”: while fixing a bug, they reformat neighboring files, rename symbols, and modernize APIs. For human reviewers, this increases the review surface and complicates root-cause analysis.

A better flow separates the work into two transactions:

```text
1. Behaviour Change
   -> minimal diff
   -> tests
   -> review

2. Structural Refactor
   -> semantically equivalent
   -> separate evidence
   -> review
```

For a pure refactor, the central invariant is that observable behavior remains unchanged. Compilers, tests, API-compatibility checks, and where appropriate snapshot/golden tests can support that claim.

The separation also improves rollback behavior: if a regression appears, it is clearer whether it came from the functional change or the structural transformation.

---

## Conclusion

Test-Driven Agentic Engineering is a natural extension of TDD: not only humans but agents also work against explicit, automatable feedback.[^1]

The decisive difference lies in threat and failure modeling. Tests, policies, and completion criteria must be protected from manipulation. Compilers, type checkers, AST tools, and scanners should be used as deterministic verifiers. Iterations need budgets and clear escalation paths.

An autonomous coding agent is strongest when it does not have to decide for itself whether the result is correct. **The system around it should be able to prove it.**
