“Human in the Loop” initially sounds like a simple safety measure: the agent works, a button appears before a critical action, and a human clicks **Approve**. In real systems, this mechanism is effective only when the human has enough context, time, authority, and a genuine alternative to approving.

A poorly designed approval gate can even be more dangerous than open autonomy: it creates the impression of human control while the reviewer merely rubber-stamps requests.

Human-in-the-Loop (HITL) is therefore not a single UI step. It is an architecture for **risk-based delegation of decision rights**.

---

## 1. Not Every Agent Action Needs Approval

If every file read requires confirmation, the agent becomes unusable. If no action requires confirmation, meaningful control disappears.

The solution is capability and risk classification:

```text
Read repository                 -> autonomous
Run unit tests                  -> autonomous
Modify branch in sandbox        -> autonomous
Create external issue           -> conditional
Push protected branch           -> approval
Production deployment           -> approval
Delete production data          -> strong approval / separation of duties
```

The objective is **progressive autonomy**: the agent receives more freedom for reversible, well-verifiable actions than for irreversible or high-impact operations.

---

## 2. Risk = Impact × Uncertainty × Reversibility

A practical decision matrix can combine several factors:

```text
Impact        low / medium / high
Confidence    high / medium / low
Reversibility easy / difficult / impossible
Data Class    public / internal / confidential / restricted
Environment   dev / test / prod
```

Example:

```yaml
action: database-migration
impact: high
reversibility: difficult
environment: production
required_gate: two-person-approval
```

This policy should be enforced by the platform. The agent must not be able to downgrade its own risk class through persuasive language.

---

## 3. Approval Requires Decision-Relevant Evidence

A human cannot make a meaningful decision if the interface shows only:

> “Agent wants to deploy. Approve?”

A good gate instead displays:

```text
Change: PR #4812
Risk: production / write
Diff: +48 / -12 lines
Tests: 412 passed, 0 failed
Security: 0 new high findings
Migration: none
Rollback: verified artifact v3.8.1
Agent confidence: not used as approval evidence
```

The reviewer receives **deterministic evidence**, not merely a model-generated summary.

---

## 4. Human Oversight Can Fail Too

NIST’s AI Risk Management Framework emphasizes that roles and responsibilities for human oversight must be clearly defined and that humans have their own biases and limitations.[^1]

Typical failure modes include:

### Automation Bias

People tend to follow apparently competent automation.

### Approval Fatigue

Too many gates are confirmed mechanically.

### Diff Overload

An agent produces 8,000 lines of changes; a human reviewer cannot realistically inspect them completely.

### Ambiguous Responsibility

The human believes the agent is responsible. The organization believes the reviewer is responsible. In practice, no one truly owns the decision.

HITL must therefore be treated as a **human-factors problem**.

---

## 5. Good Gates First Reduce the Review Surface

The most effective human control is not a better button, but a smaller and better-prepared decision space.

```text
Agent output
 ↓
Automated tests
 ↓
Policy checks
 ↓
Security scans
 ↓
Diff minimization
 ↓
Human review
```

Humans should not have to verify what a compiler or scanner can check more reliably. Their attention belongs on architecture, business intent, unusual risk, and accountability.

---

## 6. Four-Eyes Principle and Separation of Duties

For especially critical actions, neither the agent alone nor the same human should be able to approve everything.

```text
Agent proposes
   ↓
Engineer reviews technical change
   ↓
Service owner approves production impact
   ↓
Deployment system executes
```

The identities must be technically distinct. An “approval agent” running with the same credentials as the executing agent is not true separation of duties.

---

## 7. Time-Bounded and Scope-Bounded Approvals

Approvals should not become permanent privileges.

Bad:

```text
"Agent may deploy to production" -> forever
```

Better:

```json
{
  "approval": "deploy",
  "artifact": "sha256:abc...",
  "environment": "prod-eu",
  "expires_at": "2026-08-23T01:15:00Z",
  "max_uses": 1
}
```

If the artifact changes after review, the approval becomes invalid. The approval is therefore cryptographically bound to **exactly the object that was reviewed**.

---

## 8. Progressive Delivery as a HITL Amplifier

Not every decision must be binary: “deploy” or “do not deploy.”

```text
Agent Change
 ↓
Canary 1%
 ↓ metrics
Canary 10%
 ↓ metrics
50%
 ↓
100%
```

Humans can intervene at critical transitions while automated SLOs trigger rollbacks.

This increases reversibility—and therefore allows more autonomy at lower-risk stages.

---

## 9. Escalation Is a Feature, Not a Failure

A professional agent must be allowed to escalate uncertainty:

```text
"Two schemas conflict.
Option A preserves backward compatibility but violates ADR-12.
Option B follows ADR-12 but requires migration.
Human decision required."
```

A system that must always answer autonomously incentivizes guessing.

The platform should therefore support explicit states:

```text
COMPLETE
BLOCKED
NEEDS_APPROVAL
NEEDS_DOMAIN_DECISION
FAILED_SAFELY
```

This makes uncertainty operationally manageable.

---

## 10. Human Feedback Must Not Disappear as Unstructured Chat

A reviewer corrects an agent:

> “No, we do not use a direct database connection in this service.”

If that information remains only in the chat, the same mistake will recur.

A good process asks:

```text
Was this...
- a one-time preference?
- a repository rule? -> AGENTS.md
- an architecture decision? -> ADR
- a skill update? -> SKILL.md
- a new test? -> acceptance suite
```

Human oversight then becomes a way to **improve the system**, not merely correct individual runs.

---

## 11. Evals for the Approval System

Not only the agent but HITL itself should be measured:

- approval rate,
- rejection rate,
- median review time,
- number of approved changes later rolled back,
- share of gates without sufficient evidence,
- override frequency,
- false-positive policy blocks,
- review load per engineer.

An approval system with a 99.9% approval rate may be working perfectly—or may be meaningless. The number needs context.

---

## 12. Target Architecture: Risk-Based Autonomy

```text
Agent Action Proposal
        ↓
Deterministic Risk Policy
        ↓
┌──────────────────────────────┐
│ Low: automatic              │
│ Medium: automatic + audit   │
│ High: human approval        │
│ Critical: dual approval     │
└──────────────────────────────┘
        ↓
Scoped Capability Token
        ↓
Execution
        ↓
Evidence + Revocation / Expiry
```

The human is therefore not “in every loop,” but **at the points where human judgment provides a real safety benefit**.

---

## 13. Human-on-the-Loop and Human-out-of-the-Loop

Not every controlled form of autonomy requires synchronous approval. For well-understood, reversible actions, a human can be **on the loop** rather than **in the loop**: the agent acts autonomously, but telemetry, limits, and a kill switch allow supervision and intervention.

```text
Human-in-the-loop  -> action waits for explicit approval
Human-on-the-loop  -> action proceeds, human monitors and can stop it
Human-out-of-loop  -> fully automated within pre-approved policy
```

This distinction prevents scarce human attention from being wasted on trivial actions. An autoformatter can usually run fully autonomously; a canary rollout may run on-the-loop; an irreversible deletion of production data may require strong synchronous approval.

The exact mapping is risk-based and organization-specific.

---

## 14. Approval UX Is Part of the Security Model

Security architecture does not end at the policy engine. If an approval interface presents ten pages of unstructured agent explanation, the human will miss critical information.

A good review interface prioritizes:

```text
WHAT changes?
WHERE does it act?
WHAT is the blast radius?
WHICH checks passed or failed?
WHAT is irreversible?
WHAT changed since last approval?
```

“Diff since approval” is especially important. If a patch is regenerated after human approval, the previous approval must become invalid. Otherwise, the human approves artifact A while the platform executes artifact B.

Anthropic’s recommendation to use agents only where their additional flexibility justifies the added cost and complexity can be transferred directly to HITL: human attention is also a scarce resource and should be spent where it genuinely improves the risk position.[^2]

---

## Conclusion

Human-in-the-Loop is not a blanket alternative to autonomy. Good agent platforms combine both: reversible and deterministically verifiable steps run autonomously; critical state changes are controlled through risk-based gates.

NIST’s AI RMF emphasizes that human roles, accountability, and oversight must be clearly defined and documented.[^1] At the same time, human control should not be idealized. Automation bias, approval fatigue, and oversized diffs can make it ineffective.

The strongest design binds approvals to concrete artifacts, limits them by time and scope, presents robust evidence, and uses progressive delivery to make decisions more reversible.

The series **“Agentic Software Engineering & Multi-Agent Design Patterns”** therefore ends with an apparent paradox: the better specifications, skills, tests, and policy enforcement become, the more work an agent can perform autonomously—and the more precisely we can define the few points where a human genuinely needs to decide.
