Multi-agent systems are often presented as the natural next step after a single LLM agent. That is too simplistic. More agents do not automatically mean more intelligence. They first mean **more messages, more state, more latency, more cost, and more failure boundaries**.

Anthropic therefore formulates a useful principle: start with the simplest architecture that solves the problem, and increase complexity only where it produces measurable benefit.[^1]

The right question is therefore not:

> “How many agents does our project need?”

but:

> “Which parts of the problem benefit from separation, parallelization, independent evaluation, or dynamic delegation?”

---

## 1. Workflows and Agents Are Not the Same Thing

An important architectural distinction is the one between **workflows** and **agents**. In a workflow, the control flow is largely predetermined by application code. In an agent, the model makes more dynamic decisions about next steps and tool use.[^1]

```text
Workflow:
A -> B -> C -> D

Agent:
Goal -> Model decides -> Tool -> Observe -> Decide -> ...
```

A multi-agent system can itself still be a workflow: a deterministic orchestrator may call three specialized agents in a fixed sequence.

These terms should not be conflated, because they create different operational and security models.

---

## 2. Pattern 1: Router

A router classifies a task and sends it to the appropriate specialization.

```text
Request
  ↓
Router
  ├─> Security Agent
  ├─> Database Agent
  └─> Frontend Agent
```

The pattern works well when tasks are clearly distinguishable and require different contexts or tools.

Its main benefit is less “more thinking” than **context isolation**: the database agent does not need frontend design rules, and the security agent may require only the diff rather than the entire repository.

Failure mode: incorrect routing can degrade the entire task. Routing therefore belongs in evals.

---

## 3. Pattern 2: Orchestrator-Worker

Anthropic describes orchestrator-workers as a workflow in which a central LLM dynamically decomposes a complex task, delegates subtasks to workers, and synthesizes the results.[^1]

```text
                  ┌─> Worker A
Goal -> Orchestrator ─> Worker B -> Synthesis
                  └─> Worker C
```

This is useful when the number and nature of subtasks **cannot be known reliably in advance**. A large code change may affect five files or fifty.

Benefits:

- dynamic decomposition,
- parallel work,
- smaller local contexts,
- specialization.

Costs:

- coordination errors,
- duplicated work,
- merge conflicts,
- higher token and tool costs,
- more difficult traceability.

An orchestrator should therefore assign ownership explicitly rather than merely delegate work:

```json
{
  "task": "update API validation",
  "scope": ["src/api/**", "tests/api/**"],
  "forbidden": ["db/migrations/**"],
  "acceptance": ["npm test -- api"]
}
```

---

## 4. Pattern 3: Parallelization

Sometimes no intelligent orchestrator is needed. Independent checks can simply run in parallel:

```text
                ┌─> Security Review
Git Diff ───────┼─> Performance Review
                └─> API Compatibility Review
                        ↓
                     Merge
```

This pattern is especially attractive because it is easy to control. Each worker has a clearly defined task and can be evaluated independently.

Majority voting is not automatically truth, however. Three agents using the same models, prompts, and data may reproduce the same systematic error. Diversity does not arise merely from running three process instances.

---

## 5. Pattern 4: Evaluator-Optimizer

In an evaluator-optimizer pattern, one model generates a candidate, a second evaluates it against explicit criteria, and the generator iteratively improves the result.[^1]

```text
Generate -> Evaluate -> Feedback
   ^                     |
   └─────────────────────┘
```

This works particularly well when quality is **explicitly assessable**.

Code example:

```text
Implementer -> Patch
Reviewer    -> "Missing boundary test for empty input"
Implementer -> Patch v2
Verifier    -> Tests + typecheck
```

Where possible, the evaluator should use evidence—tests, compilers, scanners—instead of merely producing another opinion.

---

## 6. Pattern 5: Debate—Useful, but Not a Consensus Machine

Agent debate allows several models to exchange alternative solutions or critiques. Research and frameworks such as AutoGen popularized multi-agent conversation as a general orchestration model.[^2]

```text
Agent A: Solution X
Agent B: Counterargument Y
Agent C: Review
       ↓
Decision
```

This can improve exploration, but consensus among several models is not a formal proof. Debate is most useful when:

- several plausible strategies exist,
- arguments can be compared explicitly,
- an external evaluator checks the result.

For deterministic tasks, a compiler is usually a better “debate partner” than a third LLM.

---

## 7. Multi-Agent Trust Boundaries

A central security mistake is to trust sub-agents implicitly.

```text
Research Agent -> "Run this shell command"
                         ↓
Developer Agent executes blindly
```

An agent response is **untrusted input**. This remains true even when both agents belong to the same platform.

A more robust design is:

```text
Agent Proposal
   ↓
Structured Schema Validation
   ↓
Policy Engine
   ↓
Capability-limited Tool
   ↓
Execution
```

Delegation then becomes a real security boundary rather than a chat message.

---

## 8. Shared Memory Creates Hidden Coupling

If every agent can read from and write to the same global memory store, the result is a distributed system with difficult-to-trace state changes.

A better separation is:

```text
Run State       -> current workflow only
Agent Scratch   -> worker-local
Shared Evidence -> immutable / append-only results
Long-term Memory-> controlled, separate persistence
```

The orchestrator should exchange results as versioned artifacts, not through implicit “memories.”

---

## 9. The Economics of Orchestration

A single task involving five agents can quickly produce ten or twenty model calls. Cost accounting therefore belongs in the architecture.

Relevant metrics include:

```text
Task Success Rate
Latency p50 / p95
Model Calls per Task
Input / Output Tokens
Tool Calls
Human Escalations
Regression Rate
Cost per Successful Task
```

The important metric is not “How autonomous does the system feel?” but **cost per correctly completed unit of work**.

---

## 10. Architecture Decision Tree

A pragmatic decision tree looks like this:

```text
Can the task be decomposed deterministically?
  ├─ yes -> classic workflow
  └─ no
      ↓
Can a single agent solve it reliably with tools?
  ├─ yes -> single agent
  └─ no
      ↓
Are independent subtasks identifiable?
  ├─ yes -> parallel / router
  └─ no
      ↓
Must decomposition be dynamic?
  ├─ yes -> orchestrator-worker
  └─ no -> simplify the workflow further
```

Multi-agent is therefore not a goal; it is a cost-benefit decision.

## 11. Example: A Security-Relevant Feature as a Multi-Agent Workflow

Assume a team is introducing a new OAuth callback. Instead of launching six agents that freely chat with one another, the task can be decomposed deliberately.

```text
Orchestrator
  ├─ Repository Analyst -> existing auth architecture + ADRs
  ├─ Implementer        -> minimal patch
  ├─ Security Reviewer  -> OAuth / CSRF / redirect_uri / secret handling
  └─ Verifier           -> tests + typecheck + SAST
```

The Security Reviewer does not receive permission to change the patch directly. It returns structured findings. The Implementer may react only within its scope. The Verifier runs deterministic checks and has no write permissions. This asymmetric capability distribution is more important than which model runs inside which agent.

A result artifact might look like:

```json
{
  "implementation": "commit:abc123",
  "security_findings": [],
  "verification": {
    "tests": "pass",
    "sast": "pass"
  }
}
```

The multi-agent system becomes a **pipeline of separated responsibilities**, not a group of virtual colleagues that blindly persuade one another.

---

## 12. The Most Common Anti-Pattern: Agent Roles Without Real Isolation

Many demos define roles such as “Architect,” “Developer,” and “Reviewer” while giving all three instances the same complete context, the same tools, and the same write permissions. This creates little real specialization. Often, the same model error is simply produced three times under different role names.

A robust role needs at least one real differentiator: a different context window, a different capability, a different objective function, independent evidence, or a different model. **Epistemic independence** is particularly valuable: the reviewer should not simply inherit the implementer’s reasoning, but inspect the artifact state independently.

Multi-agent design is therefore closer to microservices than role-playing. Boundaries, contracts, and ownership determine architectural quality.

---

## Conclusion

Multiple agents are useful when they deliver a concrete architectural benefit: **context isolation, parallelization, specialization, independent evaluation, or dynamic task decomposition**.

Anthropic’s production patterns and systems such as AutoGen show that multi-agent architectures can provide powerful orchestration mechanisms.[^1][^2] They do not show that every complex problem requires several agents.

Every additional agent is a new component with its own failure domain. Communication schemas, trust boundaries, state ownership, evals, and cost must therefore be designed just as carefully as prompts.
