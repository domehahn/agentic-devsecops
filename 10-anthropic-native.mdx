Nicht jeder Modellanbieter sollte über eine OpenAI-Kompatibilitätsschicht gezwungen werden. Native Provider können Authentisierung, Request-Format, Fehlersemantik und strukturierte Antworten sauberer abbilden.

Für einen Security Scanner ist das relevant, weil Providerfehler oder falsch interpretierte Antworten direkt die Aussagekraft eines Findings beeinflussen.

<KeyTakeaway>
Native Providerintegration ist dann wertvoll, wenn sie den Transport präzisiert, ohne die interne Security-Semantik des Scanners zu verändern.
</KeyTakeaway>

## Was das Feature wirklich bedeutet

Eine native Integration sollte trotzdem denselben internen Finding-Vertrag erfüllen. Sonst ändert sich die Security-Semantik abhängig vom verwendeten Modellanbieter. Idealerweise unterscheiden sich nur Transport und Authentisierung; Severity, Evidence und Coverage bleiben providerneutral.

Außerdem sollte ein LLM-Provider keine Tools erhalten, nur weil das zugrundeliegende Modell Tool Use unterstützt.

## SkillSpector

SkillSpector führt `anthropic` als nativen Provider mit `ANTHROPIC_API_KEY`. Dadurch kann Claude direkt über die Anthropic API für die semantische Stufe genutzt werden.

Die gleiche Scannerlogik bleibt erhalten; geändert wird der Transport zum Modell.

## `skil`

`skil` besitzt ebenfalls einen nativen Anthropic-Adapter. Laut Semantic-Analysis-Dokumentation werden keine Tools mitgegeben und die Antwort wird gegen denselben begrenzten Ergebnisvertrag validiert wie beim OpenAI-kompatiblen Adapter.

Damit bleibt die providerneutrale Security-Struktur erhalten, obwohl das Transportprotokoll nativ Anthropic ist.

## Praxisbeispiel

```bash
# SkillSpector
export SKILLSPECTOR_PROVIDER=anthropic
export ANTHROPIC_API_KEY="$ANTHROPIC_API_KEY"
skillspector scan ./skill

# skil
skil scan ./skill   --semantic   --semantic-provider anthropic   --semantic-model claude-sonnet-4-5
```

Das Beispiel zeigt die gewünschte Architektur: Der Scanner wählt den Provider explizit, während das Artefakt selbst keine Kontrolle über Modell, Credential oder Endpoint erhält.

## Security- und DevSecOps-Einordnung

- Providerwahl außerhalb des gescannten Skills konfigurieren.
- Keine Tool-Rechte an das Analysemodell delegieren.
- Antwortschema strikt validieren; Freitext nicht ungeprüft als Finding übernehmen.
- Modellversion im Report erfassen, um Reproduzierbarkeit zu verbessern.
- API-Key getrennt vom Skill-Artefakt halten.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

**Bewertung aus der Vergleichsmatrix:** gleich.

## Typische Fehlinterpretation

„Native Provider sind automatisch sicherer als kompatible Adapter.“ Native Integration kann sauberer sein, aber die entscheidenden Eigenschaften bleiben Toolfreiheit, Credential-Grenze, Response-Validierung und Datenfluss.

## Einordnung in die Pipeline

Dieses Feature gehört in eine **optionale semantische Analyse-Stufe hinter dem deterministischen Gate**. So bleiben Pull-Request-Checks schnell und reproduzierbar, während modellgestützte Analyse gezielt für risikoreiche Skills, Release-Kandidaten oder Nightly-Scans zugeschaltet werden kann.

Pipeline-seitig sollten Provider, Modell, Endpoint und Credential aus vertrauenswürdiger Konfiguration stammen. Der Skill selbst darf diese Parameter nicht überschreiben. Ein Providerfehler muss als fehlende Coverage sichtbar bleiben.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Funktional Gleichstand. Beide bieten einen nativen Anthropic-Pfad. Für Security Reviews zählt vor allem, dass der Provider in beiden Fällen eine optionale zweite Analyseebene bleibt und nicht den deterministischen Scan ersetzt.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
