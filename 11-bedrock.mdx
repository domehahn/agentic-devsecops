Für Unternehmen ist AWS Bedrock interessant, weil Modellzugriff in bestehende AWS-Identitäten, Regionen, Audit- und Netzwerkmodelle eingebettet werden kann. Ein Security Scanner muss dann keinen separaten API-Key für einen externen LLM-Dienst verwalten.

Das verschiebt die Trust Boundary jedoch in IAM, AWS-SDK-Credential-Chains und Regionskonfiguration.

<Architecture>
Bedrock ersetzt einen API-Key durch Cloud Identity. Das ist kein Wegfall der Trust Boundary, sondern eine Verschiebung in IAM, Region und Workload Credentials.
</Architecture>

## Was das Feature wirklich bedeutet

Bedrock-Integration sollte native SigV4-Signierung verwenden und keine selbstgebauten Credential-Mechanismen erfinden. Gleichzeitig muss verhindert werden, dass ein gescannter Skill beeinflusst, welches Profil, welche Region oder welches Modell verwendet wird.

Die semantische Analyse bleibt externe Verarbeitung, auch wenn sie innerhalb der eigenen Cloud-Governance stattfindet.

## SkillSpector

SkillSpector unterstützt `bedrock` nativ. Die Konfiguration verwendet `AWS_PROFILE` optional sowie `AWS_REGION`; die Standard-Credential-Chain wird über `boto3` genutzt. Als Modell können Bedrock Model IDs oder passende Inference-Profile gewählt werden.

Damit fügt sich der Scanner in vorhandene AWS-Identity-Mechanismen ein.

## `skil`

Auch `skil` besitzt einen Bedrock-Provider. Die Dokumentation nennt die Standard-AWS-SDK-Credential-Chain und native SigV4-Signierung. Region und Modell werden explizit konfiguriert, während der semantische No-Tools-Vertrag erhalten bleibt.

Die Provider-Coverage wird separat ausgewiesen, sodass ein Bedrock-Ausfall nicht wie ein erfolgreicher semantischer Scan erscheint.

## Praxisbeispiel

```bash
# SkillSpector
export SKILLSPECTOR_PROVIDER=bedrock
export AWS_REGION=eu-central-1
skillspector scan ./skill

# skil
skil scan ./skill   --semantic   --semantic-provider bedrock   --semantic-region eu-central-1   --semantic-model anthropic.claude-3-7-sonnet
```

In CI sollte eine dedizierte IAM-Rolle ausschließlich die benötigte `bedrock:InvokeModel`-Berechtigung für freigegebene Modelle erhalten.

## Security- und DevSecOps-Einordnung

- Dedicated IAM Role statt Entwicklerprofil verwenden.
- Region und freigegebene Modelle über Pipeline-Policy festlegen.
- Instance-/Workload-Credentials mit Least Privilege konfigurieren.
- CloudTrail beziehungsweise Provider-Audit mit Scan-Evidence korrelieren.
- Bedrock-Ausfall als Coverage-Degradation behandeln.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

## Typische Fehlinterpretation

„Bedrock bedeutet, dass keine Secrets mehr existieren.“ API-Keys können entfallen, aber Workload Credentials, IAM-Rollen und Session Tokens bleiben hochsensible Identitäten.

## Einordnung in die Pipeline

Dieses Feature gehört in eine **optionale semantische Analyse-Stufe hinter dem deterministischen Gate**. So bleiben Pull-Request-Checks schnell und reproduzierbar, während modellgestützte Analyse gezielt für risikoreiche Skills, Release-Kandidaten oder Nightly-Scans zugeschaltet werden kann.

Pipeline-seitig sollten Provider, Modell, Endpoint und Credential aus vertrauenswürdiger Konfiguration stammen. Der Skill selbst darf diese Parameter nicht überschreiben. Ein Providerfehler muss als fehlende Coverage sichtbar bleiben.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Beide unterstützen Bedrock nativ. Die Architekturfrage liegt weniger im Scanner als in der Cloud-Governance: Welcher Workload darf welches Modell in welcher Region mit welchen Daten aufrufen?

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
