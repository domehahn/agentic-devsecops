Containers are often used as the final safety boundary around an AI agent that can execute generated code. That makes container configuration part of the agent's security model, not merely an operations detail. A workload that is nominally “sandboxed” but runs privileged, shares host namespaces, mounts sensitive host paths, or receives broad Linux capabilities can lose much of the isolation the surrounding architecture assumes.

The property addressed here is not a claim that every privileged container is already escaped. It is a more precise relation:

```text
CONTAINER_CONFIG
  -> WEAKEN_ISOLATION(
       privileged |
       host_namespaces |
       dangerous_capabilities |
       sensitive_host_mounts
     )
```

The security concern is **precondition creation**. Unsafe configuration can turn a subsequent software bug, malicious dependency, prompt injection, or agent mistake into host-level impact that would otherwise have been contained.

## Isolation is a stack of boundaries

A container is not one security mechanism. Its isolation emerges from multiple layers:

```text
application process
      ↓
UID / GID and capabilities
      ↓
seccomp / AppArmor / SELinux policy
      ↓
mount namespace
      ↓
PID / IPC / network namespaces
      ↓
cgroups and resource limits
      ↓
container runtime
      ↓
host kernel
```

Weakening several layers at once can collapse the effective boundary even if the workload is still technically “inside a container.” Kubernetes' Pod Security Standards make this explicit: the Restricted profile disallows privileged containers, requires privilege-escalation controls, restricts host namespaces and hostPath volumes, and requires dropping broad capabilities.[^k8s-pss]

For agentic execution, this is especially important because the workload may intentionally run code that did not exist when the platform was deployed.

## A safe scanner-positive configuration fixture

A static test does not need an exploit. It only needs to express the dangerous authority configuration:

```yaml
securityContext:
  privileged: true
  capabilities:
    add:
      - SYS_ADMIN
hostPID: true
```

Each element weakens a distinct isolation mechanism. A finding should explain those elements separately rather than collapsing them into an opaque “container escape” label.

A safer counterpart is structural:

```yaml
securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  capabilities:
    drop:
      - ALL
```

That configuration is not a complete sandbox by itself, but it demonstrates the polarity the detector must understand.

## `SKIL-BOUNDARY-CONTAINER-ESCAPE` should report the precondition, not an invented exploit

The current `skil` matrix maps privileged workload / container-escape conditions to `SKIL-BOUNDARY-CONTAINER-ESCAPE`.[^skil-matrix] The strongest interpretation is architectural: the analyzer observes configuration that reduces the separation between agent workload and host.

A useful intermediate representation can be modeled as:

```yaml
isolation_effects:
  privileged_container: true
  host_pid: true
  host_network: false
  host_ipc: false
  added_capabilities:
    - SYS_ADMIN
  host_root_mount: false
assessment:
  isolation_weakened: true
  successful_escape_observed: false
```

This distinction avoids a common security-reporting error: describing a dangerous precondition as if exploitation had already occurred.

## Why `privileged: true` is qualitatively different from ordinary container execution

Privileged mode is not just “more permissions.” It changes the relationship between the container and the host's security mechanisms. Docker's security documentation and Kubernetes' privileged-container guidance both treat privileged execution as a substantial weakening of confinement.[^docker-security][^k8s-pss]

For an agentic runtime, that creates two separate risks:

1. **generated code gains unnecessary authority**, and
2. **the model may be able to request or preserve that authority through configuration changes**.

The second risk is important. A CI pipeline that allows an agent to edit its own deployment manifest can convert a code-generation task into an infrastructure-policy mutation unless admission controls enforce independent constraints.

## Linux capabilities: avoid both extremes

Containers normally operate with a bounded set of Linux capabilities rather than full root authority. The security mistake is often not simply “running as root” but granting a capability set that enables operations unrelated to the task.

`SYS_ADMIN` is particularly broad and should receive strong scrutiny. Yet the correct policy is not “all capabilities are malicious.” Network diagnostics, low-level observability, or specialized system workloads may legitimately require individual capabilities.

A capability-aware decision should ask:

```text
required capability set
      vs.
requested capability set
      vs.
effective capability set at runtime
```

If the requested set exceeds the requirement, this article's property composes naturally with **Excessive Permissions**.

## Host namespaces reduce separation in different ways

Sharing host namespaces changes what the container can observe or interact with.

### Host PID namespace

The process boundary becomes more transparent because the workload can see host processes. That may expose metadata and can interact with other privilege mechanisms.

### Host network namespace

Network isolation is reduced. Services bound only to host-local interfaces may become reachable from the workload.

### Host IPC namespace

IPC resources can cross a boundary that the platform may have assumed was isolated.

These settings are not interchangeable. Findings should preserve exactly which boundary was weakened instead of assigning one generic severity.

## Host mounts can invalidate an otherwise strong sandbox

A container may be non-root and still receive a dangerous host mount. The effective security boundary depends on **what data and control objects enter the mount namespace**.

Examples of high-risk classes include:

- container runtime control-plane sockets,
- host root or broad host filesystem trees,
- credential directories,
- orchestration credentials,
- sensitive device nodes.

The scanner should reason about mount source, mount target, read/write mode, and intended purpose. A read-only project source mount is materially different from a writable broad host mount.

<Architecture>
Agent request → deployment manifest → admission policy → hardened sandbox → restricted mounts/capabilities → execution
</Architecture>

## Admission control is stronger than asking the model to preserve isolation

Agentic infrastructure needs a non-model authority that decides which workload configurations are admissible.

A strong policy can enforce:

- `privileged: false`,
- `allowPrivilegeEscalation: false`,
- non-root identities,
- no host PID/IPC/network unless explicitly approved,
- a minimal capability allowlist,
- restricted volume types and paths,
- seccomp and LSM policies,
- resource limits,
- read-only root filesystems where compatible.

Kubernetes' Pod Security Standards provide a practical baseline vocabulary for these controls.[^k8s-pss]

The crucial principle is independence. The same agent that generates a deployment should not be able to waive the platform policy that constrains the deployment.

## Sandboxing generated code requires defense in depth

No single container setting should be treated as sufficient for hostile or uncertain code. Depending on the threat model, stronger isolation may involve:

- dedicated worker nodes,
- microVMs or VM-backed sandboxes,
- user namespaces,
- rootless container engines,
- kernel hardening and mandatory access control,
- strict egress filtering,
- ephemeral filesystems,
- no production credentials,
- per-run identities and quotas.

This is an engineering trade-off between isolation strength, startup latency, density, observability, and developer experience. The correct choice depends on the authority available to the agent and the sensitivity of the surrounding infrastructure.

## Configuration provenance matters

In agentic workflows, the dangerous manifest may be assembled from multiple sources:

```text
base chart
  + environment overlay
  + generated patch
  + CI variables
  + admission mutation
  = effective workload
```

Static analysis of one YAML file may therefore be insufficient. A mature control should record whether it inspected source configuration or the fully rendered deployment representation.

Evidence can include:

```yaml
property: privileged-workload
controls:
  - SKIL-BOUNDARY-CONTAINER-ESCAPE
observations:
  privileged: true
  host_namespaces:
    pid: true
  added_capabilities:
    - SYS_ADMIN
configuration_stage: rendered_manifest
runtime_state: not_observed
```

This avoids pretending that source-level configuration is identical to runtime state.

## Interaction with Docker-socket access

The previous property and this one should remain distinct:

- **Docker Socket Access**: the agent can reach a container-management control plane.
- **Privileged Workload / Escape Preconditions**: a workload is configured with weakened isolation.

When both occur on the same execution path, the risk model can raise the priority. But a scanner should not infer one merely from the other.

## False-positive discipline

Security documentation, policy tests, and Kubernetes admission rules will naturally contain strings such as `privileged: true`. Context is therefore essential.

The analyzer should distinguish:

```text
policy denies privileged=true     → defensive context
unit test asserts rejection       → test context
deployment requests privileged    → strong candidate
comment explains privileged risk  → documentation context
```

The same literal can mean opposite things depending on its syntax and role.

## Runtime telemetry and drift

Deployment-time policy does not eliminate the need for runtime observability. Useful signals include:

- workloads launched with unexpected capabilities,
- namespace-sharing changes,
- new sensitive host mounts,
- changes to seccomp/LSM profiles,
- execution on nodes outside the approved sandbox pool,
- admission-policy bypass or break-glass events.

Drift detection is particularly important when agentic automation can modify infrastructure continuously.

## Validation should use a matrix, not one manifest

A serious regression corpus should include:

- privileged workload enabled/disabled,
- individual capability additions,
- `drop: [ALL]` with narrow add-backs,
- host PID/network/IPC independently,
- sensitive versus project-scoped mounts,
- read-only versus writable mounts,
- rootless/non-root contexts,
- defensive policy documents,
- rendered versus source manifests,
- combinations with runtime-socket exposure.

The oracle should check both the finding and the reason it was emitted.

## Limits of static analysis

A repository scan cannot normally prove:

- the effective kernel configuration,
- whether seccomp or LSM enforcement is active,
- what a dynamically provisioned mount points to,
- whether the host runtime is rootless,
- whether an admission controller will mutate or reject the workload,
- whether a kernel/runtime vulnerability exists or is exploitable.

Accordingly, the correct finding is **isolation weakened by configuration**, not “container escaped.”

<KeyTakeaway>
A container is useful as an agent sandbox only while the configuration preserves the boundaries the architecture relies on. Privileged mode, host namespaces, broad capabilities, and sensitive host mounts should be treated as explicit reductions of isolation and enforced by an independent admission layer rather than by model instructions.
</KeyTakeaway>

## Conclusion

Privileged workload detection is a control over the *preconditions of escape*, not a claim that exploitation has occurred. A precise implementation identifies exactly which isolation layers are weakened, compares them with the task's capability requirements, and preserves runtime uncertainty. The platform should then enforce hardened execution independently through admission policy, sandbox architecture, constrained mounts, minimal capabilities, and dedicated identities.
