Eine generische Remote-URL klingt nach einem kleinen Komfortfeature: URL einfügen, Datei herunterladen, scannen. In einem Security Scanner ist dieser Komfort jedoch mächtig. Jede frei beeinflussbare URL kann den Scanner in einen HTTP-Client verwandeln, der möglicherweise aus einem privilegierten CI-Netz auf interne Dienste zugreifen kann.

Deshalb ist „Remote URL unterstützt“ keine rein funktionale Aussage, sondern eine Aussage über das Netzwerk-Trust-Modell.

<Architecture>
Remote Input ist eine Capability. Der Loader sollte sie so behandeln wie einen privilegierten Tool-Aufruf: explizit, begrenzt und auditierbar.
</Architecture>

## Was das Feature wirklich bedeutet

Ein gehärteter Remote-Loader sollte Hostnamen validieren, DNS-Auflösung prüfen, private und reservierte Ziele blockieren, Redirects kontrollieren, Downloadgrößen limitieren und Credentials in URLs ablehnen. Wichtig ist außerdem, welche Dateitypen akzeptiert werden.

Je generischer die Eingabe, desto mehr muss die Implementierung die Bedeutung des Inhalts erst nach dem Download bestimmen.

## SkillSpector

SkillSpector besitzt einen direkten File-URL-Pfad. URLs, die nicht als Git-Repository klassifiziert werden, können als Datei heruntergeladen werden. Der aktuelle Code begrenzt Download-Hosts auf eine Allowlist, blockiert private/reservierte IPs und folgt keinen Redirects. ZIP-Inhalte können anhand von Dateiname oder Content-Type entpackt werden.

Damit ist SkillSpector flexibler als ein Modell, das ausschließlich definierte Remote-Archive erlaubt – allerdings innerhalb einer bewusst eingeschränkten Hostliste.

## `skil`

`skil` hält die Remote-Oberfläche kleiner. Öffentliche HTTPS-Quellen benötigen `--allow-remote`; als Download-Artefakte werden ZIP, TGZ und `tar.gz` erkannt. Andere HTTPS-Ziele werden als Git-Quelle behandelt und unter Git-spezifischen Regeln verarbeitet.

Eine beliebige Raw-Datei-URL ist damit nicht dieselbe First-Class-Eingabe wie bei SkillSpector. Die Einschränkung reduziert Mehrdeutigkeit und Netzwerkfläche.

## Praxisbeispiel

```bash
# SkillSpector: direkte Datei auf einem erlaubten Download-Host
skillspector scan https://raw.githubusercontent.com/acme/skill/main/SKILL.md --no-llm

# skil: bevorzugt lokales Artefakt oder explizites Remote-Archiv/Git
skil scan https://example.org/releases/skill.tgz --allow-remote --static-only
```

Für einen zentralen Security Service kann die restriktivere Variante attraktiv sein. Für interaktive Analysen einzelner öffentlich gehosteter Dateien ist die Flexibilität von SkillSpector bequemer.

## Security- und DevSecOps-Einordnung

- Remote-URLs niemals ungeprüft aus Pull-Request-Inhalt übernehmen.
- Redirects und DNS-Rebinding berücksichtigen, nicht nur die ursprüngliche URL parsen.
- Download-Limits vor dem vollständigen Einlesen erzwingen.
- Netzwerk-Egress des Scanner-Containers zusätzlich infrastrukturell begrenzen.
- URL-Credentials und interne Hostnamen ablehnen.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

| Aspekt | SkillSpector | `skil` |

| Bewertung | SkillSpector flexibler | SkillSpector flexibler |

**Bewertung aus der Vergleichsmatrix:** SkillSpector flexibler.

## Typische Fehlinterpretation

„Wenn die URL HTTPS verwendet, ist sie sicher.“ HTTPS schützt die Verbindung, nicht das Ziel. Ein HTTPS-Aufruf an einen internen Metadata-Service oder ein unerwartetes Redirect-Ziel kann weiterhin sicherheitskritisch sein.

## Einordnung in die Pipeline

Dieses Feature gehört in die **Ingestion-Stufe** der Pipeline. Bevor Analyzer oder Policies überhaupt laufen, muss klar sein, welches Artefakt gelesen wird, wie es kanonisiert wird und welche zusätzlichen Fähigkeiten – insbesondere Netzwerk – dafür notwendig sind.

Ein belastbares Muster ist: Input auflösen → Digest/Manifest erzeugen → statisch analysieren → Report/Evidence speichern. Bei Remote-Eingaben sollte der Netzwerkzugriff in einem eigenen Job oder Runner-Profil aktiviert werden.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

SkillSpector ist bei direkten Remote-Dateien flexibler. `skil` ist absichtlich enger und fordert Remote-Zugriff explizit an. Für Security Services ist Restriktion häufig ein Vorteil; für Ad-hoc-Analysen kann die zusätzliche Flexibilität produktiver sein.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
