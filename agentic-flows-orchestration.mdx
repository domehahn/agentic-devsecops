# Agentic Flows: Orchestrating Intelligent Work

A single agent can be impressive.

A production process needs more than intelligence.

It needs state, ordering, recovery, control points and audit.

This is the domain of the **flow**.

Skills define reusable capabilities.

Agents make context-dependent decisions.

Flows turn those decisions into a controlled process.

## Why Long Tasks Need an External Skeleton

Imagine:

```text
understand issue
→ inspect repository
→ plan
→ implement
→ test
→ security review
→ create merge request
```

A sufficiently capable agent could try to manage everything in one autonomous loop.

The problem is operational: long tasks create context growth, goal drift, repeated work, failed tools and resumability requirements.

A flow externalizes the macro structure.

## Macro Process Versus Micro Process

```text
Flow:
  defines major stages

Agent:
  decides within stage
```

For `Analyze Repository`, the flow need not specify every file.

The agent can decide where to search, which skill to load and which tool to use.

This preserves adaptability without surrendering lifecycle control.

## Flows as State Machines

A flow can be modeled explicitly:

```text
RECEIVED
  ↓
ANALYZING
  ↓
PLANNING
  ↓
IMPLEMENTING
  ↓
VERIFYING
  ├─ fail → IMPLEMENTING
  └─ pass → REVIEW
```

This gives explicit states, transitions and terminal conditions.

Model inference becomes one kind of transition logic rather than the whole architecture.

## Graphs Generalize State Machines

Graphs allow branching, loops, parallelism and joins.

LangGraph provides graph-based long-running stateful workflows and supports persistence and Human-in-the-Loop.[^1]

CrewAI Flows provides structured event-driven workflows around agents and crews.[^2]

The concepts are framework-independent.

## Deterministic Steps Should Stay Deterministic

A flow may contain LLM planning, shell execution, unit tests and approval.

Do not route every step through an LLM.

```text
Run tests
```

should call the test runner directly.

```text
Interpret why tests failed
```

may require a model.

## Flow State Is More Reliable Than Conversation History

State should be structured:

```yaml
task:
  goal: ...
  stage: verifying
  branch: fix/auth
  tests:
    passed: false
  approvals: []
```

Model context can be rebuilt from state.

This is more reliable than inferring state from a long conversation.

## Checkpoints Make Autonomy Operable

Long tasks must survive worker restarts, network outages and human delay.

Checkpointing stores state after meaningful steps.

This enables resumption and fault tolerance.

## Idempotency

A resumed flow may re-run a step.

Tools should be idempotent or use operation IDs.

Bad:

```text
create issue
```

retried twice creates duplicates.

Better:

```text
create issue idempotency_key=run-184-step-7
```

## Retry Policy Belongs to the Flow

The model can semantically decide to retry.

The runtime should limit retries mechanically.

```yaml
retry:
  max_attempts: 3
  backoff: exponential
```

## Human-in-the-Loop as a Transition

Approval should be modeled explicitly:

```text
READY_TO_DEPLOY
   ↓
WAITING_FOR_APPROVAL
   ↓ approved
DEPLOYING
```

Human intervention is a workflow state, not a blocking chat prompt.

## Skills Fit Inside Flows

```text
SECURITY_REVIEW
   ↓
load security-review skill
   ↓
agent executes procedure
   ↓
structured findings
```

This keeps procedures reusable.

## Multi-Agent Flows

Multiple agents can be useful when roles require independent context, tools, separation of duties or parallelism.

Example:

```text
Planner
  ├─ Coder
  ├─ Security Analyst
  └─ Test Analyst
       ↓
Reviewer
```

But multi-agent design adds coordination cost.

Do not create agents merely to imitate job titles.

## Parallelism

Some tasks can run concurrently:

```text
after implementation:
├─ unit tests
├─ SAST
└─ dependency scan
```

A flow can join the results.

## Handoffs Need Contracts

Pass structured state between agents:

```yaml
handoff:
  objective: review patch
  artifact: commit-sha
  constraints:
    - read_only
  expected_output: findings_schema
```

Do not rely only on a vague natural-language summary.

## Observability Becomes Non-Negotiable

A flow produces a trajectory:

```text
stage
model call
tool call
result
branch
approval
retry
```

Useful questions include which stage consumes time, where failures cluster, and which approvals are rejected.

## Flows as a Governance Boundary

Flows can encode mandatory lifecycle structure:

```text
code change
→ tests
→ security scan
→ review
→ merge
```

The model cannot skip required stages.

This is stronger than telling it to “always perform security review.”

## Flow Versioning

A flow is executable policy.

Version graph, prompts, skills, tool contracts and thresholds.

A run should identify which flow version executed.

## Agentic Flow Versus BPM Workflow

Traditional BPM and agentic flows overlap.

The difference is that agentic flows embed probabilistic decision nodes.

Both still benefit from state and audit.

Agentic flows are evolutionary, not a complete replacement for workflow engineering.

## Compensation and Saga Patterns

Agentic flows often touch systems without distributed transactions.

Suppose:

```text
create cloud resource
→ update ticket
→ notify user
```

If the ticket update fails after resource creation, define compensation where possible.

```text
create resource
compensation: delete resource
```

Not every side effect is reversible, so compensation must be explicit.

## Concurrency and Shared State

Parallel branches can race.

Example:

```text
Agent A edits config
Agent B edits same config
```

Use deterministic concurrency control such as locks, optimistic versions or merge strategies.

An LLM may assist semantic conflict resolution but should not replace the underlying concurrency mechanism.

## Flow-Level Security Invariants

Some edges should be structurally impossible.

A production deployment may require passing through:

```text
TESTED
SECURITY_CHECKED
APPROVED
```

Encoding this in topology makes governance structural.

## Testing a Flow

Test nodes, transitions, failure injection, resume behavior and policy bypass attempts.

A production flow should have CI like application code.

## State Migration

Long-running workflows may resume after software upgrades.

Version state schemas and test migrations.

## Operational SLOs

Track run completion rate, time in each state, waiting-for-human duration, retry rate and resume failures.

This turns flow orchestration into an SRE-managed service.

## DevSecOps Example

```text
Issue
 ↓
Agent understands requirement
 ↓
Flow checks repository
 ↓
Agent proposes plan
 ↓
Approval if architecture-sensitive
 ↓
Agent implements in sandbox
 ↓
CI runs deterministically
 ↓
Security tools run
 ↓
Agent interprets failures
 ↓
Flow gates merge request
```

## Conclusion

A flow answers a question an agent alone cannot answer reliably:

> How should intelligent actions be assembled into a durable, controlled process?

The strongest architecture separates:

```text
Flow = macro control
Agent = contextual decision
Skill = reusable procedure
Tool = effect
Policy = authority
```
