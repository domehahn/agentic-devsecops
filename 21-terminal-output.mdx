Der Terminal-Report ist für Entwickler oft die erste Begegnung mit einem Scanner. Wenn Findings unverständlich, zu laut oder schlecht priorisiert sind, wird das Security Tool ignoriert – unabhängig davon, wie gut seine Detection Engine ist.

Human-readable Output ist deshalb ein Teil der Wirksamkeit eines Security Controls.

<Note>
Ein Terminal-Report ist ein Human Interface für Security Evidence. Lesbarkeit und sichere Darstellung beeinflussen, ob Findings tatsächlich bearbeitet werden.
</Note>

## Was das Feature wirklich bedeutet

Ein guter Terminal-Report sollte Severity, Regel, Datei, Zeile, Evidenz und Handlungsempfehlung schnell erfassbar machen. Gleichzeitig müssen untrusted Strings aus dem Skill neutralisiert werden, damit ANSI-Sequenzen oder Steuerzeichen das Terminal nicht manipulieren.

Für CI braucht die CLI außerdem stabile Exit Codes.

## SkillSpector

SkillSpector bietet Terminal als Standardformat und beschreibt die Ausgabe als „pretty formatted“. Das passt zum interaktiven lokalen Scan: Entwickler bekommen Befunde direkt ohne zusätzlichen Reportparser.

Andere Formate können parallel für Maschinenintegration verwendet werden.

## `skil`

`skil` besitzt einen detaillierten Terminal-Report sowie einen `--compact`-Modus für eine klassische Ein-Zeile-pro-Finding-Darstellung. Die Dokumentation betont transparente Scores, Coverage und Inspection Ledger. Stabile Exit Codes trennen Security-Fail, Input/Config-Fehler und interne Fehler.

Das erleichtert sowohl Menschen als auch Shell-/CI-Steuerung die Interpretation.

## Praxisbeispiel

```bash
skillspector scan ./skill --no-llm

skil scan ./skill --static-only
skil scan ./skill --static-only --compact
```

Ein lokaler Entwickler nutzt die ausführliche Darstellung zur Ursachenanalyse. Ein CI-Log kann dagegen den kompakten Modus bevorzugen, während der vollständige JSON- oder SARIF-Report als Artefakt gespeichert wird.

## Security- und DevSecOps-Einordnung

- Untrusted Dateinamen und Finding-Texte terminal-sicher rendern.
- Severity nicht als einzige Priorisierung verwenden; Evidenz und Confidence zeigen.
- Exit Codes dokumentieren und in Pipeline-Gates explizit auswerten.
- Maschinenreport zusätzlich zum Terminal-Log archivieren.

In einer professionellen Pipeline sollte dieses Feature nicht isoliert bewertet werden. Entscheidend ist, ob Eingabe, Analyse, Report und nachgelagerte Policy dieselbe Vertrauenskette bilden. Ein positives Ergebnis ist nur so belastbar wie der dokumentierte Analyseumfang und die Identität des tatsächlich gescannten Artefakts.

## Direkter Vergleich

| Aspekt | SkillSpector | `skil` |
| --- | --- | --- |
| Feature vorhanden | ja | ja |
| Schwerpunkt | Integration und Scanner-Ergonomie | explizite Trust Boundaries und Evidence |
| Bewertung | gleich | gleich |

**Bewertung aus der Vergleichsmatrix:** gleich.

## Typische Fehlinterpretation

„Terminal ist nur Darstellung.“ Untrusted Steuerzeichen, instabile Exit Codes oder unlesbare Findings können die Wirksamkeit des gesamten Controls schwächen.

## Einordnung in die Pipeline

Dieses Feature gehört in die **Reporting- und Integrationsstufe**. Ein guter Pipeline-Lauf erzeugt mindestens eine menschenlesbare Sicht und eine maschinenlesbare Evidence. So können Entwickler Findings verstehen, während Policy Engines und Dashboards stabile Strukturen konsumieren.

Das Ausgabeformat darf nicht bestimmen, ob ein Gate greift: Exit Code, strukturierter Status und Policy-Ergebnis sollten die technische Entscheidung tragen.

## Review-Fragen

Vor einer produktiven Nutzung dieses Features würde ich mindestens folgende Fragen beantworten:

- **Welche neue Capability wird aktiviert?** Ist es nur Dateilesen oder kommen Netzwerk, Provider, externe Engine oder Agent-Tooling hinzu?
- **Wer kontrolliert die Konfiguration?** Sie sollte aus vertrauenswürdiger CI-/Security-Konfiguration stammen und nicht aus dem zu prüfenden Skill.
- **Wie wird fehlende Coverage sichtbar?** Ein nicht ausgeführter Analyzer oder ein Providerfehler darf nicht wie „kein Risiko gefunden“ aussehen.
- **Woran ist der Report gebunden?** Idealerweise an Artefakt-Digest, Scanner-Version und die verwendeten Analyseoptionen.
- **Welche Entscheidung folgt aus dem Ergebnis?** Review, Block, Baseline oder reine Information sollten explizit und nachvollziehbar sein.

## Fazit

Beide bieten eine geeignete Terminal-Ausgabe. `skil` differenziert mit Detail- und Compact-Modus sowie expliziten stabilen Exit Codes; SkillSpector liefert ebenfalls eine auf Entwickler ausgerichtete Standarddarstellung.

<KeyTakeaway>
Die relevante Frage lautet nicht nur, ob ein Scanner das Feature besitzt, sondern **welche zusätzliche Capability und welche neue Trust Boundary dadurch entsteht**.
</KeyTakeaway>
