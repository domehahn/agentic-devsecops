Most users do not read every configuration option. Most automation does not negotiate with every library default. The first configuration that works often becomes the configuration that survives into production.

That is why **defaults are security decisions**.

The source property focuses on known cases where transport or authenticity controls are disabled by default:

```text
SECURITY_CONTROL(TLS_AUTH_VERIFY) = DISABLED_BY_DEFAULT
```

with `SKIL-TRANSPORT-INSECURE` as the documented control.

The larger lesson extends beyond TLS. An unsafe default exists whenever the system enters a materially weaker security state **without an explicit, informed opt-in**.

<KeyTakeaway>
Secure-by-default design shifts the burden of proof. Users must deliberately weaken a control instead of deliberately discovering and enabling the safe state.
</KeyTakeaway>

## The source-positive example

```python
requests.get(url, verify=False)
```

This explicitly disables certificate verification for the request.

The security effect is concrete: the client is no longer validating the server’s TLS identity in the normal way.

A useful finding:

```yaml
property: unsafe-defaults
control: SKIL-TRANSPORT-INSECURE
api: requests.get
option: verify
value: false
effect: tls_peer_verification_disabled
relation: SECURITY_CONTROL(TLS_AUTH_VERIFY) = DISABLED_BY_DEFAULT
confidence: high
```

## The source-negative example

```python
requests.get(url, timeout=5)  # TLS verification remains enabled by default
```

This keeps the library’s secure verification behavior and adds a resource bound.

A detector should not flag the request merely because `verify` is absent. In this API, absence means the safer default.

That is a critical context rule.

## Secure defaults are about expected operator behavior

A control is not truly “default” only because a library has a default constant.

Consider a product that ships:

```yaml
tls_verify: true
```

but its installation guide tells every user to set:

```yaml
tls_verify: false
```

The operational default is insecure even if the code default is technically secure.

Security review should therefore consider:

- code defaults;
- packaged config;
- templates;
- examples;
- documentation;
- environment overlays;
- Helm charts;
- Terraform modules;
- and startup flags.

## Configuration precedence creates hidden weakening

Modern systems merge configuration from multiple layers:

```text
built-in default
   ↓
config file
   ↓
environment variables
   ↓
command-line flags
   ↓
remote policy
```

A secure value at one layer can be overwritten later.

A scanner that sees only `verify: true` in the base file may miss:

```text
TLS_VERIFY=false
```

in deployment configuration.

A strong verification system computes the **effective configuration** when possible.

## Fail-open versus fail-closed

Unsafe defaults also appear in failure semantics.

Suppose an approval service is unreachable.

Fail-open behavior:

```text
approval service unavailable
→ proceed automatically
```

Fail-closed behavior:

```text
approval service unavailable
→ block high-impact action
```

There are availability trade-offs, but high-risk operations often need fail-closed semantics.

The same reasoning applies to:

- policy engine outages;
- signature verification failures;
- scanner errors;
- missing identity metadata;
- and incomplete tool schemas.

## Authentication defaults

Examples of risky defaults include:

```text
anonymous access enabled
wildcard tenant
guest role with write access
development API key accepted in production
```

Not every such case belongs to `SKIL-TRANSPORT-INSECURE`, but they belong to the broader secure-defaults discipline.

The key pattern is:

```text
absence of explicit configuration
→ unexpectedly permissive behavior
```

## Agentic systems magnify default risk

Agents explore available capabilities automatically.

A human may never click an obscure “dangerous operation” button. An agent can discover and use a permissive tool because the interface exists.

Therefore a capability that is “available but usually not used” is more consequential in an agentic environment.

Default tool sets should be minimal, and high-impact operations should require explicit grants.

## Development convenience is a recurring source of unsafe defaults

Local development frequently needs shortcuts:

- self-signed certificates;
- disabled auth;
- broad CORS;
- wildcard permissions;
- mock credentials;
- permissive sandboxes.

The danger is configuration drift into production.

A strong pattern separates profiles:

```text
dev -> permissive but visibly marked
test -> deterministic
prod -> secure, no automatic fallback to dev
```

Production should never silently adopt a development fallback because a secret or certificate is missing.

## Static detection design

`SKIL-TRANSPORT-INSECURE` can identify known patterns such as:

```text
verify=false
--insecure
certificate checks disabled
```

A higher-level verifier can also inspect:

- defaults in schemas;
- Docker/Helm environment values;
- Terraform variables;
- startup flags;
- and config precedence.

The scanner should distinguish:

```text
insecure option set
```

from:

```text
documentation saying do not set insecure option
```

## False positives

Important negative cases include:

- disabling verification only against a local test server inside a test fixture;
- code that explicitly rejects `verify=False`;
- documentation examples of insecure configurations;
- a variable named `insecure` that controls unrelated behavior;
- or mocks that do not perform network communication.

Context, environment, and execution path matter.

## A useful default hierarchy

For security-sensitive settings, design defaults according to:

```text
safe
bounded
least privilege
explicit
observable
recoverable
```

For example:

```yaml
network:
  egress: deny
tls:
  verify: true
tools:
  allowed: []
approvals:
  destructive_actions: required
limits:
  retries: 3
  timeout_seconds: 30
```

The exact values vary by system. The direction is what matters.

## Make unsafe overrides noisy

Some insecure settings are occasionally necessary for diagnostics.

If allowed, they should be difficult to activate accidentally:

- explicit command-line flag;
- startup warning;
- environment restriction;
- expiration;
- audit event;
- refusal in production mode.

An override such as `--insecure` should not be silently inherited.

## Version upgrades can change defaults

Dependency upgrades may alter behavior.

A configuration omitted because version N used a secure default may behave differently in version N+1.

This is why release review and effective-config tests matter.

Security assertions should ideally be pinned to tested versions.

## Evidence and coverage

A strong finding states what was observed:

```yaml
property: unsafe-defaults
control: SKIL-TRANSPORT-INSECURE
setting:
  name: verify
  value: false
context: runtime_call
coverage:
  local_call: verified
  external_proxy_tls: not_observable
confidence: high
```

It does not claim more than the static evidence supports.

## Deep dive: defaults should be tested as product behavior

Security teams often review configuration files but do not test the “zero-configuration” path.

A valuable CI test starts the component with the minimum documented configuration and asserts:

```text
TLS verification enabled
authentication required
network egress constrained
dangerous tools disabled
destructive actions gated
resource limits finite
```

This tests the *effective default*, including merged configuration and startup code.

### Configuration drift detection

Runtime configuration can be hashed or exported into an effective-policy snapshot.

Operators can compare:

```text
reviewed effective config
vs
running effective config
```

and alert on weakening changes.

### Safe fallback hierarchy

Fallback logic deserves the same scrutiny as defaults.

Unsafe:

```text
if TLS config fails:
    retry without verification
```

Safe:

```text
if TLS config fails:
    fail startup / mark unhealthy
```

The system should not translate misconfiguration into silent insecurity.

### Explicit development exceptions

When insecure modes are necessary locally, make them self-limiting:

```text
allowed only on loopback
allowed only in dev build
expires after one hour
cannot coexist with production credentials
emits high-visibility warning
```

This reduces accidental promotion into production.

### Default permissions for tools

Agentic runtimes should ideally begin with no high-impact tools:

```text
default tool set = minimal
```

Capabilities are added based on task policy.

This is safer than exposing every installed tool and relying on the model to use restraint.

## Unsafe defaults in tool and agent configuration

Agentic platforms introduce new default choices:

```text
all installed tools visible
tool execution automatic
approval optional
network egress open
workspace mount includes home directory
memory persistence enabled
trace payloads captured in full
```

Each may be convenient. Together they can create an unexpectedly powerful runtime.

A secure baseline often chooses:

```text
minimal tools
read-only where possible
no external egress by default
task-scoped workspace
explicit persistence
payload-minimized tracing
approval for irreversible actions
```

### Defaults in templates matter

Teams frequently bootstrap applications from example manifests.

If an official example uses broad permissions “for simplicity,” that example can become the de facto production default.

Security review should therefore include starter templates and copy-paste documentation.

### Default-deny capability discovery

A strong tool registry can distinguish:

```text
installed
discoverable
authorized
```

A tool may exist in the platform without being visible or callable by a given agent.

This prevents “installation” from implicitly granting authority.

### Safe degradation

When a secure subsystem fails, the platform should define what functionality remains.

Example:

```text
policy engine unavailable
→ read-only informational mode
```

rather than:

```text
policy engine unavailable
→ allow all so work can continue
```

Graceful degradation can preserve availability without discarding security.

### Change control for default values

A one-line default change can affect every newly deployed agent.

Treat security-relevant defaults like API changes:

- document them;
- test migration behavior;
- alert on weakened values;
- and require review for permissive transitions.

The risk of a default scales with how many users will accept it without noticing.

## Final perspective

Unsafe Defaults are rarely spectacular. That is exactly why they matter.

They convert extraordinary risk into ordinary operation.

`SKIL-TRANSPORT-INSECURE` provides a concrete control for known insecure transport configurations. The broader design principle is:

> **The path requiring the least user effort should also be the path with the strongest reasonable security posture.**

The review question is:

> **What happens if an operator deploys this component without understanding any optional security setting?**

That answer reveals the true default.
